## Scope

The concrete `Table` (row set, columns, listeners held weakly, attributes), a static in-memory table built from Arrow batches, append-only and keyed input tables whose changes apply on the next cycle, `empty_table`, and `time_table` driven by an injectable clock. Run every test with the consistency checker attached.

## Notes

- `QueryTable` is the one concrete table. `QueryTable::derive` and `derive_merged` take the
  initial state and the operator and wire the listener, `satisfied` and failure handling;
  `table/mod.rs` has the recipe with a pass-through operator as a doctest.
- `InputTable::add` and `delete` queue the change and run cycles on the calling thread until
  it has been applied, because the graph has no timer. Java asks its periodic graph for a
  refresh and waits. A caller that holds the shared lock deadlocks; a caller on the update
  thread gets Java's error.
- `unported!`: a keyed input table with a `Float` or `Double` key column, and one with no key
  columns (`KeyedArrayBackedInputTable#makeKeySource`).
- Initial rows of an input table are written before the table is visible, so the column
  sources' rule that idle writes record no previous value has no effect here. Writes during
  a cycle happen in the source's `refresh` and are tracked.
- `prev_row_set` returns the current row set while the graph is idle.
- `QueryTable::derive` from inside a cycle, for a parent that has not finished updating, is
  not supported.
- The testkit's `ScriptedTable`, `RandomUpdates`, `ConsistencyChecker` and `Recorder` work
  on `SteppedUpdateGraph` unchanged.
- Not built: liveness scopes, table attributes beyond the three in the contracts, input
  table validation hooks and the non-blocking `addAsync`.
