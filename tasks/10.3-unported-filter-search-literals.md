New `unported!` calls, both narrower than what they replace:

- `ConditionFilter#init` in `filters.rs`: a match or range on a big number column that does
  not read as a big number fails over to its formula (`Y == 1.5`, `Y > 1-2`), which Java
  compiles and the formula compiler does not support for big number columns yet.
- `Character#digit` in `literal.rs`: a non-ASCII decimal digit in a big number literal,
  which Java's `BigDecimal` and `BigInteger` constructors accept.

  `oracle/scenarios/ticking/ticking_search_vectors.json` (6 steps), recorded from Deephaven

  search, and refused literals) and agreed; ticking parent under
  `ConsistencyChecker::attach_with_recompute`.
- Each new test was seen to fail under a mutation of the code it covers (any element made
  all, the null vector check removed, the column left out of the inputs, null elements of
  primitive vectors made ordinary, scale dropped from big decimal cells, negative big decimals
  compared unreversed).

## Owner questions

1. Reproduced from Deephaven, possibly a defect: a search of a primitive vector column
   (`IntVector` etc.) fails with `NullPointerException` when a null element is read before
   an element that matches, while arrays and object vectors treat a null element as any
   other. Recommendation: keep reproducing it.
2. Reproduced from Deephaven, possibly a defect: a search of any table with a `BigDecimal`
   column fails as a whole when the text is a number that is not a plain decimal (`1e1`,
   `+1`, `.5`), since `AbstractRangeFilter#makeBigDecimalRange` throws. Recommendation: keep
   reproducing it.
3. Formulas over big number columns (the failover of `Y == 1.5`) wait on the formula
   compiler; recommendation: a task in `oxhaven-expr`.

## Handover

What remains, with what I learned on the way:

- L1 (`literal.rs`, `equalsIgnoreCase`): Java compares UTF-16 code units, upper-casing then
  lower-casing each unit, as I recall it; not studied. Worth checking against `/home/user/dh-ref` and the JDK 21
  `String#regionMatches(boolean,...)`, which since JDK 16 compares code points for
  `UTF16` strings: the outcome may be that the code point compare already matches.
- L2, L3 (`literal.rs`, hexadecimal floats): not studied. The local JDK `src.zip` is a
  dangling link; JDK 21 sources fetch with curl from openjdk/jdk21u on GitHub.
- C1 (`condition.rs`, subnormal `Double#toString`): JDK 19+ prints the shortest decimal
  that reads back (`DoubleToDecimal`); not studied further, so whether Rust's shortest
  digits agree for a one-digit subnormal is unchecked.
- L4, L5 (time zone literals): not studied; only literals with an explicit offset or
  zone id can need no server zone.
- C2 (`DecimalFormat` of doubles from 2^53): not studied.
