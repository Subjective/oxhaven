## Notes

Every Java answer below was observed on Deephaven 42.9 (the oracle's embedded server, probe
scripts run with `harness show-scripts`) as well as read in the source.

### Done

- R1, count where in a rollup: every level counts the source's rows of its group, which is
  what Java's sum of the counts of the level below gives. Its output, and a formula's,
  counts among the outputs that clash with the null column of a group-by column
  (`Duplicate output columns found: K used 2 times`).
- R3, one group aggregation in a rollup: every level has the source's values of its rows,
  in the order of the source (Java's `GroupByReaggregateOperator` unions the row sets of
  the level below).
- R2, formula aggregations in a rollup, at every level over the source's rows of the
  group, with `__FORMULA_DEPTH__` (an `int`, the level's number of group-by columns) and
  `__FORMULA_KEYS__` (their names, a vector of strings), which take the place of source
  columns of those names (`AggregationProcessor#maybeInitializeVectorColumns`). The engine
  gives them as `FormulaConstant`s to `aggregate_with_constants`. Java makes a coarser
  level from the level below, which keeps only the grouped columns the first formula reads
  and that the level below does not group by. So Java refuses:
  - a formula that reads a group-by column, at the level that stops grouping by it: with
    `Inconsistent return type in rollup for Formula column 'L': previous level was int,
    but level 1 is interface io.deephaven.vector.IntVector` when the result's type
    changes (reproduced, with the component-type variant), otherwise with a
    `NoSuchColumnException` for an internal column (`J_GRP___ROLLUP__`);
  - a formula after the first that reads a column the first does not
    (`NoSuchColumnException` for `D_GRP___ROLLUP__`), also after a first that reads
    nothing (`U = 1`).
  The two `NoSuchColumnException` cases stay refused as not ported (owner question 7).
  Without group-by columns there is one level and any formulas are served. A formula with
  `reaggregating=True` (Python only; the gRPC message has no such field) is refused as not
  ported in the Python package: Java applies it to the level below's results.
- R4, a rollup of a blink table: every level aggregates every row the table ever had, as
  the blink operators of Java's finest level do (compared for sum, abs sum, avg, count,
  count where, min, max, var, count distinct, distinct, unique and weighted average; std
  and weighted sum take the same operators).
  Refused with Java's texts: a blink table with constituents (`Blink tables do not support
  rollup with included constituents; ...`, `QueryTable#rollup`, before anything else),
  and per aggregation, in order: `AggFirst`/`AggLast with exposed row redirections (e.g.
  for rollup(), AggFirstRowKey, or AggLastRowKey)`, `AggSortedFirst`/`AggSortedLast with
  exposed row redirections (e.g. for rollup())`, `AggGroup for rollup`, `AggFormula for
  rollup`. A partition aggregation is refused before the others, as in
  `AggregationProcessor#forRollupBase`.
- T2, a tree of a blink table: Java does not serve it (10.2 thought it did). Refused with
  `Blink tables do not support tree; use BlinkTableTools.blinkToAppendOnly to accumulate
  full history` before the columns are looked at (`QueryTable#tree`), also when orphans are
  promoted.
- T1: the refusal of a tree whose identifier and parent columns differ in type names every
  type as `Class#toString` does (`describe_for_compatibility`, now also for `Object`
  columns and `boolean[]`).

### Still unported

- Two group aggregations in one rollup, or a group and a formula aggregation
  (`AggregationProcessor.Converter#ensureGroupByOperator`): owner question 7.
- A formula in a rollup that Java fails with a `NoSuchColumnException`
  (`GroupByReaggregateOperator#GroupByReaggregateOperator`): owner question 7.
- A formula with `reaggregating=True` in a rollup (Python).
- R5, R6 (PARITY A15) and T3 (A12), as before.

### Differs from Deephaven

- Java finds a refusal of its walk over the aggregations (a blink refusal, `Agg<name> is not
  supported for rollup()`) after the errors of the aggregations before it (an unknown
  column, a type without the aggregation); here the refusal comes first. Only the text
  differs (A5).
- A formula that Java fails at a coarser level and the expression crate cannot compile
  there (`` L = `` + J ``, a string plus a vector) is refused as a formula that does not
  compile; Java fails it with a `NoSuchColumnException`.
