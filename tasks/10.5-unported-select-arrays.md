### Done

- P1, P2: an offset of `Col_[i ± n]` is read by `Long#parseLong` of the literal's text while
  the formula is parsed (`ShiftedColumnsFactory#parseForConstantArrayAccessAttributes`, from
  the constructor of `QueryLanguageParser`), so `update`, `update_view`, `view`,
  `lazy_update`, `select` and `where` of `X_[i + 0x1]`, `X_[i - 1_0]`, `X_[i + 0b1]` fail with
  `FormulaCompilationException` caused by `NumberFormatException: For input string: "0x1"`,
  before any column is looked at (`Nope + X_[i + 0x1]` gives the same error). Oxhaven now
  fails the formula with `For input string: "0x1"` in place of `unported!`. Only an `int`
  literal counts (`IntegerLiteralExpr`): `X_[i - 0x1L]`, `X_[i - 1f]` and `X_[i - 1e1]` are
  no shifts and stay column arrays, as in Java; `X_[i + 010]` is a shift of 10 and
  `X_[i + 2147483648]` one of 2147483648 (both served by Java).
- P3: `ShiftedColumnsFactory#getShiftedColumnDefinitions` takes a column array only when the
  array is written as a name ending in `_` (`ArrayAccessExpr#getName`). `(X_)[i - 1]` and
  `((X_))[i]` are therefore column arrays, served on a static table and refused on a
  refreshing one as unsafe to refresh (`Formula '(X_).get(longCast(minus(i, 1)))' uses i,
  ii, k, or column array variables`); `X_[(i - 1)]` was already right. The text scanner now
  reads these, names outside ASCII (`Ä_[i - 1]` of a `new_table` is a shift in Java), and
  qualified names (`Foo.X_[i - 1]`, which Java and Oxhaven both fail as formulas). The
  `unported!` stays as a guard against a text that is not the expression's; no text a client
  can send is known to reach it.
- With a column `X_` beside `X`, Java's `X_[i - 1]` indexes the column `X_` and fails
  (`Cannot find method get(int) in int`); Oxhaven took the shift. It now keeps the formula's
  error when the table has a column named like the column array.
- P4: Java does not serve two distances correctly (10.2 thought it did): see owner question
  8. The refusal stays. The dirty-row computation is now written for any reach on both
  sides (`dirty_positions_within`): a change marks the rows within the farthest distance
  before it and the farthest after it, which for one distance, or one distance and zero, is
  Java's computation. `shifted_table` is `add_shifted_columns` without the refusal, so the
  tests can serve two distances; removing `refuse_two_distances` serves them.
- `docs/HIERARCHICAL.md`, "Which aggregations": count where, group and formula are served
  in a rollup since task 10.4, with what stays refused. The table of "Refused for now" in the
  same file still lists `CountWhere`, `Group`, `AggFormula`, a rollup of a blink table and a
  tree of a blink table as refused for now; that section was not in this task's paths.

### Differs from Deephaven

- An offset beyond the `long` range (`X_[i - 9223372036854775808]`) is refused by the
  expression crate's lexer first (`integer literal ... is out of range`); Java's text is
  `For input string: "9223372036854775808"`. Both are formula errors (A5).
- `X_[i /* c */ - 1]`: Java serves the shift; the expression crate does not read comments
  and refuses the formula as a syntax error. Not part of this task.
- A `where` over a table with a column `X_` beside `X` was not looked at; only `select` and
  `update` keep the error now.

## Owner questions

8. Column arrays at two different distances, neither of them zero, on a refreshing table
   (`update("M = X_[i - 1] + X_[i + 1]")`, `X_[i - 1] + X_[i - 2]`, and filters such as
   `where("X_[i - 1] < X_[i + 1]")`). Java computes the rows a change makes dirty with the
   one-distance computation run twice, the second time over the positions the first one
   returned as if they were row keys
   (`ShiftedColumnOperation#computeDirtyModifiedRowSetInPositionSpace(RowSet, RowSet, long,
   long)`). Seen on Java 42.9 with a keyed input table of eight rows: after a modify, an
   append and a remove, `update` keeps every first value (for example `M` of the row before
   a modified row stays 60 where it should be 61), while `update_view` of the same formula,
   and the same `update` made again, show the new values; a `where` with two distances even
   kept a row that had been removed. This is the most likely of the column array requests.
   Serve it with the values the formula has when it is made again, marking modified the
   rows within the farthest distance on each side of a change, as A13 does for `aj`
   (recommended: the code and its random tests are in place, and removing
   `refuse_two_distances` serves it), or refuse it as A15?
