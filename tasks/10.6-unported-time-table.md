## Notes

Every Java answer below was observed on Deephaven 42.9 (the oracle's embedded server,
`pydeephaven` `Session.time_table(period=10**18, start_time=...)`, reading row 0) as well as
read in the source (`TimeTableGrpcImpl#adaptStartTime`, `DateTimeUtils#parseInstant`,
`#parseZonedDateTime`, `TimeTable#refresh`).

### Done

- The server no longer has an instant parser of its own: a start time written as text is
  read by the expression crate's (`oxhaven_expr::parse_instant_reach`), which already held
  Deephaven's time zone aliases, the time zone database, the `SystemV` zones and the
  lenient spaced form, each observed on Java 42.9 when it was written.
- Z3, a named zone other than UTC: served through the aliases (`ET`, `CT`, `MT`, `PT`,
  `HK`, `JP`, `LON`) and the database, case sensitively; `NY`, `EST` and
  `america/new_york` are errors as in Java. A local time the clocks skip is moved later by
  the gap (`2024-03-10T02:30:00 America/New_York` is 07:30Z), and one that occurs twice is
  the earlier (`2024-11-03T01:30:00 America/New_York` is 05:30Z), as
  `LocalDateTime#atZone` does; checked for New York, London and Lord Howe (half-hour gap).
- Z2, hour 24: `2024-01-01T24:00:00 UTC` and `2023-12-31T24:00 America/New_York` are the
  next midnight (the lenient formatter resolves `ResolverStyle.SMART`);
  `2024-01-01T24:00:00Z`, `...T24:00:00+00:00` (strict `ZonedDateTime#parse`, then no
  space) and `...T24:00:01 UTC` are errors. 10.2 had this as served for the `Z` form; Java
  refuses that one.
- Z4, an offset and a region that disagree: `Parsed#resolveInstant` gives the offset
  priority, so `2024-01-01T00:00:00+05:00[Europe/Paris]` is 19:00Z of the day before, and
  `2024-03-10T02:30:00-04:00[America/New_York]` 06:30Z. A bracket zone Java does not know
  as a region (`[ET]`) is an error.
- Z1, a year with a sign: the expression crate now reads, for this entry point only, the
  year as `appendValue(YEAR, 4, 10, SignStyle.EXCEEDS_PAD)` parses strictly: `+` only
  before more than four digits, `-` not before zero, at most 999999999. Every such year is
  outside the instants a `long` of nanoseconds holds. A start after them all
  (`+10000-01-01T00:00:00Z`, `2300-01-01T00:00:00 ET`, `2262-04-11T23:47:16Z`) is a table
  that never gains a row in Java, which compares `Instant`s; Oxhaven gives the engine the
  last nanosecond as the start. `+2024-...`, `-0000-...`, `10000-...` and `+10000-01-01 UTC`
  (date and zone without a time) are errors as in Java.
- The whole number `-9223372036854775808` is Java's null instant: no start, the table
  begins at its first refresh. Oxhaven started at it and overflowed.
- A start so early that the time since it overflows a `long` (`-9223372036854775807`,
  `1677-09-21T00:12:44Z`) is an error at creation in Java (`DateTimeUtils#minus`,
  `Subtracting ... would overflow`); the engine computed it unchecked. It now fails creation
  with Java's text, and fails the table if a later refresh overflows.

### Still unported

- A start before the first instant a `long` of nanoseconds holds (before
  1677-09-21T00:12:43.145224192Z, every negative year, `+00001-...`):
  `DateTimeUtils#epochNanos` (owner question 9).
- A spelling the expression crate leaves unsupported (`DateTimeUtils#parseInstant`): none
  known for a time table; the guard stays.

### Differs from Deephaven

- A start after the last instant of a nanosecond clock is the last nanosecond
  (2262-04-11T23:47:16.854775807Z) to the engine. Java never reaches such a start, and a
  start in the last 0.85 s fails its table when reached (`epochNanos` refuses it); Oxhaven
  adds row 0 if its clock ever reads that last nanosecond. No clock reaches it before 2262.

## Owner questions

9. A time table start before 1677-09-21T00:12:43.145224192Z (`1600-01-01T00:00:00Z`,
   `-0001-01-01T00:00:00Z`). Java converts it to nanoseconds with
   `epochSecond * 1_000_000_000L + nanos`, which wraps around without a check below the
   range (`DateTimeUtils#safeComputeNanos` checks the top only), and then depends on the
   wall clock: seen on Java 42.9, `-0001-...` gave nine rows from a timestamp in 1752,
   `1600-...` and `-2024-...` none, `-10000-...` an error. Recommended: keep refusing (A15
   kind); the alternative is Java's error text for an out-of-range instant, which Java
   itself does not give.
