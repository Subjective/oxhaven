- **Status:** in review

## Scope

1. `io.deephaven.time.calendar.Calendars` as `deephaven/calendar.py` uses it: `calendar()`,
   `calendar(name)`, `calendarName`, `calendarNames`, `setCalendar`, `addCalendar`,
   `addCalendarFromFile`, `removeCalendar`.
2. A stand-in for `BusinessCalendar` and `Calendar` with Java's methods and overloads, at
   least everything `FigureCalendar.py` calls. What is not done is refused by its name and
   listed below.
3. The calendar file format (`BusinessCalendarXMLParser`). The files Deephaven ships are
   copied only if they are under Apache-2.0 or MIT.
4. `DateTimeUtils#timeZone` and `#toLocalTime` in the `jpy` stand-in.
5. `StaticCalendarMethods` in formulas only if it is little work; otherwise a follow-up.

## Notes

### Done

- `oxhaven_expr::calendar`: the file format (`roxmltree`, MIT OR Apache-2.0), the zone of a
  calendar, a calendar's days, hours and arithmetic, and the process-wide collection of
  calendars. It is in `oxhaven-expr` so that the formula language can reach it later.
- `deephaven.calendar`'s six functions, a `BusinessCalendar` with every public method of
  Java's `BusinessCalendar` and `Calendar` and their overloads, `CalendarDay`, `TimeRange`,
  and the `List`, `Set` and `Map` a calendar hands out.
- `LocalDate` getters (`getYear`, `getMonthValue`, `getDayOfMonth`, `getDayOfWeek`,
  `toEpochDay`), `LocalTime` getters and `DayOfWeek` in `deephaven._java_time`.
- `jpy`: `io.deephaven.time.DateTimeUtils.timeZone` and `toLocalTime` are carried out; every
  other member stays refused.
- `deephaven.numpy.to_np_busdaycalendar` and the `BusinessCalendar` dtype's `j_type`.
- Every value was compared with Java 42.9 by running the same expressions on both servers
  over three calendar files written for this task (`src/calendar/fixtures/`, not copied from
  Deephaven) and about thirty malformed ones: about 400 expressions, the same values everywhere but
  where `docs/CONSOLE.md` ("Business calendars") lists a difference.
  `to_np_busdaycalendar` matched too; it has no Rust test, because the console's test
  environment has no numpy.
- `dx.line(..., calendar="NAME")` with a calendar added from a file makes a figure, and
  `FigureCalendar.to_dict()` is Java's for the three files.

### Handover

- The registry is process-wide (`oxhaven_expr::calendar::calendars()`), as Java's
  `Calendars` is per JVM: every session sees the same calendars. The console tests share it,
  so they add a file only when its name is not there.
- Java's month and year summary cache (`YearMonthSummaryCache`) is not reproduced: counts
  are computed day by day, which gives the same answers; the first invalid date named in an
  error over a long range can differ.
- `DateTimeUtils.timeZone` and `toLocalTime` in `jpy` go beyond the owner's ruling of
  2026-11-16 ("every use of a Java class fails by that class's name"); the owner approved
  the task that asked for them, and `docs/CONSOLE.md` says so, but `PARITY.md`'s wording of
  that ruling was not changed (it is protected).
- Surprising Java behaviour is listed in `docs/CONSOLE.md` ("Business calendars").
