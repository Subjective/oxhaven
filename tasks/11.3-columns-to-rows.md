## Notes

### Done

- `oxhaven_engine::ops::columns_to_rows::columns_to_rows`: the result's rows are at
  Java's row keys (`k << bits | slot`, `bits` the fewest that hold the last label), its
  columns read the parent through the key (no copy), and a refreshing result is kept up
  to date with Java's case analysis: every row of an added, removed or shifted parent row;
  for a modified row, every row when a column that is not transposed changed and
  otherwise the rows of the labels whose columns changed; modified columns by name, so a
  label or value column that took the place of a parent column changes with it. Checked
  against a rebuild of a static copy over random updates (60 seeds in the full budget).
- Names are not checked, as in Java; a name the result already has replaces that column
  where it is. No attributes are carried over and the result is not flat, as in Java.
- Every column type, a column twice in one group, a column in two groups of one type.
- Java's refusals with Java's texts: no value column, counts that differ, no labels
  (`AssertionFailure`), an unknown column, two types in a group (by the parent's column
  order), and a group whose columns are all in earlier groups (`NullPointerException`).
- `jpy`: `get_type("...ColumnsToRowsTransform").columnsToRows` with jpy's choice among the
  overloads, its conversions (a string is an array of its characters where an array is
  expected) and its texts, and Java's `NullPointerException`s for `None`, in Java's order.
- `dx.data.marketing`'s body has Java's table for `ticking=False`; its ticking form refreshes.

### Still not ported

Refused as `not ported: io.deephaven.engine.table.impl.util.ColumnsToRowsTransform#columnsToRows`,
where Deephaven's result is undefined or inconsistent (owner question 7.12 in
`review-items-2.md`):

- on a refreshing table, a transposed column named twice, or a group whose columns are not
  in the table's column order: Java finds the modified rows by counting each group's
  columns in the table's order and maps a column to the last group it is in, so its update
  names the wrong rows or columns (observed: labels `[a, b]` for `[B, A]`, a change of `A`
  marked the row of `a`; `A, A, C`, a change of `C` marked the second row);
- a column in two groups whose value columns have different types: Java declares the
  value column with one type and reads the other column as it;
- parent row keys too large for the labels: Java's key arithmetic overflows.

### Handover

- `columns_to_rows` is in the engine for the console only; a table service request for it
  does not exist in Deephaven.
- The plugin itself was not installed and run against this server in this task: the
  console test runs the body of `dx.data.marketing` as the plugin has it.
- jpy's overload choice is modelled for this method only (`_columns_to_rows.py`): the
  fits are ordered to reproduce what was observed, not jpy's own numbers.
