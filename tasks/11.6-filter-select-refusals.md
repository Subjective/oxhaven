### Done

- F1: `oxhaven-expr` compares a `BigDecimal` or `BigInteger` column with another, with a
  primitive number or `char`, by value (`eval/big.rs`, `CompareDomain::Big`): an integer
  as `valueOf(long)`, a `double` as `BigDecimal.valueOf(double)`, which is the number of
  Java's `Double#toString` text and not the exact double (`BD == 0.1` is true for `0.10`),
  a `float` widened first (`0.1f` is `0.10000000149011612`); null below everything, a
  NaN operand false for every operator but `!=`. Beside a `String` or `Boolean` it is
  `eq(Object, Object)` or a `compareTo` that fails where two values meet. `BI == null` is
  `isNull`; `BI < null` does not compile, as in Java ("reference to less is ambiguous").
  `where` with such a failover, and `update("Y = BD > 1")`, are now served.
- F2: a range filter of a vector, array or `Object` column is refused as Java refuses it.

## Handover

- F3 (`Object` columns in match filters): Java's convertor and the answers are in the
  table above (console, `O = (Object) (int) i`: `O == 3` one row, `O == 3L`, `O == 3.0`,
  ``O == `a3` `` none, `OS == 'a3'` fails `For input string`, `OL == 99999999999` keeps
  nothing through its formula, `O > 2` fails to compile). Needs a `Cells` variant for
  `Object(Some(class))` that keeps a cell holding the primitive's null value as a value
  (only validity is null) and compares by class and `equals` (`Double#equals`: NaN equals
  NaN, `-0.0` not `0.0`). About 150 lines and tests.
- F4 (parser annotation): strip the prefix, check the name (`Deephaven`, `Numba`, else
  `IllegalArgumentException`), fail without `:`; a `Numba` formula filter throws
  `UnsupportedOperationException` ("Python condition filter should be created from
  python"), not yet observed. Observe over gRPC first: the probe through `pydeephaven`'s
  table `where` hung on this run. About 40 lines.
- F5 (regular expressions): the cheap ones are named groups `(?<n>X)` (a plain group when
  only whether the whole string matches counts), `(?i)`/`(?-i)` and `(?s)` scopes (the
  translator already folds ASCII case per literal), an empty `\Q\E`, and `\x`, `\u`, `\0`
  escapes; observe each with `java.util.regex` on JDK 21. Lookaround, back references and
  possessive quantifiers need a backtracking engine the `regex` crate is not; a full port
  of `java.util.regex` is large (thousands of lines) and must not be translated from JDK
  source.
- F1, the rest: arithmetic of big numbers (`BD + 1`, `BD * D`, `-BD`, casts), method
  calls (`BD.add(...)`), and a big number as a function argument stay refused by the
  expression crate. Java computes them in `QueryLanguageFunctionUtils` (`plus(BigDecimal,
  double)` and the rest, `divide` with a `MathContext`) and returns `BigDecimal` cells;
  needs a decimal arithmetic type in `oxhaven-expr` and result columns of big numbers:
  about 1,500 to 2,500 lines with tests.
- F9: years of more than four digits in time literals, in `oxhaven-expr`
  `parse/instant.rs`; small, but not started.
