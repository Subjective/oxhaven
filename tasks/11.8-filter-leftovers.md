## Notes

Every Java answer below was observed on Deephaven 42.9 (the oracle's embedded server,
`oracle/bin/start-java.sh`), from console scripts through `pydeephaven` and, where named,
over gRPC (`pydeephaven`'s table `where`, an `UnstructuredFilterTableRequest`). Regular
expressions were asked of JDK 21's `java.util.regex` directly, from a program that calls
its API.

### Done

- F3, `Object` columns (`O = (Object) x`): the literal is read as Java's `Object` convertor
  reads it (`null`; a `"` or back tick quoted `String`, its first and last character
  dropped; with a `.`, `Double.parseDouble`; ending in `L`, `Long.parseLong`, which never
  succeeds; else `Integer.parseInt`) and compared with `Objects.equals`: a value equals
  only a cell of its own class, a `Double` by its bits (`-0.0` is not `0.0`, NaN equals
  NaN), and a cell holding a primitive's reserved value is a value, not a null. `icase`
  changes nothing. A literal that does not convert falls back on the comparison's formula
  as before, which `oxhaven-expr` already compiles as Java does (`OI == 3L` none,
  `OI == 0x3` row 3, `OL == 3L` row 3, `OD == 1e0` row 6, `OZ == true` the true rows).
  New `Cells::Boxed` in `filters.rs`.
- F9: `oxhaven-expr` reads a time literal's year as Java's ISO formats do (a sign before
  more than four digits, `-` not before zero, at most 999999999), so the spellings Java
  rejects (`'+2024-...'`, `'10000-...'`, `'+1000000000-...'`, `'+10000-01-01 UTC'`) are
  syntax errors, as in Java, and no longer "unsupported". An instant outside the range of a
  column is still unsupported in a formula (see Handover). The filter's own reader of UTC
  instants (`literal.rs`, `... UTC` and `...Z`) reads the same years and says where an
  instant falls: a match filter with an instant no column holds matches no cell (Java
  compares `Instant` objects: `T == '+10000-01-01T00:00:00 UTC'` none, `!=` every row,
  nulls included); a range filter with one past 2262 fails, as Java's
  `DateTimeUtils#epochNanos` does (`INVALID_ARGUMENT` over gRPC); one before 1677 is
  refused (owner question 7.17). An instant exactly at the smallest `long` of
  nanoseconds, which the reader took for null before, is now one no column holds.
- F5: named groups (`(?<name>X)`, a group when only the whole string counts; Java's errors
  for a bad or repeated name), the inline flags `i` and `s` (`(?i)`, `(?-i)`, `(?is-s:X)`,
  scoped to their group), escapes by number (`\xhh`, `\x{h..h}`, `\uhhhh` with surrogate
  pairs, `\0n`, `\0nn`, `\0mnn`) inside and outside classes, `\Q...\E` as Java reads it (it
  removes the quotation first, so a quantifier after it applies to its last character,
  `\Qab\E*` is `ab*`, and an empty one leaves nothing: `\Q\E+` is a dangling `+`), and `^`
  anywhere, which without `MULTILINE` is the start of the input. Before, a quantifier
  after `\Q...\E` applied to the whole quotation, which Java does not do.
- F4: the annotation is read as `FormulaParserConfiguration#extractParserAndExpression`
  reads it. `Deephaven` is the default; with `Numba` a match, range, `in` and `includes`
  filter is served and a formula fails (`UnsupportedOperationException`), including the
  formula a match or range filter would fall back on, so the conversion error is the
  answer (`Numba:X == 2.5` fails; `Deephaven:X == 2.5` would be a formula). A name other
  than these two (exact case, no spaces) and a missing `:` fail. Every failure is
  `INVALID_ARGUMENT` over gRPC. The gRPC probe did not hang on this run: every request
  answered at once (each was given 20 seconds).

### Deephaven's behaviour worth knowing

- An annotated formula filter (`<ObfuscatedParserAnnotation>Deephaven:X + 1 > 2`) is served
  from a console script and refused over gRPC: `ParsingColumnExpressionValidator` checks a
  filter that is a formula by compiling `__boolean_placeholder_0__ = (<the whole text>)`,
  annotation included. An annotated match or range filter is not a formula there, and is
  served on both paths, even when it falls back on its formula (`Deephaven:X == \`a\``).
- An `Instant` outside the range of a column is a valid `java.time.Instant` to the
  convertor and to formulas, which compare it correctly (`T < '+10000-...' && true` keeps
  every row); only where it becomes nanoseconds does it fail (after 2262) or wrap around
  (before 1677).
- `(?d)` with `DOTALL` on, as every pattern filter has it, makes `.` stop matching `\n`.

### Differs from Deephaven

- Nothing new. Refused as not ported (`UNIMPLEMENTED`), where Deephaven answers:
  - a formula filter after a `Deephaven` annotation that compiles (Java: served from a
    console, refused over gRPC; this server runs both through one path);
  - an `Instant` literal outside the range of a column in a formula, and in a filter where
    it names a zone other than UTC (it goes through the formula compiler);
  - a range filter with an instant before 1677 (owner question 7.17);
  - regular expressions with lookaround, back references, possessive quantifiers, atomic
    groups, the flags `d`, `m`, `u`, `x`, `c`, `U`, nested classes and `&&`, `]` first in
    a class, `$` before the end, `^` before a quantifier, `\p{..}`, `\b` and the other
    escapes not listed above, a class range ending in an escape, and a lone surrogate;
  - an `Object` literal whose last character is outside the Basic Multilingual Plane
    (Java would keep half of it).

## Handover

- A formula filter after a `Deephaven` annotation needs the server to know whether the
  request came from a console script (served) or from a gRPC client (refused by the
  validator); both reach `unstructured_filter` through one handler today.
- Instants outside the range of a column in formulas: `Literal::Instant(i64)` of the
  contracts cannot hold one. Java compares them correctly and fails or wraps where they
  become nanoseconds (7.17), so serving the comparisons needs a contract change (a literal
  for an instant beyond the range, or the instant's seconds and nanoseconds). The filter
  path could then read named zones too.
- Regular expressions: lookaround, back references, possessive quantifiers and atomic
  groups need a backtracking engine. The candidate is `fancy-regex` (0.20.2, MIT, built on
  the `regex` crate); its syntax and case folding differ from Java's, so a translation
  would still be needed. Not added: a new dependency is the owner's call.
