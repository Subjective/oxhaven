## Scope

Widen the differential fuzzer to what the last tasks started serving, in this order:

1. Chained as-of joins: `aj` and `raj` whose input is another as-of result, static and
   refreshing, compared so that the comparison means something under `PARITY.md` A13 as
   written.
2. Vector columns offered to `update_by` (minimum and maximum, count-where filters,
   buckets), to aggregations (group-by columns, `distinct`, count-where filters) and to
   `select_distinct` (tasks 11.4 and 11.5).
3. Rolling formulas over conditions between windows and slices (task 11.4).

For each: lift the generator's restriction, run seeds against Deephaven 42.9, and triage
every difference as a bug here (fixed when small and in the operator's scope, otherwise
written up with a minimal scenario and stepped around narrowly), a case an owner item or an
allowed difference covers (stepped around exactly, citing it), or a behaviour of Deephaven
that needs an owner's answer.

### Findings

#### F1. Java fails an as-of join when its right table changes off the join's columns

`F1_asof_static_left_right_change_off_its_columns.json`. Static `t(K, C2, S)`, keyed
ticking `r(RId, K, RS)`; `o1 = raj(t, r, S <= RS, J3 = RId)`;
`o4 = raj(t, o1, K, S < S, J5 = C2)`; a step deletes the row of `r`. Java fails `o4` in
that cycle: `ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0` in
`RightIncrementalHashedAsOfJoinStateManager#addToSequentialBuilder`, called from
`AsOfJoinHelper` (the listener for a static left and a refreshing right table). The
listener sizes its builders by the rows whose stamp it must look at again; when the right
table reports modified rows and neither a match column nor the stamp is among the modified
columns, that size is zero and the first row written is out of bounds. It needs exact
match columns (the hashed state manager), a static left table, and a right table that can
report such a change: an as-of result does (its joined columns change alone), an input
table of the harness does not (it reports every column). Oxhaven keeps `o4`, which a
change of `J3` cannot alter.

This is the chain case of `PARITY.md` A13. The ten chain seeds recorded there
(`--ops aj` 2, 465, 540, 675, 1371, 1427, 1735, 2110, 2669, 2873) all have this shape and
all fail with this exception. When A13 was written a failed table was compared by the
rows Java still serves for it, which read as "keeps a match that is gone"; since a failed
table is compared by its failure alone (A11, task 0.18) the same seeds showed as
`failure_expected`, which the known finding (kind `value`) did not fit, so `--ops aj`
stopped at seed 2. Outcome:

- `aj`: A13 covers it as written (Java's incremental result, a failure, differs from its
  result from scratch, and Oxhaven gives the result from scratch). The known finding
  `aj-reference-failure` sets it apart under the stricter check above. The generator draws
  the shape on purpose (17 of 3000 seeds of `asof_chains` hit it).
- `raj`: A13 names `aj` only, so the generator does not draw the shape for `raj` (C1) and
  owner question 7.19 asks.
- Seen in 1 of the first 300 seeds of `asof_chains` (seed 294 of the generator as it then
  was), the only difference of that run.

#### F2. Java's operators fail or go stale over vectors of a refreshing group

`F2_vector_of_a_refreshing_group_as_key.json`. Keyed ticking `t(Id, K, C)`;
`g = group_by(t, K)`; then `agg_by(g, count by C)`, `select_distinct(g, C)`,
`update_by(g, cum_sum by C)` and `agg_by(g, distinct D = C)`; a step adds a row to the
group of `K` 1. Java fails the first three in that cycle (`IllegalStateException: Missing
value in probe` in `IncrementalAggOpenHasherObject`), and the `distinct` either fails
(`AggregationOperatorException: Failed to modify data` or `Failed to remove data`) or
keeps the vector it had. A vector of a refreshing `group_by` result is a view of its
group, so the key or value an operator holds has changed under it. On such a table a
vector of Booleans or Instants used as a key also comes back as `list<string>`, where a
static table keeps the type. This is the behaviour `tasks/4.17-fuzz-findings.md` (Notes
on A2) describes for the comparing aggregations. Oxhaven's vectors are values and its
results follow the groups. Outcome: stepped around on refreshing tables (V5); owner
question 7.19. It was the cause of most of the 75 differing seeds in the first 300 of
`vectors` (the others were F3 to F5 and the refusal of `select_distinct` below). The minimum and maximum of `update_by` over such vectors, and count-where filters, showed no
difference on refreshing tables and stay drawn there.

#### F3. The minimum or maximum of vectors of strings loses its element type in Java

`F3_ungroup_of_a_minimum_of_string_vectors.json`. `cum_min`, `cum_max` and the rolling
forms of a column of vectors of strings: Java's result column is a vector without a
component type. A client receives it as a list of strings, as it does Oxhaven's typed
column, so the tables compare equal; after `ungroup` Java's column is `java.lang.Object`
and Oxhaven's is `java.lang.String` (sortable). The same difference is decided for
`head_by` and `tail_by` (A14) and recommended for owner item 3.3, but neither names this
case. Outcome: no `ungroup` of a table with such a column (V6); owner question 7.20.

#### F4. A slice of a window of strings is refused

`F4_F6_conditions_between_windows_of_strings.json`, tables `s1` and `s2`. Java serves
`each.subVector(0, 1)[0]` and `(c ? each : each.subVector(0, 1)).size()` over a window of
strings. Oxhaven refuses: "unsupported in formulas: method call .subVector() on a value of
a vector type". The expression crate does not compile a method of a vector of objects yet
(`crates/oxhaven-expr/tests/data/java_vectors_refused.txt` records it as one Java
accepts). A bug here, not fixed: it is in the expression crate, not in the operator.
Outcome: no slices of windows of strings (V7); Handover.

#### F5. A count-where filter on an element of a vector of Booleans is refused

`F5_count_where_of_an_element_of_a_boolean_vector.json`. Java serves
`cum_count_where` and the `count_where` aggregation with the filter `isNull(B[0])` over a
vector of Booleans. Oxhaven refuses: "unsupported in formulas: an element of a Boolean
vector or array, which Java compiles in a formula column and not in a filter". A bug
here, in the expression crate's filter path, not fixed. Outcome: no such filter (V8);
Handover.

#### F6. An element of a condition between vectors of strings is an Object to Java

`F4_F6_conditions_between_windows_of_strings.json`, tables `c1`, `c2` and `f`.
`(each.size() > 1 ? each : each)[0]` over a window of strings, `(S.size() > 1 ? S : S2)[0]`
over two, and in `update` over a `group_by` result `(K > 1 ? S : S2)[0]`: Java types the
column `java.lang.Object` (the condition between two vectors of objects loses their
element type; `S[0]` alone is a `java.lang.String`). Oxhaven types it `java.lang.String`.
The values are the same. For vectors of Instants Java's `Object` column reaches a client
as text and Oxhaven's as timestamps. Not fixed here: it is the expression crate's typing
of a condition, and whether to follow Java into `Object` is the question of 3.3 and A14
again. Outcome: no element of a condition between windows of strings (V9); owner question
7.20. It was all 6 differing seeds of the second 300 of `vectors` and 21 of 300 of
`windows`.

#### F9. A filter on the row key over a refreshing sort result reads keys A4 does not compare

Seeds 724 and 831 of a first run of 1000 seeds of `all3` (997 clean, 1 known, 2
differing), the only family that draws `where` and `sort` with the rest. Both hold
`where(..., "k >= 2")` over the `sort` of a refreshing table (in 724 over an `aj` whose
left table is one, which keeps the keys). Java gives the rows of a refreshing sort result
row keys far from zero and Oxhaven numbers them from zero: with four rows, `k >= 2` keeps
all four in Java and the last two here; over the sort of a static table both keep the
last two, and `i >= 2` keeps the same rows on both everywhere. Without the `k` filter
both scenarios compare equal. Row keys are never compared (A4), so this is not a
difference to decide; the generator replaces a filter on `k` over a refreshing sort
result, or over a table made from one, by one on `i` (V12). The other families draw no
`sort`, so their scenarios and runs are unchanged (the pinned digests say so).

#### F13. Empty groups kept from history cannot be made again

Seeds 35, 86, 101 and 126 of the second and third runs of 300 seeds of `vectors` (task
14.2). An aggregation grouped by a vector of a refreshing group, with `preserve_empty` or
with `initial_groups` from a refreshing table: Java fails it when a group changes, as A22
records. Oxhaven keeps the group of the vector before the change as an empty group (a key
once seen stays, and initial groups are those of the table when the aggregation was
made) and adds the new vector's group; Java's answer made again holds only the vectors of
the step it is made in. So that answer cannot be the one A22 holds Oxhaven to, and the
check has nothing to compare with. Not a difference of its own: Oxhaven's result is what
`preserve_empty` asks for once vectors are values. Outcome: on a refreshing table no
initial groups and no `preserve_empty` for an aggregation grouped by a vector (V16).

#### F14. Groups in the order of their history, read in order

Seeds 1517, 1597 and 770 of the full run of 2000 seeds of `vectors` (task 14.2). An
aggregation or `select_distinct` grouped by a vector of a refreshing group, read by an
operation that depends on row order (`cum_min`, a rolling window, `last`). Java fails the
grouped result (A22). Oxhaven lists a group whose key vector changed after the others, as
for any key that changes, so the operation that reads it in order sees another order than
Java's answer made again, and its values differ although the grouped result holds the
same rows. A22 leaves row order out of its rule, so there is nothing to decide; but
nothing to check either. Outcome: such a result is read by an `ungroup` only (V17).

#### F15. Java repeats a distinct's last vector where null fill asks for a null

Seed 339 of the full run of 1000 seeds of `all3` (task 14.2), static tables. A `group_by`
with no keys, an aggregation by its vector `K = [true, false]` with `distinct` of
`RS = [null, 7]` (one group, so the column of `distinct` holds one vector), and an `ungroup`
of every vector column with null fill (the default). The key has two elements and the
`distinct` column one: Oxhaven fills the second row with null, as null fill asks; Java
serves `[null, 7]` again in it. This is the request of A24's third row ("`ungroup` with
null fill where the shorter column is the vector of a `distinct`"), for which A24 records
that Java fails; here Java does not fail but repeats a value. Not set apart: A24 names the
failure only. Outcome: reported; owner question 7.28. The generator is not changed for it.
Answered 2026-11-21 ("as recommended"): A24's third row covers it. Task 14.4 added the
known finding `null-fill-ungroup-repeat-of-a-distinct` (shape
`null_fill_repeat_of_a_distinct`: a cell of the `distinct`'s vector in such an `ungroup`
that Oxhaven fills with null and Java fills with the vector Oxhaven shows last above it),
