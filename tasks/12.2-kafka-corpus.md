## Scope

Kafka consumption was compared with Deephaven 42.9 by hand, in the probes of tasks 7.4.x
and 7.5.x. Record it: fixed topic contents, what the Java reference makes of them, and a
check on every pull request that Oxhaven makes the same of the same topics on a real
broker. One case per distinct behaviour that `docs/KAFKA.md` says is served. Everything
that depends on the clock or on the broker is made deterministic or taken out, each with a
comment. A difference is fixed in `crates/oxhaven-kafka` when it is a small clear bug, and
otherwise listed as a known difference, never by loosening the comparison.

Out of scope: producing; a replay through a scripted `RecordSource`.

## Notes

### The design

**A Kafka case is a script scenario.** Java has no gRPC call that consumes: a topic becomes
a table through `deephaven.stream.kafka`, in a script. The hand probes were scripts sent to
both servers with `run_script`, whose tables were then read by a client. The oracle already
has that as a recorded form (`oracle/README.md`, "Script scenarios"), so a case is one
Python file under `oracle/scenarios/kafka/`, its recording is a directory under
`oracle/corpus/kafka/` in the format of every script recording, it is compared by
`harness/rules.py` unchanged, and a known difference is a line of a baseline with the
states and verdicts of the replay gate (`harness/baseline.py`, unchanged). What is
compared is what a client of the server sees: the columns with their Arrow and Deephaven
types, the table's attributes, every row, whether a table fails and with which status code,
and whether a call fails and with which Python exception.

**What the scenarios needed and the oracle did not have**, all added, none changed:

- *The topics* are `oracle/corpus/kafka/topics.json`: 20 topics with 72 records (each with
  its partition, timestamp, key, value and headers) and the six subjects of the schema
  registry. The file is written from `harness/kafka_topics.py`, which encodes the binary
  records by hand from the formats' specifications and says what each topic is for; a
  harness test fails when the two differ.
- *Publishing* (`harness kafka-publish`) with `kafka-python` 3.0.13 (pure Python,
  Apache-2.0, no dependency of its own), pinned in both requirements files. It is the one
  new dependency, and only of the harness.
- *A schema registry* (`harness kafka-registry`): Python's `http.server` over the subjects
  of the file, with Confluent's paths, bodies and error codes. No registry image; the CI
  job has none.
- *A wait*: the directive `# oracle: await t 12, u fails` of the script scenario format. A
  consumer's thread fills its table outside the update graph, so the runner's wait for an
  update cycle does not wait for the rows; the directive asks for the table again until it
  has its rows or has failed. A wait the reference does not meet refuses the recording; on
  another server the tables are compared as they are, so missing rows show as a difference.
- *A gate of its own* (`harness kafka-gate`, `oracle/bin/kafka-replay.sh`) with
  `oracle/kafka-baseline.json`. The Kafka scenarios cannot be a section of
  `replay-baseline.json`: `ci-replay.sh` has no broker, and would call their lines stale.
- *Recording* (`oracle/bin/kafka-record.sh`): the same broker and registry, and the Java
  reference of `start-java.sh`.

**Where this departs from the task's wording, and why.**

1. *The check runs in the `oracle-replay` job, not in `kafka-broker`.* A script scenario
   needs the server built with its Python console and the harness's Python environment.
   `oracle-replay` has both by the time its replay gate has run; `kafka-broker` has
   neither, and building them there would add a second build of the server to a job of a
   minute and a half. So the step is added after the replay gate, with a broker of its own
   in Docker, as `kafka-broker` starts one. `kafka-broker` is unchanged. Moving the step is
   moving its lines and the venv set-up, should the other job be preferred.
2. *The replay goes through the server and a broker, not through a Rust test.* A Rust test
   over `oxhaven_kafka::consume` would have run in `kafka-broker` at no cost, but it would
   have needed a second description of each case next to the Python the reference ran, a
   second comparison next to `rules.py`, and would not have seen the Python package or the
   schema a client receives.
3. *No raw spec, no headers in a column.* `docs/KAFKA.md` has it: no Python API of the
   reference reaches a raw spec, and no column shows a header. One record carries headers,
   to show that.

**Deterministic or masked**, each with its comment in the scenario or in `kafka.py`:

| What | How |
| --- | --- |
| Record timestamps | given by the producer, a second apart from a fixed start in 2023; none is 0, which librdkafka's producer takes as "now" |
| Offsets | a fresh broker, each record sent and acknowledged alone; `publish` refuses a broker that gives another offset |
| Retention | topics are created with `retention.ms=-1`: with the default, the broker deleted the records of 2023 within minutes of the first run here, and "the beginning" became the end |
| When rows arrive | `await` in every scenario |
| Rows of two partitions in one poll | sorted by partition and offset in the script (`PARITY.md` A3) |
| The order of a partitioned table's constituents | the merge and the keys are sorted (owner's item 26) |
| The receive time column | reduced to whether it is set, then dropped |
| A blink table | compared empty, with its columns and attributes, and through `blink_to_append_only` and a sum of it |
| A ring table | waited for through its row of the last offset |
| Committed offsets | the group of the one `DONT_SEEK` case never commits |
| The broker's address and the registry's URL | read by the scripts from the server's environment, so a script's text, and with it the recording's hash, does not hold a port |

### The cases

19 scenarios, 48 tables, recorded from Deephaven 42.9 (`deephaven-server==42.9`, the
oracle's embedded server) on `apache/kafka:3.9.1`. Recorded twice in full, the second time
on a fresh broker and a fresh JVM: every file came out byte for byte the same.

| Scenario | What it records |
| --- | --- |
| `kafka_simple_text` | text keys and values: simple specs; `FROM_PROPERTIES` with the types from `deephaven.*.column.type`; the key ignored. An empty value, no key, a tombstone, text beyond ASCII, headers |
| `kafka_simple_numbers` | `short`, `int`, `long`, `float`, `double`, with NaN, an infinity and Java's null value of each type; names and types from the properties and a deserializer |
| `kafka_simple_bytes` | a `byte[]` value column: its type, and its cells as length and text |
| `kafka_simple_bad_number` | a value of the wrong size fails the table |
| `kafka_simple_not_utf8` | bytes that are not UTF-8 in a `String` column (a known difference) |
| `kafka_json` | every JSON column type, a mapping, pointers into objects and arrays, Jackson's coercions, nulls and missing fields, an object as text, a record that is an array |
| `kafka_json_failures` | invalid JSON and a tombstone fail the table |
| `kafka_offsets` | all partitions, one partition, an offset per partition (a number, the end, the beginning), `DONT_SEEK` with a group and `earliest`, the end |
| `kafka_table_types` | ring, blink, and append through `blink_to_append_only` |
| `kafka_columns` | the common columns renamed, removed and added by the properties |
| `kafka_compressed` | gzip batches |
| `kafka_avro` | a registry subject at its latest version; `mapping` with `mapped_only`; a schema as text; a record from an older writer's schema (promotions, a default); a tombstone; null values, a wrapping timestamp |
| `kafka_avro_arrays` | arrays of ints and strings, a decimal as `BigDecimal` |
| `kafka_avro_failures` | an unknown schema id and a wrong magic byte fail the table |
| `kafka_protobuf` | `serdes` and `raw`, `include`, an optional field, a nested message, a repeated field, a `Timestamp`, the empty message; a tombstone fails the table |
| `kafka_protobuf_enum` | an enum field (a known difference) |
| `kafka_cdc` | `cdc.consume` (current rows, with the tombstone that brings a deleted key back), `stream_table`, `consume_raw` |
| `kafka_partitioned` | `consume_to_partitioned_table`: the merge, the keys, a constituent |
| `kafka_call_errors` | eight calls that fail before a table exists, by exception type and `DHError` message |

Two things Java did that the scenarios had first expected otherwise, both the same in
Oxhaven: `FROM_PROPERTIES` refuses `StringDeserializer` (`Deserializer type ... not
supported`), and `mapped_only` with `venue.lot` mapped and `venue` not gives no column for
it. Both are recorded.

### Differences found

None that was not known. Oxhaven gives the reference's tables in 17 scenarios. The two
others are listed in `oracle/kafka-baseline.json`, and the gate fails when either differs
in another way or stops differing:

| Scenario | Java | Oxhaven | Standing |
| --- | --- | --- | --- |
| `kafka_simple_not_utf8` | `fine`, `��abc`, `caf�` | the table fails (`INVALID_ARGUMENT`) | the owner's ruling of 2026-11-17 (`PARITY.md` A15; `docs/KAFKA.md`, item 7) |
| `kafka_protobuf_enum` | a column `color` of the values' names (`GREEN`, `RED`) | `consume` fails, naming `ProtobufImpl.ProtobufConsumeImpl#getIngestData` | open (`docs/KAFKA.md`, item 23) |

Minimal reproductions, on any broker and registry:

```python
# kafka_simple_not_utf8: a topic `t` with one record whose value is the bytes ff fe 61
kc.consume({"bootstrap.servers": broker}, "t", offsets=kc.ALL_PARTITIONS_SEEK_TO_BEGINNING,
           key_spec=kc.KeyValueSpec.IGNORE, value_spec=kc.simple_spec("V", dtypes.string),
           table_type=kc.TableType.append())

# kafka_protobuf_enum: a subject `t-value` holding
#   syntax = "proto3"; enum Color { RED = 0; GREEN = 1; } message Paint { Color color = 1; }
kc.consume({"bootstrap.servers": broker, "schema.registry.url": registry}, "t",
           key_spec=kc.KeyValueSpec.IGNORE, value_spec=kc.protobuf_spec(schema="t-value"))
```

No change to `crates/oxhaven-kafka` was needed, so there is no new unit test there.

`docs/KAFKA.md` says of a simple `byte[]` column that "the server does not send such a
column to a client yet". It does now, as Arrow binary with the reference's metadata; the
sentence is out of date, and is left for the owner of that section.

### The check can fail

- The gate was run against a broker filled from a topics file changed in six records (a
  double, a JSON text, a record's partition, an Avro int, a timestamp by a millisecond, a
  change event's `op`). Ten scenarios were `REGRESSED`, each naming the changed cell; the
  two known differences stayed as listed; the seven that read none of the changed records
  stayed clean.
- With an empty baseline the gate reported all 19 as `UNLISTED`.
- The harness tests of the task (`oracle/tests/test_kafka.py`, 27) were run against three
  breaks at once (a changed record in the topics file, a wait that never waits, a registry
  that answers 200 for an unknown subject): five failed, as they should.

### CI time

- `kafka-broker`: 1 min 33 s and 1 min 36 s on the two last runs of `main` before this
  task; unchanged, the job is not touched.
- `oracle-replay`: 5 min 5 s and 6 min 19 s on the same runs. The new step was not run on
  GitHub (no pull request is open). Here it takes 32 s after the build: about 10 s for the
  broker, the topics and the registry, 2 s for the server, 18 s for the 19 scenarios. On a
  runner add the pull of `apache/kafka:3.9.1` (204 MB), which `kafka-broker` does on every
  run inside its minute and a half. Expected: under a minute more.

### Limits

- **The comparison rules do not compare Arrow binary** (`rules.py` reports the type and
  never passes it, and a harness test holds that). So a `byte[]` and a `BigDecimal` column
  are not results themselves: `kafka_simple_bytes` and `kafka_avro_arrays` compare the
  column's type through the meta table and its cells as text. Teaching the rules binary
  would compare them directly; that is a change to the rules and to one of their tests,
  and was not made here.
- **Every edit of `kafka-baseline.json` is protected**, a promotion too:
  `check-baseline-change.sh` and the `rules` job know `replay-baseline.json` only, and were
  not touched.
- Not in the corpus: what `oracle/README.md`, "The Kafka corpus", lists at its end.
- A scenario reads topics that were filled before the server started. Records that arrive
  under an open table are covered by the broker tests, against Oxhaven alone.
