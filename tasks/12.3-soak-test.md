## Scope

Every existing check is short. Run the server for a long time under a ticking workload of
the kind a deployment has and check throughout, not only at the end: results stay right, no
table fails and no request fails, resident memory (measured from outside the process) and
processor time stay flat, the update cycle keeps up, nothing deadlocks, and the server stops
cleanly. A machine-readable result and a readable summary; non-zero exit on any violated
invariant. A short version on pull requests if it fits in about three minutes, the long one
nightly. Investigate what it finds; fix what is small and local, with a unit test.

Not part of it: storage and Kafka tables, partitioned tables, trees, figures; a count of
live exports and sessions (the server exposes none; `docs/SOAK.md`, "Memory", says what it
would take).

## Notes

### Design, and where it departs from the expected shape

- **A Python driver beside `bench/bench.py`**, not a Rust test: it must start the binary that
  is deployed and be a real client (pydeephaven, `pydeephaven_ticking` for Barrage), and it
  reuses the benchmark's barrier and the oracle's session and hierarchical-view helpers.
- **The correctness check is exact, in two forms.** For the chains over input tables the
  driver is the only writer, so after its barrier a static `snapshot()` of the inputs and the
  ticking results are of one cycle; the chain is run again on the snapshots and compared row
  for row. For the tables fed by the clock no client call sees two tables in one cycle, so
  one console command takes the snapshots: a command holds the update graph's lock. Without
  a console those tables are only read, and the summary says so.
- **A steady state by construction.** The long-lived tables are keyed input tables with a
  fixed key space, blink tables, tails and a ring table, so nothing grows by design and a
  slope of resident memory is a finding. What comes and goes (sessions, tables,
  subscriptions) is sized to show if kept.
- **Cycles are counted in the server**, by a `deephaven.table_listener` on a blink time
  table: a Barrage subscriber gets at most one update a second
  (`BarrageRequestHelpers#DEFAULT_MIN_UPDATE_INTERVAL_MS`), so it cannot count cycles of
  100 ms. Without a console the cycle count is not available.
- **Live exports and sessions are not counted**: the server has no call for it. File
  descriptors and threads of the process are checked against their baseline instead, and
  abandoned sessions are found by their memory.
- **Every invariant is shown to fail**: `selftest` (the judging on made-up series), and
  `--inject leak|mismatch|stall` against a real server.
- **`--skip`** leaves parts of a round out, which is how the finding below was narrowed down.

### What the long run found: a sort by a time leaked 12 bytes per row

The first 45-minute run (seed 1, release build with console, 1,345 rounds, 325,425 requests,
46,331 cycles, 30,935 exact comparisons, all equal) failed one invariant: resident memory.
It rose in steps from 150 MB to about 195 MB in the first 13 minutes and then kept a slope
of 10 to 17 MB per hour (`bench/results/2026-11-18-task-12.3-soak-long-first.json`).

Narrowing it down, each variant a fresh server:

| variant | rounds | resident memory |
| --- | ---: | --- |
| nothing but the barrier and the cycle count | 3,276 in 4 min | flat |
| console script only | 3,174 in 4 min | flat |
| churn only | 566 in 4 min | flat |
| checks only | 901 in 4 min | flat |
| abandoned sessions only (329 of them) | 2,639 in 4 min | flat at about 200 MB: expired sessions are released |
| writes only | 2,953 in 10 min | 112 to 135 MB, monotone: 7.8 KB per round |
| writes to one input table and no derived table | 100 s each | flat |
| writes with one chain: `sort("Sym", "Qty", "Id")`, `aj`, the joins, the aggregations | 110 to 200 s each | flat |
| writes with `sort("Ts")` alone, or with `update`, `update_by`, `last_by` after it | 150 to 200 s each | 11 to 14 bytes per row written |

`Ts` rises with every write, so each new row sorts after all others. The incremental sort
(`ops/sort/gapped.rs`) put such rows after the last row and grew its key space for them; the
keys of rows that had left were before the last row and were never used again. The two
arrays it indexes by row key (8 and 4 bytes per key) therefore grew by 12 bytes for every row
ever appended, without bound, in the commonest ticking sort there is: by a timestamp, over a
table that also loses rows. At 1,000 rows a second that is about 1 GB a day.

**Fixed** in this branch (`engine/sort: lay the result out again when appends outrun the
rows`): when an append would take the key space past twice the room the rows need, the whole
result is laid out again, and the moved rows are reported as shifts, as for any other
layout. Unit test `rows_appended_while_others_leave_keep_the_key_space_in_proportion`
(fails before the fix at round 63: "the last key is 643 for 104 rows").

Two things the first run taught about the test itself, both changed before the runs below:

- The leak was 12 bytes per written row and a round wrote about 500 rows, so it was near
  the limit of what the slope could show. A round now writes 2.5 times as much
  (`WRITE_STEPS = 10`): a leak per written row is larger against the same noise.
- Resident memory takes about 13 minutes to reach its plateau (steps of 10 to 20 MB as the
  allocator's retained memory reaches what the churn needs at its peak). The long profile's
  warm-up is now 15 minutes of its 45, not 7.
