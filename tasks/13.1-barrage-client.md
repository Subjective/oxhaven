## Scope

Oxhaven as a client of another Deephaven-compatible server: a session (connect, authenticate, keep alive, release,
close), a table fetched by ticket, a snapshot as a static table, and a full subscription as a refreshing table of the
local update graph. Not part of it: `dh://` URIs and resolvers and the Python modules `deephaven.barrage` and
`deephaven.uri` (13.2), recorded scenarios and the soak test (13.3).

## Notes

### A module of the server crate, not a crate

`crates/oxhaven-server/src/barrage_client/`. The client is the other end of what the server crate already has: the
row set, shift and column set codecs (`barrage::codec`), the schema metadata (`schema`), the reading of an IPC schema
(`flight`), the ticket encodings (`session`, `app`). A crate of its own would depend on the server crate for those and
the server crate (where 13.2's Python modules and resolver live) would depend on it: a cycle, unless the codecs move
to a third crate first. The module adds no dependency: `tonic`'s channel, `tokio`, `flatbuffers` and `arrow` are all
dependencies of the crate already.

| File | Holds |
| --- | --- |
| `session.rs` | `BarrageSession`: the connection, authentication, the bearer token and its rotation, the ping, exports, `fetch`, `snapshot`, `subscribe`, `close` |
| `schema.rs` | `RemoteSchema`: the definition and attributes a fetched table's schema carries, and which columns can be read |
| `message.rs` | `MessageReader`: Flight messages put together into `RemoteMessage`s (port of `BarrageMessageReaderImpl`) |
| `decode.rs` | One column read off a record batch and turned into the cells the engine stores |
| `replica.rs` | The local copy: messages applied to column sources, and the refreshing table (`BarrageRedirectedTable`, `BarrageBlinkTable`) |
| `error.rs` | `ClientError` |

### What is served

- **Session.** Plaintext `host:port`. The first call is `ConfigService/GetConfigurationConstants` with
  `Authorization: <type> [<value>]` (default `Anonymous`; a pre-shared key is
  `io.deephaven.authentication.psk.PskAuthenticationHandler <key>`), as Java's `Authentication` does it. The bearer
  token is taken from the headers and trailers of every answer and of every status, the last `Bearer` value winning,
  with Java's rule for a rotation. Every later call sends `Authorization: Bearer <token>` and the extra headers. The
  server is pinged with the same call every third of `http.session.durationMs` (every minute if the server does not
  say). `close` calls `SessionService/CloseSession`; `release` calls `SessionService/Release`. The largest message
  accepted is 100 MiB, Java's default.
- **Fetch.** `TableService/FetchTable` of any ticket (`s/<name>`, `a/<app>/f/<field>`, `h/<shared id>`, an export)
  into a new export of the session, numbered from 1 as Java numbers them. The answer's schema gives the definition
  and the attributes.
- **Snapshot.** `DoExchange` with a `BarrageSnapshotRequest`: the whole table, or a viewport (from the start or from
  the end) and a choice of columns, as Java's `BarrageSnapshot#partialTable`. The result is a static, flat table. A
  column that was not asked for is there, with null cells, as in Java.
- **Subscription.** `DoExchange` with a `BarrageSubscriptionRequest` for the whole table. The call returns once the
  server has said that it sends the whole table and every column (Java's `entireTable` future). The table is a root
  of the local update graph: the session's task reads the stream, and each cycle applies what arrived, in order, and
  tells the listeners one update. Rows keep the server's row keys. Removes, shifts, adds and each column's own
  modified rows are applied in the order of Java's `BarrageRedirectedTable#processUpdate`; several messages in one
  cycle are composed into one update (Java's `UpdateCoalescer`). Previous values are kept from the moment the table
  is made. A blink table shows the rows that arrived since the last cycle at `0..n` and takes them away on the next,
  as `BarrageBlinkTable`. `BlinkTable`, `AddOnly`, `AppendOnly` and `IsFlat` are carried to the local table; every
  attribute of the schema is in `RemoteSchema::attributes`.
- **Options.** `use_deephaven_nulls`, `columns_as_list`, `min_update_interval_ms`, `batch_size`, `max_message_size`
  with Java's builder defaults (false and 0), and the options of Java's resolver (`SubscriptionOptions::RESOLVER`,
  `SnapshotOptions::resolver()`: Deephaven nulls on).
- **Failure.** A subscribed table fails on the next local cycle when its stream ends: with
  `Barrage subscription closed by server` when the server ends it, and with
  `Barrage subscription error for <host:port>/export <n>: <status>` when the call fails, which is what happens to
  every table of a session whose connection is lost. Closing the session fails its tables the same way. A message
  that does not fit the table (rows it does not have, cells that do not match the rows) fails the table and never
  panics. Dropping a subscribed table ends its call and releases its export.

### Column types

Read, and compared with Deephaven 42.9 cell by cell (below): `Boolean`, `byte`, `char`, `short`, `int`, `long`,
`float`, `double`, `String`, `Instant`, `LocalDate` (as `Date32`, or as `Date64` in milliseconds, which
Java reads too), `LocalTime`, `Duration`, `Period`, `ZonedDateTime`, `BigDecimal`, `BigInteger`, arrays of all of these
(`byte[]` as Arrow `Binary`), and vectors (`IntVector`, ..., `ObjectVector` of `String` and `Instant`), nested too.
This is every type the serving side of Oxhaven writes except the ones below.

Refused by name when the table is fetched, in Java's words where Java's client refuses them too:

| Column | Refused with |
| --- | --- |
| `LocalDateTime`, `ZoneId`, `DayOfWeek`, `java.lang.Object`, a column of tables | `Column '<name>' with type <class> cannot be serialized directly. Consider an updateView() expression ...` and `(io.deephaven.extensions.barrage.chunk.DefaultChunkReaderFactory#newReader)`: both servers send these as text, and Java's client has no reader that makes the type of text |
| A vector of vectors (`ObjectVector` of `ObjectVector`) | An error that names the column and says that Java reads its elements as `java.lang.Object`, which cannot be serialized directly |
| Any other pair of a Java class and an Arrow type (an `int` column sent as `Int64`, a timestamp in another unit, a dictionary, a union, a map) | `not ported yet: io.deephaven.extensions.barrage.chunk.DefaultChunkReaderFactory#newReader: reading Arrow type <type> as <column type>`. Java reads many such pairs, converting as it reads; neither server sends them for a table of its own |
| A class no column type stands for | `not ported yet: io.deephaven.extensions.barrage.util.BarrageUtil#convertArrowSchema: ...` |
| A column name Java would rename | `not ported yet: io.deephaven.api.util.NameValidator#legalizeColumnName` |

Kept as Java has it, and lossy in Java: a `Period` arrives as its total months (years and days are lost: Java's
writer sends `toTotalMonths`), and a `ZonedDateTime` arrives as its instant in the zone the field names, which is
`UTC` from Deephaven whatever zone the values had.

### Not ported

There is no `unported!` call: everything missing is an error value that names the Java code.

- **TLS** was refused here (owner question 7.24); task 13.4 added it, through the system's OpenSSL
  (`barrage_client/tls.rs`, `docs/CONSOLE.md`, "TLS").
- **A subscription to a viewport or to some columns** (`io.deephaven.client.impl.BarrageSubscription#partialTable`,
  `#snapshotEntireTable`): `SubscriptionOptions` has no viewport and no columns, so it cannot be asked for. The
  reader and the copy already follow the server's effective viewport and columns while a full subscription grows.
- **Dictionary batches** in a stream: `not ported yet: ...BarrageMessageReaderImpl#safelyParseFrom: dictionary batches`.
- **Of `ClientConfig` and `SessionImplConfig`**: `overrideAuthority`, `userAgent`, the SSL configuration, the close
  timeout, `SessionImplConfig#delegateToBatch`. The fetch is one `FetchTable` call where Java sends a batch of one.
- **Attributes other than the four above** are not attributes of the local table (`SortedColumns`, `InputTable`
  and the rest are readable from `RemoteSchema::attributes`).
- **Subscriptions to blink tables served by Oxhaven**: the client has them (tested on messages and against
  Deephaven), but Oxhaven's server answers `UNIMPLEMENTED` (`BarrageMessageProducer (blink tables)`), which the
  client passes on.

### Differs from Deephaven

- A static snapshot table has no attributes: Java's snapshot `BarrageTable` carries the schema's attributes,
  `BlinkTable` among them, on a table that does not refresh (where Java's engine does not treat it as a blink
  table). Owner question 7.25, answered 2026-11-21: `PARITY.md` A28.
- A snapshot whose messages remove, shift or modify rows is refused as a protocol error; Java applies them. A server
  answers a snapshot request with included rows only.
- A snapshot of a blink table keeps the rows of every message; Java's static blink table replaces its rows with each
  message (`BarrageBlinkTable#applyUpdates`), so it would keep the last one. Both servers answer with one message.
- The cells are kept by row key in sparse sources; Java keeps them densely behind a row redirection. A reader sees
  the same table.
- The log name in the failure text is `<host:port>/export <n>`; Java's is the export id and an identity hash.

### Tests

`cargo test -p oxhaven-server --lib barrage_client` (30 tests, about 25 s, of which 11.5 s wait for a token to
expire):

- `replica/tests.rs`: the copy against a scripted table that plays the server, with the testkit's consistency
  checker on every cycle: random changes with one to three messages per local cycle (60 seeds, some growing to
  thousands of rows), each column modified at its own rows, a shift with modifies, two messages composed into one
  update, empty messages, growth to 70,000 rows followed by a shift and modifies across blocks, a blink table, a
  subscription that grows by viewport, an error delivered before the messages that came with it, messages that do
  not fit.
- `message/tests.rs`: the reader against the messages of this crate's own writer for random changes (every batch
  size, both null encodings, columns as lists, an empty change), 400 damaged streams that must not panic, messages
  out of place.
- `schema.rs`: the schema the server writes read back, the refusals, the attribute rule.
- `tests.rs`: the client against this crate's server over a socket: static tables of every readable type
  (snapshot and subscription, both null encodings, columns as lists), a ticking table changed at random (12 seeds),
  a 150,000-row table that then shifts and changes, keyed and append-only input tables, a blink table's snapshot,
  snapshot viewports and columns, the kinds of ticket, authentication and its refusals, a session kept alive past
  its first token, closing (exports released on the server, tables failed, further calls refused), a cut connection
  (through a TCP relay), the wake.

The barrier of the socket tests is "run local cycles until the copy has the server's rows at the server's keys",
with the server's graph at rest; the consistency checker then confirms every update the copy told was true.

Each was shown to fail with the handling broken (the change, then the test that failed):

### Compared with Deephaven 42.9

`tasks/13.1-barrage-client/check.py` starts the reference server on a free port, makes tables on it with a script,
and drives Oxhaven's client (`examples/barrage_client_check.rs`, a line protocol around the client) while reading
the same tables with `pydeephaven`. Both sides write each cell as the same text; a ticking table is compared after
each change, waiting until the client has caught up.

```bash
cargo build -p oxhaven-server --example barrage_client_check
<python of oracle/requirements.txt> tasks/13.1-barrage-client/check.py \
    --client <target dir>/debug/examples/barrage_client_check
```

Result on 20 November: `102 passed, 0 failed`.

- `every_type` (1000 rows, 23 columns: the types above with nulls) and `vectors` (a `group_by`, nine vector columns):
  a snapshot, and a subscription in each of the four combinations of Deephaven nulls and columns as lists.
- `big` (700,000 rows, three columns): snapshot and two subscriptions, compared by row count and a hash of the rows.
  Deephaven sends this subscription as a viewport that grows.
- Ticking: a keyed input table and its `sort_descending`, `agg_by`, `where().update()` and `group_by`, and an
  append-only input table; ten steps of adds, changes and deletes; every table compared after every step (60
  comparisons). The append-only table is `add_only` and `append_only` here.
- A blink table from a table publisher: five batches; every row is shown once (compared with the server's
  `blink_to_append_only`), and the table is empty at rest.
- A time table that ticks on its own ten times a second: what the client holds is always the first rows of what
  the server holds a moment later, and it grows.
- A `LocalDateTime` column is refused with Java's text.

Three things of the check are not `pydeephaven`'s reading: pyarrow cannot hold the month interval a `Period`
arrives as, so the expected text of a `Period` is its total months, computed by a formula on the server; the
elements of a `byte[]` arrive without validity, and the byte -128 is written as null on both sides, as Deephaven's
null byte is for an `int[]` element of `NULL_INT`; and the zone of a `ZonedDateTime` is the one the field names.

## Handover

### For 13.2

Everything is in `oxhaven_server::barrage_client`. The calls are `async` and must run on a tokio runtime that
stays alive: the session spawns its ping, and each subscription spawns the task that reads its stream.

```rust
pub struct ClientConfig {
    pub host: String,
    pub port: u16,
    pub use_tls: bool,
    pub tls_root_certs: Option<Vec<u8>>,
    pub authorization: String,
    pub extra_headers: Vec<(String, String)>,
    pub max_inbound_message_size: usize,
}
impl ClientConfig {
    pub fn new(host: impl Into<String>, port: u16) -> Self;          // plaintext, "Anonymous"
    pub fn with_auth(self, auth_type: &str, auth_token: &str) -> Self; // an empty token sends the type alone
    pub fn with_psk(self, key: &str) -> Self;
}
pub const PSK_AUTH_TYPE: &str;
pub const DEFAULT_MAX_INBOUND_MESSAGE_SIZE: usize;

pub type Wake = Arc<dyn Fn() + Send + Sync>;

#[derive(Clone)]
pub struct BarrageSession { /* clones share the session */ }
impl BarrageSession {
    pub async fn connect(config: ClientConfig, graph: Arc<dyn UpdateGraph>, wake: Option<Wake>)
        -> Result<Self, ClientError>;
    pub fn target(&self) -> &str;                                     // "host:port"
    pub fn is_closed(&self) -> bool;
    pub async fn fetch(&self, ticket: &[u8]) -> Result<RemoteTable, ClientError>;
    pub async fn release(&self, export_id: i32) -> Result<(), ClientError>;
    pub async fn snapshot(&self, ticket: &[u8], options: SnapshotOptions)
        -> Result<Arc<dyn Table>, ClientError>;
    pub async fn snapshot_of(&self, table: &RemoteTable, options: &SnapshotOptions)
        -> Result<Arc<dyn Table>, ClientError>;
    pub async fn subscribe(&self, ticket: &[u8], options: SubscriptionOptions)
        -> Result<Arc<dyn Table>, ClientError>;
    pub async fn close(&self) -> Result<(), ClientError>;
}

pub struct SubscriptionOptions {               // Default: Java's builder (all false and 0)
    pub use_deephaven_nulls: bool,
    pub columns_as_list: bool,
    pub min_update_interval_ms: i32,
    pub batch_size: i32,
    pub max_message_size: i32,
}
impl SubscriptionOptions { pub const RESOLVER: SubscriptionOptions; } // BarrageTableResolver.SUB_OPTIONS

pub struct SnapshotOptions {                   // Default: Java's builder and the whole table
    pub use_deephaven_nulls: bool,
    pub batch_size: i32,
    pub max_message_size: i32,
    pub viewport: Option<RowSet>,
    pub reverse_viewport: bool,
    pub columns: Option<Vec<String>>,
}
impl SnapshotOptions { pub fn resolver() -> Self; }                   // BarrageTableResolver.SNAP_OPTIONS

pub struct RemoteTable { pub export_id: i32, pub schema: RemoteSchema, pub is_static: bool, pub size: i64 }
pub struct RemoteSchema {
    pub definition: TableDefinition,
    pub attributes: BTreeMap<String, RemoteAttribute>,
    pub arrow: arrow::datatypes::Schema,
}
pub struct RemoteAttribute { pub value: String, pub java_type: Option<String> }

pub enum ClientError {
    Config(String), TlsNotAvailable, Connect(String), Status(tonic::Status),
    Protocol(String), NotReadable(String), Closed, Table(TableFailure),
}

// tickets, re-exported from where the server defines them
pub fn scope_ticket(name: &str) -> Vec<u8>;                           // s/<name>
pub fn application_field_ticket(application_id: &str, field_name: &str) -> Vec<u8>; // a/<app>/f/<field>
pub fn shared_id_to_bytes(shared_id: &[u8]) -> Vec<u8>;               // h/<id>
```

What `deephaven.barrage` needs, by Python name:

| Python | Rust |
| --- | --- |
| `barrage_session(host, port, auth_type, auth_token, use_tls, tls_root_certs, extra_headers)` | `ClientConfig::new(host, port).with_auth(auth_type, auth_token)`, then set `use_tls`, `tls_root_certs`, `extra_headers`; `BarrageSession::connect(config, graph, wake)`. `tls_root_certs` without `use_tls` is refused with Python's own message; `use_tls` is refused (`TlsNotAvailable`) |
| `BarrageSession.subscribe(ticket)` | `session.subscribe(ticket, SubscriptionOptions::RESOLVER)` |
| `BarrageSession.snapshot(ticket)` | `session.snapshot(ticket, SnapshotOptions::resolver())` |
| `BarrageSession.close()` | `session.close()` |

- `graph` is the server's `PeriodicUpdateGraph` (`state.graph.clone()`), and `wake` should be
  `Some(Arc::new(move || graph.request_cycle()))`: without it a change waits for the next cycle of the timer, and a
  blink table's rows go on the cycle after they arrive.
- `subscribe` takes the graph's shared lock for a moment on a blocking thread when it makes the table. Do not call
  it from inside a cycle.
- For the URI resolver: a `dh+plain://host:port/scope/<name>` URI is `scope_ticket(name)`, `/app/<id>/field/<name>`
  is `application_field_ticket(id, name)`. Java's resolver keeps one session per target; `BarrageSession` is `Clone`
  and may be kept in a map by `target()`. A session whose tables are all dropped stays open until `close` or until
  the last clone is dropped (the ping stops then, and the server lets the session expire).
