## Notes

### Where it lives

A new crate, `crates/oxhaven-uri`, with no dependencies (dev: `serde_json`, already in the workspace). The URI types
are needed by the server (resolvers, the console) and by the Barrage client of 13.1, and no existing crate fits:
`oxhaven-engine` and `oxhaven-expr` are table and formula crates that a client should not pull in, `oxhaven-server`
is the binary's crate, and `oxhaven-contracts` is protected. A crate with no dependencies cannot make a cycle.

`ResolveTools`, `UriResolver`, `UriResolvers` and `UriResolversInstance` are resolver plumbing, left to 13.2b.

`Uri` reproduces `java.net.URI` from its documentation and from Java's answers, not from JDK source (none was
read or translated). What it had to learn from the recordings, beyond RFC 2396: a host name with two labels or more
needs a letter first in its last label, but a single label may start with a digit (`1host`, `1`); IPv4 parts may
have leading zeros (`0001.1.1.1`); a port is any number up to 2^31 - 1; when the server-based reading fails, the
authority is registry-based (no host, no port) unless a bracket is in it; the error text and position of each
failure; an encoded surrogate decodes to one U+FFFD; `getAuthority` and `getSchemeSpecificPart` leave escapes
inside `[...]` encoded. `toASCIIString` is not ported (nothing in Deephaven uses it).

### Java behaviour kept

Matched, recorded here, and asked as owner question 7.23 in `review-items-2.md`:

- **A `dh://` URI whose host Java cannot read is a local URI.** `java.net.URI` reads `host_name`, `é.com`,
  `ho%41st`, `1.2.3`, `-host`, `host:-1`, `host:99999999999` and `host:80:80` as registry-based authorities, which
  have no host. `UriHelper.isLocalPath` only asks for no host, so `dh://host_name/scope/t` is a well-formed
  `QueryScopeUri` for `t` (its `toString` is `dh:///scope/t`) and not a `RemoteUri`. Through the resolvers,
  `resolve("dh://my_server/scope/t")` returns the local variable `t` (or `None`) instead of failing; the user
  meant another server. Same for `/app/.../field/...` and `/field/...` (the latter has no local resolver).
- **Ports above 65535** (up to 2^31 - 1) are accepted in targets: `dh://host:65536`. The connection fails later.
- **Host case**: `DeephavenTarget` compares hosts exactly, so `dh://HOST/scope/x` and `dh://host/scope/x` are
  different remote URIs (Java's `BarrageTableResolver` then opens one session per spelling).

Not hazards, but easy to get wrong:

- A proxied inner URI that is not a remote Deephaven form is a `CustomUri`; a `dh`/`dh+plain` inner URI that is
  not a remote form is rejected (`Invalid custom URI 'dh:///scope/x'`). The inner URI is the decoded query, so it
  may be written encoded or not; it is written back encoded (custom) or as is (remote).
- The application id is the greedy group of `^/app/(.+)/field/(.+)$`: the last `/field/` splits.
- Names are checked after percent-decoding; a decoded line terminator (`%0A`, `%0D`, `%C2%85`, `%E2%80%A8`,
  `%E2%80%A9`) makes the pattern fail, so the error is "Invalid ... URI", not "Invalid ... name".
- Constructors accept an empty name (`QueryScopeUri::new("")` is `dh:///scope/`), which does not parse back.

The probe had to work around jpy, not Java: jpy hands a character outside the BMP to Java cut to its low 16 bits,
so such inputs go in through reflection, and Java messages come back through modified UTF-8 read as UTF-8, so a
character outside the BMP (or a NUL) in a message is put back by the probe (`fix_garbled`).

### What 13.2b must implement

Resolvers, as Deephaven 42.9 installs them (`UriModule`; there is no `UriRouter` in 42.9):

| Resolver | Schemes it registers | `isResolvable(uri)` | `resolve(uri)` |
| --- | --- | --- | --- |
| `QueryScopeResolver` | `dh` | `QueryScopeUri.isWellFormed` | the query scope variable, or `null` when there is none (`readParamValue(name, null)`; no error) |
| `ApplicationResolver` | `dh` | `ApplicationUri.isWellFormed` | the application field's value, or `null` when the application or the field does not exist |
| `BarrageTableResolver` | `dh`, `dh+plain` | `RemoteUri.isWellFormed` (proxied forms included, see below) | a full subscription to the remote table, waited for (`subscribe(...).get()`) |
| `CsvTableResolver` | `csv+http`, `http+csv`, `csv+https`, `https+csv`, `csv+file`, `file+csv`, `csv` | the scheme is one of those (any shape) | the URI rebuilt with scheme `http`, `https` or `file` (`new URI(scheme, userInfo, host, port, path, query, fragment)`), read by `CsvTools.readCsv(String)` |
| `ParquetTableResolver` | `parquet` | scheme `parquet` and `UriHelper.isLocalPath` | `ParquetTools.readTable(uri.getPath())` (the decoded path) |

How `ResolveTools.resolve(String)` picks one: `URI.create(s)` (a syntax error is an `IllegalArgumentException`
with `UriSyntaxError`'s message), then the resolvers registered for exactly `uri.getScheme()` (case-sensitive; a
relative URI has scheme `null` and none), filtered by `isResolvable`. None: `UnsupportedOperationException`
`Unable to find resolver for uri '<uri>'`. More than one: `Found multiple resolvers for uri '<uri>': [class
a.B,class c.D]` (cannot happen with these five: the three `dh` resolvers' shapes are disjoint). So
`dh:///field/f` and `dh+plain:///scope/x` find no resolver, and `parquet://host/x` neither.

`BarrageTableResolver` in detail:

- The inner URI becomes a ticket: `QueryScopeUri` `s/<name>`, `ApplicationUri` `a/<app>/f/<field>`,
  `FieldUri` `a/<target host>/f/<field>` (the host is the application id). A proxied inner `RemoteUri` throws
  `UnsupportedOperationException("Proxying not supported yet, see https://github.com/deephaven/deephaven-core/issues/1483")`
  and a `CustomUri` throws `UnsupportedOperationException("Remote custom URIs not supported yet, see https://github.com/deephaven/deephaven-core/issues/1483")`,
  both before any connection (Java's comment: `isResolvable` claims these on purpose, for the better error).
- One session per `DeephavenTarget` (equal by secure flag, exact host, port), cached for the server's life and never
  closed (deephaven-core#1482). Sessions are made with an empty `SessionConfig`: no authentication
  (deephaven-core#3421). TLS to a `dh` target uses the server's outbound SSL configuration (`outbound.` properties,
  `MainHelper.parseOutboundSSLConfig`) unless the client config sets one. A target without a port uses 443 (`dh`)
  or 10000 (`dh+plain`).
- Options: `useDeephavenNulls(true)` for subscriptions and snapshots. `maxInboundMessageSize` is the configuration
  property `BarrageTableResolver.maxInboundMessageSize`, default 104857600 (100 MiB).
- Its public methods (`subscribe` and `snapshot` with a target URI string, a `TableSpec`, optional viewport, columns
  and reverse flag) parse the target with `DeephavenTarget.of(URI.create(s))`.

Safety checks and switches in 42.9: none beyond the above. There is no configuration property that turns a
resolver or a scheme off, no allow list of hosts, paths or URLs, and no `AuthorizationProvider` hook on URI
resolution; resolving runs with the rights of whoever runs the script. `csv+file`/`csv`/`parquet` read any file
the server process can, and `csv+http(s)` fetches any URL from the server. Resolution is reachable only from
scripts (`deephaven.uri.resolve`, or Groovy calling `ResolveTools`), not from any gRPC call. Whether Oxhaven should
add a switch is a decision for 13.2b and the owner, not a parity question.

The Python modules:

- `deephaven.uri.resolve(uri: str)` calls `ResolveTools.resolve(uri)`; a Java object is wrapped
  (`wrap_j_object`, so a table becomes `deephaven.table.Table`), a value already in Python is returned as is.
  Any exception becomes `DHError(e, "failed to resolve the URI.")`.
- `deephaven.barrage.barrage_session(host, port=10000, auth_type="Anonymous", auth_token="", use_tls=False,
  tls_root_certs=None, extra_headers=None)`: `tls_root_certs` without `use_tls` raises
  `DHError(message="tls_root_certs is provided but use_tls is False")`; the target is
  `DeephavenTarget.of(new URI("dh://host:port" or "dh+plain://host:port"))` (so the host is checked as above, and an
  IPv6 host must be given in brackets); extra headers go into the client config; root certificates become a custom
  trust; the session is authenticated with `"<auth_type> <auth_token>"` (or `auth_type` alone when the token is
  empty) through the server's `SessionFactoryCreator.barrageFactory(...)`, falling back to a directly built session
  when the server is not fully initialized. Errors become `DHError(e, "failed to get a barrage session to the target remote Deephaven server.")`.
- `BarrageSession.subscribe(ticket: bytes)` and `snapshot(ticket: bytes)`: `TableSpec.ticket(ticket)` with the
  resolver's options, then `entireTable().get()`, wrapped in `Table`; errors become `DHError` with "failed to
  subscribe to the remote table with the provided ticket." and "failed to take a snapshot of the remote table with
  the provided ticket.". `close()` closes the session and shuts the channel down (waiting up to 10 s); the class is
  a context manager.
