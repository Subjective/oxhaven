## Scope

Remote tables usable from the Python console as in Deephaven 42.9: Java's five URI resolvers with its selection rules
and error texts, `deephaven.uri.resolve`, and `deephaven.barrage` (`barrage_session`, `BarrageSession` with
`subscribe`, `snapshot`, `close`, `with`). Not part of it: TLS (owner question 7.24), recorded scenarios (13.3).

## Notes

### Where it lives

- `crates/oxhaven-server/src/uri/mod.rs`: `Resolver` (the five), `resolver_for` (Java's `UriResolvers#resolver`),
  `UriResolvers` (`resolve` is `ResolveTools.resolve(String)`), `ResolveError` (its `Display` is the text a script
  sees: `java.lang.<Exception>: <message>` where Java throws), the client's runtime and the wait. Compiled in every
  build; the CSV and Parquet readers are there only with the `python` feature, the only build that can resolve.
- `console/python/remote.rs`: the native functions `resolve_uri`, `barrage_session` and the class
  `BarrageSessionHandle`; `python/deephaven/uri.py` and `barrage.py` call them as the reference calls Java.
- `oxhaven-uri` gained `Uri::from_components`, the seven-argument `java.net.URI` constructor that
  `CsvTableResolver#replaceScheme` uses, from its documentation and checked against Deephaven 42.9's JVM (below):
  one thing the documentation does not say, every `%` is quoted (`/a%41` gives `/a%2541`).

### What is served

| URI or call | Result |
| --- | --- |
| `dh:///scope/<name>` (`dh:/scope/<name>`) | the console variable as the package wraps it (`Table`, `InputTable`, the Python object itself), `None` when missing |
| `dh:///app/<id>/field/<name>` | the field, `None` when the application or the field is missing |
| `dh+plain://host[:port]/scope/<name>`, `/app/<id>/field/<name>`, `/field/<name>` | a full subscription (`SubscriptionOptions::RESOLVER`) through one cached `Anonymous` session per target; a failed connection is not cached |
| `csv:`, `csv+file:`, `file+csv:` | the URI rebuilt as Java rebuilds it (`file:<path>`, re-quoted), read by `oxhaven_csv::read` with `CsvTools`' defaults |
| `parquet:///<path>` (no host) | `oxhaven_parquet::read` of the decoded path |
| `barrage_session(...)` | a new session each call: `DeephavenTarget.of(new URI("dh+plain://host:port"))` with Java's errors, `auth_type`/`auth_token` as the reference joins them (an empty result is `Anonymous`), extra headers |
| `subscribe(ticket)`, `snapshot(ticket)` | `bytes`, or `str` as its UTF-8 bytes (`TableSpec#ticket(String)`); Java's resolver options |
| `close()`, `with` | `CloseSession`; the session's subscribed tables fail on the next cycle; a second close does nothing |

Every error is a `DHError` with the reference's message (`failed to resolve the URI.`, `failed to get a barrage
session to the target remote Deephaven server.`, ...) over a `RuntimeError` with Java's text where Java throws:
`Unable to find resolver for uri '<uri>'`, URI syntax errors, invalid names and targets, the proxied and custom
refusals (before any connection, as Java), `tls_root_certs is provided but use_tls is False`, and jpy's `no matching
Java method overloads found` for a `uri` that is not a `str`.

**The wait.** A subscription is complete after a cycle of the local graph has applied it, and the client makes the
table under the shared lock, so `uri::waiting_for_subscription` runs the wait inside `yielding_to_cycles` and
`SteppedUpdateGraph::waiting_for_cycle`: a command's holds of the graph lock are given up for the wait and taken
again, as Java's `UpdateGraphAwareCompletableFuture#get` waits on a condition of the exclusive lock. The interpreter
lock is released first. A snapshot keeps the lock (Java's snapshot future does not wait on the lock either). The
client runs on a multi-threaded tokio runtime of its own (two threads, for the life of the process), so a caller on
any thread can block on it (`uri::block_on`), and the sessions' pings and readers outlive no runtime. Each session's
wake calls `request_cycle` on a weak reference to the server's graph.

### Refused (cautious, differs from Java)

- **TLS** (`dh://`, `use_tls=True`): `TLS connections to remote servers are not ported yet:
  io.deephaven.client.impl.ChannelHelper#channelBuilder (useTransportSecurity)`, as decided (7.24). With
  `tls_root_certs` and no `use_tls`, the reference's own error comes first, as in Java.
- **A subscription inside an update cycle** (a listener) or **under a shared lock Python code took itself** (outside
  a command): refused at once; Java waits for a cycle that cannot run (by reading, not tried). Owner question 7.26, answered 2026-11-21: `PARITY.md` A29.
- **`csv+http(s)`**: not ported in `oxhaven-csv` (`CsvTools#readCsv(URL, CsvSpecs)`); Java fetches any URL from the
  server.
- A target port above 65535, which Java's URI accepts: `invalid client configuration: port <n> of <target> is out
  of range` (Java fails when it connects).

### Kept as Java has it

- **Owner question 7.23**: a `dh://` URI whose authority has no host Java can read (`dh://host_name/scope/t`,
  `dh://h:99999999999/...`) resolves locally, the authority dropped; checked on Deephaven (below). The switch is the
  constant `UNREAD_HOST_IS_LOCAL` in `uri/mod.rs`, read by `check_unread_host` before the query scope, application,
  CSV and Parquet resolvers: `parquet://host_name/x` and `csv://host_name/x` drop such an authority too (the CSV
  rebuild gives `file:/x`). Set it to `false` and those URIs are refused with an `IllegalArgumentException` that names
  the authority.
- Sessions of the resolver are kept for the server's life and never closed (deephaven-core#1482), and are
  `Anonymous` (deephaven-core#3421). Host case and spelling make different targets.
- The CSV path is decoded and quoted again, so `csv:///tmp/a%20b.csv` reads the file named `a%20b.csv`, not
  `a b.csv`, on both servers.

### Differences of text (the comparison below)

The tables, the outcome of every call and every DHError message are the same. The cause text differs for: a
remote error (`NotFound: Could not resolve ...` from the client, where Java writes
`...TableHandleException: io.grpc.StatusRuntimeException: NOT_FOUND: Could not resolve ...` around the same server
message), a refused connection (tonic's `transport error`, Java's `UNAVAILABLE: io exception`), a call on a closed
session (`the Barrage session is closed`, Java's `UNAVAILABLE: Channel shutdown invoked`), a missing CSV or Parquet
file (the readers' I/O error, Java's `Caught exception` and `makeHandle encountered exception`), and TLS and
`csv+https` above. `j_session` is the session handle itself, and `j_managed_channel` is `None`: the channel is the
session's.

### Tests

`cargo test -p oxhaven-server --lib uri::` (13 tests, 12 without the `python` feature) and
`--features python --lib remote_tests` (2):

- `uri/tests.rs`: the choice of resolver for 32 URIs (schemes exact, shapes, relative, 7.23), syntax errors, names
  checked by the resolver chosen, the 7.23 authority, tickets and the proxied and custom refusals, the CSV rebuild,
  the client configuration of a target; against a second server over a socket: local variables and fields, remote
  scope variables and both kinds of application field with one session per target and the copy ticking (the remote
  change wakes a graph that has no timer), the remote server's error, refusals before any connection, TLS, a failed
  connection not cached, the refusal inside a cycle, a subscription by a thread that holds the shared lock while a
  cycle waits; CSV and Parquet reads (`python` feature).
- `remote_tests.rs`: both modules in a console against a second server: resolve a remote scope table and an
  application field, `barrage_session` with headers, subscribe, snapshot, a `str` ticket, `with`, local values and
  `None`, 7.23; the remote change reaches both subscriptions and not the snapshot; closing fails the session's
  table and not the resolver's; the error texts of bad URIs, no resolver, proxying, TLS (`dh://` and `use_tls`),
  `tls_root_certs`, bad hosts, a missing remote table, a closed session, a non-string URI.
- `oxhaven-uri/tests/components.rs`: `Uri::from_components`, with the strings Java gave.

Shown to fail with the handling broken: the wait not giving the lock up (the shared-lock test times out after 20 s),
no wake (both subscriptions in the console never see the change), sessions not cached (the one-session assertion),
the session made before the proxied refusal (`remote_failures_come_before_or_without_a_session`), `%` kept before
two hex digits (the components test, after Java's answer). Not shown to fail: the refusal under a Python-held shared
lock (no test: a command's nested hold does not count, and a thread of a script was not set up), and the in-cycle
refusal by removing it (the test would hang rather than fail).

### Compared with Deephaven 42.9

`tasks/13.2b-uri-python/check.py` starts three servers on free ports: R, a Deephaven server with anonymous
authentication, two applications (`remote_app`, and `127.0.0.1` for `/field/<name>`) and a keyed input table; J, a
Deephaven console; O, an Oxhaven console (`oxhaven-server` built with `--features python`). J and O run the same
script, which resolves R's tables, a CSV and a Parquet file, opens Barrage sessions, and records the outcome of 38
calls (value or `DHError` message and cause) in a table. The check compares 14 tables column by column (names,
Deephaven types, values), the outcomes, then changes R's input table and waits until both consoles' copies equal it,
closes the script's session in both and sees its table fail and the resolver's not, and asks J's JVM for the
seven-argument `java.net.URI` of the cases of `components.rs`.

```bash
PYO3_PYTHON=/usr/bin/python3.11 cargo build -p oxhaven-server --features python --bin oxhaven-server
<python of oracle/requirements.txt> -I tasks/13.2b-uri-python/check.py --oxhaven <target dir>/debug/oxhaven-server
```

Result on 20 November: `0 failed, 13 known differences` and 59 `PASS` lines: the 14 tables, 25 outcomes the same in
every field, the 13 outcomes whose cause text differs as listed above (same outcome and message), both ticking
copies on both servers, the close, and the 13 URI constructions. The first run found two things now fixed: Java
quotes every `%` in `from_components`, and `subscribe("s/t")` with a `str` works in Java.
