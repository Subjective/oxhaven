## Notes

### The corpus

`oracle/README.md`, "The remote-table corpus", has the design and how to record. In short: the remote is a second
Oxhaven server seeded from `oracle/corpus/remote/seed/`; the Java reference's console read from it when the
recordings were made, and the Oxhaven server under test reads from it in the replay. A scenario is a script scenario
with `# remote:` lines (run on the remote first) and `# remote-sync:` lines (wait until a local copy holds the
remote's rows). Five scenarios:

| Scenario | Covers |
| --- | --- |
| `remote_scope_static` | Static scope tables of every type the wire carries (23 columns: the primitives, `String`, `Instant`, `LocalDate`, `LocalTime`, `Duration`, `Period`, `ZonedDateTime`, `byte[]`, the other primitive arrays and `String[]`) and of vectors (`group_by` of nine types, `Instant` included), through `resolve`, `subscribe` and `snapshot`; an empty table; session close |
| `remote_ticking` | A keyed input table, a sort of it, an append-only table and a table of every type made from it, through `resolve` and through a session (by name and by ticket), across adds, modifies, deletes and the shifts of the sort; `where`, `update`, `agg_by`, `sort` and `natural_join` with a local table on the copy; close: the session's tables fail, those of `resolve` keep ticking |
| `remote_app_fields` | `/app/<id>/field/<name>` and `/field/<name>`; a missing field and application; closing twice |
| `remote_blink` | A blink table on the remote: snapshot, subscription, and `blink_to_append_only` on the remote, followed |
| `remote_errors` | 30 refusals of `resolve` and `barrage_session` (those 13.2b lists among them), one a step, with Java's exception and message |

Not in it: a snapshot or subscription with a viewport or columns (`BarrageSession.snapshot`/`subscribe` take a ticket
only, so no console script reaches them; 13.1's unit tests cover them), `BigDecimal` and `BigInteger` (an Oxhaven
remote cannot make them: the formula language has no constructor for them), TLS (7.24), a remote that stops.

### The Deephaven remote against the Oxhaven remote

The same scripts were recorded once more, Java console against a Deephaven 42.9 remote
(`ORACLE_REMOTE_KIND=deephaven oracle/bin/remote-record.sh`), and compared exactly with the committed recordings
(`oracle/bin/harness remote-compare --expected oracle/.run/remote-deephaven-corpus`):

```
same  remote_app_fields
DIFF  remote_blink
same  remote_errors
same  remote_scope_static
same  remote_ticking
remote-compare ...: 5 scenarios, 4 the same, 1 differ, 0 not compared
```

Four of five are equal to the last bit: the remote does not decide what the console makes of the tables. The one
difference is a known gap of Oxhaven as a remote, not of the client under test: an Oxhaven server refuses a
subscription to a blink table (`UNIMPLEMENTED`, "not ported yet: ... BarrageMessageProducer (blink tables)",
`crates/oxhaven-server/src/barrage/producer.rs`), where Deephaven serves it. So `remote_blink` records the refusal,
and the `kept` table (fed by the subscription) fails `NOT_FOUND` against an Oxhaven remote. When the producer serves
blink tables, record the corpus again; `remote_blink` will then match the Deephaven remote.

### Findings

- **Fixed: a record batch without body bytes was unreadable to Java's client.** Oxhaven sent a Barrage record batch
  whose buffers are all empty (an empty table, a delete-only update, a blink snapshot) with an empty `data_body`,
  which proto3 leaves off the wire; Java's `BarrageMessageReaderImpl#parseFrom` then throws "Missing body tag" and
  the subscription fails with `INVALID_ARGUMENT`. Every `remote_ticking` subscription failed from its first delete.
  `BatchWriter::finish` now sends eight zero bytes as the body when there would be none (Java's reader skips unread
  body bytes); test `a_batch_without_bytes_still_carries_a_body` in `crates/oxhaven-server/src/flight/tests.rs`.
- **Fixed: a snapshot of a remote table said it was flat.** The first replay showed Java's snapshot of a keyed
  input table without `IsFlat`; Oxhaven's was a plain uploaded table, which is flat. A snapshot is now flat only when
  the remote's schema says so, as the subscription's table is (`snapshot_table` in
  `crates/oxhaven-server/src/barrage_client/session.rs`; assertions added to
  `input_tables_are_followed_through_adds_changes_and_deletes` and
  `a_blink_table_is_snapshotted_and_its_subscription_answers_as_the_server_does`, each seen to fail without it).
- **Open, in the baseline: a snapshot of a remote blink table does not carry `BlinkTable`.** Java's does. This is
  owner's item 7.25, open, whose recommendation is to keep it so; `remote_blink` is `differs` with
  `table_metadata:BlinkTable`. A first version of the fix above carried the attributes too and made `remote_blink`
  clean; it was taken back for 7.25.
- **Open, in the baseline: a copy of a remote table does not keep the remote's schema.** Java's `BarrageTable#make`
  sets the attribute `BarrageSchema` to the schema the remote sent; a server then describes the copy with that
  schema's field metadata (here `inputtable.isKey` and `inputtable.isValue` of a remote input table), and `where`
  and `sort` pass the attribute on (`BaseTable#attributeToCopySet`). Oxhaven describes a copy from its definition,
  so those two entries are missing on the copies, their snapshots, and the `where` and `sort` of them. The values
  are equal. `remote-baseline.json` lists `remote_ticking` as `differs` with these two kinds. Not small: the
  uploaded-schema memory of `crates/oxhaven-server/src/flight/wire.rs` would need a mode that keeps the field
  metadata and not the Arrow types (a copy stores the engine's types), and the engine has no attribute that
  `where` and `sort` pass on for it; `wire.rs` already says that derived tables lose it for uploads too.
- **Open: an Oxhaven server does not serve a blink table to a subscriber** (above). Not small: it needs the blink
  path of `BarrageMessageProducer`.
- **Owner's item 7.29 (new): the eight zero bytes.** Java writes the body field of an empty record batch with length
  zero; prost, which encodes `FlightData` (from the `arrow-flight` crate), leaves an empty field out, so eight zero
  bytes are the smallest body that keeps the field. A client sees `bodyLength` 8 and an aligned body no buffer
  reads. The DoGet fixture comparison of `flight/tests.rs` (`assert_do_get_matches`) now expects these eight bytes
  where Java's body is empty and its buffers are all of length zero; nothing else of the comparison changed.
  Writing the field with length zero would need the Flight service's own codec.

### The soak's remote chain

`docs/SOAK.md` ("A remote chain"). A second server, the same binary, subscribes in its console to the soak server's
`trades` through `barrage_session` with the soak server's key; four of the soak's chains are built on that copy. Each
round the copy must come to equal a snapshot of `trades`, and after a barrier on the second server each chain on the
copy must equal the same operations on the snapshot, made on the soak server. The second server's resident memory,
file descriptors and threads are held to the same limits; its exit and log are checked. `--inject mismatch` makes
the remote copy and three of the four remote chains fail (the last row is not in the `head`), and `selftest` has a
case for each new memory invariant.

Runs, on this machine (4 cpus, shared):

- Short, debug build: `soak passed: profile short, 123s (40s warm-up)`, 44 rounds, each of the five remote checks
  44 times; second server rss 99.3 -> 100.7 MB after the warm-up, fds 17 -> 17, threads 12 -> 12; violations 0.
- Long, release build: `soak passed: profile long, 2700s (900s warm-up)`, 1,333 rounds, 38,657 checks, each of the
  five remote checks 1,333 times. First server: rss slope -0.97 MB/h (allowed 24), processor time per round
  -4.0%. Second server: rss 62.1 -> 63.3 MB after the warm-up, slope 1.98 MB/h, fds 17 -> 17, threads 12 -> 12,
  SIGINT exit 0 in 0.008 s, no log errors. Violations 0.
- `--inject mismatch`, 25 s: `remote copy of trades` and `remote pipeline` `where`, `agg_by_sym` and `update_by`
  fail, as the soak server's own chains do.
