## Scope

Owner's answer to 7.24 (21 November): the Barrage client connects over TLS with the system's OpenSSL 3, the library
already admitted for Kafka. Not rustls, and no other new licence: if something you need brings one (check
`cargo deny` or the licence script the rules job runs), stop and report.

- `dh://` targets and `barrage_session(..., use_tls=True, tls_root_certs=...)` connect over TLS, with the system's
  root certificates, or only the given PEM roots when `tls_root_certs` is set (as Java's `TrustCustom` does: read
  the Java to see whether custom roots replace or add to the system roots, and match it).
- Hostname verification and ALPN `h2` as Java's Netty channel does. Error texts for a failed handshake, an
  untrusted certificate and a wrong host name follow Java's shape where the corpus or the source shows it.
- Keep it behind the `python` feature as Kafka is, if that is how the build is split; CI already installs what
  Kafka's OpenSSL needs.
- Remove `ClientError::TlsNotAvailable` and the "not ported yet" rows for TLS; update `tasks/13.1-barrage-client.md`
  "Not ported" and `docs/CONSOLE.md`.
- Added 21 November (owner's answer to 7.23, "fail with a clear error"): refuse a URI whose host Java cannot read
  (`check_unread_host` in `uri/mod.rs`, the switch `UNREAD_HOST_IS_LOCAL` removed), record it as `PARITY.md` A26,

## Notes

What was built:

- `barrage_client/tls.rs`: the connector. `SslConnector` with OpenSSL's default verify paths (the system's roots;
  `SSL_CERT_FILE`/`SSL_CERT_DIR` move them), or a store of only the `tls_root_certs` PEM roots (Java's `TrustCustom`
  is the only trust material: `KickstartUtils#create`; Python's `_build_client_config`). The host is checked as
  Java's `HTTPS` endpoint identification does (`X509_check_host`, `X509_check_ip` for an address), SNI unless an
  address, ALPN `h2` required ("Failed ALPN negotiation: Unable to find compatible protocol", gRPC's
  `ProtocolNegotiators.ClientTlsHandler`). In the `tls` feature of the crate, which `python` turns on; without it a
  TLS connection is a `Config` error that names the feature. `ClientError::TlsNotAvailable` is gone. Every error of
  a failed connection now carries tonic's causes (before, only "transport error").
- Java's server adds the `outbound.ssl.*`/`ssl.*` trust material to its own `dh://` connections
  (`SslConfigModule`); Oxhaven has no property system, so not ported (said in `docs/CONSOLE.md`).
- Tests: `barrage_client/tls_tests.rs` (a TLS relay in front of the test server, certificates made in memory at
  every run: snapshot, subscription, a ticking table with the consistency checker over TLS, by address and by
  name; an untrusted server with no roots and with another authority's; two roots; a wrong host by address and
  by name; no ALPN; a plaintext server; unreadable roots) and `tests/tls_system_roots.rs` (its own process: the
  system's roots through `SSL_CERT_FILE`, replaced by given roots). Each was shown to fail with the handling
  broken: roots added to the system's instead of replacing them (`tls_system_roots`), hostname check off (wrong
  host), ALPN check off (no ALPN), the default paths dropped (`tls_system_roots`).
- Oracle: a relay (`oracle/bin/tls_front.py`, Python `ssl`) in front of the remote, certificates made by
  `openssl` at every start under the output directory. New scenario `remote_tls` recorded from Java's console:
  over TLS, a static table subscribed and snapshotted and a view of an input table followed through changes;
  refusals for the system's roots (`dh://` and a session without roots), another authority's roots, an address
  the certificate does not name, the plaintext port. Replays clean.
- `remote_errors` is not re-recorded and is byte-identical: its two TLS steps connect to the remote's plaintext
  port, and Java's recording already fails them (`NotSslRecordException`); Oxhaven now fails them in the handshake
  (`wrong version number`) where it refused before, with the same `DHError` operation, so their compared outcome
  does not change.
- 7.23: the two cases of `remote_app_fields` moved to `remote_unread_host` (re-recorded: `remote_app_fields`'s
  `outcomes` table lost the two rows, its other files are byte-identical). Baseline line `differs` with only
  `script_failure_unexpected:deephaven.dherror.DHError` on `(script)`, citing A26.
- Against real Deephaven 42.9 served with TLS (`ssl.identity.type=privatekey`, the run's certificate): an Oxhaven
  console's `barrage_session(..., use_tls=True, tls_root_certs=...)` snapshotted and subscribed an application
  field; without roots, with another authority's, by address, and `dh://` were refused in the handshake. A manual
  check, not part of the gate.
