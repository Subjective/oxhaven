## Notes

### 2.4: date search

`search.rs` now serves `2023-11-14 UTC` and the other `Precision::Day` texts in an `Instant` column, and in a vector
of `Instant`s. The range runs from the start of the parsed date in the text's zone, as an instant in the server's
zone, to that local time one day later. That follows Java's `ZonedDateTime#plus` and `#ofLocal`: in a gap the
later offset is used, and in an overlap the offset of the start if it is valid there, else the earlier one. The
search for a time of day is still refused.

The server's zone is the one Oxhaven's console already uses (`deephaven/_java_time.py: system_zone`), ported to
Rust as `search::server_zone`: `TZ` without a leading `:`, else the zone `/etc/localtime` links to, else UTC.
Java's `DateTimeUtils#timeZone()` is `ZoneId.systemDefault()`, which reads `-Duser.timezone`, `TZ`, the link, or
the contents of `/etc/localtime` when it is not a link. Oxhaven has no `-Duser.timezone` and does not compare
file contents, so what it serves can differ from Java only through how the zone is set. That needs no PARITY
entry.

Recorded: `oracle/scenarios/static/search_dates.json`, recorded on a UTC Java server. It covers UTC, ET, JP, both
DST changes in ET, a gap in MT, an overlap in CT, lower-case `t`, a region name, a date without a zone, and vectors.
Java's answers in `America/New_York` (from a second Java server started with `TZ=America/New_York`) are in the
unit tests, along with the overflow of a day that ends after 2262-04-11 (Java: `INVALID_ARGUMENT`,
`DateTimeOverflowException`).

### 3.3: typed vectors (PARITY.md A27)

Observed on 42.9 (`oracle/corpus/agg_typed_vectors`): the following results of a column of vectors of `Boolean`
or `Instant` are `ObjectVector`s of `Object`:

- `min`, `max`, `median`, `pct`, `unique` and `formula` (`each`);
- `cum_min`, `cum_max`, `rolling_min_*` and `rolling_max_*`;
- `distinct` and `group` of such vectors.

Barrage sends these as lists of strings with component type `java.lang.String`. After `ungroup` they, and the same
results of vectors of strings, are `java.lang.Object` text. `first`, `last` and `sorted_last` keep the element type.

Oxhaven serves the element type. The oracle accepts this through `rules.typed_vector_columns` and `rules.a27_field`.
Each element must equal Java's text exactly, and every other metadata key must match. The tests are in
`oracle/tests/test_rules.py`.

Vectors of other objects (`LocalDate`, `ZonedDateTime`, `BigDecimal`, ...) are now refused by these operations,
with an `unported!` that names the `Object` element type. Before this change, `min`, `max`, `median` and `pct` of
them were served typed, which silently differed from Java.
