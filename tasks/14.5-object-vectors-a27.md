## Scope

Owner item 3.3 ("vector results with no element type: send the typed result instead") covers every vector Java
gives with element type `Object` and sends as text, not only Boolean and Instant. 14.3 found that `LocalDate`,
`LocalTime`, `ZonedDateTime`, `BigDecimal`, `BigInteger` and similar vectors are among them and refused them. Serve
them typed, and extend A27 with an exact comparison rule per type: each element must equal Java's text for it
(`toString` of that Java class). Where the typed value cannot be compared with Java's text exactly (a
`ZonedDateTime` whose zone Java's text drops, a `BigDecimal` scale), say so in A27 and keep the comparison as
strict as the text allows; if a type cannot be compared at all, keep refusing it and report it.

## Gate

As task 14.3's gate, plus `OXHAVEN_TEST_SEEDS=full cargo test -p oxhaven-engine`.

## Notes

Observed on 42.9 (`oracle/corpus/agg_object_vectors`, recorded on a UTC Java server): `min`, `max`, `median`,
`pct`, `unique`, `formula` (`each`), `cum_min`, `cum_max`, `rolling_min_tick`, `rolling_max_tick`, and the vectors
inside `distinct` and `group`, of vectors of `LocalDate`, `LocalTime`, `LocalDateTime`, `Duration`, `DayOfWeek`
and `ZonedDateTime` (and `formula` of `ZoneId`) are `ObjectVector`s with component type `java.lang.String`, sent
as `toString` text; after `ungroup`, `java.lang.Object` text. `first`, `last` and `sorted_last` keep the class
(a `ZonedDateTime` vector as its instants), seen in a probe run and not recorded: the server's test
`list_fields_are_described_as_java_recorded_them` reads every vector field of the corpus and has no column type for
`ObjectVector` of `java.time.LocalDate` and the like (`schema::column_type_for_java_names`, not owned here).

Oxhaven now serves all of these typed. On the wire a vector of `LocalDateTime`, `DayOfWeek` or `ZoneId` is text with
component type `java.lang.String` in both servers, the same; it differs only after `ungroup` (a column of the class).
The A27 rule in `oracle/harness/rules.py` writes each typed element as Java's `toString` writes it and compares
the text exactly; a `ZonedDateTime` is compared by the instant Java's text names, since the typed column carries
no zone. A `LocalDate` that is not the start of a day is no date and never matches.

Still refused, as reported:

- ordering operations on vectors of `ZoneId` and `Period`: Java fails (`min` and `cum_min` of vectors of `ZoneId`
  fail on 42.9 with `INVALID_ARGUMENT`; `unique` of one vector per group does not, since nothing is compared:
  identity-dependent, owner item 2.2);
- `formula` of vectors of `Period`: a client is sent a `Period` as its months alone, so Java's days cannot be
  compared;
- vectors of `BigDecimal` and `BigInteger`: no formula makes them, so no static scenario can record Java's text
  (only a Parquet or Kafka source can), and their order is not ported (`Scalar::Big`). A typed `BigDecimal` is sent
  without trailing zeros, so the comparison could be by value only.
