# 15.6 Serve over HTTPS

- **Status:** in review
- **Branch:** `task/15.6-https-serving`
- **Needs:** nothing open
- **Owns:** the server's listener and its options (`crates/oxhaven-server/src/main.rs`, `config/`, `transport/`),
  `docs/CONSOLE.md` or a new `docs/TLS.md`, tests
- **Read:** `tasks/13.4-barrage-tls.md` (the client's TLS through the system's OpenSSL), Deephaven 42.9's server TLS
  (`ssl.identity.type=privatekey`, `ssl.identity.certPath`, `ssl.identity.privateKeyPath`, `ssl.trust.*`,
  `http.port` defaulting to 443 with TLS; `io.deephaven.ssl.config.*`, the Jetty server config)

## Scope

Owner's go-ahead (25 November). The server serves gRPC, Flight, Barrage, the web IDE and JS plugins over TLS when
given a certificate and private key, with the same options' meaning as Deephaven's (`--tls-cert`, `--tls-key`, and
the Deephaven property names where the server reads properties), HTTP/2 with ALPN `h2`, and HTTP/1.1 for the IDE's
files. Use the system's OpenSSL already admitted (owner item 7.24); no rustls, no new licence. Plain HTTP stays the
default. Optional: client certificate trust (`ssl.trust.*`) if small, else list it as not ported.

## Verification

Rust tests with certificates made at test time (never check in a key that could pass for a real one);
`pydeephaven` with `use_encryption=True` and the Rust Barrage client with `dh://` against an Oxhaven server over TLS;
the web IDE loads over `https://` (the IDE test, or a browser check with Playwright). Also a Deephaven 42.9 console
reading an Oxhaven table over `dh://` with the test root, as task 13.4 did the other way.

## Notes

What was built:

- `transport/tls.rs`, `transport::serve_tls`: the port over TLS through the system's OpenSSL (the `tls` feature, which
  `python` turns on; without it `--tls-cert` is refused by name). `main.rs`: `--tls-cert`, `--tls-key`, `--tls-trust`,
  `--tls-client-auth NONE|WANTED|NEEDED` (`ssl.identity.certChainPath`, `ssl.identity.privateKeyPath`, `ssl.trust.path`,
  `ssl.clientAuthentication`), the default port 443 with TLS. The property is `ssl.identity.certChainPath`, not
  `certPath` as the Read line says. Client certificate trust is in (small).
- Every TLS behaviour was observed on Deephaven 42.9 with `ssl.identity.*` set (`openssl s_client`, raw requests) and
  matched: TLS 1.3/1.2 with `CiphersIntermediate` (no DHE, no CBC); ALPN in the server's order, `h2` first, no ALPN
  is HTTP/1.1, only unknown protocols is a completed handshake then a closed connection; Jetty's SNI host check (each
  request's `Host`/authority must be a name of the certificate, else `400` "Invalid SNI", gRPC included; DNS names
  and common names, `*.x` matching `x` and one label, address literals only in the forms Java reads); no websockets
  over TLS (`JettyConfig#websocketsOrDefault`), the upgrade is a `404`; `NEEDED`/`WANTED` client certificates.
  `docs/TLS.md` has the list and the remaining differences (the TLS alert for an untrusted client certificate,
  signature algorithm lists, the 1.0 status line of a 400 to an HTTP/1.0 request).
- The web IDE over `https://` needs `BrowserFlightService/OpenDoExchange` and `NextDoExchange` (the JS API has no
  websocket there), which answered `UNIMPLEMENTED` (tasks 2.6, 7.8). Added in `flight/browser.rs`, on the browser
  streams of `console/browser.rs`, with `Barrage::exchange` taking any stream of requests. Outside the paths this
  task owns, but without it the IDE does not load over TLS. `OpenHandshake`/`NextHandshake` stay not ported.
- Tests: `transport/tls_tests.rs` (certificates made in memory each run, written to a run directory): the Barrage
  client snapshots by name and address; ALPN cases and the IDE's files over both protocols; gRPC-web over h2 and the
  refused websocket; the host check over HTTP/1.1, HTTP/1.0 and HTTP/2; protocol and cipher refusals with an RSA key
  (DHE is refused although RSA could sign it); client certificates in the three modes; refused certificates and keys.
  `flight::tests::a_browser_exchange_is_sent_what_a_native_exchange_is` compares a browser exchange with a native one
  message for message and checks that giving up the open call ends the stream. Each was shown to fail with its
  handling broken (host check off, websockets on over TLS, unknown ALPN served, `NEEDED` as `WANTED`, DHE in the
  cipher list, the browser stream not ended when its open call is dropped).
- By hand (task 15.6 run, certificates made with `openssl`): `pydeephaven` `Session(use_tls=True, tls_root_certs=...)`
  made and read a table on Oxhaven and on Java alike, and with a client certificate against `NEEDED`; refused without
  roots on both. `node oracle/ide/ide-test.js --url https://localhost:<port> --psk <key>`: panels, iframe, jsapi
  passed over grpc-web on h2 (they failed on `OpenDoExchange` before it was added). A Deephaven 42.9 console started
  with `-Doutbound.ssl.trust.type=certs -Doutbound.ssl.trust.path=<root>` read `ide_static` and the ticking
  `ide_ticking` of an Oxhaven TLS server with `resolve("dh://localhost:<port>/app/ide_app/field/...")`, by name and
  by address, and with `barrage_session(..., use_tls=True, tls_root_certs=...)`.
