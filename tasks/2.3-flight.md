## Scope

Arrow Flight `GetSchema`, `GetFlightInfo`, `DoGet` (snapshot of a table) and `DoPut` (upload a table). Schemas carry the same Deephaven metadata keys and values as Java. Capture schemas from the oracle for every `ColumnType` and assert equality; if `ColumnType::arrow_type` disagrees with Java, record it in Notes for a contract change.

## Notes

Done on branch `task/2.3-flight` together with 2.5.

**`ColumnType::arrow_type` agrees with Java for all ten column types.** `Instant` is
`Timestamp(ns, "UTC")` on the wire, not `"+00:00"` (`fixtures/engine_nulls.schema`; the test
`arrow_type_of_every_column_type_is_the_one_java_sends`). No contract change is needed.

Fixtures: `crates/oxhaven-server/src/flight/fixtures/`, written by `capture.py` from the
reference server at the pinned tag. The tests compare schemas as schemas (every field, type,
nullability and metadata entry) and `DoGet` record batches by field nodes, buffer layout and
body bytes.

What Java does, as captured:

- `DoGet` writes with Arrow nulls, not Deephaven nulls: a validity buffer only when the
  column has a null in the batch, and the null sentinel in the value buffer under each null.
  Bitmaps are whole 64-bit words.
- The first record batch has at most 4096 rows. A static table without rows gets the schema
  message only; a refreshing one gets one batch of no rows.
- An uploaded table is described with the field types and nullability the client sent (a
  timestamp without a zone stays one), plus `deephaven:unsent.attribute.BarrageSchema`.
- A cell uploaded with the sentinel value and no validity bit reads back null.
- `GetSchema`, `GetFlightInfo` and `DoGet` of an export that is not defined yet wait for it;
  they do not fail.
- The zero-row-batch row set bug was not visible in any capture (`put_zero_*`,
  `put_rows_then_zero`); the tables came back right.

Different from Java, on purpose:

- Record batch boundaries after the first batch (Java first cuts a static snapshot into
  pieces of 4096 rows). PARITY.md A6.
- `DoGet` sends no `app_metadata`; Java attaches a `BarrageUpdateMetadata` to the first batch.
  It belongs to task 2.4; `record_batch_messages` takes it as an argument.
- The uploaded schema is kept beside the table, so a table derived from an upload is
  described from its definition alone. In Java filter, sort and a few others pass it on.
- `DoPut` to `scope/<name>` is `FAILED_PRECONDITION`: there is no query scope.
- Schema-level `deephaven:attribute.*` metadata of an uploaded schema is ignored.

Client-reachable paths that answer `UNIMPLEMENTED` ("not ported yet: <java method>"):

- `BarrageUtil#getDefaultType`: Arrow types other than the ten column types' own
- `BarrageUtil#convertArrowSchema`: `deephaven:type` names other than the ten column types
- `DefaultChunkReaderFactory#newReader`: a column type read from another Arrow type
- `NameValidator#legalizeColumnName`: column names Java would rename
- `ArrowToTableConverter#addDictionaryBatch`: dictionary batches
- `ArrowFlightUtil.DoPutObserver#processMessage`: `BarrageSerializationOptions` on an upload
- `FlightServiceGrpcImpl#doExchangeCustom`, `#doAction`, `#listActions`

Contract gaps: `TicketRouter`/`TicketResolver` in `session` resolve tickets only. Java's also
resolve and publish by `FlightDescriptor`, answer `flightInfoFor` and list flights; here the
`export/<id>` descriptor is handled inside `flight/service.rs` (`export_id_of`), which the
scope, application and shared resolvers will need to share.

Gate: `cargo test -p oxhaven-server flight` passes; `client-smoke flight` passes 5 of 5
against this server and against Java.
