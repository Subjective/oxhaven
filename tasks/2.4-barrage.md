## Scope

`DoExchange` for Barrage: snapshot requests, subscription requests with optional viewport and column subset, the initial snapshot, and per-cycle delta messages with added, removed, shifted and modified row data in Barrage's encoding. Viewport changes on a live subscription. The gate is that the unmodified Java-derived client (pydeephaven-ticking or the Java client) reconstructs the same table state after every cycle as it does from the Java server.

## Notes

Built in `crates/oxhaven-server/src/barrage/`: `codec` (row sets, shift data, column sets),
`writer` (a message as one subscriber or snapshot request receives it), `producer` (the port of
`BarrageMessageProducer`), `snapshot` (`DoGet` and snapshot requests) and `exchange` (the
`DoExchange` call). `fixtures/capture.py` records what Java sends; `tests.rs` replays the same
calls and compares, and runs a model of a client against random updates and viewport changes.

Checked against real clients: `node oracle/ide/ide-test.js` passes on the routes `panels`,
`iframe` and `jsapi`; `pydeephaven-ticking` prints the same updates as against Java;
`oracle/bin/harness client-smoke barrage` passes.

Differences from Java, none visible in the state a client ends with:

- Blink tables are refused with `UNIMPLEMENTED`.
- A snapshot is read under the update graph's shared lock; Java first tries without it.
- The parts of a large snapshot are Java's minimum number of cells, then its maximum; Java
  sizes them by how long the last part took.
- A subscription's call is completed when the client closes its side; Java leaves it open.
- A request that is not the flatbuffer it claims to be, or whose viewport is not a row set, is
  `INVALID_ARGUMENT`; Java reads such bytes unchecked.
- A snapshot request does not read positions past the end of a static table; Java reads them
  part by part.
- `preview_list_length_limit` has nothing to apply to, and dictionary-encoded columns and
  response compression are not ported.
