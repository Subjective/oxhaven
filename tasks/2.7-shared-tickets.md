## Scope

Shared tickets (`h` followed by an identifier of at least one byte): a session publishes one of its exports under a shared ticket with `PublishFromTicket`, and any session resolves the ticket wherever a ticket is accepted, or the Flight path descriptor `["shared", "<identifier in hex>"]` in `GetFlightInfo` and `GetSchema`. Every refusal has Java's status code and message. Not part of it: an authorization hook (the reference server's default allows everything), and Flight descriptors for scope and application tickets.

## Notes

- The resolver is `src/session/shared.rs`, registered in `ServerState::new`. `TicketResolver`
  gained three methods with defaults, so the other resolvers are unchanged:
  `publish_from` (publishing an existing export, which a shared ticket does at once and every
  other ticket does by copying the value when it is available), and `descriptor_route` with
  `flight_for` and `publish_descriptor` for resolvers that can be named by a Flight path
  descriptor. The router now picks the resolver of a descriptor
  (`TicketRouter::flight_for`, `::publish_descriptor`); the Flight service no longer knows
  about export descriptors itself.
- Lifetime, as in Java: a shared ticket names the publisher's export and does not keep it
  alive. It ends when the publisher releases the export or the publisher's session ends;
  values other sessions took from it before stay theirs, and the identifier can then be
  published to again by anyone.
- Known differences from Java:
  - Java keeps the published exports in a map with weak values, so an entry outlives its
    export until the next garbage collection. In that window Java answers a resolve with
    `FAILED_PRECONDITION` "Export in state DEPENDENCY_FAILED" and a publish to the
    identifier with `ALREADY_EXISTS`; after a collection it answers `NOT_FOUND` and accepts
    the publish. Oxhaven always answers as Java does after a collection. Seen live by
    running the same requests with and without `jcmd <pid> GC.run`.
  - No authorization hook: Java passes each resolved value through
    `AuthorizationProvider#getTicketResolverAuthorization` (`transform`, and
    `authorizePublishRequest` before a publish), which allows everything in the reference
    server's default configuration.
  - A descriptor whose hex does not parse is `INVALID_ARGUMENT` "Details Logged w/ID '…'" in
    both; the logged text differs (Java logs a `NumberFormatException`).
- Kept on purpose, because clients can observe it: `SharedTicketResolver#flightInfoFor`
  builds the endpoint ticket with `FlightExportTicketHelper#descriptorToFlightTicket`, so
  `GetFlightInfo` of `["shared", "1234"]` answers the ticket of *export* 1234 (the hex text
  read as a decimal number), and of `["shared", "abcd"]` fails with `FAILED_PRECONDITION`
  "export id not numeric (found: /shared/abcd)".
- Fixed on the way, in `src/session/ticket.rs`: the two descriptor messages of
  `descriptor_to_export_id` named the path length and the last path element where Java names
  the whole path (`found: /export/x`).
- Not touched, seen while comparing with Java: an empty source or result ticket in
  `PublishFromTicket` is `INVALID_ARGUMENT` in both, but Java's message is "Details Logged
  w/ID '…'" and ours names the empty ticket (`TicketRouter::log_name`); and Java resolves
  Flight descriptors of scope variables (`["scope", "<name>"]`), which here are
  `FAILED_PRECONDITION` "no resolver for path route 'scope'".
- No `unported!` added.
