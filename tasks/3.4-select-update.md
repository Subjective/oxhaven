## Scope

`view`, `update_view`, `select`, `update`, `lazy_update` and `drop_columns`, including which columns are recomputed for a given modified-column set and the difference between materialized and on-demand columns. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine select && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops view,select,update,drop_columns --within view,select,update,drop_columns,input_table && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops view,select,update,drop_columns --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness does not cover `update_view` and `lazy_update` yet, so this gate does not check them; that needs an oracle task first.

## Notes

Done in the engine: all six operations, static and refreshing, in `crates/oxhaven-engine/src/ops/select/`. Not done: the gRPC handler, and the two harness parts of the gate, which need a running server. In their place `tests/corpus.rs` replays every recorded scenario as far as these operations reach: 33 results, 59 table states; it lists the six results it cannot run and why.

`lazy_update` in Java (`QueryTable#lazyUpdate`, `DhFormulaColumn#getLazyView`): the columns are computed on read like a view's, and each formula remembers its results in a map keyed by the values of its inputs, which is never trimmed and is shared by current and previous reads. A failed evaluation is not remembered. Its listener reports every column as modified, whatever changed.

Differences from Java that this task could not close:

- `ColumnSource` cannot say whether it holds its values in memory (`InMemoryColumnSource#isInMemory`), which decides whether `select` shares a parent column or copies it, and so whether a static `select` gets new row keys. The module knows its own computed columns and takes every other column to be in memory. That is wrong for a redirected column, such as a sort result's: Java copies those. Proposed: `fn is_in_memory(&self) -> bool` on `ColumnSource`.
- `update_view` and `lazy_update` of an input table keep the input table's write side in Java (`BaseTable#copyAttributes`). `TableSpec` has no place for it, so the results here are not input tables.
- Java lets a test source table through `validateSafeForRefresh`; there is no such marker here.
- `Formula::uses_row_variables` does not tell `i` and `ii` from `k`, which `validateSafeForRefresh` needs; the module walks the expression instead.

Left as `unported!`:

- `io.deephaven.engine.table.impl.ShiftedColumnsFactory#getShiftedColumnDefinitions`: a formula that reads a column at another row (`A_[i - 1]`).
- `io.deephaven.engine.table.impl.select.DhFormulaColumn#generateAppropriateGetMethod`: a lazy formula with a row variable or a column array.
- `io.deephaven.engine.table.impl.select.analyzers.SelectAndViewAnalyzer#createContext`: a row variable in a formula that also reads an earlier column of the same static `select`, when the result gets new row keys.

The formula compiler refuses row variables and column arrays so far, so those three and `validateSafeForRefresh` are reached only through the test compiler in `tests/mod.rs`.
