## Scope

Every remaining aggregation in the `Aggregation` and `AggSpec` protos (abs sum, var, std, median, percentile, weighted avg and sum, count distinct, distinct, unique, sorted first and last, group, formula, count where, partition), plus `aggregate_all`, `combo_aggregate`, `head_by` and `tail_by`. Read only the operator classes in `by/` for the aggregation you are porting. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine agg && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops agg_by --within agg_by,input_table && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops agg_by --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness does not cover `aggregate_all`, `combo_aggregate`, `head_by`, `tail_by` and aggregations other than `sum`, `count`, `min`, `max`, `first`, `last` and `avg` yet, so this gate does not check them; that needs an oracle task first.

## Notes

- Built, static and incremental: `abs_sum`, `var`, `std`, `median`, `percentile`,
  `count_distinct`, `unique` (null non-unique sentinel), `weighted_avg`, `weighted_sum`,
  `sorted_first`, `sorted_last` (one to three ascending sort columns). The module comment of
  `ops/agg/mod.rs` lists which file holds which, and what is not here.
- Server: `Aggregate` and `AggregateAll` take the new specs, with `AggSpecAdapter`'s checks of
  the unique sentinel. `AggregateAll` leaves out the weight column, and the formatting
  columns for the specs Java drops them for (`AggregateAllExclusions`,
  `AggAllByExcludeFormattingColumns`; this also changes `sum` and `avg`). `ComboAggregate`
  has a handler (`ComboAggregateGrpcImpl`), with its validation messages. The handler file is
  `crates/oxhaven-server/src/table/ops/aggregate.rs`, which task 3.6 created; this task's
  `agg.rs` is that file. The combo handler was ported from source only: its results were not
  recorded from Java.
- Not built, and why:
  - `distinct`, `formula`, `partition`, and so `head_by` and `tail_by` (which Java builds
    from `groupBy`, `updateView` and `ungroup`). `group` is built; see below.
  - `count_where`: it evaluates filters inside the aggregation; not started.
  - `approximate_percentile`, `t_digest`, `freeze`, `first_row_key`, `last_row_key`,
    `initial_groups`, a non-null non-unique sentinel (Java's `checkType` and numeric widening
    of the sentinel were not ported), more than three sort columns (`ArrayTuple`), and
    sorted first or last of a blink table. The engine has `unported!` for the last two; the
    server answers `UNIMPLEMENTED` with the Java name for the rest.
- Compared with Java: `ops/agg/fixtures/` holds two fixtures recorded from the Java server by
  `fixtures/record.py` (a copy of `ops/snapshot/fixtures/record.py` with the `agg`
  operation), because the oracle harness does not know these aggregations yet.
  `agg_static.json` has 27 results and 15 refusals; `agg_ticking.json` has 19 aggregations
  over 21 steps of a keyed input table (adds, replaces, deletes, a key change, groups that
  empty and refill, NaN, infinities, signed zeros, overflow). `tests/fixtures.rs` replays both
  and compares all 426 results with the rules of `oracle/harness/rules.py`, the floating
  point results of sums, averages, variances and weighted aggregations within A1's tolerance
  and everything else exactly, including the sign of zero.
- `tests/random.rs` checks every aggregation under random updates against the aggregation of
  a static copy, except two whose Java result depends on the history, which the ticking
  fixture records from Java instead:
  - `weighted_avg` after a modification: `ChunkedWeightedAverageOperator#modifyChunk` compares
    the new sum of weights with the old weighted sum, and keeps a stale sum of weights when
    they are equal (group `w`: 1.5 where the average is 1.0). It is checked under random adds,
    removes and shifts.
  - `weighted_sum` of an integer by an integer weight: each chunk's sum is added with
    `NullSafeAddition#plusLong`, which drops a chunk sum that wrapped onto `NULL_LONG`
    (group `n`).
- Java behavior that looks like a bug, recorded and matched:
  - The integer weighted sum widens values and weights with a plain cast
    (`ToLongCast`), so a null `byte`, `char`, `short` or `int` counts as -128, 65535,
    -32768 or -2147483648. Only a null `long` excludes its row.
  - The stale sum of weights above.
- Sign of zero (PARITY.md Q4): `abs_sum` of a single `-0.0` is `0.0`, as the sum is. A median,
  percentile or unique of zeros shows the zero Java's sorted multiset keeps, the first one
  inserted, and within one chunk `-0.0` before `0.0` (Java sorts the chunk with
  `Arrays.sort`): `unique` and `median` of `0.0, -0.0, 0.0` are `-0.0` in Java and here.
  Not reproduced: Java's percentile splits a group into two multisets, each with its own
  representative of a zero; here there is one, which can show the other zero after some
  histories. A weighted average or sum whose value goes from `-0.0` to `0.0` is reported as
  modified here, where Java stores the new value without reporting it
  (`newResult != existingResult`); PARITY.md A4 does not compare that.
- Sorted first and last rescan the group's rows when it changes, where Java keeps a sorted
  array per group (`SortedFirstOrLastChunkedOperator`); the results are the same.
- Gate: the cargo part passes. The harness commands need a server and were not run; they do
  not cover these aggregations.
- `group` and `group_by` (4.1b), static and incremental, in `ops/agg/group.rs`:
  - The result column is `Vector(element)` for every input type, also for an input that is
    itself a vector or an array. The elements are in the order of the parent's row set, nulls
    are elements, and a group kept by `preserve_empty` is an empty vector, not a null.
  - A group's result row is reported modified when a row joins or leaves it or a row in it is
    modified in the grouped column, without comparing the vectors; a shift alone is not
    reported. `group` of a blink table is refused, as in Java
    (`AggregationProcessor#unsupportedForBlinkTables`).
  - The modified column set of every aggregation now follows
    `ChunkedOperatorAggregationHelper#extractDownstreamModifiedColumnSet`: when some result
    row is modified, the columns are those of every operator whose state changed for any
    group in the cycle, also for a group that is new or gone. Before, only the operators
    that changed a row that stays were named. The ticking fixture found this.
  - The vectors are stored, where Java's column is a view of the input column through each
    group's row set (`AggregateColumnSource`). The groups that change in one cycle may hold
    at most 2^31 - 1 rows together; more fails the result table.
  - Server: `Aggregate`, `AggregateAll` and `ComboAggregate` (also by itself, which is
    `Table#groupBy`) take `group`. The harness scenarios `group_by_ungroup` and `agg_all_by`
    now differ only in `ungroup` and `distinct`.
  - Compared with Java: `fixtures/group_static.json` (16 results over every column type,
    vectors and arrays included, and 4 refusals) and `fixtures/group_ticking.json` (8 tables
    over 18 steps, with the 119 updates Java sent listeners, modified columns included),
    recorded by `fixtures/record.py`. `tests/fixtures.rs` compares them; `tests/corpus.rs`
    runs the `group` tables of the recorded corpus.
  - Not ported, each an `unported!` or refusal that was there before: a result column with
    the name of a group-by column (Java replaces the key column), a vector or array as a
    group-by column, and `first`, `last` and the other aggregations of a vector column. The
    server cannot describe a vector of vectors of strings, booleans or instants to a client
    (`BarrageUtil`), so a `group` of such a `group` works in the engine only.
  - `preserve_empty` with `group` was ported from source: the Python client cannot ask for
    it, so it was not recorded from Java.

- `distinct`, `count_where`, the non-unique sentinels of `unique`, an output named like a
  group-by column, and `first` and `last` of vector and array columns (4.1c), static and
  incremental:
  - `distinct` (`ops/agg/distinct.rs`): a `Vector(element)` of the group's values in Java's
    order, nulls first when included, NaN last. A group with keys and without values is a
    null; without keys it is an empty vector until a removal empties it, then a null
    (the `*ChunkedDistinctOperator`s make the set in the singleton `addChunk` only).
  - `unique` takes every sentinel `AggSpecNonUniqueSentinel` can carry, with Java's checks
    (`AggSpecUnique#checkType`, `UnionObjectUtils`): a sentinel of the column's type, or a
    number without a fraction within the column's range for a numeric column; the null
    value of the type shows as a null. The modified rows follow the operators' state
    machine: a group that goes from one value to several is not reported when the value
    was the sentinel.
  - `count_where` (`ops/agg/count_where.rs`) parses its filters as `where` does
    (`ops/filter`, where `RowFilters` and reading previous values were added for it). It
    refuses `i`, `ii`, `k` and `Column_` as Java does. With keys every group given rows is
    reported modified, as `CountWhereOperator#addChunk` does. A filter that fails on a row
    fails the result. `aggregate_with` takes the formula compiler; `aggregate` refuses a
    count where.
  - An output with the name of a group-by column takes that column's place; the rows are
    still grouped by the hidden key (`AggregationContext#getResultColumns`).
  - `first` and `last` of a table that is not add-only now report as Java does
    (`FirstOrLastChunkedOperator`): modified when the row shown is another row, whatever
    its value, and when the row shown is modified in any column. Before, they compared
    values. The ticking fixture found this.
  - Compared with Java: `fixtures/rest_static.json` (188 results, 220 refusals: every
    column type, every sentinel type against every column type) and
    `fixtures/rest_ticking.json` (12 tables over 26 steps with the 312 update lists Java
    sent listeners). The six fixtures together: 1098 results, 239 refusals, 431 update lists.
  - Known differences from Java:
    - A `distinct` without keys that goes from a null to an empty vector is reported
      modified here; Java changes the cell without telling listeners
      (`tests/fixtures.rs`, `DIFFERENT_UPDATES`).
    - `distinct` of an Instant column with keys, for a group without values: a null here;
      in Java every read of the table throws a `NullPointerException`
      (`InstantSsmSourceWrapper`).
    - `first` and `last` decide at the end of the cycle whether the row shown is another;
      Java decides per chunk, so a row removed and added again with the same key and value
      in one cycle is reported by Java and not here.
    - `count_where` evaluates its filters per group and chunk, Java per chunk.
    - The message of a refused sentinel does not print the number as Java does.
  - Not ported, each refused by name (`unported!` in the engine unless noted):
    - `formula` (`AggSpecFormula` and `Aggregation.Formula`): built since, see 4.1d below.
    - `partition` (no partitioned tables), `first_row_key`, `last_row_key`,
      `approximate_percentile`, `t_digest`, `freeze`, `initial_groups`: refused by the server.
    - `count_where` without filters: Java counts the contents of an unset chunk
      (`CountWhereOperator#applyFilters`). A `count_where` filter of a vector or array
      column (`WhereFilter#filter`).
    - `min`, `max`, `median`, `percentile`, `unique`, `count_distinct`, `distinct` and the
      sort columns of a sorted first or last, of a vector or array column
      (`AggregationProcessor`'s operator makers). Java orders vectors and fails on arrays.
    - A vector or array as a group-by column; more than three sort columns; sorted first
      or last of a blink table (as before).
  - Outside the owned paths: `ops/filter/mod.rs` and `ops/filter/filters.rs` (`RowFilters`,
    previous values), one test in `ops/list_columns.rs`, and the handler tests in
    `crates/oxhaven-server/src/table/tests/handlers.rs`.
  - Gate (4.1c): `oracle/bin/ci-replay.sh` after merging main: 83 scenarios, 71 clean, 12
    differ (the baseline before: 70 and 13). `agg_all_by` is promoted to clean and
    `agg_by_sets` loses three tables. `harness fuzz --ops agg_by` against Java, seeds
    0..1999: 1997 clean; seeds 337, 351 and 785 differ in the sign of a zero that `min`
    keeps (`-0.0` in Java, `0.0` here; PARITY.md A2, Q4), in code this task did not change.
    Mutation check of the new code: 20 mutants, 18 killed. The two that live: the range
    check of a sentinel for a long column at `Long.MIN_VALUE` (not tested), and the refusal
    of `Column_` in a count where filter (the filter parser refuses it first).

- `formula` in both of Java's forms (4.1d), static and incremental, in `ops/agg/formula.rs`
  and the planning in `ops/agg/mod.rs`:
  - `AggSpec::Formula` is a formula with a parameter token, applied to each input column
    (`FormulaChunkedOperator`): the token is replaced as `FormulaUtil#replaceFormulaTokens`
    does, and the formula sees that one column as a vector and nothing else, not the key
    columns either. `Aggregation::Formula` is `Out = expression` over any columns
    (`FormulaMultiColumnChunkedOperator`): every column that is not grouped by is a vector,
    a group-by column is the group's key. Both are compiled by `ArrayFormula`, whose
    signature did not change, and need `aggregate_with`.
  - A group is evaluated again when a row joins or leaves it or a row in it is modified in
    a column the formula reads as a vector, and its row is then reported modified whatever
    the value. A formula that reads no column, and one that follows a `group` aggregation
    (Java then shares that aggregation's operator), never has its column among the
    modified columns. A formula that fails on a group fails the result. A blink table is
    refused.
  - Framework: `AggOperator` gained `shown_empty` (a group shown without rows, for
    `preserve_empty`) and `names_result`, and `GroupReader` gives the key columns.
  - Java oddities matched: a formula with a token, then a `group`, then an aggregation
    that makes Java rebuild the shared group operator fails with a
    `NullPointerException` (`AggregationProcessor.Converter#ensureGroupByOperator`); the
    engine refuses the same requests with that name.
  - Server: `Aggregate` and `AggregateAll` take both forms; the `Selectable` of an
    `Aggregation.Formula` is parsed as `Selectable#parse` does. Every refusal is Java's
    `INVALID_ARGUMENT`.
  - Not ported, each an `unported!` (`UNIMPLEMENTED` from the server):
    - `i`, `ii` and `k` in a formula with a token, which Java takes and evaluates as the
      position of the group's row (`FormulaChunkedOperator#propagateInitialState`). Java
      refuses them in the other form, and so does this.
    - A formula with a token whose result is a vector of `Boolean` or `Instant`, such as
      the column itself: Java's column is an `ObjectVector` without an element type
      (`FormulaChunkedOperator#FormulaChunkedOperator`).
    - A formula that reads a key column whose place an output took
      (`K = K + 1` by `K`, which gives nulls in Java, and `K` by `K`, which fails there;
      `FormulaMultiColumnChunkedOperator#propagateInitialState`).
    - A formula over several columns of a table without columns, and the remaining cases
      of the shared group operator that do not end in Java's exception.
  - Compared with Java: `fixtures/formula_static.json` (327 operations: every column type
    through both forms, keys in formulas, refusals) and `fixtures/formula_ticking.json`
    (19 tables over 26 steps with the update lists Java sent listeners). The eight
    fixtures together: 1905 results, 272 refusals, 925 update lists. `tests/random.rs` runs
    nine kinds of formula, of both forms, among the other aggregations. Through gRPC against both
    servers: 75 `agg_by` and `agg_all_by` requests; 68 give the same table, types and
    status. The seven that differ: `i`, `ii`, `k` (three) and the two key-column cases
    above answer `UNIMPLEMENTED`, and `new String("a")` in either form is refused by
    `oxhaven-expr` with `INVALID_ARGUMENT` where Java makes the column.
  - `oxhaven-expr`: the functions of vectors and arrays `absAvg`, `ste`, `tstat`,
    `countPos`, `countNeg`, `countZero`, `indexOfMax`, `indexOfMin`, `cumprod`, `cummin`,
    `cummax`, `percentile`, `diff`, and of two vectors or arrays `wsum`, `wavg`, `cov` and
    `cor`, on the kernels of `functions/vectors.rs`. `tests/data/java_vectors.txt` has 382
    more formulas for them, recorded from Java: every element type as a vector and as an
    array, and pairs of every promotion class. All agree exactly; the refused list went
    from 272 to 239 lines. Java computes the products of `wavg`, `cov` and `cor` in the
    type the two elements promote to, so two `int` vectors wrap in `int` and two `float`
    vectors round to `float`; that is matched. Still refused by name: `wvar`, `wste`,
    `wtstat`, `nth`, `forwardFill`, `rank`, `enlist`, `firstIndexOf`, `concat`, `in`,
    `replaceIfNull`, the two-argument `countDistinct` and `distinct`, a `char` percentile or stride for
    `percentile` and `diff`, every function of an object vector, and operators on lists.
  - `ops/filter`: a match filter on a vector or array column takes `null`
    (`V == null`, `V != null`, `V in null`), as
    `MatchFilter.ColumnTypeConvertorFactory#getConvertor` does; any other value is refused
    as in Java. A range filter on such a column is an `unported!` (`RangeFilter#init`;
    Java refuses it with `INVALID_ARGUMENT`). 20 `where` requests against both servers:
    17 the same, the three range filters differ in that status.
  - Mutation check of the formula operator and its planning: 15 mutants, 14 killed. The
    one that lives gives a slot that was not evaluated the first value instead of a null;
    such a slot has no row in the result, so the cell is never read.
  - Outside the owned paths: `crates/oxhaven-expr/src/functions/vectors.rs` and its
    recordings, `ops/filter/literal.rs`, `ops/filter/filters.rs` and their tests, one test
    in `ops/list_columns.rs`, and the handler test in
    `crates/oxhaven-server/src/table/tests/handlers.rs`.
  - Gate (4.1d), after merging main: `oracle/bin/ci-replay.sh`: 83 scenarios, 76 clean, 7
    differ (the baseline before: 74 and 9), the five client smokes clean. `agg_by_sets` and
    `ticking_agg_by_full` are promoted to clean. `cargo fmt`, `clippy -D warnings` and
