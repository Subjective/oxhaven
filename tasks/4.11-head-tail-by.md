## Scope

The engine operators `head_by(n, columns)` and `tail_by(n, columns)`, static and incremental, with the results, row order and updates of Java's, which builds them from a group aggregation, an `updateView` that slices and an `ungroup`. The gRPC handler for the two batch operations is a follow-up. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine head_by && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops head_by,tail_by --within head_by,tail_by,input_table
```

`$OXHAVEN_URL` is described in `tasks/README.md`. The harness part needs the gRPC handler, which is the follow-up.

## Notes

- In review: the engine side. Not done: the gRPC handler (`crates/oxhaven-server/src/table/ops/head_by.rs`).
- `oxhaven_engine::ops::head_by` has `head_by(source, rows, columns)` and `tail_by(source, rows, columns)`. The refusals are `HeadByError`, in Java's order: `RowsNotPositive` (`Require.gtZero`, also for a negative number, which the Java handler refuses before the engine), `GroupColumns` (a group-by column named twice or not a column: Java fails with an `ArrayIndexOutOfBoundsException` or a `NegativeArraySizeException` while it sizes its formula arrays, and never looks at the names), `NoOtherColumns` (every column is a key: `aggBy must have at least one aggregation`), `ArrayKey` (a group-by column of Java arrays, the first of those given: `Cannot aggregate using an array column: Arr, column type is an array of int`, with the element's class as `Class#toString` prints it), `Blink` (`Blink tables do not support AggGroup`), then `Failed` for a failed source. The Java server answers `INVALID_ARGUMENT` for `RowsNotPositive`, `GroupColumns`, `NoOtherColumns` and `Blink` (recorded); the status code for `ArrayKey` is not recorded, since the recorder cannot make a table with an array column through the handler. The texts are Java's messages.
- How it is made. Java's three steps are kept as far as they show, without the arrays. `groups.rs` keeps the source rows of every group and reports, as the change of an unseen grouped table (a row per group, at the row key of the group's slot), what Java's aggregation reports: a group added with its first row, removed with its last, and modified when a row joins or leaves it or a row of it is modified in a column that is not a key; shifts move rows within the groups and report nothing. The order of the cycle is the aggregation's (`ops/agg`): removed rows, re-keyed rows out, shifts, modified rows in place, re-keyed rows in, added rows; so the new key of a re-keyed row gets its place before the new key of an added row. `ops/ungroup` then turns that table into the result: its `ArrayColumn` seam is implemented by `groups::Kept`, the first or last `n` rows of a group, read through the group's row set from the source's column. So the result has Java's row keys (`slot << base` plus the offset, base 10 and growing when a group keeps more than 1024 rows) and Java's updates: every kept row of a reported group is modified, whether it changed or not.
- Changed outside the owned paths, all to reuse what is there: `agg::keys` and `KeyTable` are `pub(crate)`; `ungroup::{keys, operator, sources}`, `ArrayColumn`, `Ungrouped`, `ungroup_arrays` and `MINIMUM_BASE` are `pub(crate)`; `ops/mod.rs` declares the module.
- Vector and array columns. One that is not grouped by is kept whole, with its type: Java's `ungroup` takes apart the arrays of the aggregation, not the cells in them (`fixtures/java_lists.txt`, recorded by `fixtures/record_lists.py` in the Java console: a source with `IntVector`, `int[]` and `String[]` columns and four results, with the Java classes of the columns). An array to group by is `ArrayKey`.
- `unported!`, two. `io.deephaven.engine.table.impl.QueryTable#headOrTailBy` for a vector column to group by (`vector_key` in `mod.rs`, after all the refusals): Java does not refuse it, groups by the vectors, and its `ungroup()` then takes the key column apart with the others, so that the result has a row for each element of the key and the request fails with `IllegalStateException: Array sizes differ at row key 0 (position 0), V has size 2, K has size 1` when a key has not as many elements as its group keeps rows, at once or in a later cycle. And `ChunkedOperatorAggregationHelper#aggregation` for the Java class name of a column type added to the contracts later (`binary_name`, unreachable with the types there are).
- No contract gap: the arrays of the groups stay behind `ungroup`'s private seam, and list cells are read with `ColumnSource::chunk_by_keys` like any other.
- Java behavior worth knowing: `n` of 0 is refused, not an empty table. The result has the group-by columns first, in the order given. A key column shows the key of the first row the group ever had (`-0.0` stays when the group is emptied and comes back with `0.0`). A group that is emptied keeps its place for when it comes back. `tail_by` of a group reports all its kept rows as modified for a row added in front of the group.
- Differences from Java known: those of `ungroup` (4.7): the previous base is the current one as soon as the graph is idle; row keys that would wrap fail the result instead of being wrong; 64-bit arithmetic where Java's is `int`. Not ported: the result made in the middle of a cycle from previous values, memoization of the aggregation, the limit of 2^31 groups. The modified column set of an update is Java's as read from the source; the recordings do not show it. A source whose update modifies only key columns, to equal keys, gives no update: read from `GroupByChunkedOperator#resetForStep`, not recordable, since an input table reports every column as modified.
