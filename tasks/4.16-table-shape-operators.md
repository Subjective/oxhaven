## Scope

The engine operators that the core table methods of the Python package wait for, each with a
plain Rust function a handler or a local operation can call, static and incremental, with the
consistency checker attached in every engine test:

1. `QueryTable#headPct`, `#tailPct`, `#slicePct`: the rows of a share of the table, which
   follows the size of a refreshing table; refused for a blink table and for a share outside
   0 to 1, as Java refuses.
2. `QueryTable#renameColumns` and `#moveColumns` (`renameColumnsImpl`), and
   `Table#moveColumnsUp` and `#moveColumnsDown`, which are `moveColumns`: the same column
   sources and row set under another definition, with Java's checks of the pairs, its
   attributes and sort marks, and the modified columns mapped.
3. `QueryTable#restrictSortTo`, and `sort` refusing a column the restriction does not name
   (`NotSortableException`).
4. `QueryTable#where` of a `FilterOr` of filter strings, and of `Filter#ofFalse` (which Java
   refuses): the engine has `FilterSpec::Or` and no public function that takes strings.
5. `TableTools#mergeSorted` of static tables, in the `merge` handler (`key_column`) and so
   in `merge_sorted` of the Python package.
6. `AttributeMap#getAttributes`: an attribute map readable from Python (`Table.attributes()`),
   with Java's names and values for the attributes an operation leaves (`AddOnly`,
   `AppendOnly`, `BlinkTable`, `SortedColumns`, ...). Say which attributes cannot be given
   and why.
7. `where_in` and `where_not_in` with no columns: Java answers (every row when the filter
   table has rows, none otherwise, and the opposite for `where_not_in`); the `where_in`
   handler refuses the request as Java's handler does, so the Python method needs another
   way to the engine.

Then fill in the local operations of `console/python/ops.rs` so that the Python methods
answer, and promote the baseline lines.

## Notes

- The scenarios hold each waiting call in a step of its own: `table_head_tail` steps 1 to 3,
  `table_select` steps 1 to 5, `table_where` step 1, `table_creation` step 2. `attributes`
  and `where_in` with no columns have no scenario yet; add them to `table_*` and record them.
- Seen on Java 42.9: `attributes()` of a plain table is `{}`, of a sorted one
  `{'SortedColumns': 'I=Ascending', 'SortRowRedirection': <a Java object>}`, of a time table
  `{'AddOnly': True, 'AppendOnly': True}` and of its `head(1)` `{'AppendOnly': True}`.
- Where the operators are: `ops::sort::{head_pct, tail_pct, slice_pct, restrict_sort_to}`,
  `ops::select::{rename_columns, move_columns, move_columns_up, move_columns_down, ColumnPair}`,
  `ops::filter::where_one_of`, `ops::merge::merge_sorted`, and
  `table::{attribute_map, sortable_columns, AttributeValue}`.
- No contract changed. The attributes that `TableAttributes` cannot say (`SortedColumns`,
  `SortRowRedirection`, `SortReverseLookup`, `SortableColumns`, `MergedTable`) are in the
  marks the engine keeps beside a table (`table/copied.rs`), which is outside the owned
  paths and had to change: the marks, which operation copies which, and the attribute map
  are one thing. `select`, `update`, `view`, `update_view`, `lazy_update` and `drop_columns`
  now carry the sortable columns as `SelectAndViewAnalyzer` and `QueryTable#dropColumns` do.
- Also outside the owned paths: `crates/oxhaven-server/src/schema.rs` leaves
  `deephaven:isSortable` off a column that the restriction does not name
  (`BarrageUtil#columnDefinitionsToFields`), which the `restricted` table of `table_select`
  compares; and `merge_sorted` in `python/deephaven/table_factory.py` goes to the local
  operation for every list of tables, since the `merge` handler refuses an empty list and
  sorts refreshing tables, and Java's `TableTools.mergeSorted` does neither.
- Scenarios added and recorded on Java 42.9: `table_where` step 2 (`where_in` and
  `where_not_in` with no columns) and `table_select` step 6 (attributes, as asserts, since
  no table carries them to a client).
- Attributes that cannot be given, and why:
  - `AggregationRowLookup` of an aggregation's result: its value is the lookup function of
    the Java operator, and no operation here reads it.
  - The value of `SortReverseLookup` and of `InputTable`: Java objects. The names are in the
    map, with a placeholder for the value.
  - `SortableColumns` on the result of `natural_join`, `where_in` and a `merge` of restricted
    tables, which Java copies there: those operators are outside this task and do not copy
    the marks yet.
  - `SortRowRedirection` names the last column that Java reads through the sort's
    redirection. Java leaves out a column whose source has one value for every row
    (`RowKeyAgnosticChunkSource`); no source says so here, so the last column is named.
- Differences from Java left in place:
  - A sorted merge by a vector or an array column, which Java compares, is `unported!`, as
    is the type check of two such columns of one name with different types.
  - A null key that is compared in a sorted merge is refused where Java throws a
    `NullPointerException`; when the null is the key compared with, Java's text names the
    class of the key and the text here does not.
  - A restriction to a name that is not a column of the table (after a rename or a drop
    leaves `SortableColumns` empty, for example) makes Java's schema fail with a
    `NullPointerException`; here the schema is sent and the name is passed over.
  - `move_columns` with an index that is not an `int` is refused by the local operation;
    Java's Python refuses it with "no matching Java method overloads".
- `tasks/6.4-python-table-core.md` still lists these operations as waiting.
