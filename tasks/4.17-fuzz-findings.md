# 4.17 Engine defects found by the widened fuzzer

- **Status:** in review
- **Track:** E
- **Needs:** 0.15 (the widened fuzzer, pull request 81), 4.16
- **Owns:** the engine operators named below; `oracle/fuzz-known-findings.json` and the
  restrictions in `oracle/harness/fuzz_wide.py` only to remove an entry or a restriction
  whose cause this task fixes

## Read

- The module comment of `oracle/harness/fuzz_wide.py`: the six restrictions that exist only
  because of these findings (F1, F2, F4, F5, F6, U1).
- `oracle/fuzz-known-findings.json` and `oracle/harness/known.py`.
- `tasks/4.17-fuzz-findings/`: a minimal scenario file for each finding, as the fuzzer
  wrote it. Replay one with the harness's `diff` against the Java reference.

## Scope

Fix the differences from Java below, each with a regression test that fails before the fix,
then lift the fuzzer restriction or known entry that hid it and run that family for 1000
seeds. Probe the running Java reference for each before changing anything.

### A1. `aj` loses left rows

Seed `--family all` 308. `r` is a keyed input (`RId int32`) holding `[[6]]`; `q` is static
(`Q1 int32`) and empty; `o1 = snapshot_when(source q, trigger r, stamp_columns ["P2 = RId"],
history true)`; `o3 = aj(r, o1, on ["RId > Q1"], joins ["J4 = P2"])`; one step adds `[9]`
and `[6]` (a replacement) to `r`. Java: `o3` has `RId [6, 9]`. Oxhaven: `[6]`, although `r`
itself shows `[6, 9]`, and nothing is logged. It also happens when the replacement is in one
cycle and the add in a later one, and not without the replacement. Scenario:
`F11-aj-snapshot-history.json`.

### A2. Aggregations of array columns

`t(C0 int64, C2 int16)`; `o1 = agg_by distinct A2 = C2 by C0`; `o4 = agg_all_by min by C0`.
Java succeeds (`A2: list<int16>`). Oxhaven refuses: "not ported: AggregationProcessor:
makeMinOrMaxOperator for a column of type Vector(Short)". The same for median and
percentile (`visit(AggSpecPercentile)`), max, count_distinct and unique; first and last
match. Scenarios: `F1-vector-min.json`, `F1-vector-median.json`.

### A3. `agg_all_by first` of an append-only table lacks `AppendOnly`

Append-only input `t(C4 int32)`; `agg_all_by first by []`. Java: attributes
`[AppendOnly, IsFlat]`. Oxhaven: `[IsFlat]`. Java: `BaseTable.java`,
`APPEND_ONLY_TABLE_ATTRIBUTE` copied for `CopyAttributeOperation.FirstBy`. Known entry
`agg-all-by-first-append-only`. Scenario: `F3-first-appendonly.json`.

### A4. `IsFlat` missing downstream of A3

Append-only `t(C1 timestamp, C2 int8, C3 string)`; `o6 = agg_all_by first by C3`;
`o7 = agg_by first A9 = C2 by C1`. Java: `o7` has `[IsFlat]`. Oxhaven: `[]`. Scenario:
`F8-isflat.json`.

### A5. `head_by` and `tail_by` over array columns of strings, booleans or timestamps

`t(K string, C1 timestamp)`; `group_by K`; `head_by 2 by K`. Java: `C1` is `list<string>`,
and after `ungroup` the column is `java.lang.Object`. Oxhaven: `list<timestamp>` and
`java.lang.String`. Java: `QueryTable.java:1106-1151`, `headOrTailBy`, whose final
`updateView(casting)` casts to the raw vector class. This looks like a Java defect that
clients can observe. Ruled on 2026-11-17: Oxhaven keeps its types (`PARITY.md` A14); the
fuzzer restriction stays. Scenarios: `F4-headby-*.json`.

### A6. `update_by` min and max of a boolean column on an empty table

`t(K bool, T timestamp)` with no rows; `update_by rolling_min_time U8 = K` (also cum_min
and rolling_max, in ticks or time). Java succeeds with an empty result and fails only once
rows exist (`ComparableRollingMinMaxOperator.java:60`). Oxhaven refuses when the operation
is made. With rows both refuse. Scenario: `F9-bool-min-empty.json`.

### A7. A table that fails during an update cycle keeps answering

Chain 1: append-only `t(C1 timestamp)`; `rolling_min_tick rev 1 fwd -1` (an empty window);
a step adds rows. Java fails the table, the snapshot returns `INVALID_ARGUMENT` and
downstream tables show nulls. Chain 2: keyed `t(Id, K float64, T)`;
`ems_time decay PT1S, on_nan POISON`; a step adds `[2, NaN, …4s]` and `[4, 0.0, …5s]`. Java
fails with "Timestamp values in UpdateBy operators must not decrease"
(`DoubleEMOperator.java:83`). Oxhaven in both: the snapshot succeeds with stale contents and
nothing is logged. This is the general question of how a failed table is served, which is
open for the owner (see `runlog/journal.md`); fix the two operators so that they fail as
Java's do, and leave the serving of failed tables to that decision. Scenarios:
`U1-empty-window.json`, `U1-poison.json`.

## Not in scope: Java defects, recorded for the owner

- J1. `agg_all_by first/last` with keys that are not the leading columns: Java serves the
  columns in source order over key-first data (`BaseTable.java:374-383`), so values are
  garbage. `F2-first-schema.json`.
- J2. `distinct` of a timestamp column when a group holds only nulls: Java throws when the
  snapshot is written (`InstantSsmSourceWrapper.java:147`). `F7-distinct-timestamp.json`.
- J3. `rolling_group_time` on a refreshing table when a row with a null timestamp arrives:
  Java fails in the cycle (`UpdateByWindowRollingBase.java:137`).
  `F10-rolling-group-null-time.json`.
- J4. `emstd_time` with infinities: Java kept up to date answers `inf`, from scratch `nan`.
  `U2-emstd.json`.
- J5. As-of join: on 15 `--ops aj` seeds Java's kept result differs from its own
  from-scratch result.

## Notes

- A1 is not a defect of `aj`. On the reference both `o1` and `o3` are failed tables: `r` is
  not append-only, so the replacement reaches the history snapshot as a modify and fails it
  (`Assert updateToSend.modified.empty()`, `BaseTable#notifyListeners`), and the join fails
  with its right table. The reference's `[6, 9]` is the failed join still sharing the row
  set of `r`, with nulls in `J4`. Oxhaven fails both tables too and serves the last rows it
  published. That is the serving of failed tables (Q11 in `PARITY.md`), so nothing
  is changed and seed 308 of `--family all` still differs. Ruled on 2026-11-17: the contents
  of a failed table are not compared (`PARITY.md` A11); see `tasks/0.18-owner-rulings.md`
  for seed 308 under that rule.
- A2: the minimum, maximum, median, percentile, count of distinct values, unique value and
  sorted first and last now take a vector column whose elements are not themselves lists,
  compared element by element as Java's `Vector#compareTo`. The fuzzer restriction stays,
  because lifting it shows two behaviours of the reference that are not reproduced (11 of
  1000 seeds of the aggregations family, seeds 49, 276, 323, 371, 496, 499, 570, 630, 674,
  810, 820):
  - a vector that an aggregation made (`group`, `distinct`) is a view of its group. The
    reference's operators that compare keep the view, so when the group changes in a later
    cycle the value to remove is not the value held and the result fails
    (`ObjectComparisons.eq(valuesToRemove.get(offset), singletonValue)`, or an assertion
    or `NullPointerException` in the sorted multiset). Oxhaven keeps the result up to
    date. Minimal chain: keyed `t(Id int32, K int64)` with `[1, 3], [2, 0]`;
    `o1 = agg_by group A3 = Id, sum A4 = K by []`; `o5 = agg_all_by min by []`; a step
    adds `[6, 1]`.
  - the minimum, maximum, median, percentile and unique value of a vector of Booleans or
    Instants come back from the reference as `list<string>`. Oxhaven answers those
    `UNIMPLEMENTED`.
  Narrowing the restriction to these two cases is an edit of `oracle/` that this task may
  not make; the owner approved it on 2026-11-17 and task 0.18 made it. Its comment in `fuzz_wide.py` ("the engine lists aggregations of vector columns
  as not ported") is out of date. Still not ported: `distinct` of a list column, and the
  comparing aggregations of arrays and of vectors of vectors.
- A3 and A4 were one cause: `agg_all_by first` did not copy `AppendOnly`, and the flatness
  downstream follows from it. The known entry is removed.
- A6: the minimum and maximum of a Boolean column are accepted and fail with the first
  rows, as the reference's operator of objects does.
- A7: both operators already failed the result in the cycle; two tests pin that. The
  reference refuses a snapshot of the failed result and Oxhaven serves its last rows,
  which is Q11 again, so the fuzzer restrictions for U1 stay.
- A5 is untouched.
