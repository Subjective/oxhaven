## Scope

The script scenarios that still differ because the engine lacks an operator or one of its
arguments:

1. Aggregation with initial groups (`QueryTable#aggBy` with `initialGroups`, and
   `preserveEmpty` where it depends on them): scenario `agg_by`, table `seeded`.
2. `count_where` without a filter.
3. Keyed transpose (`KeyedTranspose#keyedTranspose`): scenario `join_multi`, table `transposed`.
4. `range_join` without an aggregation.
5. `multi_join` without a key column.
6. Any other operator gap named in the baseline's `why` texts.

Probe the running Java reference first, port with engine tests (static, and ticking where the
operation ticks, with the self-consistency checker and seeds), and promote the scenario entry
when the gate prints it clean. Not part of it: storage, Parquet, dtype and partitioning-column
gaps, the partition aggregation (7.6), formulas, the Python listeners.

## Notes

- Initial groups: `aggregate_seeded`. The rows are the initial keys in the order of their
  rows, then the other keys as they appear; the initial groups are read once; each operator
  is told of a seeded group (`AggOperator::seeded`), as Java gives it an empty chunk, which
  is why `distinct` of a group that never had a row is `[]` and of an emptied one null.
- Keyed transpose: `ops/transpose`, a composition of the aggregation, `partition_by` and
  `multi_join` as in Java. The Python `keyed_transpose`, a `multi_join` with an input
  without key columns and a `range_join` without aggregations are local operations
  (`console/python/ops.rs`): the engine answered the last two already, and the table
  service's check of the request refuses them, as Java's does.
- Refused, naming the Java method:
  - `ChunkedOperatorAggregationHelper#copyKeyColumns`: initial groups that a refreshing
    table has no rows for, without `preserveEmpty`. Java shows such a group with null key
    columns once it gets rows (the keys are copied for the first row set and for new states
    only). Needs a ruling.
  - `CountWhereOperator#applyFilters`: a count where without filters, as before. Java never
    sets the chunk it counts and answered `[0, 0, 0]` and `[3, 3, 0]` for the same table.
    Needs a ruling.
  - `KeyedTranspose#keyedTranspose`: a column-by column of floats, of `Instant`s, of
    vectors or of arrays (`Float#toString` and `Instant#toString` are not ported).
- Differs from Java: a keyed transpose that has failed for a new column keeps the rows it
  had; Java's failed result is the multi join's table and goes on showing its changes to a
  reader of its rows.
- Left, as not operator gaps: `csv_not_ported`, `dtypes_partitioning_definition`,
  `parquet_*` (storage, types), `listen_counts` (6.12), `input_key_types` (the keyed input
  table's floating point key, `KeyedArrayBackedInputTable#makeKeySource`) and
  `input_ring_and_generated` (`RingTableTools#of`, `FunctionGeneratedTableFactory#create`):
  the last two are table sources of their own size, not arguments of an operator.
