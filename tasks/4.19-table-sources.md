## Scope

The table sources that kept two script scenarios differing in `oracle/replay-baseline.json`:

1. A keyed input table whose key is a `float` or `double` column: scenario
   `input_key_types`.
2. Ring tables (`RingTableTools#of`): scenario `input_ring_and_generated`, table `ring`.
3. Function generated tables (`FunctionGeneratedTableFactory#create`), refreshed by source
   tables and by an interval: the same scenario, table `generated`.

For each: probe the running Java reference, on ticking inputs too; port into the engine with
tests (the self-consistency checker and seeds where the table ticks); bind it in the Python
package; record a script scenario for what the two existing ones do not reach; promote the
entries when the gate prints them clean. A generated table calls Python in an update cycle:
it follows the lock rule of the listeners (graph lock first, interpreter lock second).

Not part of it: `TableReplayer`, storage and Parquet, the table service (it has no call
that makes a ring table or a generated table; `CreateInputTable` only loses its refusal of
a floating point key).

## Notes

Every behaviour below was observed on Java 42.9 before it was written.

- Floating point keys (`table/input.rs`, `one_bit_pattern_per_key`). What makes two keys
  the same depends on the number of key columns, as in Java: with one key column, or four
  and more, the key is the boxed value or an array of boxed values and `Double#equals`
  decides (every NaN is one key, `0.0` and `-0.0` are two); with two or three, the key is a
  typed tuple and `DoubleComparisons#eq` decides (every NaN is one key, `0.0` and `-0.0`
  are one). Null is a key of its own. The row holds the value written last (`-0.0` over
  `0.0`), and a deleted key gets its row back. The table service's `CreateInputTable`
  takes such a key column too.
- Ring tables (`table/ring.rs`, `ring_table`). The last `capacity` rows by arrival; row
  keys `n - capacity .. n` after `n` rows; a removal upstream is ignored; a modify or a
  shift fails the ring ("Not expecting modifies or shifts"). No attribute of the parent,
  not flat, static over a static parent. The errors are Java's: capacity 0, a negative
  capacity (`NegativeArraySizeException`), a capacity above 2147483639, a static parent
  with `initialize=False`. As in Java the capacity is not looked at when the parent has no
  columns; then a static parent with rows is `ArrayIndexOutOfBoundsException` and a
  refreshing one `IllegalArgumentException`. The Python `ring_table` narrows `capacity` to
  32 bits as jpy does and wraps every error in `DHError` "failed to create a ring table."
- Generated tables (`table/generated.rs`, `generated_from_sources`,
  `generated_on_interval`). Every source table must be refreshing; no source tables, or a
  negative interval, makes a static table generated once; an interval of 0 makes a
  refreshing table that is never generated again. A refresh reports every row that stays
  as modified in all columns, with adds and removes at the end, and nothing when no row
  was and none is. Columns are copied by name. With an interval, a function that returns a
  refreshing table fails the table at the first refresh, as in Java, which asks the graph
  whether every source has refreshed while the sources are refreshing. With source
  tables the function runs once in a cycle in which any of them changed.
- The Python `function_generated_table` (`console/python/generated.rs`) raises what the
  reference package raises: only the two argument checks are `DHError`; a source that is
  not refreshing, an interval jpy cannot convert and what the function raises are
  `RuntimeError`, `TypeError` or `ValueError`. The interval is narrowed to 32 bits
  (`2**31` is negative, so the table is static).
- The lock rule: the function is called by the cycle thread, which holds the graph's
  exclusive lock and takes the interpreter lock for the call; making the table releases
  the interpreter lock before the engine takes the graph lock. Test
  `a_generated_table_and_a_command_make_progress_together`.
- Refused, naming the Java method (both fail the generated table at that refresh):
  - `FunctionGeneratedTableFactory#copyTable`: the function returns a table without one of
    the columns. Java keeps the column's values of the generation before in the rows that
    stay and null in new rows. Needs a ruling.
  - `FunctionGeneratedTableFactory#copyTable`: the function returns another reference type
    for a column (a `BigDecimal` where the first table had a `String`). Java stores the
    objects in the column, whose type still says `String`. Needs a ruling.
  - `KeyedArrayBackedInputTable#makeKeySource`, as before: a vector or array key column.
- Differs from Java (`docs/CONSOLE.md`, the table under "Input tables written from a
  command"): a failed generated table still serves the rows it had, where Java's cannot be
  fetched; a `ring_table` error has the Java exception's class and message after the
  prefix and not its stack; `function_generated_table` with source tables on a thread the
  command joins makes the table, where Java never returns (the thread waits for the lock
  the command holds).
- Scenarios recorded from Java: `input_ring_ticking`, `input_generated_ticking`. The
  generated table on an interval is made deterministic by letting the interval pass in
  the script before the write that makes the cycle run.
- Not reached by a scenario, covered by engine tests only: a ring over a blink table (the
  console has no blink source that a script steps; probed on Java with `time_table(...,
  blink_table=True)` and by hand), the failures of a generated table in a cycle.
- Left in the baseline, none of it a table source: `csv_not_ported`,
  `dtypes_partitioning_definition`, and the five `parquet_*` entries.
