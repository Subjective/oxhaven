## Notes

- Built: the engine side of `natural_join` and `exact_join`. `oxhaven_engine::ops::join` has `natural_join(left, right, on, add, join_type)` and `exact_join(left, right, on, add)`, each from two `Arc<dyn Table>` to `Result<Arc<dyn Table>, JoinError>`, with `JoinMatch`, `JoinAddition` and `NaturalJoinType` (the four types of the gRPC `NaturalJoinTablesRequest`). The variants of `JoinError` name the Java exception, for the handler to map to a status; the recordings give `INVALID_ARGUMENT` for every one of them.
- Not built: `multi_join`, and the gRPC handler (`crates/oxhaven-server/src/table/ops/join.rs`).
- There is no left join to port. The pinned reference has `LeftJoinTables` in `table.proto`, and `JoinTablesGrpcImpl.LeftJoinTablesGrpcImpl#doJoin` answers it with `UNIMPLEMENTED`; the engine has no such operation.
- One implementation, for every combination of static and refreshing tables, over an ordered map from key to the left rows and the right rows that have it. The result has the left table's row set, and its added columns read the right table through a `WritableRowRedirection` from left row key to right row key. Java has four implementations with generated hash tables per key type; their order of work within a cycle is kept (right table: removes, shifts, modifies, adds; then the left table; then the keys the right table touched).
- Keys are equal as Java's hashers compare them: null equals null, every NaN equals every NaN, `-0.0` equals `0.0`. A match column may be of any of the ten types of `ColumnType`; a pair of match columns must have one type.
- What Java does, and this does too, that is not obvious:
  - A duplicate right key fails a join only when a left row has the key, at the start and in every cycle.
  - With no additions given, the right columns added are those not named like the *left* column of a match, also when the right column of the match has another name.
  - Of several additions with one name the last wins, at the position of the first.
  - An exact join with a static right table and match columns does not check the left rows that arrive or change key later: such a row gets nulls.
  - Without match columns, a first-match or last-match join with a static right table of more than one row is refused (Java's `ClassCastException`), also when the left table is empty; the other two types are refused only if the left table has a row.
  - The result is add-only and append-only when the left table is (a static table counts) and the right table is static, or is add-only in an exact join.
- One known difference from Java, in the updates only: when a right row is removed and another row with the same key is added at its row key in one cycle, Java's `ModifiedSlotUpdater#accept` compares row keys and reports nothing; here the left rows of the key are reported as modified. The cells are the same.
- `unported!`: a match column stored as an Arrow type other than those of the ten column types (`TypedHasherFactory#makeNaturalJoin`).
- Tests: `ops/join/tests.rs` (every static rule, every incremental case with the exact update), `ops/join/random.rs` (random updates over 40 seeds of both tables, of the left only and of the right only, for the four join types on seven sets of match columns, each result checked every cycle against the join of static copies, including the cycle in which it must fail), `ops/join/corpus.rs` (every result of `oracle/corpus` that is a natural or exact join of inputs: 17 tables; the other 170 result tables need other operations; and the 101 tables of `ops/join/testdata`).
- `ops/join/testdata` holds eight more scenarios in the oracle's format and their Java results, recorded by `testdata/record.py` (usage in the file). They cover keys of every type, the arguments and every refusal, joins without match columns, first and last match while ticking, failures in a cycle, and the attributes. `record.py` also records, in `failed.json`, the steps after which a result table had failed in Java, by asking the server for `where("true")` of it: a snapshot of a failed table still answers (PARITY.md Q11).
- Gate: `cargo test -p oxhaven-engine join` passes. The two `oracle/bin/harness` commands were not run: there is no server for these operations yet.
- Handlers (follow-up, branch `task/4.10-join-snapshot-handlers`): `crates/oxhaven-server/src/table/ops/join.rs` serves `NaturalJoinTables`, `ExactJoinTables` and `LeftJoinTables`, one-shot and in a batch. The match and addition strings are read as `MatchPairFactory` reads them, in `validateRequest` and again in `create`, and refused with `INVALID_ARGUMENT` and Java's message; every `JoinError` is an internal error (`INVALID_ARGUMENT`), as every recorded refusal is; `LeftJoinTables` answers `UNIMPLEMENTED` once its columns have been read. Replay: `natural_join_*`, `exact_join`, `pipeline`, `error_types_and_matches` (join tables) and the left join tables of `raj_and_left_join` match. Not matched: the result of a join of an input table lacks Java's `inputtable.isKey`/`isValue` column metadata, because `natural::join` does not carry the left table's input table (`BaseTable#copyAttributes` with `CopyAttributeOperation.Join` copies `INPUT_TABLE_ATTRIBUTE`); an engine fix, `with_input_table_of(left)`.
