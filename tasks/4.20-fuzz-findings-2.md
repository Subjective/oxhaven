# 4.20 Differences found by the second parity pass

- **Status:** in review
- **Track:** E
- **Needs:** 0.16 (the second parity pass, which found them)
- **Owns:** the engine and server code named below; `oracle/fuzz-known-findings.json` and the
  restrictions in `oracle/harness/fuzz_second.py` only to remove an entry or a restriction
  whose cause this task fixes

## Read

- The module comment of `oracle/harness/fuzz_second.py` and its `RESTRICTIONS`: what the
  generator steps around because of a finding below, by the finding's number.
- `oracle/fuzz-known-findings.json`: the entries whose reason names this file.
- `tasks/4.20-fuzz-findings-2/`: a scenario file for each finding. Replay one with the
  harness's `diff` against the Java reference:
  `oracle/bin/harness diff --a <java> --b <oxhaven> --scenarios tasks/4.20-fuzz-findings-2/<file>`.
  The script operations (`ring_table`, `keyed_transpose`) need a server with a Python
  console, so Oxhaven built with `--features python`.
- `tasks/5.5-column-arrays.md`, `tasks/5.6-formula-gaps.md`, `tasks/3.2-where.md`,
  `tasks/4.18-missing-engine-pieces.md`: where the refusals below were first written down.

## Scope

Fix the defects D1 to D5, each with a regression test that fails before the fix, then remove
its known entry or restriction and run the family named for 1000 seeds. The refusals R1 to
R8 are requests Java computes and Oxhaven refuses by name; each is a piece of an earlier
task that was left out on purpose, and porting one lifts its restriction. Probe the running
Java reference for each before changing anything. Every observation below was made on Java
42.9.

### D1. `update` with a fixed-distance read of an append-only table lacks `AddOnly`

Append-only input `t(V int32)`; `update X = V_[i-1]`. Java: the result has `AddOnly` and
`AppendOnly`. Oxhaven: only `AppendOnly`. The same for `lazy_update` and for `X = V_[i]`.
With a read ahead (`X = V_[i+1]`) neither server sets either attribute, and `view`,
`update_view` and `select` with the same formulas, and `update` without a column array,
have the same attributes on both. Oxhaven: `ops/select/arrays.rs`, where the result of the
rewritten formula gets `append_only` and never `add_only`. Known entries
`update-shift-add-only` and `lazy-update-shift-add-only`. Scenario: `D1_update_shift_add_only.json`. Seen in every family
with `update`: `formulas2` 129, `ring` 37 and 111, `statistics` 26.

### D2. Merged and fetched partitions lose `AddOnly` and `AppendOnly`

Static `t(K string, V int32)`; `f = where V > 0`; `partition_merge f by K`. Java: the merged
table has `AddOnly` and `AppendOnly`, as `f` has on both servers
(`QueryTable.java:1664-1667`). Oxhaven: neither. With `head` in place of `where` it is
`AppendOnly` alone. The same for `partition_get`, and for a refreshing append-only table
that an operation made. A table partitioned straight from an input, or from `sort` or
`update`, matches. Java: `PartitionByChunkedOperator` copies the parent's attributes to
each constituent and `PartitionedTableImpl#computeSharedAttributes` gives the merged table
what the constituents share. Known entries `partition-merge-add-only`,
`partition-merge-append-only`, `partition-get-add-only`, `partition-get-append-only`.
Scenario: `D2_partition_attributes.json`. `partitions` 4, 20, 32, 45, 91, 116.

### D3. `distinct` of no rows is null where Java has an empty array

`t(C0 bool, C1 int32, C2 string)` without rows; `agg_by distinct` with no key columns and
`preserve_empty`. Java: one row whose cells are empty arrays. Oxhaven: one row of nulls.
`group`, `unique`, `count_distinct`, `sum` and `first` match in the same request, and so
does `distinct` for an empty initial group of a keyed aggregation
(`oracle/scenarios/static/partitioned_tables.json`, `seeded_kept`). Known entry
`distinct-of-no-rows`. Scenario: `D3_distinct_of_no_rows.json`. `initial_groups` 44.

### D4. `where` with a time literal that is none answers `UNIMPLEMENTED`

`t(T timestamp)`; `where T >= '2023-11-14T22:13:21'` (no zone) or
`'2023-11-14T22:13:21 NY'` (a zone Java does not know). Java: `INVALID_ARGUMENT`. Oxhaven:
`UNIMPLEMENTED`, "not ported: DateTimeUtils#parseZonedDateTime", because the refusal R2 is
made before the literal is found to be invalid. Inside a formula
(`T >= '… NY' && true`) both answer `INVALID_ARGUMENT`. Scenario:
`D4_where_invalid_time_literal.json`. Fixed by porting R2. `statistics` 43.

### D5. `aj` of a keyed input with a history snapshot it triggers loses a row

Keyed input `r(RId)` with the row `6`; `history = snapshot_when(q, trigger r, history)`;
`r aj history on RId > Q1`. One cycle adds `9` to `r` and writes `6` again. Java: the join
has two rows, as `r` has. Oxhaven: one row. The same for `raj`. A cycle that only adds, or
only writes the row again, is the same on both, and so is the join when the snapshot keeps
no history or the right side is an `update_view` of `r`. Found by the family `all` of the
wide generator (seed 308, one seed in 1000), where the join had one row more than `r`
after later cycles; the families of the second generator did not draw it. No known entry: an
entry for a row count of `aj` would hide any other. Scenario:
`D5_aj_right_snapshot_of_left.json`.

### R1. `lazy_update` with a row variable or a column array

`lazy_update X = i`, `X = k`, `X = V_.size()`, `X = isNull(V_[i-1])`. Java computes;
Oxhaven: `UNIMPLEMENTED`, `DhFormulaColumn#generateAppropriateGetMethod` (3.4, 5.5).
`X = V_[i-1]` and `X = V - V_[i-1]` are computed by both, so a fixed-distance read is
rewritten unless it is the argument of a call; `update X = isNull(V_[i-1])` is computed by
both. Scenario: `R1_lazy_update_row_variables.json`. `all2` 63, 137 before the restriction.

### R2. `where` comparing a timestamp with a literal in a zone other than UTC

`where T >= '2023-11-14T17:13:21 ET'`, `T == '… Europe/Paris'`, `T in '… ET', '… UTC'`,
`T > '2023-11-14 ET'`. Java computes; Oxhaven: `UNIMPLEMENTED`,
`DateTimeUtils#parseZonedDateTime` (3.2). With `UTC`, and with any zone inside a formula
(`T >= '… ET' && true`), both compute the same. This was the most frequent difference of
the pass: about one seed in ten of every family with `where` before the generator was
restricted. Scenario: `R2_where_time_zone.json`.

### R3. A zone written as an offset

`update X = '2023-11-14T23:13:21 +01:00'`. Java computes; Oxhaven: `INVALID_ARGUMENT`
(`TimeZoneAliases#zoneId`, 5.6). Scenario: `R3_offset_zone.json`.

### R4. Initial groups a refreshing table has no rows for, without `preserve_empty`

Append-only `t(K, V)`, `keys(K) = [a, c]`; `agg_by sum by K` with initial groups `keys`.
Java computes; Oxhaven: `UNIMPLEMENTED`, `ChunkedOperatorAggregationHelper#copyKeyColumns`
(4.18, which says what Java shows: the group with null keys once it has rows). With
`preserve_empty` both compute the same. Scenario: `R4_initial_groups_refreshing.json`.

### R5. Column arrays at two distances on a refreshing table

Append-only `t(V)`; `update X = V_[i-1] + V_[i+1]`, `where V_[i+1] > V && V_[i-1] < 100`.
Oxhaven: `UNIMPLEMENTED`, `ShiftedColumnOperation#computeDirtyModifiedRowSetInPositionSpace`
(5.5). Java answers, and wrongly after a step: see J3. Scenario:
`J3_two_distances_stale.json`.

### R6. The column array of an array column

`g = group_by K`; `update X = V_.size()`, `X = V_[0]`. Java computes; Oxhaven:
`INVALID_ARGUMENT`, "unsupported in formulas: column array V_ of a column of type
Vector(Int)" (`ColumnVectors#of`, 5.5). `X = V_[i-1]` is computed by both. The status is
not the one of a refusal by name. Scenario: `R6_column_array_of_array_column.json`.

### R7. `keyed_transpose` with columns named after a `float` or a timestamp

`keyed_transpose` with `col_by` a `float32` or a timestamp column. Java computes; Oxhaven:
"not ported: KeyedTranspose#keyedTranspose: a column-by column of type Float (Instant),
whose values Java names columns after with String#valueOf" (4.18). A `float64` column
matches. Scenario: `R7_keyed_transpose_column_types.json`. `transpose` 1, 4, 12, 15, 26
before the restriction.

### R8. A period of months or years added to a timestamp that is never evaluated

`where T + 'P1m' > T` or `update X = T - 'P1y'` of a table without rows, and
`update X = isNull(T) ? T + 'P1m' : T`. Java: succeeds, because `DateTimeUtils#plus(Instant,
Period)` fails only when it is given a timestamp that is not null. Oxhaven: refuses when the
formula is made, `INVALID_ARGUMENT`. With a row that is evaluated both answer
`INVALID_ARGUMENT`. On a refreshing table Java's failure comes in the update cycle that
brings the first such row. Scenario: `R8_month_period.json`. `transpose` 112.

## Not in scope: Java defects, recorded for the owner

### J1. `update_by` count where over a comparison of columns stops the server

`t(K int32, T timestamp)`; `update_by cum_count_where U1` with the filter `T >= T` (also
`rolling_count_where_tick` and `_time`, and a boolean column, `B != B`). Java: a
`NullPointerException` in `CountWhereOperator$Context.<init>`
(`CountWhereOperator.java:237`: `originalFillContexts` is null because
`originalChunksRequired` is computed from the chunk and condition filters only), reported as
"Unexpected iteration job error", after which the server process shuts down. The same when
the comparison is of two integer columns and another filter of the operator reads a
timestamp column: `t(K int16, C int32, T timestamp)`, filters `C == K` and `!isNull(T)`.
`T == null`, `B == true`, `isNull(B)` and `B == B && K > 0` are computed. Oxhaven answers
`UNIMPLEMENTED` to the first and has not been asked the second. The generator never draws a
count where filter that compares two columns (restrictions J1 and J4), because the reference
would be gone for the rest of the run, as it was in this pass before each form was known.
Scenarios: `J1_count_where_stops_java.json`, `J1_count_where_two_filters_stops_java.json`;
do not run them against a reference that another run uses. `update_by2` 300 before the
restriction covered the second form.

### J2. `select` of a filtered static table with a fixed-distance read

Static `t(V) = [1, 0, 3, -2, 5]`; `f = where V > 0`; `select X = V_[i-1]` of `f`. Java:
`[null, 1, 0]`, the values of `t` at the new row keys; `update` with the same formula gives
`[null, 1, 3]`. Oxhaven refuses the `select` by name
(`SelectAndViewAnalyzer.AnalyzerContext#getPublishedColumnSources`, 5.5 and 5.6, where the
defect is described). The generator draws a fixed-distance read in a `select` only of an
input table. Scenario: `J2_select_shift_after_where.json`.

### J3. Column arrays at two distances on a refreshing table go stale

Append-only `t(V) = [1, 0, 3, -2, 5]`, then `[7]` is added. `update X = V_[i-1] + V_[i+1]`:
Java keeps `X = null` in the row of 5, where -2 + 7 = 5 is due.
`where V_[i+1] > V && V_[i-1] < 100`: Java keeps `[0, -2]`, where `[0, -2, 5]` is due; with
the one distance (`V_[i+1] > V`) both servers answer `[0, -2, 5]`. This is the defect 5.5
describes for a keyed table, seen here on an append-only one; Oxhaven's refusal is R5.
Scenario: `J3_two_distances_stale.json`.

### J4. `update_by` count where over a comparison of two columns fails on its first row

`t(Id int32, C0 float32)` with rows; `update_by cum_count_where` (or `rolling_count_where_*`)
with the filter `Id == C0` or `Id == Id`. Java: `INVALID_ARGUMENT`, a
`NullPointerException` ('Cannot read the array length because "keys" is null'). Oxhaven
answers the same, with the same message in its log. Written as one formula
(`Id == 3 && Id == C0`) both compute. Of a refreshing table without rows both accept the
request, and the failure comes in the cycle that brings the first row: Java then refuses the
snapshot and Oxhaven serves the rows it had (Q11 in `PARITY.md`), which is the one
difference. Scenario: `J4_count_where_two_columns.json`. `update_by2` 36, 49 before the
restriction.

### J5. `distinct` of a timestamp column for a group that lost its rows

Keyed `r(Id int32, T timestamp, V int32)` with one row; `agg_by distinct A = T by Id` with
`preserve_empty`; a step deletes the row. Java: the snapshot fails with `INVALID_ARGUMENT`,
as in J2 of `tasks/4.17-fuzz-findings.md` (`InstantSsmSourceWrapper`), which the group kept
by `preserve_empty` reaches without any null. Oxhaven: the group stays with a null. With
`group` in place of `distinct`, and with `distinct` of the `int32` column, both servers
agree. Scenario: `J5_distinct_timestamp_empty_group.json`, whose `of_no_rows` table shows
D3 for a timestamp. `initial_groups` 329 before the restriction.

### J6. Initial groups with `first` and `last` of a refreshing table

Keyed `t(Id, K, V, W)` with one row; `agg_by first A = V, last B = W by K` with initial
groups. Java: `INVALID_ARGUMENT`, "Requirement failed: required indices.get(destination) !=
null" in `FirstOrLastChunkedOperator$ComplementaryOperator.updateSingleton`
(`FirstOrLastChunkedOperator.java:569`), from
`ChunkedOperatorAggregationHelper#initialKeyTableAddition`. Oxhaven computes it. Two `first`
aggregations, `first` with `sum`, the same request of a static or an append-only table, and
the request without initial groups are computed by both. Scenario:
`J6_first_and_last_initial_groups.json`. `initial_groups` 369, 795 before the restriction.

## Harness limitations, recorded for the owner of `oracle/`

- H1. A table that fails in an update cycle cannot be compared (Q11 in `PARITY.md`), so the
  generator keeps out: a `ring_table` over a table that can modify or shift rows, a
  `keyed_transpose` with the new-column behaviour `fail` on a refreshing table, a
  `multi_join` without match columns of a refreshing table that can hold two rows, and
  arithmetic on two array columns of different groupings of a refreshing table.
- H2. The columns of a `keyed_transpose` are named after values, so the comparison rules
  cannot tell which hold sums; with a computing aggregation every column but the row keys is
  compared with the float tolerance (`rules.computed_columns`), and the generator draws no
  `sum` next to a float aggregation.
- H3. A script operation that fails has one code, `SCRIPT_FAILED`, on both servers: the
  status of the failure inside the console is not compared.
- H4. Comparisons of arrays (`A == 1`) are not generated: their result is a `boolean[]`,
  which the comparison rules do not know.
- H5. The scenario files of `tasks/4.17-fuzz-findings/` cannot be loaded as they are: a
  scenario's name must be its file's name and an identifier, and theirs have hyphens.

### What task 4.20 did (branch `task/4.20-fuzz-fixes`)

Fixed, each with a regression test, its scenario file clean against Java 42.9, and its
known entries or restrictions removed:

- D1. `ops/select/arrays.rs`: Java applies the columns after a shifted column with the
  operation asked for even when there are none (`remainingCols` is an empty list), and
  that `update` or `lazyUpdate` of an append-only table is add-only; `updateView` of no
  columns returns its parent. Known entries `update-shift-add-only` and
  `lazy-update-shift-add-only` removed.
- D2. `ops/partitioned/partition.rs`: add-only and append-only are copied from a static
  parent too. That made a second difference visible, fixed with it: the merge
  `partition_get` makes for a refreshing key table took the constituents' attributes,
  where Java permits constituent changes there and gives none (`partitions` 413, 606, 967
  of the generator as it is now; `PartitionedTable#with_constituent_changes_permitted`).
  For a static key table Java keeps them, and so does Oxhaven. The four `partition-*`
  known entries removed.
- D3. `ops/agg/distinct.rs`: without key columns the group has its set from the start, so
  a table without rows gives an empty vector; a removal that takes the last value still
  makes it null, and a later row an empty vector again, as probed. The result depends on
  the history, so the random test without keys leaves `distinct` out when `preserve_empty`
  is set, as the seeded one already did. Known entry `distinct-of-no-rows` removed.
- D4 and R2. `ops/filter/literal.rs`: a match or range filter on a timestamp column reads
  a literal the UTC parser does not know through the formula compiler, as Java reads both
  with `DateTimeUtils#parseInstant`. Restrictions D4 and R2 removed.
- R3. `oxhaven-expr`, `parse/instant.rs`: a zone may be an offset (`+01:00`, `+1`,
  `-05:30`, `+010030`, `UTC+1`, `GMT-05:00`, `UT+01:30`, at most 18 hours) or `UT`, and a
  region of the time zone database without a `/` (`Japan`, `CET`, `EST5EDT`). Java was
  asked for all 597 names of the database compiled in and reads all but `EST`, `HST`,
  `MST` and `ROC`. A zone Java does not know (`NY`, `utc`, `+19:00`), a date and time
  without a zone, and a date alone with a zone that is not letters are syntax errors now,
  as in Java, where they were refusals. Restriction R3 removed; the generator draws
  `+01:00` and `UTC-5`.

Left as they were, and why:

- Still refused by name in a time literal: a region with a `/` that the compiled database
  lacks (`SystemV/EST5`, which Java reads; `Europe/Nowhere` and `Europe/paris`, which Java
  rejects with `INVALID_ARGUMENT` where a filter here answers `UNIMPLEMENTED`), a zone
  directly after the time (`...T22:13:20+01:00`, `...Z[UTC]`), and a `ZonedDateTime` whose
  zone is an offset (`parseZonedDateTime('... +01:00')`): no column holds such a zone id.
- R4, R7, R8, R1, R6: not started; the context budget of the task ran out after R3. For
  R4, note that Java's answer is the group with null keys once it has rows, so the port
  has to write nulls into the key columns of the result for the initial groups without
  rows, and must be probed for formula aggregations that read the key.
- R5, J1 to J6 and D5: out of scope by instruction (D5 is Q11 of `PARITY.md`, ruled on
  2026-11-17 as allowed difference A11; see `tasks/0.18-owner-rulings.md`).
