## Scope

In order, probing the Java reference for each type and operation before writing it, one
commit per piece:

1. `sort` and `sort_descending` on `LocalDate`, `LocalTime`, `Duration`, `ZonedDateTime` and
   `DayOfWeek`; `ZoneId`, `Period` and `Object` refused with Java's error.
2. Match filters (`=`, `!=`, `in`, `not in`) and range filters (`<`, `<=`, `>`, `>=`) in
   `where` on those types, with the literals Java's filter parser accepts for each.
3. Keys of those types in `natural_join`, `exact_join`, `join`, `agg_by`, `group_by` and
   `distinct`, and the `min`, `max`, `first`, `last`, `count_distinct`, `unique` and
   `sorted_first` aggregations where Java computes them.
4. If small: the types in the fuzzer's column generators.

At least one recorded scenario covers sort, filter and key use of these types.

Not in scope: sorting arrays and vectors (`ComparatorRegistry`), `BigDecimal` and
`BigInteger` sort keys, an `Object` column in filters and keys.

### Differences from Java found, all in the formula fallback of a filter

When a match or range filter cannot convert its literal, Java and this server both fall back
to the filter's formula; these formulas are refused by `oxhaven-expr` where Java computes
them (the expression crate, not this task):

- `D == 2024-03-10` (a `LocalDate` against the `int` 2011): Java keeps no row; here
  `operator == on values of type LocalDate and int` is unsupported.
- ``D == `2024-03-10` `` (`LocalDate == String`): Java keeps no row; refused here.
- `Dur < null`: Java keeps no row; refused here.
- `P == 'P1Y'` (`Period` equality): Java keeps the `P1Y` rows; refused here.

### Aggregation values of `ZonedDateTime` and `Period` (probed on Java 42.9)

`agg/values.rs` holds a `ZonedDateTime` as its instant, its zone's offset at that instant
and its zone id (`Scalar::Zoned`), ordered as `compareTo` and equal as `equals`, and a
`Period` as its three fields (`Scalar::Period`), which has no order.

- `ZonedDateTime`: `min`, `max`, `first`, `last`, `count_distinct`, `unique`, `median`,
  percentile, and `sorted_first`/`sorted_last` by it and of it are computed as Java computes
  them: of one instant, Tokyo is after New York; one instant in two zones is two distinct
  values.
- `Period`: `first`, `last` and `sorted_first`/`sorted_last` of it are computed. Sorted
  first or last *by* a `Period` on a static parent follows Java's operator, which compares
  each row with the best so far in row order and fails (`ClassCastException`) only when two
  periods meet: sorted first by `P` keeps the first null it meets. On a refreshing parent, or
  with other sort columns, it is refused with `unported` (Java keeps a sorted array there).
  `min`, `max`, `median`, percentile, `count_distinct`, `unique` and `distinct` of a
  `Period` are refused with `unported`: Java fails once it compares two periods, but answers
  a group with at most one period (probed: `min` and `count_distinct` of one row each).
- The recorded scenario `time_types` runs sort, match and range filters, natural, exact and
  cross joins, `select_distinct` and these aggregations on columns made by formulas. Its
  results are views without the date, time and duration columns, which `rules.py` cannot
  compare (`unsupported_type`); those columns are keys only. The engine's corpus tests do
  not run it (its sources are made by `update`, and the select corpus test skips columns
  that the server sends in another form); the replay gate does.
