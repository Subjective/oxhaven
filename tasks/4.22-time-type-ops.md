## Scope

In order, probing the Java reference for each type and operation before writing it, one
commit per piece:

1. `sort` and `sort_descending` on `LocalDate`, `LocalTime`, `Duration`, `ZonedDateTime` and
   `DayOfWeek`; `ZoneId`, `Period` and `Object` refused with Java's error.
2. Match filters (`=`, `!=`, `in`, `not in`) and range filters (`<`, `<=`, `>`, `>=`) in
   `where` on those types, with the literals Java's filter parser accepts for each.
3. Keys of those types in `natural_join`, `exact_join`, `join`, `agg_by`, `group_by` and
   `distinct`, and the `min`, `max`, `first`, `last`, `count_distinct`, `unique` and
   `sorted_first` aggregations where Java computes them.
4. If small: the types in the fuzzer's column generators.

At least one recorded scenario covers sort, filter and key use of these types.

Not in scope: sorting arrays and vectors (`ComparatorRegistry`), `BigDecimal` and
`BigInteger` sort keys, an `Object` column in filters and keys.

The order and equality of a `ZonedDateTime` are in `crates/oxhaven-engine/src/ops/zoned.rs`,

### Differences from Java found, all in the formula fallback of a filter

When a match or range filter cannot convert its literal, Java and this server both fall back
to the filter's formula; these formulas are refused by `oxhaven-expr` where Java computes
them (the expression crate, not this task):

- `D == 2024-03-10` (a `LocalDate` against the `int` 2011): Java keeps no row; here
  `operator == on values of type LocalDate and int` is unsupported.
- ``D == `2024-03-10` `` (`LocalDate == String`): Java keeps no row; refused here.
- `Dur < null`: Java keeps no row; refused here.
- `P == 'P1Y'` (`Period` equality): Java keeps the `P1Y` rows; refused here.

### For the owner

- `SortError::NotSortableColumn` is new; its gRPC code is not recorded (`sort/corpus.rs`).
- Aggregation values of a `ZonedDateTime` (`min`, `max`, `first`, `last`, `count_distinct`,
  `unique`, `sorted_first` by it) still fail with `unported`; Java computes them (probed:
  `min` is the earliest instant). They need a `Scalar` that holds the instant, offset and
  zone (`agg/values.rs`). `sorted_first` by a `Period` is refused here; Java answers it for
  a group whose first row is null, and would fail with `ClassCastException` otherwise.
- `BigDecimal` and `BigInteger` as sort keys and aggregation values: not started.
