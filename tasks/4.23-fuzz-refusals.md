## Findings of this task

Each was observed on Java 42.9. A scenario file for each is in `tasks/4.23-fuzz-refusals/`.

### J7. Initial groups with `first` or `last` of an add-only table fail in a later cycle

Append-only `t(K, V)` with rows of `a` and `b`; `agg_by first A = V by K` with the initial
groups `[a, c]`, without `preserve_empty`; a step adds a row of `c`. Java accepts the
request, and in the cycle of that step the result fails: "RowSet update error detected",
the row of `c` is reported modified and never added
(`BaseTable#validateUpdateOverlaps`). The same for `last`, `sorted_first` and
`sorted_last`, alone or with other aggregations, unless a `count` comes before them in the
request. The first and last operators of an add-only table are state change recorders that
record nothing (`BaseAddOnlyFirstOrLastChunkedOperator extends NoopStateChangeRecorder`:
"We can never empty or reincarnate states since we're add-only"), and
`AggregationContext#getStateChangeRecorder` takes the first recorder among the operators;
an initial group without rows does appear later. Of a keyed table, with `preserve_empty`,
or with a `count` first, Java computes, and Oxhaven computes the same. Oxhaven refuses the
failing request by name when it is made (`UNIMPLEMENTED`,
`BaseAddOnlyFirstOrLastChunkedOperator`), also for a blink table, whose operators are the
same kind of recorder (read, not probed). A failed table cannot be compared (Q11 of
`PARITY.md`), so the generator gives such a request `preserve_empty`. Scenario:
`J7_first_of_add_only_initial_groups.json`.

### R6, what is left of it. Column arrays whose elements Java gives no type

`g = t.group_by("K")` over `t(K, T)` with `T` a timestamp column; `g.view("X = T_[i]")`.
Java answers a column of `list<string>`: the column array of a column of
`ObjectVector<Instant>` has elements without an element type, and so has its shifted
column. The same for a column of vectors of booleans, for `T_[i - 1]`, and for
`T_[i * 1][0]`, a string. `T_[i].size()` and `isNull(T_[i - 1])` are computed as one
expects. Oxhaven refuses every column array and every fixed-distance read of such a column
in a formula column by name, also the first of those two; a filter reads it. Before this task the fixed-distance read answered a
typed list, which the generator restriction hid. Scenario:
`R6_column_array_of_object_vectors.json`.

The column array of an array column that a formula made (`u = g.update("A = 1 - F")`,
`u.where("isNull(A_[i+1])")`) is one of Java arrays, not of vectors; Java computes it and
Oxhaven refuses it by name ("column array A_ of a column of type Array(Float)"). Scenario:
`R6_column_array_of_java_arrays.json`.

The generator draws the column array of an array column of numbers or strings that an
aggregation made, and neither of these two (restriction R6, narrowed).

## Notes

What was done, finding by finding. Every behaviour named was observed on Java 42.9 unless
it says "read".

- **R4.** An initial group a refreshing table has no rows for is a row of the result once
  it gets rows, and its key columns are null in that row for good: Java writes the keys of
  the initial groups only for those that have rows (`copyKeyColumns`), and never again.
  The same for every aggregation, for a keyed and an append-only parent, and a formula
  aggregation reads the null key. `Aggregator::forget_keys_of_absent_groups` writes the
  nulls in one bulk fill. New finding J7 (above): refused by name, generator gives the
  request `preserve_empty`. Restriction R4 removed.
- **R7.** `keyed_transpose` names its columns after a `float32` value with
  `Float#toString` and after a timestamp with `Instant#toString` made legal
  (`column_20240101T000000Z`). `java_float_to_string` is a function of
  `ops/transpose/names.rs`: the shortest digits that read back as the same `float`, in
  Java's plain or `E` notation. Restriction R7 removed.
- **R8.** Was computed on main already (the scenario of 4.20 is clean). The generator draws
  periods of months and years for static tables only: a refreshing one fails in a later
  cycle in Java. Restriction R8 removed.
- **R1.** A lazy formula is remembered by the values of the columns it reads and by `i`,
  `ii` and `k` when it reads them; a column array is no part of the key (the arguments of
  the method Java's generated formula memoizes). Restriction R1 removed. Not probed: a
  blink parent (ported from reading `FormulaColumn` and `AbstractFormulaColumn`).
- **R6.** The column array of a column of vectors of numbers or strings is read:
  `V_.size()`, `V_[0]`, `V_[i - 1]`, `V_[N]`, `V_[i][0]`, `sum(V_[0])`, `isNull(V_[5])`.
  Still refused by name, each also by Java in another way or rarer: `V_` as the value of a
  formula (Java sends strings), `V_.subVector(...)`, `toArray`, `getDirect`,
  `getComponentType`, `equals`, comparisons of two vectors; `first(V_)`, `last(V_)`,
  `sum(V_)` and `countDistinct(V_)`, which Java fails. What is left of R6 is written up
  above; the restriction is narrowed to it.
- **Time literals.** `parse/instant.rs` reads, for a year of four digits: an offset or `Z`
  in either case directly after the time, with an optional zone in brackets, as
  `ZonedDateTime#parse` does (the offset places the time, the calendar and the clock are
  strict); the thirteen `SystemV` zones, which are all the ids of Java's
  `ZoneId#getAvailableZoneIds` that the compiled database lacks (the two lists were
  compared), with the daylight rule of the `SystemV` entry of the time zone database;
  and, before a space and a zone, fields of one or two digits, `t`, a bare `.`, hour 24
  and a day past the end of its month as `FORMATTER_ISO_LOCAL_DATE_TIME` resolves them.
  A region with a `/` that Java does not know is a syntax error now, as in Java. A
  battery of 200 spellings in four places each (the value of a formula, a comparison in a
  formula, a `where` filter, the text of `parseInstant`) agrees with Java but for those
  below. The generator draws the new spellings.
- Still refused by name in a time literal, on purpose: a year with a sign or of more than
  four digits, and an instant outside the range of a cell. Java answers an instant far
  from the one written for some of them (`'-2023-11-14T22:13:20Z'` is 2069-09-30,
  `'0000-01-01T00:00:00Z'` is 1753-08-29) and fails others in one place and not in
  another. A `ZonedDateTime` whose zone is an offset or a `SystemV` zone is refused: no
  column of this server holds such a zone id. A literal with a space before the date is
  refused where Java rejects it.
