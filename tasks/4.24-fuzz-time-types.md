## Scope

1. A family of the second generator that builds columns of `LocalDate`, `LocalTime`,
   `LocalDateTime`, `Duration`, `DayOfWeek`, `ZonedDateTime`, `Period` and `ZoneId` through
   formulas, with nulls and with one instant in several zones, on static and refreshing
   parents, and draws: sorts (one and several columns, descending), match and range filters
   with literal spellings, join keys (natural, exact, cross, as-of where Java allows the
   type), group keys, `select_distinct`, and the aggregations `min`, `max`, `first`,
   `last`, `count_distinct`, `unique`, `distinct`, `sorted_first`, `sorted_last`, `median`
   and percentile.
2. 1000 seeds of it against Java 42.9. Every difference is triaged as a refusal here of
   something Java computes (R), a Java defect (J) or a wrong answer here (D). D findings
   and cheap R findings are fixed; the others are written up below with a minimal scenario
   and a named entry in `fuzz_second.RESTRICTIONS`.
3. Known before the task started (`tasks/4.22-time-type-ops.md`): `min`, `max`,
   `count_distinct` and `unique` of a `Period`, sorted first or last by a `Period` on a
   refreshing parent, match and range filters on `LocalDateTime`.
4. All families of both generators again, 1000 seeds each.

Not in scope: `BigDecimal` and `BigInteger`; seed 308 of the family `all` (D5 of 4.20).

## Findings

Each was observed on Java 42.9 (port 10908) against this server (port 10909). The open
ones have a scenario file in `tasks/4.24-fuzz-time-types/` and an entry of the same name in
`fuzz_times.RESTRICTIONS`. R is a refusal here of something Java computes, J a Java defect,
D a wrong answer here.

### R1. `toLocalDateTime(Instant, ZoneId)` was refused (fixed)

It was the only way a formula could make a `LocalDateTime` column. Computed now
(`oxhaven-expr`, `functions/java_time.rs`).

### D1. The component type of a vector of `LocalDateTime` or `ZoneId` (fixed)

`agg_by` with `distinct` of a `LocalDateTime` or a `ZoneId` column: Java declares the
column's `deephaven:componentType` as `java.lang.String`, because it sends the elements as
text (`BarrageUtil#columnDefinitionsToFields`, `#isTypeNativelySupported`); this server
named the class itself. The cells were the same. Fixed in
`crates/oxhaven-server/src/schema.rs` (`java_component_type_name`), with a test that was
seen to fail without the fix. An array (not a vector) of these classes has no component
type in Java (read, not probed: no operation here makes one).

### R2. Filters on a `LocalDateTime` column

Java has a convertor for the type (`MatchFilter.ColumnTypeConvertorFactory#getConvertor`,
which reads the quoted text with `DateTimeUtils#parseLocalDateTime`) and a range filter
(`RangeFilter#init`, `makeComparableRangeFilter`): `M == null`, `M in null`, `M != null`,
`M == '2023-11-14T22:13:20'` and `M > '2023-11-14T22:13:20'` are computed. This server
refuses every one (`UNIMPLEMENTED`). Not ported: `parseLocalDateTime` is not a function of
`oxhaven-expr` yet, which the convertor here would call as it does for the other types.
The generator draws no filter on such a column. Scenario:
`R2_filter_on_local_date_time.json`.

### R3. Ordering aggregations of a `Period` for a group with one period

`min`, `max`, `median`, percentile, `count_distinct`, `unique` and `distinct` of a `Period`
column: Java answers a group that holds at most one period that is not null, and fails
with a `ClassCastException` (`INVALID_ARGUMENT`) once two meet. This server refuses all of
them by name (`UNIMPLEMENTED`). Not ported. Scenario: `R3_ordering_of_one_period.json`.

### R4. Sorted first or last by a `Period`

On a static parent Java compares each row with the best so far and fails when two periods
meet, but not when the two are the same object
(`io.deephaven.util.compare.ObjectComparisons#compare` returns before the cast for
identical references): with `P = V % 3 == 0 ? 'P1Y2M' : 'P3D'` every `P1Y2M` is the one
constant of the formula, and a group of them is answered. This server fails whenever two
periods that are not null meet (`INVALID_ARGUMENT`), and refuses a refreshing parent by
name. What Java answers depends on object identity, which no column of this server has;
for the owner. The generator draws no sorted first or last by a `Period`. Scenario:
`R4_sorted_first_by_period.json`.

### R5. A `Period` compared with a period literal (no longer a finding)

`P == 'P1Y2M'` was refused when task 4.22 wrote it down; it is computed on main now and
agrees with Java. The restriction is lifted and the generator draws it.

### R6. As-of joins on the date and time types (closed by task 4.26)

Closed: the six types are computed and the generator draws `aj` and `raj` on them; a
`Period` or `ZoneId` stamp is refused with `INVALID_ARGUMENT`, which is R8 below. As found:

Java computes an as-of join whose stamp column is a `LocalDate`, `LocalTime`,
`LocalDateTime`, `Duration`, `DayOfWeek` or `ZonedDateTime`, and refuses one on a `Period`
or a `ZoneId` (`INVALID_ARGUMENT`). This server refuses all eight by name
(`AsOfJoinHelper#asOfJoin: an as-of join on a column of type ...`, `UNIMPLEMENTED`), so
the status code differs for the last two as well. Not ported: not cheap (the as-of join's
stamp kernels are per type). The generator draws no as-of join. Scenario:
`R6_asof_join_on_time_types.json`.

### R7. A range comparison with null on a type without a range filter

`W >= null` on a `DayOfWeek` column: `RangeFilter` refuses the type, the filter falls back
to a formula, and Java computes it: every row is kept, the rows where `W` is null too.
This server refuses the formula (`INVALID_ARGUMENT`). The same for `Duration` (task 4.22
wrote down `Dur < null`). Not ported; the generator draws no range comparison with null
on a `DayOfWeek`, `Duration`, `Period` or `ZoneId` column (the last two were not probed
one by one). Scenario: `R7_range_with_null.json`.

### R8. An as-of join on a `Period` or `ZoneId` stamp (found by task 4.26)

Neither class is a `Comparable` (a `ZoneId` of a region is a `ZoneRegion`). Java fails with a
`ClassCastException` (`INVALID_ARGUMENT`) when it compares two stamps that are not one
object: while it sorts the left or the right stamps of one key, or compares a left stamp
with a right one. `ObjectComparisons#compare` returns 0 for one object before it casts, so
Java answers a join in which no two stamps that are not null and not the same object meet:
a left table with one stamp a key and a right table without rows, or stamps that are all
the one constant of a formula. This server has no object identity and refuses every such
join before it computes (`AsOfJoinError::IncomparableStamps`, `INVALID_ARGUMENT`, Java's
text). Seen on Java 42.9: with several distinct periods or zones on the left, Java fails
also when the right table has no rows or only nulls. The generator draws no as-of join on
these stamps; they are drawn as exact-match columns. Scenario:
`R8_asof_join_on_period_or_zone.json` (Java answers both joins, this server refuses them).

### J2. A strict as-of rule joins an added right row with an equal stamp (found by task 4.26)

`raj` with `<`, and `aj` with `>`, on a stamp of a `java.time` type (seen with
`LocalDateTime`, `LocalTime`, `LocalDate`, `Duration` and `ZonedDateTime`; not with a
`long` stamp nor a `String` one in the same shape) of two refreshing tables: when a step
adds a right row whose stamp equals a left row's, Java's ticking result joins that left row
with it, which the strict rule excludes. The same join made from the rows after the step
joins nothing there, and so does this server, which follows the answer made from scratch
(PARITY.md, A13). The fuzzer's entry for that rule (`aj-reference-history` in
`oracle/fuzz-known-findings.json`) names the operation `aj`, so it does not reach a `raj`
or a view of an `aj` (which this family makes when the result has a `Period` column). The
generator draws no strict rule whose right table is refreshing (it draws `>=` or `<=`
there). Scenario: `J2_strict_asof_on_an_added_equal_stamp.json`. Seeds 19 (`raj`) and 294
(`aj` under a view) of `time_types` found it; for both, the join made from the rows after
the step agreed with this server on Java.

### J1. Ordering aggregations of a `ZoneId`

A `ZoneId` is not a `Comparable`. Java fails `min`, `max`, `median`, percentile,
`count_distinct`, `unique`, `distinct` and sorted first or last by a `ZoneId` with a
`ClassCastException` (`INVALID_ARGUMENT`) once two zones that are not null meet in a
group, also two equal ones, and answers a group with one. This server refuses `min`,
`max`, `median` and percentile by name whatever the groups hold (`UNIMPLEMENTED`: an R
where Java answers, another status code where Java fails), and computes `count_distinct`,
`unique`, `distinct` and sorted first or last by it where Java fails. Task 4.22 recorded
the last four as "computed" from groups of one zone. Not changed here: to follow Java
the engine would have to fail what it computes today; for the owner. The generator draws
none of these. Scenario: `J1_ordering_of_zone_ids.json`.
