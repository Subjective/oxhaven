## Scope

In this order, a commit and a push after each piece:

1. `LocalDateTime` match and range filters with literals and the null forms (R2), with
   `parseLocalDateTime` in `oxhaven-expr`.
2. A range comparison with null (`W >= null`) on `DayOfWeek`, `Duration`, `Period` and
   `ZoneId` columns, as Java computes it (R7).
3. `min`, `max`, `median`, percentile, `count_distinct`, `unique` and `distinct` of a
   `Period` for groups with at most one period, failing where Java fails (R3).
4. The formulas `toLocalDate(Z)`, `toLocalTime(Z)`, `toLocalDateTime(Z)`, `Z.getZone()`,
   `D.atTime(L)`, `toZonedDateTime(D, L, zone)`, `parseLocalDateTime`, `Z.toString()`,
   `P.toString()`, `formatDate(D)`, `formatDateTime(Z)`.
5. As-of joins (`aj`, `raj`) on `LocalDate`, `LocalTime`, `LocalDateTime`, `Duration`,
   `DayOfWeek` and `ZonedDateTime` stamps; `Period` and `ZoneId` refused with Java's status
   (R6).
6. Each closed restriction lifted from `fuzz_times.RESTRICTIONS`, the pinned digest and
   tests updated, and 1000 seeds of `time_types` against Java, clean or triaged.

Not in scope: J1 (ordering of `ZoneId`) and R4 (sorted first or last by a `Period`), which
await the owner.

## Notes

Started from main at `575de568`. Probed on Java 42.9 (port 10908) against this server
(port 10909).

### Done

1. **R2, `LocalDateTime` filters (closed).** `parseLocalDateTime` and
   `parseLocalDateTimeQuiet` in `oxhaven-expr` (`parse/instant.rs`,
   `local_date_time_nanos`): the date alone (four, two and two digits, optionally with a
   trailing `T`), or the permissive date and time of `parseLocalDate` and
   `parseLocalTime` joined by `T` or `t`, resolved `SMART` (`24:00` is midnight of the next
   day, a day past the month's end is its last day). Seen on Java: `2023-3-5`,
   `2023-11-14 22:13`, `2023-11-14T22`, `2023-11-14T24:30` and ten digits of fraction are
   not read. A date outside the years of a cell (1677 to 2262) is refused by name. The
   filter's convertor reads the literal with it (`ops/filter/literal.rs`); `RangeFilter`
   orders it as Java's comparable range filter does, null lowest.
2. **R7, range comparison with null (closed).** `W >= null` and its relatives on a
   `DayOfWeek` are `compareTo(Comparable, Comparable)`, null first (`types/mod.rs`); a
   `Duration` was already computed on main. `Period` and `ZoneId`: Java fails to compile
   the formula (`Cannot find method greaterEquals(java.time.Period, ...)`), and so does
   this server, with the same status (the fuzz run below draws them).
3. **R3, ordering aggregations of a `Period` (closed).** `ops/agg/periods.rs` wraps the
   operator. Seen on Java (scripts in the Notes' probes, summarised):
   - every one of `min`, `max`, `median`, percentile, `count_distinct`, `unique`,
     `distinct` answers a group of nulls and one period, and fails a group of two periods
     that differ (`ClassCastException`);
   - the minimum and maximum of a static or add-only parent answer a group holding one
     period object twice (`'P1D'`, a formula constant) and fail two equal periods made
     apart (`Period.ofDays(1)` twice): `ObjectComparisons#compare` returns 0 for one
     object before it casts;
   - the others, and the minimum and maximum of a keyed input table, sort the rows a
     group is given at once, and fail two periods there even when they are one object;
   - on a keyed input table, a row added in a later cycle with a period equal to the
     group's is answered (the multiset tests `equals` first), also for two equal objects
     made apart.
   This server has no object identity: the minimum and maximum of a static or add-only
   parent answer every group of equal periods. They differ from Java only for equal
   periods made as different objects (`Period.ofDays(1)` in two rows), where Java fails.
   Within one cycle Java casts per chunk of at most 4096 rows; here per group's rows of
   the cycle, which differs only for a group with more rows than that.
