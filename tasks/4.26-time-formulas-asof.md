### 1. As-of joins on the date and time types

- Java reinterprets only `Boolean` (to `byte`) and `Instant` (to `long`) for an as-of join;
  a `ZonedDateTime` only when its column source keeps the zone apart, which a formula's
  column does not. Every `java.time` stamp is an object compared with `compareTo`, null
  first, and two stamp columns join only when they hold one class (`Can not aj() with
  different stamp types: left=class java.time.LocalDate, right=class java.time.LocalTime`).
  A `DayOfWeek` stamp, held here as a byte, does not join a `byte` one. Exact-match columns
  of any two object classes are read alike (no `ClassCastException`), as before for
  `String`.
- `ops/asof/stamps.rs`: a `LocalDate`, `LocalTime`, `LocalDateTime`, `Duration` and
  `DayOfWeek` stamp is the count its cell holds, whose order is `compareTo`'s; a
  `ZonedDateTime` is its instant, its zone's offset then and its zone id, the order of
  `ChronoZonedDateTime#compareTo` (as `ops/zoned.rs` orders it for sorts). The incremental
  half is the same code for every stamp, so it needed no change.
- `Period` and `ZoneId` (R8 in 4.24): Java fails with a `ClassCastException`
  (`INVALID_ARGUMENT`) when it compares two such stamps that are not one object, in a sort
  of the left or right stamps of a key or in the stamp kernel. Seen: with several distinct
  values on the left Java fails also against a right table with no rows or only nulls; it
  answers a left table with one stamp and a right table without rows. This server refuses
  every such join with Java's status and text (`AsOfJoinError::IncomparableStamps`).
- Probe (`aj` and `raj`, each stamp type, every rule, with and without an exact-match
  column of a time type, nulls and equal stamps; 36 joins): identical results and refusals
  on both servers.
- Tests: `stamps.rs` (orders, classes, refusal text), `tests.rs`
  (`date_and_time_stamps_order_as_java_compares_them`,
  `period_and_zone_stamps_are_refused_as_not_comparable`), and `random.rs`
  (`random_updates_of_date_and_time_stamps`: nine joins over columns made by formulas, as
  stamps and as exact-match columns, four rules, both, left or right table changing, each
  result checked after every cycle against the join of static copies). Breaking the order
  of a `ZonedDateTime` (offset negated) fails the first two.
- New Java defect J2 (4.24): a strict rule (`>`, `<`) on a `java.time` stamp joins a right
  row added in a later cycle whose stamp equals the left one; Java's own answer made from
  scratch does not, nor does this server (PARITY.md, A13). The generator draws no strict
  rule whose right table is refreshing.
