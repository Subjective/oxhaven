## Scope

`cross_join`, keyed and unkeyed, including how output row keys are composed from left and right keys so that output order matches Java. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine crossjoin && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops join --within join,input_table && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops join --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. `join` is the harness name for `cross_join`.

## Notes

- Built: the engine side of `cross_join` (`join` in Deephaven), keyed and without match columns, static and incremental. `oxhaven_engine::ops::crossjoin::cross_join(left, right, on, add, reserve_bits)` takes two `Arc<dyn Table>` and returns `Result<Arc<dyn Table>, CrossJoinError>`. It reuses `JoinMatch`, `JoinAddition`, the key equality and the column checks of `ops/join` (`Plan`, `KeyColumns`, made `pub(crate)`; no other change there). `DEFAULT_RESERVE_BITS` is Java's configuration default, 10.
- Not built: Java's left outer join (`CrossJoinHelper#leftOuterJoin`) shares this code but has no API in the pinned reference's protocol or `Table`; it is not ported.
- Row keys are Java's, although `PARITY.md` A4 does not require it, because the number of bits decides when a join is refused or fails for running out of row key space, and that is visible. A result row key is the left row key shifted left by the right bits, plus the right row key (no match columns) or the position of the right row among the right rows of its key. The bits only grow: without match columns `max(reserve, bits of the right table's last key)`, with match columns `max(start, bits of the largest right group - 1)`, where `start` is the reserve, or 1 for two static tables. Two static tables without match columns use a reserve of 1. Which right groups count toward the largest is Java's (`JoinControl#buildParameters`): all of them when the left table is refreshing or both are static and the left one is the larger, otherwise only those a left row has.
- Refusals: `CrossJoinError::Join` (the natural join's column refusals, the update-graph conflict, a failed table), `OutOfKeySpace` (Java's `OutOfKeySpaceException`, at the start or, failing the result, in a cycle) and `ReserveBits` (Java's `AssertionFailure` from `CrossJoinShiftState#setNumShiftBits` for a number of bits outside 1 to 62: a refreshing keyed join with such a reserve, or a join without match columns whose reserve and right table need no bits). Through the server every refusal recorded is `INVALID_ARGUMENT`; the Python client sends no reserve, so the server's default applies.
- Updates: per left row, Java's cases in `CrossJoinHelper`: a removed or re-keyed left row removes its previous region, an added or re-keyed one adds its region, and a staying one gets its right group's change, moved with the row; a modified left row marks its whole region modified; a modified right row whose key changed is removed from one group and added to another. The modified columns are the left ones when the left table modified rows and the added ones when the right table did. A ticking table joined without match columns with an empty static table is a static table, as Java registers no listener then.
- Differences from Java: (1) In a keyed join of two ticking tables Java checks the row key space only in the right table's part of a cycle, and not before it shifts the rows to more bits: in `testdata/updates/limits.java.json` a right group that outgrows the space fails the result with an `IllegalArgumentException` from a row set builder, not an `OutOfKeySpaceException`. Here the space is checked every cycle before any row key is built, and the result fails with the out-of-space message. Both fail, in the same cycle. (2) Shifts may be cut into other ranges than Java's (A4); the replay compares where each row moves. (3) Cross join copies no attributes in Java (`CrossJoinHelper` does not call `copyAttributes`), so the result has none, not even the left input table.
- Tests: `ops/crossjoin/tests.rs` (static results and every refusal, each kind of change of either or both tables, failures and the out-of-space failure in a cycle), `ops/crossjoin/random.rs` (random updates over 34 seeds of both tables, of the left only and of the right only, on seven sets of match columns and two reserves, checked every cycle against the join of static copies), `ops/crossjoin/java_updates.rs` (hand-written updates at chosen row keys replayed against Java's engine: row sets, cells, added, removed, modified, modified columns and the effect of shifts after every step, refusals and failures), `ops/crossjoin/corpus.rs` (the cross joins of `oracle/corpus` and of `ops/crossjoin/testdata/corpus`, by position and cell).
- `ops/crossjoin/testdata/scenarios` holds four scenarios in the oracle's format, recorded by `testdata/record.py` like those of `ops/join`: key types (with nulls, NaN, `-0.0`), arguments and refusals, ticking tables on either or both sides, and chained ticking joins that run out of row key space. The oracle's harness sees only snapshots, so `testdata/record_updates.py` runs Java's engine in its own process (port 10864, an update graph in unit test mode) to record the row keys and updates of `testdata/updates/*.json`; usage in the file.
- Handler: `crates/oxhaven-server/src/table/ops/crossjoin.rs` serves `CrossJoinTables`, one-shot and in `Batch`. It reads the matches and additions with the parser of the other joins (`join::parse`, made `pub(super)`), in `validate` before the export exists and again in `create`, as `JoinTablesGrpcImpl` does. A `reserve_bits` of zero or less is the default of 10; a positive one goes to the engine unchecked. Every refusal of the engine is `INVALID_ARGUMENT` with an error id.
- Handler against a live Java server (Deephaven 42.9): 252 requests sent to both servers, their code, message, columns, rows and `is_static` compared: results with and without match columns, renamed and repeated additions, empty tables, every column refusal, unreadable matches and additions and which is reported first, unset references, a result ticket in use, 15 values of `reserve_bits` from the least to the greatest `int` on twelve pairs of static, refreshing and empty tables, and five batches. The differences found are the next three notes.
- Fixed after the merge (with the handler of 4.11): a join without match columns of a refreshing table with a static table that has no rows is static, as in Java (`is_static` in the response), because `CrossJoinHelper#zeroKeyColumnsJoin` listens to neither table then; the result was refreshing and never changed. The refreshing table is still read under the graph lock, so the refusals for the row key space, the reserve and a failed table are unchanged. With match columns, or with two refreshing tables, the result is refreshing in Java and here. Against a live Java server (port 10892): `CrossJoinTables` of all 64 pairs of eight tables (static with rows; static without rows as an empty table, a filter and a `head(0)`; refreshing with rows; refreshing without rows as a time table that starts in 2200, a filter and an input table), without match columns and matched on a column, with `reserve_bits` 0 and 1, 256 requests: `is_static` and the size agree for all (48 differed before). Tests: `a_join_without_match_columns_of_a_ticking_and_an_empty_static_table_is_static` in `ops/crossjoin/tests.rs` and `a_cross_join_of_a_refreshing_table_and_a_static_table_without_rows_is_static` in the handler tests; both fail without the fix.
- Difference from Java, shared with the other joins: a match or an addition that cannot be read and is empty or ends in a space (`""`, `" "`, `"A B "`; not one that ends in a tab or a line feed). Java's handler throws `INVALID_ARGUMENT` with a message that then ends in a space, and what reaches the client is `CANCELLED`, `RST_STREAM` with error code 8. Here the client gets the `INVALID_ARGUMENT` and the message.
- Difference from Java, in the session and not in this handler: a result ticket that is already in use is `INVALID_ARGUMENT` with an error id in Java and `INVALID_ARGUMENT: export N can only be defined once` here.
- Handler tests: `crates/oxhaven-server/src/table/tests/handlers.rs`, the four tests named `cross_join`. Each fails against a handler that always takes the default bits, passes the request's bits on as they are, swaps the tables, does not validate, or answers a refusal with a status of its own.
- Gate: `cargo test -p oxhaven-engine crossjoin` passes. `oracle/bin/harness replay --ops join --within join,input_table`: 1 scenario, clean. `oracle/bin/harness replay --ops join`: `join_duplicate_keys` and `ticking_join_merge` clean; `error_types_and_matches` differs only in its `aj` table. `oracle/bin/harness fuzz --ops join --seeds 10000` against Java: 10000 seeds clean, none of them a request Java refuses. `oracle/replay-baseline.json` has the two scenarios as clean and the third without its cross join table.
