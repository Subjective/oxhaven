## Scope

`aj`, `raj` and the legacy `as_of_join`, with all four match rules. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine asof && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops aj --within aj,input_table && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops aj --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness does not cover `raj` yet, so this gate does not check it; that needs an oracle task first.

## Notes

- Built: the engine side. `oxhaven_engine::ops::asof` has `as_of_join(left, right, exact, as_of, add)`, and `aj` and `raj`, which are `as_of_join` after the check of `AsOfJoinMatch#parseForAj` and `#parseForRaj` that the rule is one of theirs. Each goes from two `Arc<dyn Table>` to `Result<Arc<dyn Table>, AsOfJoinError>`, with `AsOfMatch` (left stamp column, `AsOfRule`, right stamp column) and the `JoinMatch` and `JoinAddition` of the natural join. The variants of `AsOfJoinError` name the Java exception; Java reports every one of them as `INVALID_ARGUMENT` (`fixtures/asof_refusals.json`). The legacy `AsOfJoinTablesRequest` is the same operation.
- Built: the gRPC handlers, `crates/oxhaven-server/src/table/ops/asof.rs`: `Aj` and `Raj` (`AjTables`, `RajTables`, one `AjRajTablesRequest`) and the deprecated `AsOfJoin` (`AsOfJoinTables`), which Java 42.9 still serves; each as a one-shot call and in `Batch`. The reading of the strings is there too, beside the handler as it is for the natural join.
  - `Aj` and `Raj` read their columns with the parsers of `io.deephaven.api`, not with `MatchPairFactory` as the other joins do: an exact match (`JoinMatch#parse`) and an addition (`JoinAddition#parse`) are split at the first `=` and each side is trimmed as `String#trim` trims and checked as a column name. So `X==V` is an addition for the other joins and is refused here for the name `=V`, and `K===K2` is refused for the name `=K2`. The as-of match is a column name alone (then both stamps have that name and the rule is `>=` for `Aj`, `<=` for `Raj`) or `Left <rule> Right` by the pattern of `AsOfJoinMatch#parse`; a rule of the other operation is refused in the request check, before the tables are looked at.
  - The order of the request checks is Java's: `left_id`, `right_id` and `as_of_column` are present (an empty `as_of_column` counts as absent), then the shape of the two references, then the exact matches, the as-of match and the additions. Everything in this list is `INVALID_ARGUMENT` with Java's text. Java's check for unknown fields, which comes after the presence checks, cannot be made: prost drops unknown fields.
  - `AsOfJoin` reads its columns as the natural join does. The last match names the stamps and the others are exact; the rule is a field of the request that Java reads with its sides exchanged (`LESS_THAN_EQUAL` gives `left >= right`). A rule number the protocol does not have is `INVALID_ARGUMENT` "Unrecognized as-of match rule", checked after the columns. A request without matches is an exception in Java (`ArrayIndexOutOfBoundsException`), so `INVALID_ARGUMENT` with an error id.
  - What the engine refuses is `INVALID_ARGUMENT` with an error id, as the recordings have it.
- Compared with Java 42.9 live: 251 raw requests (every case of the request checks, every form of the three kinds of string, the engine's refusals, the four rules of each operation), each as a one-shot call and in a `Batch`, 502 comparisons of status, message, schema and rows. 496 are the same. The six that differ are not of this handler: a `Batch` whose operation has no table reference, or one without a `ref`, in a request that Java does not check for it (`AsOfJoinTables`, and `NaturalJoinTables` the same). Java ends the stream with `CANCELLED` (`RST_STREAM`); here the batch is refused with `INVALID_ARGUMENT` "invalid table reference: ".
- Fuzzed against Java 42.9, `harness fuzz --ops aj --seeds 3000 --keep-going`: 2985 seeds clean, 15 with differences, all of them values of an `aj` after a step of a ticking table, none at step 0. They are of the engine, not of the handler, and they are open:
  - A NaN stamp, both tables the same ticking table, rule `>` (seeds 39, 257, 1319, 2619; 1774 is close): after a row with a NaN stamp is added, Java joins a NaN left row with the new NaN right row. Java's own static answer for the same rows does not (`RS > RS` over stamps 1.0, NaN, NaN gives null, 1, 1 on both servers), and that is what Oxhaven gives after the step.
  - A chain of three or four `aj` whose last join has a refreshing left table that itself depends on the right table (seeds 2, 465, 540, 675, 1371, 1427, 1735, 2110, 2669, 2873): after a row is added to or deleted from the right table, Java's result keeps the match it had (no row after an add, the deleted row's values after a delete in seed 1371, the same row after its stamp changed in seed 540), where Oxhaven has the row the rule selects from the tables as they are after the step.
  - Each seed shrinks with `harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops aj --seeds 1 --seed <seed>`.
- One implementation, for every combination of static and refreshing tables and with or without exact-match columns: an ordered map from the exact-match key to the left rows and the right rows that have it, each ordered by stamp and then by row key. The result has the left table's row set, and its added columns read the right table through a `WritableRowRedirection`. Java has six implementations over hash tables of segmented sorted arrays. The order of work in a cycle is Java's: the left table's removes and shifts, the right table (removes, shifts, adds, modifies), the left table's adds. Where Java walks the left rows after each right row it removes, shifts, inserts or modifies, this looks up again every left row between a stamp the right table's change touched and the next right stamp.
- Stamps order as Java's stamp kernels order them: null is the least value and NaN the greatest, `-0.0` equals `0.0`, a string orders by its UTF-16 code units. A stamp column may be of any of the ten types of `ColumnType`.
- What Java does, and this does too, that is not obvious:
  - A null stamp is a value: under `>=` and `<=` a left row with a null stamp is joined with a right row with a null stamp.
  - Of several right rows with one stamp, `aj` takes the last in the right table's order and `raj` the first.
  - The stamp columns must have one type after `Boolean` is read as `byte` and `Instant` as `long`, so an `Instant` stamp joins a `long` stamp.
  - Exact-match columns of different types are refused only when a right row is read (Java's `ClassCastException`): at once when the right table has rows, and otherwise the result fails in the cycle in which the first right row arrives.
  - A static left table without rows gives a static table without rows, also when the right table is refreshing, and nothing is checked but the names of the added columns.
  - The added columns are the right column of every match that is not the name of a left column, then the additions; an addition that renames such a column takes its place. With no additions given, the right columns added are those not named like the *left* column of a match.
  - The result has no attributes and is not flat.
  - With two refreshing tables and exact-match columns, when a key that has had left rows gets its first right rows, every left row of the key is reported as modified, whether or not its right row changed (`processInitial` in `BucketedChunkedAjMergedListener#process`).
- Not compared with Java, in the updates only: a right row removed and another added at its row key in one cycle. Here the left rows that read it are reported as modified. An input table cannot make this change, so it is not in the recordings.
- `unported!`: a stamp or exact-match column of a type that is not one of the ten (`AsOfJoinHelper#asOfJoin`), and a stamp column stored as an Arrow type other than theirs (`StampKernel#makeStampKernel`).
- Tests: `ops/asof/tests.rs` (the static rules, the refusals, each incremental case with the exact update), `ops/asof/random.rs` (random updates over 40 seeds of both tables, of the left only and of the right only, for the four rules on nine pairs of exact-match columns and stamp column, each result checked every cycle against the join of static copies), `ops/asof/corpus.rs` (the `aj` and `raj` results of `oracle/corpus`, and the fixtures). Every ticking test has the consistency checker attached.
- `ops/asof/fixtures` holds nine scenarios in the oracle's format and their Java results, recorded with `ops/snapshot/fixtures/record.py`: every refusal, the four rules and the added columns, the columns added when none are named, stamps and exact-match columns of every type, a ticking right table, a ticking left table, both ticking, and exact-match columns of different types that fail in a cycle. The ticking scenarios record Java's updates too, and the updates here are the same. An operation of a fixture names its tables twice, as `left` and `right` for `record.py` and as `source` and `set` for the replay of `ops/snapshot/testing.rs`.
- Tests of the handler: `table/ops/asof.rs` (the three parsers, on strings whose Java answer was observed) and `table/tests/handlers/asof.rs` (the handlers called over gRPC, one-shot and in a batch). Each fails under at least one of sixteen changes made to the handler to try them.
- Gate: `cargo test -p oxhaven-engine asof` passes. With the handler, `oracle/bin/harness replay --url "$OXHAVEN_URL" --ops aj,raj` goes from 0 of 6 scenarios clean to 5 of 6 (the sixth, `error_types_and_matches`, still lacks cross join and `update_by`), and the whole corpus from 48 of 83 clean (883 mismatches) to 53 (825). The fuzz part of the gate does not pass: see the differences above.
