## Notes

- Built: the engine side. `oxhaven_engine::ops::asof` has `as_of_join(left, right, exact, as_of, add)`, and `aj` and `raj`, which are `as_of_join` after the check of `AsOfJoinMatch#parseForAj` and `#parseForRaj` that the rule is one of theirs. Each goes from two `Arc<dyn Table>` to `Result<Arc<dyn Table>, AsOfJoinError>`, with `AsOfMatch` (left stamp column, `AsOfRule`, right stamp column) and the `JoinMatch` and `JoinAddition` of the natural join. The variants of `AsOfJoinError` name the Java exception; Java reports every one of them as `INVALID_ARGUMENT` (`fixtures/asof_refusals.json`). The legacy `AsOfJoinTablesRequest` is the same operation.
- Not built: the gRPC handler (`crates/oxhaven-server/src/table/ops/asof.rs`) and with it the reading of the match strings (`AsOfJoinMatch#parse`). The tests read the strings of the fixtures with a parser of their own.
- One implementation, for every combination of static and refreshing tables and with or without exact-match columns: an ordered map from the exact-match key to the left rows and the right rows that have it, each ordered by stamp and then by row key. The result has the left table's row set, and its added columns read the right table through a `WritableRowRedirection`. Java has six implementations over hash tables of segmented sorted arrays. The order of work in a cycle is Java's: the left table's removes and shifts, the right table (removes, shifts, adds, modifies), the left table's adds. Where Java walks the left rows after each right row it removes, shifts, inserts or modifies, this looks up again every left row between a stamp the right table's change touched and the next right stamp.
- Stamps order as Java's stamp kernels order them: null is the least value and NaN the greatest, `-0.0` equals `0.0`, a string orders by its UTF-16 code units. A stamp column may be of any of the ten types of `ColumnType`.
- What Java does, and this does too, that is not obvious:
  - A null stamp is a value: under `>=` and `<=` a left row with a null stamp is joined with a right row with a null stamp.
  - Of several right rows with one stamp, `aj` takes the last in the right table's order and `raj` the first.
  - The stamp columns must have one type after `Boolean` is read as `byte` and `Instant` as `long`, so an `Instant` stamp joins a `long` stamp.
  - Exact-match columns of different types are refused only when a right row is read (Java's `ClassCastException`): at once when the right table has rows, and otherwise the result fails in the cycle in which the first right row arrives.
  - A static left table without rows gives a static table without rows, also when the right table is refreshing, and nothing is checked but the names of the added columns.
  - The added columns are the right column of every match that is not the name of a left column, then the additions; an addition that renames such a column takes its place. With no additions given, the right columns added are those not named like the *left* column of a match.
  - The result has no attributes and is not flat.
  - With two refreshing tables and exact-match columns, when a key that has had left rows gets its first right rows, every left row of the key is reported as modified, whether or not its right row changed (`processInitial` in `BucketedChunkedAjMergedListener#process`).
- Not compared with Java, in the updates only: a right row removed and another added at its row key in one cycle. Here the left rows that read it are reported as modified. An input table cannot make this change, so it is not in the recordings.
- `unported!`: a stamp or exact-match column of a type that is not one of the ten (`AsOfJoinHelper#asOfJoin`), and a stamp column stored as an Arrow type other than theirs (`StampKernel#makeStampKernel`).
- Tests: `ops/asof/tests.rs` (the static rules, the refusals, each incremental case with the exact update), `ops/asof/random.rs` (random updates over 40 seeds of both tables, of the left only and of the right only, for the four rules on nine pairs of exact-match columns and stamp column, each result checked every cycle against the join of static copies), `ops/asof/corpus.rs` (the `aj` and `raj` results of `oracle/corpus`, and the fixtures). Every ticking test has the consistency checker attached.
- `ops/asof/fixtures` holds nine scenarios in the oracle's format and their Java results, recorded with `ops/snapshot/fixtures/record.py`: every refusal, the four rules and the added columns, the columns added when none are named, stamps and exact-match columns of every type, a ticking right table, a ticking left table, both ticking, and exact-match columns of different types that fail in a cycle. The ticking scenarios record Java's updates too, and the updates here are the same. An operation of a fixture names its tables twice, as `left` and `right` for `record.py` and as `source` and `set` for the replay of `ops/snapshot/testing.rs`.
- Gate: `cargo test -p oxhaven-engine asof` passes. The two `oracle/bin/harness` commands were not run: there is no server for these operations yet.
