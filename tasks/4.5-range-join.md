## Scope

`range_join` with its start and end match rules and group aggregations over the matched range. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine rangejoin && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops range_join && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops range_join --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness has no `range_join` operation yet: the harness part of this gate stops with exit code 2 and says so. It needs an oracle task (scenario format, runner, corpus, fuzzer) before this task can close.

## Notes

Engine on branch `task/4.5-range-join`; the result table, the gRPC handler and the server runs on branch `task/4.5b-range-join-tables`.

- The module is `crates/oxhaven-engine/src/ops/range_join/` (not `rangejoin/` as under Owns), declared in `ops/mod.rs`, and the handler is `crates/oxhaven-server/src/table/ops/range_join.rs`. The engine part of the gate is therefore `cargo test -p oxhaven-engine range_join`; the filter `rangejoin` matches no test.
- Java has no incremental path: `RangeJoinOperation` refuses a refreshing table on either side, and so does this port, with Java's message. The consistency checker has nothing to attach to.
- What exists: the range match (`RangeJoinMatch`, its text form and refusals), every refusal of `RangeJoinOperation` in Java's order (refreshing, exact matches, range match, a range column that is a vector or an array, aggregations, right rows out of order, missing group input), the range search for all nine pairs of rules over byte, short, int, long, char, float, double, Boolean, Instant and String range columns, and the result: a static table over the left table's rows whose group outputs are `GroupColumn` sources of type `ColumnType::Vector` of the right column's type, which is what Java 42.9 reports for every element type (an `ObjectVector` of vectors for the group of a vector column).
- The handler serves `RangeJoinTables` and the operation inside `Batch`, with the checks of `RangeJoinGrpcImpl#validateRequest` in Java's order and with its messages. It uses `validate_aggregation`, taken out of `Aggregate::validate` in `table/ops/aggregate.rs`.
- Two `unported!` remain: a range column of a type outside the list above (`RangeJoinOperation#validateRangeMatchColumns`), and a range that ends before it starts (`RangeAggregateColumnSource#get`; the search never produces one).
- Tests: `testdata/scenarios` holds seven scenarios recorded from Java 42.9 by `testdata/record.py` into `testdata/corpus` (80 tables and 37 refusals compared, `of_a_range_join` among them, plus the 9 tables and 8 refusals of the oracle's own scenario through the shared replay). `range_join_rule_pairs` is sent with the separate fields of the request, since the text cannot name `<-` with a strict end or `->` with a strict start. The handler has five gRPC tests in `table/tests/handlers/range_join.rs`, whose expected vectors are what Java answered.
- Against servers: `harness replay --ops range_join` is clean (2 scenarios), and the two lines of `oracle/replay-baseline.json` are promoted. `harness fuzz` does not generate `range_join`, so that part of the gate cannot run; instead `harness diff --a java --b oxhaven` over `testdata/scenarios` is clean (7 scenarios), and 1500 random range joins sent to both servers gave the same answers. Of 301 answers to raw requests (every validation case, alone and in a batch) 297 are the same; the others are the two differences below and two client timeouts on references that never resolve.
- Java behavior found by recording and kept:
  - With `->`, a row whose end falls between two right values gets no following row when another left row of the same bucket, in the same read of 2048 left rows, ends exactly at the right value before the gap (`processRangeEndsGreaterThanEqualAllowFollowing`). The result depends on the left table's size and order.
  - `-0.0` and `0.0`: the binary search tells them apart and the comparison at the walk's position does not, so which right rows a zero bound finds depends on where the walk stands.
  - String range columns order by UTF-16 code unit.
  - Right rows are checked for order only in buckets some left row has; with an empty left table nothing is checked.
  - A missing left end column is reported as "left start column".
  - A group output named like a left column, or like an earlier output, takes its place.
- Differences from Java:
  - An exact match column that is a vector or an array: Java joins on it, here the request fails with UNIMPLEMENTED (`TypedHasherFactory#makeNaturalJoin`, no hashing of list keys).
  - A group of a column that is a vector of strings (the result of another range join): Java returns the table, here describing its schema stops at `unported: BarrageUtil#arrowFieldFor` for `Vector(Vector(String))`. Vectors of vectors of numbers work.
  - Unknown fields of the request cannot be refused: the generated types drop them.
  - Messages that Java only logs carry no `rangeJoin[...]` description prefix, name column types by `ColumnType`, and name an unsupported aggregation by its protocol name. The client sees the same status and "Details Logged w/ID" text either way.
  - The limit on a bucket's size (`MAX_ARRAY_SIZE`) is not ported; no memoization and no parallel jobs.
