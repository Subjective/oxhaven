## Scope

`range_join` with its start and end match rules and group aggregations over the matched range. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine rangejoin && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops range_join && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops range_join --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness has no `range_join` operation yet: the harness part of this gate stops with exit code 2 and says so. It needs an oracle task (scenario format, runner, corpus, fuzzer) before this task can close.

## Notes

Engine side only, on branch `task/4.5-range-join`. No gRPC handler, and nothing run against a server.

- The module is `crates/oxhaven-engine/src/ops/range_join/` (not `rangejoin/` as under Owns), declared in `ops/mod.rs`. The engine part of the gate is therefore `cargo test -p oxhaven-engine range_join`; the filter `rangejoin` matches no test.
- Java has no incremental path: `RangeJoinOperation` refuses a refreshing table on either side, and so does this port, with Java's message. The consistency checker has nothing to attach to.
- What exists: the range match (`RangeJoinMatch`, its text form and refusals), every refusal of `RangeJoinOperation` in Java's order (refreshing, exact matches, range match, aggregations, right rows out of order, missing group input), the range search for all nine pairs of rules over byte, short, int, long, char, float, double, Boolean, Instant and String range columns, and the result at a private seam: `grouped::Joined`, whose `GroupColumn::chunk` gives the Arrow list array of a group output for any rows of the left table.
- What waits for list column types in `oxhaven-contracts`: a result with a group output. `Joined::into_table` stops with `unported!("io.deephaven.engine.table.impl.sources.aggregate.AggregateColumnSource#forRangeJoin")`. With no group output (no aggregations, or `group` of no columns) `range_join` returns a real static table. Once the types exist: implement `ColumnSource` for `GroupColumn`, build the table in `into_table`, let the shared replay (`ops/oracle.rs`) compare the nine tables of `oracle/scenarios/static/range_join.json` that it now reports as not run, run `range_join_refusals/of_a_range_join` (a range join of a range join's result), then the gRPC handler and the harness part of the gate.
- Two more `unported!`: a range column of a type outside the list above (`RangeJoinOperation#validateRangeMatchColumns`; no such `ColumnType` exists today), and a range that ends before it starts (`RangeAggregateColumnSource#get`; the search never produces one).
- Tests: `testdata/scenarios` holds seven scenarios recorded from Java 42.9 by `testdata/record.py` into `testdata/corpus` (79 tables and 37 refusals compared at the seam, plus the 9 tables and 8 refusals of the oracle's own scenario). `range_join_rule_pairs` is sent with the separate fields of the request, since the text cannot name `<-` with a strict end or `->` with a strict start.
- Java behavior found by recording and kept:
  - With `->`, a row whose end falls between two right values gets no following row when another left row of the same bucket, in the same read of 2048 left rows, ends exactly at the right value before the gap (`processRangeEndsGreaterThanEqualAllowFollowing`). The result depends on the left table's size and order.
  - `-0.0` and `0.0`: the binary search tells them apart and the comparison at the walk's position does not, so which right rows a zero bound finds depends on where the walk stands.
  - String range columns order by UTF-16 code unit.
  - Right rows are checked for order only in buckets some left row has; with an empty left table nothing is checked.
  - A missing left end column is reported as "left start column".
  - A group output named like a left column, or like an earlier output, takes its place.
- Differences from Java: messages carry no `rangeJoin[...]` description prefix and name column types by `ColumnType`; `RangeJoinMatch::parse` does not refuse Java reserved words as column names; the limit on a bucket's size (`MAX_ARRAY_SIZE`) is not ported; no memoization and no parallel jobs.
