## Scope

`update_by`: cumulative operations first (sum, min, max, product, forward fill, count), then rolling windows by ticks and by time, then exponential moving operations and delta. Gate each group separately. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine updateby && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops update_by --within update_by,input_table && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops update_by --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness does not cover update-by operations other than `cum_sum` yet, so this gate does not check it; that needs an oracle task first.

## Notes

- `ops::update_by::update_by(parent, operations, by)` is `Table#updateBy`. Ported: the
  cumulative sum, product, minimum, maximum, forward fill and delta; the rolling sum,
  average, minimum, maximum, count and product over windows in rows or in time; the
  exponential moving average, sum, minimum and maximum decaying by ticks or by time, with
  every `BadDataBehavior`; and (branch `task/4.6c-update-by-rest`) the rolling standard
  deviation and weighted average and the exponential moving standard deviation.
  `unported!`: rolling formula and count-where, and cumulative count-where.
- The rolling group (branch `task/4.6d-update-by-group-count`, `group.rs`) stores its
  vectors where Java reads the input column through a slice of the bucket's row set; the
  values are the same at the same times. Over rows, a window that holds no row is an
  empty vector, also where the other rolling operators fail Java's assertion. In time, the
  vector holds the rows of the window that have a timestamp, and a row without one has a
  null. Java looks up the rows it computes among the rows with a timestamp and fails when
  one is missing, so a rolling group in time fails (static: refused; ticking: the table
  fails) when it computes a row without a timestamp that stands before a row with one;
  rows without one that come last, or are all there is, are answered. Java's test depends
  on the kind of row set it holds (`Stamped::positions_exist`), and on row keys, which are
  not Java's here for a ticking table. The count-where operators were not started.
- `fixtures/java_update_by_group.json` (`fixtures/record_java_update_by_group.py`) holds
  the recordings of the rolling group, with two more sections: `stamped`, the timed table
  with a timestamp in every row, and `burst`, where 70 and 200 rows enter a window in
  time at once. `burst` also records the rolling sum, average, product, standard
  deviation and weighted average, and fails if the initial capacity of either ring buffer
  is changed. With buckets its floating point results are compared under PARITY.md A1:
  Java keeps an operator's buffer per thread and across buckets, at the capacity it grew
  to, so the order it multiplies a bucket's values in depends on the buckets the thread
  computed before, and one recorded product differs in its last bits.
- An exponential moving average in time with a decay of 5 nanoseconds differs from Java
  in the last bit of one cell of the `stamped` table (compared under A1 there); every
  other recorded exponential result is still reproduced bit for bit.
- The exponential moving standard deviation differs from Java on purpose in one place. Java
  seeds a run that starts inside a bucket with the square of the previous result as the
  variance, which is not the variance it computed, so Java's own incremental results differ
  in the last bits from a static recompute. Here the average and the variance after each
  row are kept beside the result column and a run is seeded with them, so a result does
  not depend on the updates that led to it and the consistency checker holds. Against
  Java's results after an update this is a difference within PARITY.md A1 (`corpus.rs`
  compares those columns of the ticking fixtures under A1, everything else bit for bit).
- An exponential moving operator in time that poisons on NaN fails, as in Java, with
  "Timestamp values in UpdateBy operators must not decrease" when a NaN comes before any
  other value: the poisoned state has no timestamp, and the time since it is negative.
- `fixtures/java_update_by_rest.json` (`fixtures/record_java_update_by_rest.py`) holds the
  recordings for the operators of `task/4.6c-update-by-rest`, in the same sections.
- Within a bucket, non-null timestamps must not decrease; the whole bucket is checked on
  every update. Java checks only the rows added (and re-stamped) in one update, so a
  decrease across updates fails here with Java's message where Java computes something
  undefined.
- `fixtures/java_update_by.json` is recorded from Java 42.9 by
  `fixtures/record_java_update_by.py` (sections `static`, `long`, `timed`, `ticking`) and
  compared bit for bit by `corpus.rs`; `oracle_corpus.rs` replays the oracle scenarios that
  only need `update_by`, comparing every result column but those of the `unported!`
  operators.
- The gRPC handler is `crates/oxhaven-server/src/table/ops/update_by.rs` (branch
  `task/4.6b-update-by-handler`; the file is named like the engine module, not `updateby.rs`
  as under Owns). It reads the request in Java's order and answers the request checks of
  `UpdateByGrpcImpl#validateRequest` with Java's messages; 78 raw requests gave the same
  status, message and result on Java 42.9 and here. The control options are checked and
  then have no effect.
- The handler needed no change for the rolling standard deviation and weighted average
  and the exponential moving standard deviation: 917 requests with them gave the same
  result, bit for bit, or the same status on Java 42.9 and here.
- A request with an operator the engine has not ported is answered `UNIMPLEMENTED` by the
  service's `unported!` guard, also where Java would have refused it for another reason
  (a filter or formula its `ColumnExpressionValidator` rejects, a column the table lacks
  in an operation after the unported one). The handler makes no formula check of its own:
  the operators with formulas are all unported.
- The engine reads its column pairs with ASCII names; a pair with any other Java
  identifier is answered `UNIMPLEMENTED` by the handler.
- The recorded scenarios `update_by_cumulative`, `update_by_rolling_tick`,
  `update_by_time_and_ema` and `ticking_update_by_full` each have tables with an unported
  operator among the ported ones (12 tables in all: a rolling group, formula or
  count-where, or a cumulative count-where), so the replay cannot go clean on them. With
  those operators taken out, the four scenarios are clean against live Java. With the
  rolling group ported, `ticking_update_by_full` and `update_by_rolling_tick/of_special`
  are clean, and 10 tables of the other three scenarios still have a count-where or a
  formula.
