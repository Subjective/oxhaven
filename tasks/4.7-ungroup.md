## Scope

Array-valued columns as Arrow lists, the group aggregation that produces them, and `ungroup`. Adding list types to `ColumnType` needs a contract-change pull request first. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine ungroup && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops ungroup && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops ungroup --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness has no `ungroup` operation yet: the harness part of this gate stops with exit code 2 and says so. It needs an oracle task (scenario format, runner, corpus, fuzzer) before this task can close.

## Notes

- Done and in review: the engine side of `ungroup`, static and incremental, as far as it can go without array columns. Not started: array columns themselves (`ColumnType` has no list type, which is a contract change), the `group` aggregation and `group_by` that produce them, and the gRPC handler (`crates/oxhaven-server/src/table/ops/ungroup.rs`). The task cannot close before the contract change.
- `oxhaven_engine::ops::ungroup::ungroup(source, null_fill, columns)` is the operation. Since no column of a table can be an array today, it answers what Java answers for such tables: without `columns` it returns the source itself, and a named column is refused, the first bad one in the order asked: `UngroupError::NoSuchColumn` ("Unknown column names [..], available column names are [..]") or `UngroupError::NotAnArray` ("Column X is not an array or Vector"). Both are `INVALID_ARGUMENT` in the recorded corpus, as is `UngroupError::SizesDiffer` (`group_by_ungroup/uneven_strict`).
- Everything behind that is written and tested against a private trait, `sources::ArrayColumn` (the sizes of the arrays at some rows, and elements by row and offset, now or as of the previous cycle), which only tests implement. It is the seam for list columns, not a contract. `operator::ungroup_arrays` takes such columns.
- `unported!`: `io.deephaven.engine.table.impl.sources.UngroupedColumnSource#getColumnSource` (`arrays_of` in `mod.rs`: the one function that turns a column of a table into an `ArrayColumn`), and `io.deephaven.engine.table.impl.UngroupOperation#UngroupOperation` (`is_array` in `mod.rs`, for a `ColumnType` this module does not know, so that a list type added later is not silently treated as "not an array"). Neither can be reached with the column types there are.
- Contract change needed, in `crates/oxhaven-contracts/src/schema.rs`: list variants of `ColumnType` whose `arrow_type()` is `List` of the element's Arrow type, with a nullable item field named `""` as in the recorded files. The recordings show that the Deephaven type must tell a vector from an array: `group_by` columns carry `deephaven:type` `io.deephaven.vector.IntVector`, `DoubleVector`, `FloatVector` or `ObjectVector` with `deephaven:componentType` `int`, `double`, `float`, `java.lang.Boolean`, `java.time.Instant`; PARITY.md "Wire representation" also has Java arrays (`int[]`) as `List`. So something like `Vector(Box<ColumnType>)` and `Array(Box<ColumnType>)`. No new trait is needed: `ColumnSource::chunk`, `prev_chunk` and `chunk_by_keys` of such a column return a `ListArray`, a null cell being a null array, and `ArrayColumn` is then one implementation over that (sizes from the offsets, elements with `take`). `WritableSource` stores Arrow arrays of any type already. What else matches on `ColumnType` and needs a list arm: `oxhaven-testkit` (`RandomUpdates::values`), `ops/oracle.rs` (`column_type`, `cells`, and `same_cells` for the element-wise float rule), `oxhaven-server/src/schema.rs` (the `deephaven:type` and `componentType` metadata).
- Ported from `UngroupOperation`: the base (`determineRequiredBase`, minimum 10), the row keys (`getUngroupRowset` with its key overflow check on the last row), sizes read back from the result's row set (`computeSizeFromResultRowset`), `computeMaxSize` with and without `nullFill` including which difference is reported (chunks of 1024 rows, then column order) and its message, and the listener: `clearAndRecompute` when the parent removed every row it had (the base goes back to the minimum), `evaluateAdded`, `evaluateRemoved`, `evaluateModified` with its three ways to get the sizes, `updateRowsetForRow`, `processShifts`, `rebase` and its `ShiftWrapper`, the identity modified-column transformer, the blink attribute. Columns: `BitShiftingColumnSource` (`sources::Repeated`) and `UngroupedColumnSource` (`sources::Elements`), with the previous base for previous values.
- Java behavior kept on purpose: in a cycle whose added rows need a larger base, an array column modified alone is not compared with the unmodified ones, so a size that differs goes unnoticed and the row keeps its number of elements (`UngroupListener#onUpdate`, the branch "cannot increase base when we have not modified all the arrays"). The whole slot of a row is checked when the row is added and when it is removed, not when it shifts or the base grows, so a row can move into the last slot and then fail the table when removed. Both have a test.
- Differences from Java: where Java moves keys without a check (shifts, a growing base) and the keys would wrap, the result fails with the key overflow error instead of holding wrong keys; a modified row whose keys would be negative fails with that error instead of Java's assertion text. The previous base is the current one as soon as the graph is idle (the `ColumnSource` contract), where Java keeps answering with the old base until the next cycle starts. Java's `int` arithmetic for slots of `1 << 31` keys and more (`rebase`, the ungrouped sources' offset mask) is 64-bit here. Not ported: the initial result from the parent's previous values (`usePrev`; `QueryTable::derive` does not build inside a cycle), the `intSize` limit of 2^31 parent rows, memoization, `RowKeyAgnosticChunkSource` pass-through, the configuration properties for the minimum base and chunk size (constants).
- Tests (`cargo test -p oxhaven-engine ungroup`, 48 tests): `keys.rs` (bases, slots, overflow, sizes read back, shifts, rebase), `tests.rs` (the public refusals; static results; each incremental case with its exact update: add, remove, modify of an array and of another column, grow, shrink, shift, shift with modify, rebase by add and by modify, all at once, restart, no visible change, parent failure, sizes that differ in an added or modified row, null fill, blink; and random updates over 200 seeds each for one column, two columns with null fill and two columns of equal sizes, all with `ConsistencyChecker::attach_with_recompute` on the stepped graph), `corpus.rs`.
- Corpus: through the shared replay, `group_by_ungroup/no_arrays` and `group_by_ungroup/not_an_array` are compared; the other 13 `ungroup` results are not run because their sources come from `group_by`, `agg_by` with `group`, or a `natural_join` of those. Around the replay, `corpus.rs` ungroups the tables Java recorded for those sources (their list columns as `ArrayColumn`s of a static table) and compares with the recorded `ungroup`: `back`, `back_two`, `back_all`, `back_empty`, `back_some`, `back_one`, `uneven_filled`, `uneven_strict` (refused), `uneven_one`, `agg_back`, and `back` and `back_ids` of `ticking_group_ungroup_head_by` at all 9 steps; names, types, row count and cells, not attributes, and a list column that stays a list by name only. Not run there: `group_by_ungroup/unknown` (the name check is in the public function, which cannot see stand-ins). The updates of a ticking `ungroup` are not compared with Java anywhere: the corpus records tables, not updates.
- Gate: `cargo test -p oxhaven-engine ungroup` passes. The two `oracle/bin/harness` commands were not run: there is no server for them.
