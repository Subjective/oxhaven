## Scope

Array-valued columns as Arrow lists, the group aggregation that produces them, and `ungroup`. Adding list types to `ColumnType` needs a contract-change pull request first. Build the static path first and get it through the gate, then the incremental path. Add the gRPC handler for these batch operations. Run every engine test with the consistency checker attached.

## Gate

```bash
cargo test -p oxhaven-engine ungroup && oracle/bin/harness replay --url "$OXHAVEN_URL" --ops ungroup && oracle/bin/harness fuzz --a "$JAVA_URL" --b "$OXHAVEN_URL" --ops ungroup --seeds 10000
```

`$OXHAVEN_URL` and `$JAVA_URL` are described in `tasks/README.md`. The oracle harness has no `ungroup` operation yet: the harness part of this gate stops with exit code 2 and says so. It needs an oracle task (scenario format, runner, corpus, fuzzer) before this task can close.

## Notes

- Done and in review: `ungroup` of vector and array columns, static and incremental, and the `Ungroup` gRPC handler (one-shot and in `Batch`). Not started: the `group` aggregation and `group_by`, which another task adds. Gate: `cargo test -p oxhaven-engine ungroup` passes. `oracle/bin/harness replay --ops ungroup` runs its two scenarios, `group_by_ungroup` and `ticking_group_ungroup_head_by`, and both differ, in the tables that need `group_by` or the other missing handlers. `oracle/bin/harness fuzz --ops ungroup` stops: the fuzzer does not generate `ungroup`.
- `oxhaven_engine::ops::ungroup::ungroup(source, null_fill, columns)` is the operation. Without `columns` every vector and array column is ungrouped, and a source that has none is returned as it is. A named column is refused, the first bad one in the order asked: `UngroupError::NoSuchColumn` ("Unknown column names [..], available column names are [..]") or `UngroupError::NotAnArray` ("Column X is not an array or Vector"); arrays of one row that differ in size without `null_fill` are `UngroupError::SizesDiffer`. A column named twice is ungrouped once, as on the Java server.
- `sources::Lists` reads a vector or array column as `ColumnType::list_element` describes it: the sizes of the cells of some rows from `chunk` or `prev_chunk`, and elements by row and offset from `chunk_by_keys`, a null cell having no elements whatever it spans. One implementation serves every element type and both kinds of list; the ungrouped column has the element's type. It implements `sources::ArrayColumn`, which stays the seam of the operator: `head_by` has another implementation, for the rows it keeps of each group. The stand-ins the tests of this module used are gone.
- Ported from `UngroupOperation`: the base (`determineRequiredBase`, minimum 10), the row keys (`getUngroupRowset` with its key overflow check on the last row), sizes read back from the result's row set (`computeSizeFromResultRowset`), `computeMaxSize` with and without `nullFill` including which difference is reported (chunks of 1024 rows, then column order) and its message, and the listener: `clearAndRecompute` when the parent removed every row it had (the base goes back to the minimum), `evaluateAdded`, `evaluateRemoved`, `evaluateModified` with its three ways to get the sizes, `updateRowsetForRow`, `processShifts`, `rebase` and its `ShiftWrapper`, the identity modified-column transformer, the blink attribute. Columns: `BitShiftingColumnSource` (`sources::Repeated`) and `UngroupedColumnSource` (`sources::Elements`), with the previous base for previous values.
- Java behavior kept on purpose: in a cycle whose added rows need a larger base, an array column modified alone is not compared with the unmodified ones, so a size that differs goes unnoticed and the row keeps its number of elements (`UngroupListener#onUpdate`, the branch "cannot increase base when we have not modified all the arrays"). The whole slot of a row is checked when the row is added and when it is removed, not when it shifts or the base grows, so a row can move into the last slot and then fail the table when removed. Both have a test.
- Differences from Java: where Java moves keys without a check (shifts, a growing base) and the keys would wrap, the result fails with the key overflow error instead of holding wrong keys; a modified row whose keys would be negative fails with that error instead of Java's assertion text. The previous base is the current one as soon as the graph is idle (the `ColumnSource` contract), where Java keeps answering with the old base until the next cycle starts. Java's `int` arithmetic for slots of `1 << 31` keys and more (`rebase`, the ungrouped sources' offset mask) is 64-bit here. Not ported: the initial result from the parent's previous values (`usePrev`; `QueryTable::derive` does not build inside a cycle), the `intSize` limit of 2^31 parent rows, memoization, `RowKeyAgnosticChunkSource` pass-through, the configuration properties for the minimum base and chunk size (constants).
- The handler (`crates/oxhaven-server/src/table/ops/ungroup.rs`) follows `UngroupGrpcImpl#create`, which has no check of its own: each string is read as a column name (`ColumnName#of`) before the engine is asked, and that and every refusal of the engine are exceptions, answered `INVALID_ARGUMENT` with an error id ("Details Logged w/ID '..'"). So the client cannot tell them apart; the name check changes only the logged text. Raw requests sent to both servers (no columns, null fill, an empty table, a ticking table, not an array, unknown, both orders of those, a bad, empty, padded and reserved name, a name twice, no source, no result, neither, an empty reference, a ticket of no route, a batch offset in a one-shot, a bad result ticket, a result ticket used twice; each one-shot and in a batch) answer alike for everything the handler decides. They differ in three answers of the service around it, for every operation: a batch whose operation has no source (Java resets the stream, `CANCELLED`; here `INVALID_ARGUMENT` "invalid table reference: "), the text for a result ticket of no route, and a result ticket used twice (Java an error id, here "export N can only be defined once").
- No operation of the server makes a list column yet: Flight `DoPut` refuses a list field (`BarrageUtil#getDefaultType`), `CreateInputTable` with one is `UNIMPLEMENTED`, and no formula builds an array. So the handler's tests export engine tables with list columns into the session, and no list column was compared with Java through a live Oxhaven server. The comparison with Java is in the engine tests.
- Tests (`cargo test -p oxhaven-engine ungroup`, 56 tests): `keys.rs`; `sources.rs` (the list reading, with a source that answers a null cell spanning elements and previous cells that differ); `tests.rs` (as before, now on real `Vector(Long)` and `Array(Long)` columns: the refusals, static results, each incremental case with its exact update, blink, key overflow, and random updates over 250 or 200 seeds each for one column, two with null fill and two of equal sizes, with arrays of up to ten elements so that the slots grow, all with `ConsistencyChecker::attach_with_recompute` on the stepped graph); `corpus.rs`; `fixtures.rs`. Server: `cargo test -p oxhaven-server ungroup` (5 tests).
- Corpus: through the shared replay, `group_by_ungroup/no_arrays` and `not_an_array`. Around it, `corpus.rs` makes static tables of the tables Java recorded for the sources, with their vector columns, runs the public `ungroup` and compares with the recorded result: all 11 other static results (`uneven_strict` and `unknown` refused with Java's code) and `back` and `back_ids` of `ticking_group_ungroup_head_by` at all 9 steps; names, types (a vector not being an array), row count and cells.
- Fixtures (`fixtures/*.json`, recorded from Java 42.9 by `fixtures/record.py`, replayed by `fixtures.rs`): `static_lists` (arrays of int, long, short, float, double, boolean, String and Instant elements and vectors made with `vec`, null and empty cells, null elements, null fill, four refusals), `arrays_ticking` (two keyed input tables with array columns over 10 steps, six results, one array of 1030 elements that outgrows Java's slots) and `vectors_ticking` (the vectors of a `group_by` of a keyed input over 9 steps, four results). The sources are built from the recording and a ticking one is driven by the updates Java's source delivered, so nothing here needs `group_by`. Compared at every step: the tables, and each update of each result by position (added, removed, modified) with its modified columns. Not covered by a recording: a source that reports only some columns as modified (an input table and `group_by` report all), and a result that fails in a cycle.
- Mutation check of the new code, 22 hand-made mutants (9 in `sources.rs`, 5 in `mod.rs`, 8 in the handler and its registration): 21 killed. The survivor removes the handler's name check, which no client can observe (see above); its function has a unit test.
- Replay against the recordings (`oracle/bin/harness replay`): 83 scenarios, 58 clean, 25 with differences before and after; 687 mismatches before, 685 after (`group_by_ungroup/no_arrays` and `not_an_array`). The baseline line of `group_by_ungroup` is tightened by those two tables. The other `ungroup` results of the two scenarios need `group_by` on the server.
