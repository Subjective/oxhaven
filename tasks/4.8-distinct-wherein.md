## Notes

- Done and in review: `select_distinct`, `where_in` and `where_not_in` in the engine, and the handlers of `SelectDistinct` and `WhereIn`. The notes on `where_in` are at the end.
- `oxhaven_engine::ops::distinct::select_distinct(source, columns)` takes column names. `DistinctError::NoSuchColumn` is the handler's `FAILED_PRECONDITION` ("column(s) not found"); an expression such as `X=I` is refused the same way, as in Java's handler.
- As in Java it is an aggregation without aggregations: a group's row key is its number in the order the keys were first met; the result's rows are the groups that have rows. A new key is appended, a key without rows leaves, a key that comes back takes its old row key and shows the value of the row that first made it (`-0.0` stays `-0.0` when `0.0` brings the key back). Within a cycle the keys of rows whose key changed are met before the keys of added rows, whatever the row order (recorded: `fixtures/select_distinct_changed_before_added.json`). No row is ever reported as modified.
- Recorded and ported: without columns the result has no columns and one row while the source has rows; a column named twice counts once; a static source gives a flat result with the add-only and append-only attributes; an append-only source gives a flat result with those attributes; any other refreshing source a result that is not flat. From the Java source only: an add-only source that is not append-only, and a blink table, of which the result is flat and keeps every key (the oracle has neither).
- Written without `ops::agg`. What a keyed aggregation can share: `keys.rs` (the key of a row as bytes, with Java's equality for null, NaN and the two zeros) and `Groups` in `mod.rs` (group numbers, rows per group, the order of removes, key changes and adds, the downstream added and removed groups). The groups are a `BTreeMap` from key bytes to number: deterministic and plain, not fast.
- No `unported!`. Not ported: array columns as keys (Java refuses them; there is no such `ColumnType`), data indexes, symbol tables.
- Found in `ops::sort` (task 3.3) and fixed on this branch: a modified row whose new sort key comes before its old one but that keeps its neighbours was reported as modified, where Java removes and adds it (`SortListener.TargetComparator` compares the new value with the previous values, the row's own included). The rows of the sort were the same; the order of a `select_distinct` or aggregation of the sorted table was not. `fixtures/select_distinct_of_sort.json` records it and `corpus.rs` tests it; `ops/sort/fixtures/sort_modified_rows.json` records the sort's updates.
- Tests: `tests.rs` (order, every key type, null, NaN, zeros, each incremental case with its update, blink, failure, random updates over 60 seeds against a model with the checker), `corpus.rs` (27 static results, 16 results over 14 steps, and the two fixtures above).
- Gate: `cargo test -p oxhaven-engine distinct` passes. The two `oracle/bin/harness` commands were not run: the harness has no such operation, and there is no server for it.
- Handler (follow-up, branch `task/4.10-join-snapshot-handlers`): `crates/oxhaven-server/src/table/ops/distinct.rs` serves `SelectDistinct`, refusing names that are not columns with `FAILED_PRECONDITION` as Java's handler does. Replay of `select_distinct` from `origin/oracle/more-operations` is clean, and so is the `select_distinct` table of `ticking_select_distinct_where_in`; that scenario's other tables need `where_in`, which has no handler.
- `where_in` (branch `task/4.8b-where-in`): `oxhaven_engine::ops::distinct::{where_in, where_not_in}(left, set, on)` take `JoinMatch`es (left column, set column). `WhereInError::NoSuchColumn` and `MismatchedTypes` are Java's `IllegalArgumentException`s, which its server sends as `INVALID_ARGUMENT`; `UpdateGraphConflict` is two tables of two update graphs.
- As in Java (`QueryTable#whereInInternal`, `DynamicWhereFilter`): a static set table is read once and used as it is; of a refreshing one the `select_distinct` over the set columns is taken and listened to. The set of keys handles removed rows, then modified rows (a row whose key changed leaves its old key and takes its new one), then added rows; a key added twice or removed without being there fails the result. Keys that arrived filter the left rows that did not match again, keys that left those that matched, both everything (the other way round for `where_not_in`), as `FilteredTable#doRefilter` does; a cycle in which only the left table changed is a `where` (`WhereListener#completeUpdate`), which `ops::filter::filtered_update` now serves to both. When both change in one cycle, the left table's rows are filtered first and the refilter reports the rest.
- Key equality is Java's: null equals null, NaN equals NaN, `-0.0` equals `0.0`. A Boolean column matches a byte column (true 1, false 0, null the null byte) and an Instant column a long column, because Java compares the reinterpreted columns; every other pair of different types is refused. Without match columns every row of the left table matches while the set table has rows (engine only: Java's handler refuses a request without columns, and so does this one).
- Attributes: the left table's blink attribute; add-only and append-only only when the set table is static; never flat.
- Recorded from Java 42.9 and ported: `fixtures/where_in_static.json` (55 results: every key type, null, NaN, zeros, two columns, renamed columns, Boolean against byte, Instant against long, no columns, unknown columns and mismatched types on either side) and `fixtures/where_in_ticking.json` (29 results over 20 steps, with the updates of 13 of them). `corpus.rs` also replays the `where_in` tables of the oracle's `where_in` and `ticking_select_distinct_where_in` scenarios. From the Java source only: a blink left table with a ticking set table, and a set-table row that changes its key without the `select_distinct` in between (Java always puts it in between; `where_in_tests.rs` tests the code path).
- One `unported!`: `key_class` for a `ColumnType` this crate does not know (`DynamicWhereFilter#beginOperation`). Not ported: data indexes and partitioning columns of the left table (there are no such tables).
- `ops/snapshot/testing.rs` (shared test code, outside this task's paths): `compare_updates` compares recorded updates by position, so that results whose row keys are not positions can be compared, and leaves out updates that only shift, on both sides (PARITY A4: row keys are not compared). It no longer requires row keys to be positions.
- Handler: `crates/oxhaven-server/src/table/ops/distinct.rs` serves `WhereIn` with the checks of `WhereInGrpcImpl#validateRequest` in its order (`left_id`, `right_id`, no `columns_to_match`, then the two references); a match that does not parse (`JoinMatch#parse`) and every engine refusal are `INVALID_ARGUMENT`, as recorded.
- Tests: `where_in_tests.rs` (19 tests with the checker and a recompute: static, key types, refusals, each incremental case with its update, both tables in one cycle, a failed parent, random updates over 90 seeds against a model), `corpus.rs` (above), `crates/oxhaven-server/src/table/tests/handlers.rs` (three tests) and a unit test of `join_match`. Mutations: 30 of the engine (27 killed; the three that survive change nothing that can be observed: removing rows from a set they are not in, filtering modified rows when no key column changed, and refiltering when the set of keys did not change) and 15 of the handler (all killed).
- Replay against the server of this branch: `oracle/bin/harness replay --ops where_in` 2 scenarios, 2 clean. The whole corpus went from 47 clean and 35 with differences (827 mismatches) to 49 clean and 33 with differences (767 mismatches), 1 not run, before `origin/main` was merged; `where_in` and `ticking_select_distinct_where_in` are now `clean` in `oracle/replay-baseline.json`, as the replay gate asked. `oracle/bin/harness diff` of Java against this server over the two fixtures, as scenarios: no mismatch. `harness fuzz` was not run: it has no `where_in` operation.
