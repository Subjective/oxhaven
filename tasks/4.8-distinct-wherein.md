## Notes

- Done and in review: the engine side of `select_distinct`. Not started: `where_in` and `where_not_in`, and the gRPC handler (`crates/oxhaven-server/src/table/ops/distinct.rs`).
- `oxhaven_engine::ops::distinct::select_distinct(source, columns)` takes column names. `DistinctError::NoSuchColumn` is the handler's `FAILED_PRECONDITION` ("column(s) not found"); an expression such as `X=I` is refused the same way, as in Java's handler.
- As in Java it is an aggregation without aggregations: a group's row key is its number in the order the keys were first met; the result's rows are the groups that have rows. A new key is appended, a key without rows leaves, a key that comes back takes its old row key and shows the value of the row that first made it (`-0.0` stays `-0.0` when `0.0` brings the key back). Within a cycle the keys of rows whose key changed are met before the keys of added rows, whatever the row order (recorded: `fixtures/select_distinct_changed_before_added.json`). No row is ever reported as modified.
- Recorded and ported: without columns the result has no columns and one row while the source has rows; a column named twice counts once; a static source gives a flat result with the add-only and append-only attributes; an append-only source gives a flat result with those attributes; any other refreshing source a result that is not flat. From the Java source only: an add-only source that is not append-only, and a blink table, of which the result is flat and keeps every key (the oracle has neither).
- Written without `ops::agg`. What a keyed aggregation can share: `keys.rs` (the key of a row as bytes, with Java's equality for null, NaN and the two zeros) and `Groups` in `mod.rs` (group numbers, rows per group, the order of removes, key changes and adds, the downstream added and removed groups). The groups are a `BTreeMap` from key bytes to number: deterministic and plain, not fast.
- No `unported!`. Not ported: array columns as keys (Java refuses them; there is no such `ColumnType`), data indexes, symbol tables.
- Found in `ops::sort` (task 3.3) and fixed on this branch: a modified row whose new sort key comes before its old one but that keeps its neighbours was reported as modified, where Java removes and adds it (`SortListener.TargetComparator` compares the new value with the previous values, the row's own included). The rows of the sort were the same; the order of a `select_distinct` or aggregation of the sorted table was not. `fixtures/select_distinct_of_sort.json` records it and `corpus.rs` tests it; `ops/sort/fixtures/sort_modified_rows.json` records the sort's updates.
- Tests: `tests.rs` (order, every key type, null, NaN, zeros, each incremental case with its update, blink, failure, random updates over 60 seeds against a model with the checker), `corpus.rs` (27 static results, 16 results over 14 steps, and the two fixtures above).
- Gate: `cargo test -p oxhaven-engine distinct` passes. The two `oracle/bin/harness` commands were not run: the harness has no such operation, and there is no server for it.
- Handler (follow-up, branch `task/4.10-join-snapshot-handlers`): `crates/oxhaven-server/src/table/ops/distinct.rs` serves `SelectDistinct`, refusing names that are not columns with `FAILED_PRECONDITION` as Java's handler does. Replay of `select_distinct` from `origin/oracle/more-operations` is clean, and so is the `select_distinct` table of `ticking_select_distinct_where_in`; that scenario's other tables need `where_in`, which has no handler.
