## Notes

- In review: the engine side. Not done: the gRPC handler (`crates/oxhaven-server/src/table/ops/snapshot.rs`).
- `oxhaven_engine::ops::snapshot` has `snapshot(base)` and `snapshot_when(base, trigger, &SnapshotWhenOptions)`, the options being the three flags and the stamp columns of the request. `StampColumn::parse` reads a stamp column string (`Name` or `New=Old`) as Java's `JoinAddition.parse` and name check do. The variants of `SnapshotError` say which status the Java server answers with: `Unsupported` is `UNIMPLEMENTED` (history with initial or incremental), `InvalidName`, `NoSuchColumn` and `ColumnConflict` are `INVALID_ARGUMENT`.
- `plain.rs`: `snapshot` is a flat static copy. `snapshot_when` without incremental or history copies the whole base at every update of the trigger (every row removed, every row added), stamped with the trigger's last row, or with nulls when the trigger is empty. The base is a dependency, not a parent: its failure does not fail the result. A static trigger gives a static result.
- `incremental.rs`: the result has the base's row keys and is not flat. Both tables refreshing: the base's updates are composed until the next trigger, then only the changed rows are copied and stamped. Two things Java does that look like mistakes are kept, both recorded: the first comparison of row sets (taken when the composed update shifts rows or removes and adds one row key) is against an empty row set, so it stamps every row again and removes none, and rows the base deleted stay; and stamps are never cleared, so with an empty trigger a row added at a row key used before shows the old stamp. Where Java then reports a row the result already has as added, this reports it as modified.
- `history.rs`: every trigger row appends a copy of the base, stamp columns first. The trigger must be append-only; any other update fails the result. A base column with the name of a stamp column takes its place, and with another type the request succeeds or fails by what Java's column `set` overloads accept (`fits`), only once a copy is made.
- With named stamp columns, a trigger update that modifies only other columns is no trigger. This is from reading `QueryTable#snapshotWhen` (a `view` of the trigger); it cannot be recorded, because an input table reports every column as modified.
- No `unported!`. Approximated: a stamp column name with letters outside ASCII is checked with Unicode's alphabetic and alphanumeric classes, not `Character.isJavaIdentifierStart`/`Part`. Not ported: `LazySnapshotTableProvider`, uncoalesced bases, vector columns (no such `ColumnType`).
- Not verified against Java: whether Java's `UpdateCoalescer` cancels a shift away and back between two triggers exactly as `update::compose` does. It decides which rows an incremental snapshot stamps again; input tables do not shift, so the oracle cannot show it.
- Tests: `tests.rs` (each case with its update, refusals, three random tests against models with the checker: plain against a fresh static snapshot, incremental against a model of row identity and stamp, history against merged static histories), `corpus.rs` (five fixtures recorded from the Java server: 62 static results, and 13, 10, 2 and 8 results over 14, 25, 14 and 15 steps). `fixtures/record.py` records a fixture on a Java server; `testing.rs` replays one and is shared with `ops/distinct`.
- Gate: `cargo test -p oxhaven-engine snapshot` passes. The two `oracle/bin/harness` commands were not run: the harness has no such operation, and there is no server for it.
- Handlers (follow-up, branch `task/4.10-join-snapshot-handlers`): `crates/oxhaven-server/src/table/ops/snapshot.rs` serves `Snapshot` and `SnapshotWhen` with Java's request checks (fields, table references, stamp columns read with `String#trim` and refused as internal errors before the history check, history with initial or incremental `UNIMPLEMENTED`). The handler reads stamp columns itself rather than with `StampColumn::parse`, whose `str::trim` removes Unicode spaces that Java's `trim` keeps. Replay of `snapshot_static` and `ticking_snapshot_when` from `origin/oracle/more-operations` is clean.
