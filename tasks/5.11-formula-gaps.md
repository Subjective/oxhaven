## Scope

Small gaps found by earlier tasks, each probed on Java first:

1. The instant parser panics with an arithmetic overflow on all-digit text such as `9309340999` (7.4.3, "For the owner", item 1); also unchecked arithmetic in the neighbouring date, time, duration and period parsers.
2. Four filter formulas Java evaluates and this crate refuses (4.22, "Differences from Java found"): `D == 2024-03-10` on a `LocalDate`, a `LocalDate` against a `String`, `Dur < null`, and `P == 'P1Y'`. Port the Java rule that makes each legal rather than four special cases.
3. The remaining `new` forms (5.10, "Handover", item 1): `new int[n][m]` and the other element types, `new String(char[], int, int)`, `new Integer[n]` and the other boxed arrays. A form that needs a column type the contracts lack is refused by name.
4. Size-only calls (`T_[i-1].size()`) on a column array of a vector of `Boolean` or `Instant` (4.23 refuses them wholesale).

Not in scope: changes to `crates/oxhaven-contracts`, `PARITY.md`, `oracle/replay-baseline.json` or the gate scripts.

## Notes

Started from main at `7479d977`; merged main at `64080c5`.

### What Java does, and what was ported

1. Instants. `epochAutoToEpochNanos` multiplies without a check, so a whole number too large
   for its unit wraps: `parseInstant("9309340999")` is `1680-06-12T00:28:45.290448384Z`. The
   parser now wraps the same way. A time literal of 1 to 19 digits goes through the same rule,
   and the smallest long is not an instant there (Java's quiet parser reads it as null). A
   sweep over numbers at each unit's threshold and the type limits, in every parser, finds no
   other overflow.
2. Comparisons. The general rule is Java's: equality of two unrelated classes is
   `eq(Object, Object)` (true only for two nulls, and a primitive is never null), and ordering
   is `compareTo(Comparable, Comparable)`, where null sorts first and two non-null values of
   different classes throw `ClassCastException` at the row where they meet. `Period` and
   `ZoneId` are not `Comparable`, so ordering them does not compile. `Period` and
   `ZonedDateTime` equality compares every field. This makes the four filters of 4.22 legal
   and computes about 300 corpus formulas that were refused and that Java fails at run time.
3. `new`: `new T[a][b]...[]` for every element type with literal lengths (1 to 1024, at most
   1024 elements), and `new String(char[] | int[] | byte[], offset, count)` with Java's bounds
   check. Refused by name: lengths that are not literals, `new boolean[n]`, nested array
   initializers, and boxed arrays such as `new Integer[n]` (no column type is an array of a
   boxed `java.lang` class).
4. A column array of a vector of `Boolean` or `Instant` is an untyped `ObjectVector` in Java,
   whose `size()`, `isEmpty()`, `len()`, `isNull` and `== null` compute. Those now compute; any
   other use is still refused.

Two engine tests expected the old refusals (`I > \`x\`` on an int column, and
`Z_[i - 1].size()` on a vector of booleans). Java fails both at run time, as this crate now
does, so the tests were changed to expect that. They are outside the owned path.

### For the owner

1. `new Integer[n]` and the other boxed arrays need a column type for an array of a boxed
   class in `crates/oxhaven-contracts`.
2. The engine refuses a shifted column array of a vector of `Boolean` or `Instant`
   (`crates/oxhaven-engine/src/ops/select/arrays.rs`), so `T_[i+1] == null` is refused where Java
   computes it; `T_[i+1].size()` and `isNull(T_[i+1])` compute.
3. Not ported: `parseEpochNanos`, `intSize()` on any vector, `T_[i][0]` and `T_[i].get(0)` on an
   untyped vector, `C_.toArray()`.
4. `where D in 2024-03-10` fails on both servers with different text.
5. The comment "nothing in these ranges overflows" in the engine's `time_table.rs` is wrong
   about Java's parser, though harmless where it stands.
