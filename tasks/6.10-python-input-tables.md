## Scope

`input_table` (append-only and keyed, from column definitions or an initial table) and
`InputTable.add`, `delete`, their async forms, `key_names`, `value_names`, through the
code the input table service uses. `DynamicTableWriter` over an append-only input
table. `ring_table`, `function_generated_table` and `TableReplayer` if the engine has the
operators; otherwise they raise and are listed.

## Notes from the 6.9 run (2026-11-15), observed on Java 42.9

**Blocker to solve first.** A console command runs under the update graph's shared lock
(`console/python/mod.rs`, `evaluate`), and a blocking input table change must not be made by
a thread holding it: `PeriodicUpdateGraph::run_cycle` asserts "run_cycle called while
holding the update graph's shared lock" (`crates/oxhaven-server/src/update_graph.rs`), and
the engine's `InputTable::add` documents the same panic. In Java, synchronous `add` and
`delete` work from a command and the change is visible within it (`size` is 2 right after
`add`), because Java waits on a condition of the lock, which releases it. The port needs
"release this thread's shared holds while waiting, then take them again": `GraphLock` in
`crates/oxhaven-engine/src/graph/lock.rs`, `SteppedUpdateGraph`, and
`PeriodicUpdateGraph`'s `SHARED_DEPTH`, plus the console. A helper thread holding the lock
would deadlock against a waiting cycle, because the lock prefers writers. This task now
owns those paths for that facility; do it first, with its own tests and commit.

- `input_table`: append-only attributes are `AddOnly`, `AppendOnly`, `InputTable`. With
  `init_table` the initial rows are there at once, and for a keyed table the last row for a
  duplicate key wins. A `double` key column and an empty definition are both accepted
  (Oxhaven's `create_input_table` refuses floating point keys as not ported).
  `InputTable(derived.j_table)` works, and adding through it adds to the source.
- Error heads: "add to InputTable failed.", "delete data in the InputTable failed.", "async
  add to InputTable failed.", "async delete data in the InputTable failed.", "failed to
  create an in-memory InputTable.", "the provided table input is not suitable for input
  tables.". Delete on an append-only table says `UnsupportedOperationException: Table
  doesn't support delete operation`, which is not the gRPC path's text.
- Async forms validate synchronously (an incompatible table raises at the call). Changes
  and callbacks happen after the command ends. Callback order was not the enqueue order,
  so scenarios must not depend on it.
- `DynamicTableWriter`: its table has `AddOnly` and `AppendOnly` but no `InputTable`
  attribute; rows appear after the command; `write_row` is all-or-nothing for the row; a
  wrong number of values fails with "Incompatible logRowPermissive call, values length=N
  != setters=M"; numbers go through `Number#intValue` and the like (3.7 becomes 3); a bool
  into a numeric column, a str or int into a char column, and a str into an Instant column
  are `ClassCastException`s; `close()` changes nothing observable.
- The engine has no ring table, function-generated table or replayer, so `ring_table`,
  `function_generated_table` and `TableReplayer` are refusals.
- Engine `add` blocks one cycle per call (1 s default), so a writer should coalesce queued
  rows per cycle.
