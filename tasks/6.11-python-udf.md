## Scope

`t.update("Y = f(X)")` where `f` is a Python function in the scope: the feature that most
distinguishes server-side Python and the hardest part of the console.

This task designs it and builds the first usable form. Recommended shape, to confirm or
replace in `docs/PYTHON_UDF.md`:

- **Resolution**: a call in a formula whose name is no built-in and is a callable Python
  global becomes a `PythonCall` node. Its result type comes from the function's return
  annotation as the reference maps it; without one it is `PyObject` in Java, which the
  contracts cannot hold, so here an annotation is required and its absence is a clear
  error. Record that as an allowed difference only with the owner's agreement.
- **Evaluation is by chunk, not by row**: the evaluator gathers the argument columns of a
  chunk, takes the interpreter lock once, calls the function per row (or once, for a
  function marked vectorized, with numpy arrays over the Arrow buffers), and releases it.
- **Where it may run**: `update` and `select` evaluate when the operation runs and on
  each update cycle; `view`, `update_view` and `where` evaluate on read or on cycle
  threads. Every such thread must take the interpreter lock after the graph lock, never
  the other way round; a console command holds the graph's shared lock and then the
  interpreter lock, and releases the interpreter lock around engine calls. Write the
  order down as a rule and test it with a ticking table whose formula calls Python while
  a command runs.
- **Not in the first form**: `numba` vectorization, Python filters with keyword
  arguments, callables that are not module-level functions, and functions that return
  tables.

Deliver the document, the resolution and chunked evaluation for `update`/`select`/`where`
on static and ticking tables with the annotated scalar types, and the lock test.

## Notes

- The recommendation stands on one measurement not yet made: the cost of taking the
  interpreter lock per chunk on cycle threads while a console is busy. Measure before
  building beyond the first form.
- Changes to how the expression engine resolves names may touch
  `crates/oxhaven-contracts` (`FormulaCompiler`): propose the smallest signature.
- If this cannot be made to keep the engine's determinism rule (PORTING.md 7), say so
  and stop: a Python function is allowed to be impure, and Java does not prevent it.

### What was built

- `docs/PYTHON_UDF.md` is the design, with what Java 42.9 was seen to do. The shape is the
  recommended one, with two changes: resolution is an extension point of `oxhaven-expr`
  (`Compiler::with_functions`, `ExternalFunctions`, `ExternalFunction`), so
  `oxhaven-contracts` did not change; and the function is any callable of the scope of the
  code that called the operation (a local function, a `functools.partial`, an object with
  `__call__`), not only a module-level function, because Java takes them and nothing more
  was needed.
- Built: `update`, `select`, `view`, `update_view`, `lazy_update` and `where` on static
  and ticking tables, with return annotations of `int`, `float`, `bool`, `str`, the numpy
  and `dtypes` scalar types and `Optional[...]` of them; Java's check of the arguments
  against the parameter annotations with Java's message; Java's values for null arguments.
- The Python half is `crates/oxhaven-server/python/_oxhaven_udf.py`, which is outside the
  paths this task owns, as are the lines in `console/python/mod.rs` that give the Python
  runtime's operations the compiler, and the scenarios `oracle/scenarios/python/udf_*.py`
  with their recordings.
- No missing annotation was recorded as an allowed difference: a function without a return
  annotation is refused, naming `PyCallableWrapperJpyImpl#parseSignature`.
- Only the Python package's operations can call Python. A formula of a gRPC client cannot,
  and Java refuses that too (`INVALID_ARGUMENT`).

### Refusals, each with the Java method it names

`docs/PYTHON_UDF.md`, "Refused", is the list: no return annotation or one that names no
column type, also under a cast (`PyCallableWrapperJpyImpl#parseSignature`); a time return
type (`deephaven._udf._ParsedReturnAnnotation#setup_return_converter`) and an `Instant`
argument (`deephaven._udf._ParsedParam#_setup_datetime_arg_converter`); array return types
and array or vector arguments (`deephaven._udf#_udf_parser`); a `char` return type
(`_ParsedReturnAnnotation#setup_return_converter`); a character literal as an argument
(`PyCallableWrapperJpyImpl#call`); a call without arguments of a function that takes
`*args` (`QueryLanguageParser#visit(MethodCallExpr)`); numba functions and numpy ufuncs
(`PyCallableWrapperJpyImpl#prepareSignature`); two calls in one operation that give an
`Optional[...]` parameter numbers of different types
(`deephaven._udf._ParsedParam#setup_arg_converter`); a returned value that does not fit the
annotation where Java's two ways of calling disagree (`PyCallableWrapperJpyImpl#call`).

One difference is not a refusal that names its method: `where("f(X)")`, a filter that is
nothing but the call, fails with the engine's text for a null condition when `f` returns
`None`, where Java (`FilterKernelPythonChunkedFunction#filter`) drops the row. The filter
does not know that its formula is a call. For the owner to decide.

### The measurement

`console::python::udf::tests::lock_cost` (ignored; run with `--ignored lock_cost
--nocapture`), one run of a debug build on a shared 4-core machine, Python 3.13:

- the lock taken and released with no Python thread running: 0.19 µs;
- one row of `update('A = twice(ii)')`: 0.56 µs, of `update('A = 2 * ii')`: 0.19 µs;
- a cycle that adds about 41600 rows (11 chunks): 77 ms with the call, 65 ms with
  arithmetic, no Python thread running;
- with a Python thread that computes without pause: 157 ms for 54247 rows (14 chunks) with
  the call, 80 ms for 46853 rows with arithmetic. That is about 5 ms a chunk, the
  interpreter's switch interval.

A console command does not compete with a cycle (the graph lock excludes them); threads the
script starts do, at 5 ms a chunk. That speaks for the chunk of 4096 rows and against
taking the lock per row or per smaller chunk.

### Seen in Java and not reproduced

- The order in which the formulas of one `update` call an impure function differed between
  two runs of the same script. The scenarios call a counter from one formula at a time.
- A function that returns a value its annotation does not name (an `int` beyond 64 bits in
  a `view`) left an exception behind in the interpreter that failed the next, unrelated
  call, and once stopped the server.
