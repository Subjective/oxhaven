## Scope

- `listen(table, callback)` and `TableUpdate` (`added()`, `removed()`, `modified()`,
  `modified_prev()` as dictionaries of numpy arrays, or of lists without numpy), run on
  the cycle thread under the lock rule of 6.11; `replay_initial`; `stop`.
- `update_graph.shared_lock`/`exclusive_lock` as context managers and decorators over the
  engine's graph lock.
- `liveness_scope` and `execution_context`: Rust has no liveness scopes; tables live as
  long as something holds them. Provide the names as context managers that do what is
  observable (a table released when the scope closes can no longer be used by Python)
  and say in Notes what is not observable.
- `Table.await_update`.

## Notes

- Sized for one agent context. If the list does not fit, finish the part that users type
  first, list the rest here, and stop.
- A method whose engine operation is missing raises `DHError` naming the Java method, from
  the handler's `UNIMPLEMENTED`; it is never left out silently and never approximated.
- Done: `listen`, `merged_listen`, `TableListener`, `MergedListener`, both handles,
  `TableUpdate` (the four row kinds, their chunked forms, `modified_columns`),
  `do_replay`, `dependencies`, `on_error`, `stop`; `update_graph` (both locks as
  context managers and decorators, `has_shared_lock`, `has_exclusive_lock`,
  `auto_locking_op`, `auto_locking_ctx`); `liveness_scope`, `LivenessScope`,
  `SimpleLivenessScope`, `is_liveness_referent`; `ExecutionContext`, `get_exec_ctx`,
  `make_user_exec_ctx`; `Table.await_update` and `Table.update_graph`;
  `_gc.garbage_collect`. The script scenario `listen_counts` is clean.
- What Java does was observed on 42.9 for each of these; the table of differences is in
  `docs/CONSOLE.md`, "Listeners, locks, liveness scopes and execution contexts".
- Refused, by the Java method: `make_user_exec_ctx(freeze_vars=...)`
  (`io.deephaven.engine.context.ExecutionContext.Builder#captureQueryScopeVars`).
  `TableUpdate.shifted` raises `NotImplementedError`, as in Java.
- Liveness, not observable here: the engine has no reference counts, so a scope tracks
  the Python `Table` objects and listener handles made on its thread. A released table
  whose engine table nothing else holds raises on every use, reads included (Java still
  reads its rows); one that an export, a derived table or a listener holds stays live.
  A released variable stays listed for clients until it is assigned again.
- Execution context, not observable here: this server needs none, so formula operations
  run on any thread and in a listener, where Java refuses them without one. `with ctx:`
  changes nothing. This is a difference in what is accepted and wants a ruling.
- Outside the owned paths: explicit holds of the graph lock in
  `crates/oxhaven-engine/src/graph` (a `with` block cannot be a closure),
  `PeriodicUpdateGraph::stepped`, the registration in `console/python/mod.rs`,
  `Table.await_update`, `update_graph` and the liveness hook in `deephaven/table.py`,
  `deephaven/_gc.py`.
- Left: a blocking input table edit on a thread inside its own `shared_lock` panics in
  the engine where Java refuses the upgrade (`console/python/input.rs`).
