## Scope

- **Finding packages**: the embedded interpreter uses the Python the server was linked
  against. Honour `VIRTUAL_ENV` and a `--python-home`/`--python-path` option so that a
  user's numpy, pandas, pyarrow and jedi are importable, and fail at start with a clear
  message when the environment's Python version is not the linked one.
- **`python.version`** in `GetConfigurationConstants` when there is a Python console, as
  Java reports it.
- **Distribution**: decide between (a) a server binary linked to one libpython minor
  version per build, and (b) the server as a Python extension module in a wheel
  (`pip install`, then `python -m oxhaven` starts it), which is how the Java server is
  most often run from Python and removes the libpython coupling. Build the one chosen far
  enough to start a server with a console from a clean virtual environment.
- **CI**: the `python-console` job runs the whole server test suite with the feature if
  its time allows, on the oldest and newest Python the project supports; say which
  versions those are.

## Gate

```bash
cargo test -p oxhaven-server --features python --lib -- console::
```

And, from a new virtual environment with numpy installed, a server started the documented
way runs `import numpy; print(numpy.__version__)` in its console.

## Notes

- If (b) is chosen the `deephaven` package can ship as ordinary files in the wheel instead
  of inside the binary; keep the embedded importer for the plain binary.
