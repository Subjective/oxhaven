# 6.18 Applications defined by scripts

- **Status:** in review
- **Track:** B
- **Needs:** 6.2
- **Owns:** `crates/oxhaven-server/src/app/` (script applications), `crates/oxhaven-server/python/deephaven/appmode.py`

## Read

Paths are in the reference repository at the tag pinned in `oracle/REFERENCE.md`.

- `server/src/main/java/io/deephaven/server/appmode/ApplicationInjector.java`,
  `ApplicationFactory.java`, `ScriptApplicationState.java`
- `application-mode/src/main/java/io/deephaven/appmode/` (`ApplicationConfig`,
  `ScriptApplication`, `ApplicationState`)
- `py/server/deephaven/appmode.py`
- `oracle/ide/app.d/`: an application the reference loads.

## Scope

A directory of `*.app` files (`--app-dir`, Java's `deephaven.application.dir`): each names
an application of type `script` with Python files to run at start. The scripts fill an
`ApplicationState` (`deephaven.appmode`), and its fields are listed and resolved as
application fields (`a/<id>/f/<name>`), which `crate::app` already does for fields set
from Rust. With this the built-in demo application (`--demo-tables`) can become an
`.app` file, and the IDE acceptance test runs against the same application on both
servers.

## Gate

```bash
cargo test -p oxhaven-server --features python --lib -- console:: && cargo test -p oxhaven-server --lib -- app:: ide::
```

and `node oracle/ide/ide-test.js --url "$OXHAVEN_URL"` against a server started with
`--app-dir oracle/ide/app.d`.

## Notes

- Static and `qst` application types have no Python and are not part of this task.
- `--app-dir <directory>` starts the applications; `app::script` reads the `.app` files and
  runs the scripts through the console, `deephaven.appmode` is the Python side. What Java
  does was observed on Java 42.9 with application directories made for the purpose;
  `docs/CONSOLE.md`, "Applications defined by scripts", has the observations and the
  table of differences.
- `--demo-tables` stays: the default build has no interpreter, and the replay of the
  recorded IDE calls (`crate::ide`) runs in that build against the built-in application.
  `oracle/ide/app.d` is loaded unchanged by both servers, and `ide-test.js` (routes
  `panels`, `iframe`, `jsapi`) passes against each.
- Refused by the name of the Java method: the types `static` and `dynamic`
  (`StaticClassApplication#parse`, `DynamicApplication#parse`), two scripts with the same
  number (`ApplicationUtil#findFilesFrom`), and a `\u` escape that is half a surrogate
  pair (`Properties#load`). A Groovy script is refused as Java refuses it on a Python
  server. The type `qst` is read and skipped, as in Java, where it is never enabled.
- `app::fields`: a field replaced while no client listens now moves behind the others in
  `ListFields`, as observed on Java; the test that said it keeps its place was written
  before a script could show what Java does, and was changed with the observation.
- For a ruling: `del app[name]` removes the field and then always raises `KeyError`, in
  the reference and, reproduced, here.
