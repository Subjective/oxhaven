## Scope

After 6.1 the scope has two holders: the Python globals, and the server's `Scope` map that
tickets resolve against, which the console fills after each command. Make the script
session the one holder when there is one:

- `s/<name>` resolves by asking the session, so any variable resolves: a table as a table,
  anything else as an object export (Java answers `INVALID_ARGUMENT` when a table is
  wanted, not `NOT_FOUND`).
- A client that publishes to `s/<name>` (`ScopeTicketResolver#publish`, used by
  `pydeephaven` `publish_table` and shared tickets) sets the Python global, wrapped as the
  package's `Table`.
- `observeScopeChanges`: changes made outside a command (a Python thread, a listener,
  `BindTableToVariable`, a publish) are noticed and sent to `ListFields`; Java observes
  before and after every command and after every `setVariable`.
- The type name of a variable: `Table`, and the hook for `PartitionedTable`,
  `HierarchicalTable` and plugin object types that 7.6 to 7.10 will fill; tables with the
  attribute Java calls `NON_DISPLAY_TABLE` are not listed.
- Query scope variables in formulas: `t.update("Y = x + 1")` where `x` is a Python global
  number or string. Java resolves a name that is no column against the query scope. Wire
  the expression engine's parameter lookup to the session for the value kinds the
  contracts' literals cover, and list what is refused.
- Flight descriptors `scope/<name>` if the ticket router has descriptor resolution by then.

## Notes

  contract change: propose the signature in the pull request and keep it minimal.
- Done without a contract change: the server wraps the compiler it hands to operations
  (`app::ScopedCompiler`) and replaces scope variables by literals before compiling.
- What formulas refuse, and what differs from Java, is in `docs/CONSOLE.md`, "The query
  scope".
