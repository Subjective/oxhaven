## Scope

- `deephaven.dtypes`: the `DType` objects users name (`bool_`, `byte`, `short`, `int32`,
  `long`/`int64`, `float32`, `double`/`float64`, `string`, `Instant`, `char`, the array
  types the contracts can hold), `from_np_dtype`, `null_remap` and the null constants of
  `deephaven.constants`. Types the contracts cannot hold (`BigDecimal`, `PyObject`,
  `JObject`, `LocalDate`, ...) exist as names and raise when a column of them is built;
  list them as contract gaps.
- `deephaven.column`: every `*_col` constructor, `col_def`, `ColumnDefinition`,
  `ColumnType`, and null handling as the reference does it (None, the null constants).
- `new_table` in both forms (list of input columns, mapping with inferred types) and
  `TableDefinition`.
- `deephaven.time`: `dh_now`, `dh_today`, `dh_time_zone`, `time_zone_alias_*`, and the
  conversions between Python, numpy, pandas and engine time types (`to_j_instant` and
  friends keep their names; here they return what `new_table` and formulas accept).

### Outcome

`replay-scripts --scripts dtypes_,time_` has nine scenarios clean and one,
`dtypes_partitioning_definition`, that differs where a refusal below stands. The recordings
were made from Java with numpy 2.5.4, pandas 3.1.1 and tzdata 2026.6 (`oracle/.venv`), which
the numpy and pandas forms in them need; the server tests import only the standard library.
`char` columns are now compared: `oracle/harness/rules.py` knows Arrow `uint16` as exact, a
change under the `oracle-change` label, as are the new baseline entries.

What is here beyond the owned paths, each because the scope needs it:

- `python/deephaven/_java_time.py`: `java.time` values (`Instant`, `ZonedDateTime`,
  `LocalDate`, `LocalTime`, `Duration`, `Period`, `ZoneId`) with Java's texts, and the parsers
  of `io.deephaven.time.DateTimeUtils` and its time zone aliases. `to_j_instant` and friends
  return these; `datetime_col` and `new_table` accept them.
- `python/deephaven/constants.py`: the null constants and limits of `QueryConstants`.
- `python/deephaven/table.py`: `TableDefinition` and the import of `ColumnDefinition`, in
  place of task 6.4's stand-ins.
- `console/python/mod.rs`: `column_definitions` and `validate_column_name`, next to `new_table`.

Contract gaps: `ColumnType` has no type for these, so a column of them is refused as
`not ported: io.deephaven.engine.table.ColumnDefinition#fromGenericType` (Java builds it):
`PyObject` (`pyobj_col`, and a mapping value pandas leaves as `object`), `JObject`
(`jobj_col`), `BigDecimal`, `BigInteger`, `Character`, `StringSet`, `LocalDate`, `LocalTime`,
`ZonedDateTime`, `Duration`, `Period`, `TimeZone`, `BusinessCalendar`, and the arrays
`bool_array`, `char_array` of `Character`, `zdt_array`, `local_date_array`, `local_time_array`,
`duration_array`, `period_array`. A column definition has no partitioning flag either:
`TableDefinition(...).table` of a partitioning column is refused
(`ColumnDefinition#isPartitioning`), which is what `dtypes_partitioning_definition` waits for.

Other refusals, each by the Java method it names:

| Python | Refused | Java |
| --- | --- | --- |
| `DType(...)` of a class other than `string` | making a Java object | `<class>#<init>` |
| `col_def`, `InputColumn` with a component type that is not the array's | the check and its error text | `ColumnDefinition#checkAndMaybeInferComponentType` |
| `simple_date_format` | all of it | `java.text.SimpleDateFormat#<init>` |
| a time zone `SystemV/...` | in the JDK's tz database, not in Python's | `java.time.ZoneId#of` |
| a region's offset outside the years 1 to 9999 | `zoneinfo` has no such dates | `java.time.zone.ZoneRules#getOffset` |
| the text of an instant before the year 0 | | `java.time.Instant#toString` |
| the hour 24, except `24:00` in an instant or zoned date time | | `java.time.format.Parsed#resolveTimeFields` |
| ISO text whose offset is not `Z` or `+hh:mm[:ss]`, or differs from its region's | | `java.time.ZonedDateTime#parse` |
| a duration beyond a long of nanoseconds | | `DateTimeUtils#parseDuration` |

Differences from Java that stay, none of them in a table:

- A `DType` has no `qst_type`, and its `j_type` is a Python class. `dtypes.array` returns a
  list (`JArray`) where Java returns a jpy array; `dtypes.string("abc")` returns a `str`.
- The `repr` of a column definition, a table definition and a time value is Python's; `str` is
  Java's.
- The cause after a `DHError`'s message is this engine's text, as everywhere in the package.
- `dh_now(system=True)` reads the same clock as `dh_now()`: there is no other.
- A time value is not a query scope variable a formula can name (`FormulaValue` has no
  `Instant`; `app/scope.rs`), and an alias added with `time_zone_alias_add` is known to
  `deephaven.time`, not to the engine's formulas or to `time_table`.

Left for 6.9: `iter_dict` and the other readers hand out instants as numbers; building columns
from numpy arrays goes through a Python loop.
