## Scope

The owner's ruling of 2026-11-16: the server ships a minimal `jpy` module whose every use
of a Java class fails by that class's name. `import jpy` succeeds and `jpy.get_type` hands
out an object; calling it, reading an attribute that would be a Java method or field,
`jpy.array`, `jpy.cast` and the like raise the refusal of this package, naming the class
and, where the use names one, the member. No Java class is implemented behind it.

Then the trial of `deephaven-plugin-plotly-express` again, without a stand-in.

Not part of it: a Python version of any Java call, `jpyutil`, `deephaven.ui`.

## Gate

```bash
cargo test -p oxhaven-server --features python -- jpy
cargo test -p oxhaven-server --features python
```

Nothing is recorded in `oracle/corpus`: the module has no table operation. What jpy 2.2.0
answered is in the tests as expectations.

## Notes

- The design, call by call beside jpy's answers, is `docs/CONSOLE.md` ("The jpy module");
  the trial of the plugins is `docs/FIGURES.md` ("After task 7.10.2").
- With the plugin installed as `pip` installs it (no `deephaven-core`, no `jpy`), the server
  starts, the object type and the JS plugin register, the manifest and the bundle are byte
  for byte Java's, and 42 of the 50 figures Java makes are sent as Java sends them. The
  eight others fail as before the module, on a Java object made in a formula
  (`DiscretizedRangeEqual`, six) and on `Calendars#calendar` (two).
- A use in a module body fails the import by the name. No installed plugin has one:
  plotly-express only holds a type at import, `deephaven-plugin-utilities` and
  `deephaven-plugin-ui` do not import `jpy`.
- Differences from jpy that follow from the ruling: `get_type` gives a type for a name Java
  has no class for (jpy: `ValueError`), `hasattr` and `getattr` with a default raise the
  refusal for a name that is no `__x__`, `has_jvm()` is false, and a type's class is not
  `type` itself.
- `jpy.destroy_jvm()` destroys the Java VM of the reference server; here it does nothing,
  as jpy does without a Java VM.
- No `unported!` call: the refusals are raised in Python, as `deephaven._java_time.NotPorted`.
- `deephaven.ui` 0.43.2 imports once `deephaven.table.TreeTable` exists (tried with a name
  put there by the probe); it needs no `deephaven.configuration`, which it imports inside
  `try`.
