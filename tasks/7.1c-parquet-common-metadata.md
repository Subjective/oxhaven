## Scope

The third slice of 7.1's list ("`_metadata` and `_common_metadata` files"): a directory
whose partitioning columns only `_common_metadata` knows, which is what
`write_partitioned(..., generate_metadata_files=True)` of 7.2b leaves. 7.1b and 7.2b
refused it with `ReadError::NotPorted` naming `ParquetMetadataFileLayout#create`. Read
it as Java does, with `file_layout=ParquetFileLayout.METADATA_PARTITIONED` and with the
layout inferred from the directory or from the path of either metadata file.

Not in scope: `table_definition`, data indexes, refreshing (Java refuses it for this
layout), reading only the row groups a metadata file lists of a file.

## Notes

- The refusal was `common_columns` in `crates/oxhaven-parquet/src/lib.rs`: a column of
  `_common_metadata` that `_metadata` does not have was `ReadError::NotPorted` naming
  `ParquetMetadataFileLayout#create`. It is gone; `docs/STORAGE.md`, "Metadata files" of
  the second slice, says what is read now.
- Probed against the reference (Deephaven 42.9) by hand, on directories written by its
  own `write_partitioned` and by pyarrow, and kept from Java: the columns in the order of
  `_common_metadata` (the writer puts the partitioning columns first, pyarrow's file may
  not); the files in the order `_metadata` lists them; files it does not list are not
  read; a listed file that is gone has no rows, also without `_common_metadata` (this
  crate failed on it before, and `docs/STORAGE.md` said Java fails when the rows are
  read: it does not); a null value of the last file is allowed, where the key-value
  layout refuses it; directories without `=` are values by position; the types of
  `PartitionParser`, with `String` for a type it has no parser for; `_common_metadata`
  alone is read by the key-value layout, and the metadata layout then fails; refreshing
  is refused.
- `crates/oxhaven-parquet/src/partition.rs` holds the value parsers, and its tests state
  what Java answered for each text tried (about a hundred).
- `tests/data/common/` (made by `make_arrow.py`) holds the directories the crate tests
  read; Java read each of them to what the tests expect.
- Changes `oracle/`: one new script scenario, `parquet_read_common_metadata`, recorded
  from the reference (twice, the same bytes), and its `clean` line in the baseline,
  which `bin/check-baseline-change.sh` reports as an added line: it needs the
  `oracle-change` label. No other recording changed.
- No change to `crates/oxhaven-contracts`. No `unported!` call. Refused as
  `ReadError::NotPorted`: an `Instant` partition value
  (`io.deephaven.time.DateTimeUtils#parseInstant`), a hexadecimal `float` or `double`
  value (`java.lang.Float#parseFloat`, `Double#parseDouble`), a number with characters
  outside ASCII (`java.lang.Integer#parseInt`, `BigInteger#BigInteger(String)`,
  `BigDecimal#BigDecimal(String)`), and a path in `_metadata` with `.` or `..` or from
  the root (`ParquetUtils#resolve`, shared with the writer now).
- The header comment of `parquet_write_unported` (7.2b) still says that every step is
  refused, which is stale: four of its steps now succeed. A script scenario's recording
  holds a hash of the whole script, comments included, so fixing the comment needs the
  scenario recorded again; it was left as it is.
- The first draft of the scenario filtered `common_only` (a static key-value read) with
  `where("!isNull(B)")` on its partitioning column `B`, and Oxhaven then gave the result
  the attribute `AppendOnly` besides `AddOnly`, which Java does not (Java's
  `PartitionAwareSourceTable` takes a filter of partitioning columns itself). That is a
  difference of `where` outside this task, not looked into further; the scenario reads
  the table without the filter.
