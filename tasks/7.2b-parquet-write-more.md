`parquet_write_unported` and by hand; "Java" says what it answered.

## Done

- The column types of Java's objects: `BigDecimal`, `BigInteger`, `LocalDate`,
  `LocalTime`, `LocalDateTime`, and `byte[]` as the array of bytes it is.
- `write_partitioned` of a table with partitioning columns and of a partitioned table,
  with `base_name` and its tokens.
- `generate_metadata_files=True` for `write`, `batch_write` and `write_partitioned`.
- A codec named by its class, and a `file:` URI as a destination.

Each was compared with the reference in both directions: the footers of the two
servers' files as pyarrow reads them, Java reading the files and directories written
here, and this crate reading the ones Java wrote.

## Left, each still refused by the Java method it needs

| Refusal | Java method |
| --- | --- |
| `LZO`, by its name or by `io.airlift.compress.lzo.LzoCodec`: the `parquet` crate has no LZO codec | `DeephavenCompressorAdapterFactory#getByName` |
| `index_columns` that names columns: needs data indexes and `RowSetCodec` | `ParquetInstructions.Builder#addAllIndexColumns` |
| `codec_name` in a column instruction | `ParquetInstructions.Builder#addColumnCodec` |
| `special_instructions` | `ParquetInstructions.Builder#setSpecialInstructions` |
| A destination with another URI scheme than `file` | `SeekableChannelsProviderLoader#load` |
| A column whose cells hold vectors or arrays: needs Java serialization (`SerializableCodec`) | `TypeInfos#getCodecAndArgs` |
| A column with another type in `table_definition` than in the table, the `int` written as a `short` among them, and a vector written as an array | `TransferObject#create` |
| `by_groups` on a vector or array column | `RowGroupTableIteratorVisitor.SplitByGroupsIterator#next` |
| An empty name for the file in a column instruction | `ParquetInstructions.Builder#addColumnNameMapping` |
| A partitioning column of type `Float`, `Double` or `Instant`: the first two need Java's text of a floating point number in this crate, the third fails in Java as the first key and names a directory as a later one | `PartitionFormatter#formatObject` |
| A directory or file name of a partitioned write that is `.` or `..`, starts with `/`, or starts like a URI scheme | `ParquetUtils#resolve` |

On the read side, a directory whose partitioning columns only `_common_metadata` knows
is still refused (`ParquetMetadataFileLayout#create`), so this crate does not read
through the metadata files of its own `write_partitioned`; Java does.

## Notes

- `parquet_write_unported` keeps the steps `lzo`, `indexed`, `nested` and `narrowed`,
  which are refused, and `partitioned`, whose recorded listing has the random UUIDs
  Java named its files with: no second run has those names, on either server.
- Java's key-value entries of a metadata file come in the order of a hash map; here they
  are in the order of the files. Nothing reads them by position.
- A script holds the update graph's lock, so a time table made in the script that writes
  it has no row yet; a partitioned write of it then fails as the write of an empty table
  does, on both servers. Written from a later script it has rows, and both write them.
- Probed and kept from Java, for the owner to rule on: the random file names; a
  directory that is not emptied; the `ArrayIndexOutOfBoundsException` of a table without
  rows; a null and an empty string that are one directory; a `:` in the first directory
  name; a `/` in a value; `DECIMAL(1, 0)` read back as `BigInteger`; metadata files that
  list the last write only. Java cannot read its own partitioned write with metadata
  files when a partitioning column has another name in the file (a
  `NullPointerException` in `ParquetMetadataFileLayout`).
- The replay gate does not pass with this task as it is: the step `partitioned` of
  `parquet_write_unported` was a refusal and is now a listing that differs in its file
  names, which is the kind `value`, and the baseline line lists no such kind. Listing a
  kind is a protected change (`oracle-change`), so it is left to the owner: add `value`
  to the line, or record the scenario again with a `base_name`. The line was tightened
  to the tables that still differ.
