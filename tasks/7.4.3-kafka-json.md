## Scope

The 7.4.3 row of `docs/KAFKA.md`, "Tasks": every conversion of a JSON field to a column
that is refused today (a fraction in an integer column, text in a numeric column, an
object or array in a `String` or `Boolean` column, integers beyond 128 bits), JSON
pointers to nested fields and into arrays, records that are arrays, `char` and `Instant`
columns, several fields mapped to one column, a simple `byte[]` column and the raw spec.
Each behaviour is probed on the Java reference with a real broker before it is decided,
and covered by tests in `crates/oxhaven-kafka/tests` so that the `kafka-broker` job runs
them.

## Notes

- **Built.** `src/json.rs` reads a record into Jackson's tree (its own parser, with
  Jackson's limits on depth, number length and scale, and its white space), finds each
  column's node by a JSON pointer compiled as Jackson compiles it, and converts it as
  Java's `JsonNode*FieldCopier`s do through `asInt`, `asLong`, `asDouble`, `asText` and
  `toString`. `docs/KAFKA.md`, "How a JSON field becomes a cell", has the whole table.
  `src/plan.rs` turns the mapping into pointers as `JsonImpl.JsonConsume` does, runs one
  copier per pointer, and fails the table on unequal chunk sizes as Java's publisher
  does. A simple `byte[]` column is built from its data type, the property `byte[]` or
  `ByteArrayDeserializer`. `serde_json` is no longer a dependency of the crate.
- **Probes.** Java 42.9 on port 10986 and Oxhaven on 10987, one broker
  (`apache/kafka:3.9.1`, KRaft, 127.0.0.1:19192), one topic per case read by both:
  every column type against 108 values (integers of every size up to beyond 128
  bits, fractions, exponents, text of every kind Jackson reads, `true`/`false`, `null`,
  objects, arrays, missing fields); pointers with `~0`, `~1`, other `~`, indexes,
  leading zeros, numeric field names; records that are arrays, numbers, text, `null`,
  empty, or followed by more text; Jackson's limits; mappings that collide; the column
  types Java refuses, among them Duration, Period, ZonedDateTime and LocalTime after
  pull request 120; 146 tables in all. Every schema, row and table failure is Java's,
  except the differences listed in `docs/KAFKA.md`, "Differences from Java seen in the
  probes" (parse errors carry the parser's detail; seven types refused by `json_spec`
  where Java fails at `consume`; `JObject`; lone surrogates; `Instant` text without a
  zone fails by another name). The probes are not recorded in `oracle/` (task 7.4.6).
- **Colliding pointers.** Two fields that are one pointer (`a` and `/a`) are resolved in
  the order Java iterates the `HashMap` of the mapping, reproduced from the fields' hash
  codes; probed on three mappings, the 30-pointer one among them.
- **Refused, with the Java class named** (`not_ported`):
  - text with a UTF-16 surrogate without its pair where it would become a `String` cell,
    compact JSON or an `Instant`'s text (`java.lang.String`; Java keeps it, a Rust
    string cannot);
  - colliding pointers among mapping fields of which eight or more fall in one bucket
    of Java's `HashMap` (`java.util.HashMap#treeifyBin`; not reproduced);
  - a JSON column of `JObject` (`ColumnDefinition#fromGenericType`; Java fills it with
    Jackson nodes, the engine has no such type);
  - `Instant` text in a spelling `oxhaven_expr::parse_instant_text` returns as
    unsupported (`DateTimeUtils#parseInstant`).
  No `unported!` added. The raw spec is not ported: no Python API of the reference
  reaches `KafkaTools.Consume#rawSpec`.
- **Outside the owned paths.** `crates/oxhaven-expr/src/lib.rs` gains
  `parse_instant_text`, a public wrapper of `parse::instant_of_text`, so that Kafka
  reads `Instant` text as `DateTimeUtils#parseInstant` does with the expression crate's
  parser. No change to `crates/oxhaven-contracts`, `oracle/` or `PARITY.md`.
- **For the owner.**
  1. `parse::instant_of_text` in `oxhaven-expr` multiplies digit text by 10^9 without
     wrapping (`9309340999` panics in a debug build); Java's `epochAutoToInstant`
     wraps. Kafka does not reach it (it reads digits itself); a formula may.
  2. `json_spec` in Python refuses `LocalDate`, `Duration` and the other types without
     an engine type at once (`dtypes._engine_type`); Java accepts the spec and fails at
     `consume` with `Type X not supported for JSON`. Both fail before a table exists.
  3. A simple `byte[]` column is not yet sent to clients (`ColumnType::Array`); Java
     sends Arrow `Binary`.
  4. The refusals above that Java does not make (lone surrogates, `JObject` columns,
     `Instant` text the expression crate leaves unsupported; a `HashMap` bucket of
     eight colliding fields).
  5. Colliding pointers follow Java's `HashMap` order, as `kafka.topics` does (item 8
     of "For the owner's ruling" in `docs/KAFKA.md`); say if refusing them is preferred.
