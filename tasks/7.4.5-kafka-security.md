## Scope

1. gzip: the `libz-static` feature of `rdkafka`; gzip batches are read, and
   `compression.type=gzip` is accepted when producing.
2. TLS: the `ssl` feature; `security.protocol=SSL` with Java's `ssl.*` properties
   translated to librdkafka's where there is an exact equivalent (PEM files, a PKCS#12
   keystore), and refused by name where there is none (JKS stores).
3. SASL: `SASL_PLAINTEXT` and `SASL_SSL` with `sasl.mechanism` PLAIN, SCRAM-SHA-256 and
   SCRAM-SHA-512; `sasl.jaas.config` naming `PlainLoginModule` or `ScramLoginModule`
   parsed into librdkafka's `sasl.username` and `sasl.password`; GSSAPI and OAUTHBEARER,
   and every other login module, refused by name.
4. Tests against a broker with SSL, SASL_SSL and SASL_PLAINTEXT listeners, with
   certificates made by `openssl` at test time (none committed); the `kafka-broker` job.
5. Probes of the Java reference (Deephaven 42.9) against the same broker for the
   properties it accepts and its errors.
6. The Python package passes the properties through; console tests that they reach the
   client and that refusals raise `DHError`.

Out of scope: Kerberos (Cyrus SASL) and OAUTHBEARER over OIDC (libcurl), which the ruling
keeps off; TLS to the schema registry.

## Notes

**gzip.** `rdkafka` gains `libz-static`: `libz-sys` 1.1.33 (MIT OR Apache-2.0) compiles the
zlib 1.4 sources it carries and links them statically, with `vcpkg` 0.2.15 (MIT OR
Apache-2.0) as a build dependency that only acts on Windows. The test binaries link no
`libz.so` (`ldd`). Consuming reads gzip batches written by Java's console producer and by
librdkafka; `compression.type=gzip` is accepted when producing, and broker.sh checks with
`kafka-dump-log.sh` that the batches written are gzip (run once on an uncompressed topic
to see it report `compresscodec: none`). The refusals and their tests are gone.

**TLS and SASL.** `rdkafka` gains `ssl`, which adds one crate, `openssl-sys` 0.9.118 (MIT),
and links the system's OpenSSL 3 (Apache-2.0): `docs/KAFKA.md`, "What is built", says why
not `openssl-src`. librdkafka is configured with `WITH_SSL`, `WITH_SASL_SCRAM` and
`WITH_SASL_OAUTHBEARER`; Cyrus SASL and libcurl stay off. `src/security.rs` translates
`security.protocol`, `ssl.*` and `sasl.*` for the consumer, the producer and `topics`
(table in `docs/KAFKA.md`, "TLS and SASL"), with Java's JAAS parser
(`java.io.StreamTokenizer` as `JaasConfig` sets it up) and Java's texts where Java refuses
a configuration. A refusal of TLS or SASL during the connection (an untrusted or misnamed
broker, a missing client certificate, a wrong password) ends the call at once, as Java's
`AuthenticationException`: librdkafka would retry until `default.api.timeout.ms`, so the
waits for metadata run in slices of 250 ms and read the client's error events between
them (`client::metadata`, `ClientSink::await_metadata`). The refusals are recognised by
librdkafka's codes (`__AUTHENTICATION`, `__SSL`). Under TLS 1.3 a refused client
certificate shows only as a failed transport whose OpenSSL text names an alert; that is
taken as a refusal too, by its text, as no code marks it.

**The first CI run** (pull request 140) failed `a_wrong_password_fails_at_once` (32.5 s)
and `an_untrusted_broker_or_a_missing_client_certificate_fails_at_once` (140 s: consume
60 s, produce 20 s and topics 60 s, every call to its timeout). On the runner `localhost`
is `::1` as well as `127.0.0.1`, librdkafka shuffles the two, and the broker listens on
`127.0.0.1` only. A refused connect then alternates with the TLS or SASL refusal. Its
suppression of an error identical to the last one never applies, so every attempt queues
a log event and an error event. Each slice served one event, so the queue grew and the
refusal waited behind the logs. Reproduced here by running the tests in a mount
namespace whose `/etc/hosts` gives `localhost` as `127.0.0.1` and `127.0.0.2` (nothing
listens there), with the same 140 s; the logs showed one event served every 250 ms.
Fixed by serving every queued event between two requests (`EVENTS_PER_SLICE`). After the
fix the five tests passed in that namespace, and then in nine more runs, three at a time,
with each hosts file. Every error event is now logged (`tracing`, target `librdkafka`).
`refused` gives each call's time and error when it fails, with the events the client saw.

**Probes** (Java on 10878, the same broker as the tests with its five listeners, 56
cases; scripts in the scratch directory of the task, not committed). Java's results:

- Connect and read (or produce, or list): PKCS#12 key store; PEM key store file; PEM key
  and chain as text; trust certificates as text; `security.protocol=ssl`; hostname
  verification off with an empty algorithm; `HTTPS`; a JKS-typed PKCS#12 key store;
  SASL PLAIN, SCRAM-SHA-256, SCRAM-SHA-512 over SASL_PLAINTEXT and SASL_SSL; a SCRAM
  mechanism with `PlainLoginModule`; unquoted JAAS values, comments and escapes. Oxhaven
  does the same (`tests/security.rs`).
- Java's texts reproduced: `security.protocol=TLS` (its list in hash order), `Unknown
  identification algorithm: foo`, `Invalid keystore format` for a PEM file in a JKS trust
  store, the two `InvalidConfigurationException`s of PEM trust stores, no `sasl.jaas.config`,
  and the JAAS parser's six messages.
- Failing at once in both, other words (`PARITY.md` A5): a wrong password
  (`SaslAuthenticationException: Authentication failed: Invalid username or password`, or
  SCRAM's `... invalid credentials with SASL mechanism SCRAM-SHA-256`, in 0.3 s; here the
  same exception's name and librdkafka's text with the broker's message), an untrusted
  broker (`SunCertPathBuilderException`; here `SslAuthenticationException ... certificate
  verify failed`), `127.0.0.1` against a certificate for `localhost` (`No subject
  alternative names matching IP address`), no client certificate (`bad_certificate`), a
  wrong key store password (librdkafka's words, at the call).
- Refused by name here, connecting in Java (owner's item 31): `ssl.protocol=TLSv1.2`,
  `ssl.cipher.suites`, `ssl.endpoint.identification.algorithm=ldaps`. JKS stores and
  PKCS#12 trust stores are refused too; Java reads them (not probed: the test has no JKS
  file, and making one needs `keytool`).
- Refused by name here, failing in Java in other words: GSSAPI, the default under SASL
  (`No serviceName defined in either JAAS or Kafka config`), `sasl.login.class` (class not
  found), `tokenauth=true` (fails authenticating), an unknown login module
  (`LoginException: No LoginModule found`), `ssl.key.password` other than the store's
  (`BadPaddingException`).
- Failing at once here, after 60 s in Java with `TimeoutException` (owner's item 32):
  OAUTHBEARER, `sasl.mechanism=FOO`, `plain` in lower case, PLAIN without `username`.
- Same in both: an SSL client against the plaintext port waits `default.api.timeout.ms`.
- Oxhaven on 10879 ran the same 56 cases after the change: 34 the same, 10 different in
  text only, 3 + 5 refused by name and 4 failing sooner, as listed (`docs/KAFKA.md`,
  "Differences from Java seen in the probes").
