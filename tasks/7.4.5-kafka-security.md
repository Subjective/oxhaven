## Scope

1. gzip: the `libz-static` feature of `rdkafka`; gzip batches are read, and
   `compression.type=gzip` is accepted when producing.
2. TLS: the `ssl` feature; `security.protocol=SSL` with Java's `ssl.*` properties
   translated to librdkafka's where there is an exact equivalent (PEM files, a PKCS#12
   keystore), and refused by name where there is none (JKS stores).
3. SASL: `SASL_PLAINTEXT` and `SASL_SSL` with `sasl.mechanism` PLAIN, SCRAM-SHA-256 and
   SCRAM-SHA-512; `sasl.jaas.config` naming `PlainLoginModule` or `ScramLoginModule`
   parsed into librdkafka's `sasl.username` and `sasl.password`; GSSAPI and OAUTHBEARER,
   and every other login module, refused by name.
4. Tests against a broker with SSL, SASL_SSL and SASL_PLAINTEXT listeners, with
   certificates made by `openssl` at test time (none committed); the `kafka-broker` job.
5. Probes of the Java reference (Deephaven 42.9) against the same broker for the
   properties it accepts and its errors.
6. The Python package passes the properties through; console tests that they reach the
   client and that refusals raise `DHError`.

Out of scope: Kerberos (Cyrus SASL) and OAUTHBEARER over OIDC (libcurl), which the ruling
keeps off; TLS to the schema registry.

## Notes

**gzip.** `rdkafka` gains `libz-static`: `libz-sys` 1.1.33 (MIT OR Apache-2.0) compiles the
zlib 1.4 sources it carries and links them statically, with `vcpkg` 0.2.15 (MIT OR
Apache-2.0) as a build dependency that only acts on Windows. The test binaries link no
`libz.so` (`ldd`). Consuming reads gzip batches written by Java's console producer and by
librdkafka; `compression.type=gzip` is accepted when producing, and broker.sh checks with
`kafka-dump-log.sh` that the batches written are gzip. The refusals and their tests are
gone.
