## Scope

The 7.4.6 row of `docs/KAFKA.md`, "Tasks", without its corpus:
`consumer.consume_to_partitioned_table` for the table types Java allows (blink, append,
ring), with Java's checks and error texts; one constituent per topic partition, with
Java's key column (`Partition`, `int`) and constituent column (`Table`); `partitions`,
`offsets`, and every key and value spec that `consume` supports. The result behaves as the
other partitioned tables of the engine (`constituent_tables`, `merge`, `get_constituent`,
`transform`, `proxy`). Each behaviour is probed on the Java reference with the same
broker, and covered by unit tests and a round trip in the `kafka-broker` job.

Out of scope: the recorded Java corpus for consumption under `oracle/corpus` and its
replay through a scripted source, which the row of `docs/KAFKA.md` also names. It changes
the protected `oracle/` folder and is a task of its own.

## Notes

`docs/KAFKA.md`, "A table per partition", has what was built. `src/partitioned.rs` makes
the stream table of each partition and the table of tables, a root table of the engine
whose update source shows the constituents added since its last refresh, as Java's
`StreamPartitionedQueryTable#run` does. It is made before the constituents, so it
refreshes first, as Java's `UpdateSourceCombiner` orders them.

**The task's wording and Java.** The scope said constituents are "added as partitions
first produce records". Java does not do that: `KafkaIngester`'s constructor registers a
consumer, and so a constituent, for every partition it is assigned, before any record, and
the table of tables shows them all on the next update cycle (probed: blink constituents of
a topic whose records had passed are there, empty). That is what is built.

**Outside the task's paths.** `crates/oxhaven-engine/src/ops/partitioned/merge.rs`: a
merge now fails when a constituent it would listen to has failed, when it is made (the
call fails) or in the cycle that shows the constituent (the merge fails), with Java's
`TableAlreadyFailedException: Can not listen to failed table QueryTable`. Before, the
merge listened to the failed table and went on without its rows. Partition aggregations
never show a failed constituent, so only this task's tables reached it.
`crates/oxhaven-kafka/src/client.rs`: the topics that exist are listed before the topic
is asked for (see "Probes").

### Probes

Java on port 10898, Oxhaven on 10899, one broker (`apache/kafka:3.9.1`), topics `kp3`
(three partitions, nine records with keys) and `kp2` (two partitions, six records, one of
them `xx`, which is not JSON). Each case is a script sent with `run_script`; tables are
read in a later script, because Java runs no update cycle while a script runs (a first
round that waited inside the script saw no rows on Java at all). 38 cases in three rounds:
22 on the table types, `partitions`, `offsets`, `get_constituent`, `filter`, `sort`,
`transform`, a proxy and the errors; 12 on a bad record, merges made before and after it,
a topic of two partitions, the order of a merge and a topic the request creates; 4 on a
topic the request creates, for both forms.

| Case | Java | Oxhaven |
| --- | --- | --- |
| right after the call: size, constituents, merge size | `(0, 0, 0)` | the same |
| columns of the table of tables | `Partition` int, `Table` `io.deephaven.engine.table.Table` | the same |
| `key_columns`, `unique_keys`, `constituent_column`, `constituent_changes_permitted`, `is_refreshing`, constituent columns | `['Partition']`, True, `Table`, True, True, the columns of `consume` | the same |
| keys of `kp3` | `[1, 2, 0]` | `[0, 1, 2]` (owner's item 26) |
| append: rows of each constituent and of the merge | each partition's records in offset order | the same |
| blink, after the records passed | three blink constituents, empty | the same |
| `partitions=[2, 0]`, `ring(2)` | keys `[2, 0]`, the last two records of each | keys `[0, 2]`, the same rows |
| `offsets={0: 1, 1: SEEK_TO_END, 2: SEEK_TO_BEGINNING}` | from offset 1, nothing, everything | the same |
| `transform(lambda t: t.tail(1))`, `proxy().where(...).head(2)` | the last row, the first two kept rows of each | the same |
| `get_constituent(1)`, `get_constituent(5)` | partition 1's rows, `None` | the same |
| `filter('Partition > 0')`, `sort('Partition')` keys | `[1, 2]`, `[0, 1, 2]` | the same |

| merge after that | `TableAlreadyFailedException: Can not listen to failed table QueryTable` | the same (after the change to `merge.rs`) |
| merge made before the first cycle | failed | failed (after the change to `merge.rs`; before it, not failed) |

Not probed: Avro and Protobuf specs through a partitioned table (the specs are the ones
`consume` uses, unchanged); a broker failure under a partitioned table (the scripted test
covers a failed poll); records arriving while a Java table is watched over several cycles
(the broker test covers it on Oxhaven only).

### Tests that can fail

Each new test was broken once (`mutate.py` in the scratch directory: one change to the
code, the tests run, the code restored):

| Change | Tests that failed |
| --- | --- |
| a bad record fails every constituent | `a_record_that_cannot_be_read_fails_its_partition_alone` |
| the merge does not check for a failed constituent | `a_merge_fails_with_a_failed_constituent` |
| the table of tables shows its rows in reverse | `each_partition_is_a_constituent_from_the_next_cycle` and three others |
| a failed poll fails nothing | `a_failed_poll_fails_every_constituent` |
| no check for no partition | `no_partition_is_java_s_null_pointer_exception` |
| the last constituent dropped does not stop the thread | `dropping_the_partitioned_table_stops_the_consumption` |
| every record goes to the first constituent | `records_of_partitions_not_read_are_dropped` and four others |
| the table type is ignored (blink constituents) | `append_and_ring_constituents_keep_their_rows`, `a_record_that_cannot_be_read_fails_its_partition_alone` |
| the table of tables shows its rows at once | six of the eight |
| a topic made by the request keeps librdkafka's partitions | none: the broker test passed three times with this change. librdkafka's answer for a topic it has just had created depends on timing (the probe server got partition 0, the test got none), so the broker test is not evidence for the change in `client.rs`; the probe is |
