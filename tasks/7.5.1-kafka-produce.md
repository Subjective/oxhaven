## Scope

The 7.5.1 row of `docs/KAFKA.md`, "Tasks": `deephaven.stream.kafka.producer.produce` over
librdkafka's producer, with `simple_spec`, `json_spec` and `KeyValueSpec.IGNORE`,
`publish_initial`, `last_by_key_columns`, the default `partition`, and the records Java
publishes for the rows a table has and for the adds, removes and modifies of each cycle.
The returned callback stops publishing. Avro and raw specs and the topic, partition and
timestamp columns are 7.5.2 and are refused by name.

Each behaviour is probed on the Java reference with a real broker before it is decided:
the records of the initial rows and of each kind of change, with and without
`last_by_key_columns`, keys and values byte for byte, nulls, the partition and timestamp
of records, the callback, a table that fails, a broker that cannot be reached. Broker
tests in `crates/oxhaven-kafka/tests` cover producing, with a produce-then-consume round
trip, so that the `kafka-broker` job runs them.

## Notes

Built:

- `deephaven.stream.kafka.producer` over `oxhaven_kafka::produce`. The specs are
  `simple_spec`, `json_spec` and `KeyValueSpec.IGNORE`; the options are
  `publish_initial`, `last_by_key_columns` and `partition`.
- Records go out as `PublishToKafka` sends them: the rows a table has, then each cycle's
  removes as tombstones, then its adds and modifies.
- Records are serialized as Kafka's serializers and Jackson write them.
- Producer properties are translated for librdkafka.

`docs/KAFKA.md`, "Producing", has the details. Its "Refused, by Java method" table has
the refusals, and "For the owner's ruling" items 11 to 14 have the open questions.

The work stopped once, when the machine's disk filled. It was resumed after the
coordinator freed space.

Verification:

- `cargo test -p oxhaven-kafka`: unit tests and `tests/produce.rs`, the scripted sink.
  Mutations of the publisher, the chunking, the flush and the settings were each caught
  by a test.
- `tests/broker.sh`: a round trip through `consume`, the partitions murmur2 gives on a
  topic of two, `partition=1`, and the metadata timeouts. A wrong partitioner, and a
  partition that is not set, are each caught.
- `console::python::kafka`: the Python checks, refusals and errors.
- Probes p1 to p5 ran on Java (port 10986) and Oxhaven (port 10987), on one broker. The
  records were the same byte for byte: simple specs; JSON of every column type Oxhaven
  can build; mappings and nesting; the records of refreshing tables, `last_by`, blink
  tables and failures; the partitions; the encodings; the properties. The error texts
  were the same too.
- Differences found in the probes:
  - the refusals decided above;
  - Java's identity number in `LivenessScope-NNN`;
  - one metadata wait per batch rather than one per record;
  - how a cause chain is printed (Oxhaven inline, "(caused by ...)");
  - `DHError`'s last line: the port's shared `dherror.py` leaves out the type name of
    the cause.
- The probe tables with `BigDecimal` and other object columns could not be built on
  Oxhaven: its formulas have no `new java.math.BigDecimal(...)` or
  `BigDecimal.valueOf(...)`. Their JSON forms are checked by unit tests against the
  text Java published.
- One consumer behaviour was not compared and is outside this task: a JSON `consume` of a
  tombstone (a record with no value) fails the table here. The round-trip test reads the
  values as text instead.
