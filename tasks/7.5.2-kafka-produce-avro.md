## Scope

The 7.5.2 row of `docs/KAFKA.md`, "Tasks": `producer.produce` with `topic_col`,
`partition_col` and `timestamp_col`, with Java's checks, their precedence over `topic` and
`partition`, and Java's texts; `producer.avro_spec` for the key and the value (a schema from
the registry by subject and version, `field_to_col_mapping`, `timestamp_field`,
`include_only_columns`, `exclude_columns`, `publish_schema` with `schema_namespace` and
`column_properties`), and records in Confluent's wire format, byte for byte as Java writes
them; the raw spec, if the reference's Python reaches it. The `kafka-broker` script gains an
Avro produce-then-consume round trip and the three column options.

Each behaviour is probed on the Java reference and on this server against the same broker
and a request-logging registry stub, and the records compared byte for byte.

## Notes

### What was built

- `producer.avro_spec` for keys and values (`src/avro_produce.rs`): the schema from the
  registry by subject and version, or made from the columns with `publish_schema`;
  `field_to_col_mapping`, `include_only_columns`, `exclude_columns`, `timestamp_field`,
  `schema_namespace`; Avro's binary encoding as `GenericDatumWriter` writes the boxed
  cells, with its failures; Confluent's wire format, with the schema registered under the
  topic's subject first (`Registry::register`, a POST).
- Java's `Schema#toString` (`src/avro_text.rs`), so the registry is sent the same text.
- `produce` with `topic_col`, `partition_col` and `timestamp_col`, with Java's checks,
  texts and precedence; the producer waits for a record's topic before serializing it, as
  `KafkaProducer#doSend` does (`RecordSink::ready`).
- The raw spec: `KafkaTools.Produce#rawSpec` takes a Java `Serializer` class, and the
  reference's `producer.py` has no `raw_spec`. Not reachable from Python; nothing ported.
  `docs/KAFKA.md` says so.
- Schemas fetched for producing are read without checking defaults
  (`avro::parse_registered`), as Confluent reads them.
- Shared with the consumer, changed: `UncheckedDeephavenException` from the registry now
  carries its cause (`... (caused by ...)`) as Java's does, and a null schema version is
  `Cannot parse null string` (Java's text when producing; see "For the owner's ruling" 21).

### Probes

Java on 10948, Oxhaven on 10949, one `apache/kafka:3.9.1` broker, and a registry stub that
logged every request with its body and handed out ids in order. Each case ran on both with
its own tag in topic and subject names; the comparison takes, per case, the error's
exception chain, the registry requests (Java's `/associations/...` left out), and every
record of the case's topics (partition, key and value as hex, and the timestamp where it
comes from a column).

| Round | Cases | What | Result |
| --- | --- | --- | --- |
| 1 | 22 | Avro value and key from the registry, nulls, mappings, include and exclude, published schemas (with `byte`, `short`, `char`, `Boolean`), version with `publish_schema`, no registry URL, `timestamp_field`, a missing subject; the three columns, their type and missing-column checks, a negative timestamp, a null topic, `partition` with `partition_col` | same in all, once the fixes below were made, except a10 (the timestamp field holds the time of making) and the send times of c1 and c2 |
| 2 | 420 | every column type (byte, short, char, int, long, float, double, String, Boolean, Instant, and nulls) against every Avro field type (primitives, nullable unions, other unions, enum, fixed, bytes, array, map, record, logical types) | same in 390, rerun after the fixes (in the first run 241 differed only in that Java's topic existed and was empty and Oxhaven's did not exist; fixed by waiting for the topic before serializing). The other 30, every `char` case, never reach `produce`: the probe's `char_col` with a Python `str` fails in `new_table` on both servers, in other words (`TypeError: ...` in Java, `failed to create a Java char array. : ...` here), outside Kafka. `char` columns are probed in round 3 instead |
| 3 | 37 | char columns, negative instants, schemas that are not records, the timestamp field's checks, enums and unions in namespaces, docs and properties, a bad default, published-schema names (dots, dashes, digits, namespaces), include and exclude when publishing, a key and a value both Avro, topics from a column with an empty one, a registry that is down, `schema_version` `1` and `None`, `last_by_key_columns` with an Avro key | same in 28; the other 9 below |
| 4 | 5 | registry schemas with names Java's parser refuses (field, record, enum symbol, empty) and a bad `long` default | the record of the bad default is the same; the 4 refusals differ in text only (below) |

The differences that remain:

- r_ts_first, a10: the timestamp field holds the time the record is made.
- r_pub_dot, r_pub_dotns, r_pub_badns, r_pub_incl, r_pub_excl: the 4 bytes of the schema
  id, which the stub gave in the order of requests; the rest of each record and every
  request are the same.
- r_ts_nanos: refused by name (Java's text prints `LogicalTypes$TimestampNanos@10474dac`).
- r_neg_ts: refused by name. Java sends the timestamp 0 (-1500 ns truncated); librdkafka
  takes 0 as the time of sending.
- r_topics: the send failure's cause is written after a colon, as since 7.5.1; Java chains
  it. The records and the registry requests are the same.
- h_fname, h_rname, h_sym, h_empty: the same `SchemaParseException` text; Java wraps it in
  Guava's `UncheckedExecutionException` and Confluent's `IllegalArgumentException: Invalid
  schema {...}`, which prints a GUID.

Fixed after the probes showed a difference: the topic is waited for before the record is
serialized (a7, a7b, r_topics, and the 241 of round 2); a fetched schema's defaults are not
checked (r_dec); the cause of `UncheckedDeephavenException` (a11, r_reg_down); the text of
a null version (r_version_none).

### Tests, and that each can fail

`tests/produce_avro.rs` (6 tests, a scripted sink and a registry the test serves),
`src/avro_text.rs` (Java's `Schema#toString` on 6 probed schemas), two broker tests in
`tests/broker.rs`, and the console tests of `console::python::kafka`. Each new test was
broken once, by changing the code under it, and failed: the magic byte, the null text, the
`Boolean` field of a published schema, the partition column, the previous values of a
removed row, the namespace of `Schema#toString`, the check of defaults, the wait for the
topic, the refusal of 0 ms, and in the broker tests the magic byte and the truncation of
timestamps.
