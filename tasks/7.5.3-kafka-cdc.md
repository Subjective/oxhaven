## Scope

The 7.5.3 row of `docs/KAFKA.md`, "Tasks": `cdc.consume`, `cdc.consume_raw`,
`cdc.cdc_long_spec` and `cdc.cdc_short_spec` as `CdcTools` implements them, over Avro specs
read from the schema registry (Debezium's key and value schemas, the `after`, `before`
and `op` fields, `last_by` on the key, the columns dropped, the topic and subject names of
the two spec forms). What Java does with deletes and tombstones is probed and reproduced,
or refused by name. The Avro features 7.4.7 refused that Debezium's schemas need are
ported where small, otherwise refused by name, with the Debezium shapes that work and
those that do not listed. Each behaviour is probed on the Java reference with the same
broker and a stub registry, and covered by a round trip in the `kafka-broker` job.

## Notes

**Built.** `oxhaven_kafka::consume_cdc`, `consume_cdc_from`, `consume_cdc_raw`,
`current_rows`, `CdcSpec` and `CdcOptions` (`crates/oxhaven-kafka/src/cdc.rs`), the native
functions `kafka_cdc_consume` and `kafka_cdc_consume_raw`, and
`deephaven/stream/kafka/cdc.py` (`consume`, `consume_raw`, `cdc_long_spec`,
`cdc_short_spec`, `CDCSpec`). `docs/KAFKA.md`, "Change data capture", has what each does.
Two lines register the native functions in `console/python/mod.rs`, outside the paths
this task owns.

**Probes.** Java on 10878, Oxhaven on 10879, one broker (`apache/kafka:3.9.1`) and a stub
registry that logs every request; 249 cases in six rounds: the Debezium Postgres envelope
of a table of every common column type (`customers`, with a `connect.decimal`), the same
without the decimal (`customers2`), a composite key, a key without fields, nested
records, a value without `op`, a key field missing from `after`, `op` values `c`, `u`,
`r`, `d`, `D`, empty and `t`, a delete followed by its tombstone, a key reinserted after
it, evolved schemas and numbered versions, both spec forms with every argument `None`,
of a wrong type or empty, subjects shared by key and value, `partitions`, `stream_table`
and `cols_to_drop` of every Python type, `consume_raw` with each table type, and the
registry or the broker absent. Compared: the columns, types and rows of each table, the
error of each call, and the registry requests made before the first record.

Same in 196. Different in 53, each by design:

- 22: a non-key `BigDecimal` column of the current-rows table, refused by name
  (`BlinkLastChunkedOperator`) where Java shows the rows. The 99 cases over `customers2`
  cover the same calls without the decimal, and match.
- 21: `cols_to_drop` given as `jcompat.j_array_list(...)`, the only way it works in Java;
  this package has no `jcompat`.
- 4: a `None` topic, refused by name (`KafkaConsumer#partitionsFor`) where Java fetches
  both schemas and then fails asking the broker (`Unexpected error fetching metadata`).
- 2: no broker, text only (`PARITY.md` A5, as since 7.4.4).
- 2: registry credentials (`basic.auth.user.info`), refused since 7.4.7.
- 1: a plain `bytes` column (Postgres `bytea`), refused since 7.4.7 where Java's table
  fails.
- 1: `stream_table=numpy.bool_(True)`: Oxhaven's interpreter in the probe had no
  `numpy`, so the case did not run; Java refuses it (no overload).

**Java's behaviour reproduced, for the owner.**

- A Debezium tombstone after a delete brings the deleted key back as a row of null
  columns in the current-rows table (`last_by` keeps the tombstone, whose `op` is null,
  and `op != `d`` keeps it). Reproduced, not refused.
- `cdc.consume` with any Python `cols_to_drop`, even `[]`, fails in Java with `no matching
  Java method overloads found`; so does `consume_raw` with any `TableType`, its default
  included. Reproduced. Only `table_type=TableType.<x>().j_object` works on both.
- The registry client caches the latest version of a subject and schemas by id, not a
  numbered version; Oxhaven's registry client now does the same, which also changes
  `avro_spec` of a plain `consume` when key and value name the same subject (one
  request fewer, as Java).

**Debezium shapes.** Work: the envelope (`before`/`after` as unions of null and the row
record, `source`, `transaction` as a union of null and a record, `op`, `ts_ms`, `ts_us`,
`ts_ns`); `io.debezium.time.Date`, `MicroTimestamp` and the other names on `int` and
`long` (as their plain types); `io.debezium.data.Enum` on `string`; `connect.decimal`
(`bytes` with `decimal`) in the blink and raw tables. Refused by name: a plain `bytes`
column; a decimal (or `BigInteger`) non-key column in the current-rows table, until the
engine's `last_by` of a blink table holds objects other than primitives and strings.

**Tests.** `tests/cdc.rs` (five, a scripted source and a registry stub served by the
test), `tests/broker.rs`,
`change_events_become_the_current_rows_of_their_table` (both forms against the broker),
and `deephaven_kafka_cdc_checks_refuses_and_raises_dherror` in the console. Each was
broken once (a mutation of `cdc.rs` or `cdc.py`) and failed.
