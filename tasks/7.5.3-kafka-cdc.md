## Scope

The 7.5.3 row of `docs/KAFKA.md`, "Tasks": `cdc.consume`, `cdc.consume_raw`,
`cdc.cdc_long_spec` and `cdc.cdc_short_spec` as `CdcTools` implements them, over Avro specs
read from the schema registry (Debezium's key and value schemas, the `after`, `before`
and `op` fields, `last_by` on the key, the columns dropped, the topic and subject names of
the two spec forms). What Java does with deletes and tombstones is probed and reproduced,
or refused by name. The Avro features 7.4.7 refused that Debezium's schemas need are
ported where small, otherwise refused by name, with the Debezium shapes that work and
those that do not listed. Each behaviour is probed on the Java reference with the same
broker and a stub registry, and covered by a round trip in the `kafka-broker` job.

## Handover

Not started: the agent that did 7.4.6 on the same branch stopped at its size limit after
part A. Nothing of cdc is built; `deephaven.stream.kafka.cdc` still does not exist. What
was read of the reference, for the next agent:

- `CdcTools#consumeToTable` (lines 297-345 at v42.9) fetches the value schema, then the
  key schema, from the registry by subject and version (`AvroImpl#getAvroSchema`), then
  calls `KafkaTools#consumeToTable` with `ALL_PARTITIONS_SEEK_TO_BEGINNING`, `avroSpec` of
  each schema and a blink table. It `view`s that table to the key's fields as they are,
  `X=after__X` for each column whose name starts with `after__` (`CDC_AFTER_COLUMN_PREFIX`
  is `after` and Java's nested separator `__`), and `op`. As a blink table it drops
  `drop_columns`; otherwise it is `last_by` of the key's field names, then `where("op !=
  `d`")`, then drops `drop_columns` and `op`. All of these operations exist in the engine.
- `consumeRawToTable` is `consumeToTable` of the topic with `avroSpec(subject, version)` of
  the key and the value and the table type given.
- To probe first: a Debezium tombstone (a record with the key and no value), which comes
  after each delete by default. Avro reads it as a row of null cells (7.4.7), so after
  `last_by` its `op` is null and `op != `d`` keeps it: Java may show a deleted key again,
  with null columns. Reproduce or refuse it by name, and report it.
- Debezium's value schema: `before` and `after` are unions of `null` and the row's record,
  `source` a record of strings, longs and unions with null, `op` a string, `ts_ms` and
  `ts_us`/`ts_ns` unions of null and long, `transaction` a union of null and a record.
  Whether 7.4.7's reader takes a union of null and a *record* (and flattens it) is the
  first thing to check; Debezium's own logical types (`io.debezium.time.*`,
  `connect.decimal` on `bytes`) are names on `int`, `long` and `bytes` fields, which 7.4.7
  maps as their plain types or refuses (`bytes` without Avro's `decimal`).
