## Scope

Done here, each observed on Java 42.9 first (`docs/PARTITIONED.md`, "Transforms"):

- `transform` of a refreshing partitioned table: the function is called in the update cycle
  for each constituent that appears, also for a key that has rows again, and for a row
  whose constituent changes.
- `partitioned_transform`, of partitioned tables that are refreshing and that are not, in
  any mix: the pairs follow the keys of both.
- `dependencies`: the function waits for them in a cycle, and one makes the transform of a
  partitioned table that is not refreshing a refreshing one.
- What Java refuses of a function, when the result is made and in a cycle: raising, `None`,
  something that is not a table, other columns, a refreshing table where none may be.
- `Table.is_failed` in the Python package, to assert with in the failure scenario.

Not done, and refused by name:

- `partitioned_transform` of a partitioned table whose keys are not unique
  (`PartitionedTableImpl#partitionedTransform`, its `join`): nothing makes such a table
  before 7.6.3.
- A function that enters an execution context to compile formulas (6.12).

## Handover for 7.6.2 (`PartitionedTableProxy`), not started

- Java is `PartitionedTableProxyImpl` (1173 lines). Each operation is `basicTransform` (one
  partitioned table: `transform`) or `complexTransform` (the other argument is a table, or
  a proxy: `partitioned_transform`), which `PartitionedTable::transform` and
  `partitioned_transform` now are. Both take a `Transformer`, a Rust closure over tables,
  so a proxy operation needs no Python in the cycle: the closure calls the engine
  operation.
- Unlike `transform` from Python, the proxy's transforms run in an execution context that
  has a query scope (`getOrCreateExecutionContext`), so `where` and `update` with formulas
  work through a proxy. The closure has to compile its formulas with the scope of the call
  that made the proxy operation, also when it runs in a later cycle; the thread flag
  `without_query_scope` must not be set for it.
- `require_matching_keys` is `matchingKeysValidation`: a dependent table of the keys that
  only one side has, which fails when it is not empty, at once and in a cycle.
  `sanity_check_joins` is `overlappingLhsJoinKeysValidation` and its siblings: a join key
  may occur in one constituent only. Both are `DependentValidation`s that the transform
  takes as dependencies; `transform_table` has the `dependencies` argument for that, and a
  validation that fails has to fail the result, which a dependency does not do here yet.
- The proxy keeps `consistentKeyColumnNames` (`PartitionedTableImpl`'s second
  constructor), so that a filter on key columns is applied to the underlying table and not
  to each constituent (`isValidAgainstKeyColumns`). `PartitionedTable` has no such field.
- The Python class has 38 operations; the gate asks for one scenario per family. Probe
  each family on Java first: this task found the first slice's notes wrong in one place
  (`None` from a function was listed as not ported; Java refuses it).
