## Scope

Done here, each observed on Java 42.9 first (`docs/PARTITIONED.md`, "The proxy"):

- `PartitionedTable.proxy(require_matching_keys, sanity_check_joins)` and
  `PartitionedTableProxy` with its 37 table operations, of partitioned tables that
  refresh and that do not: each is the `Table` method, recorded once and run again on
  every constituent, in the update cycle for one that appears.
- The variables of a formula are those of the call, kept for later cycles.
- Consistent key columns: which a partitioned table has, which each operation keeps, and
  the filters (`where`, `where_in`, `where_not_in`) that go to the underlying table.
- `require_matching_keys` and `sanity_check_joins` of two proxies: they fail the call, or
  in a cycle the result (`PartitionedTable::require_distinct_join_keys`,
  `require_matching_keys` in the engine).
- `PartitionedTable.sort` leaves no consistent key columns, as observed.

Not done: nothing of the scope. No operation of the proxy is refused. `update_graph` of a
proxy is the target's, which is refused until 6.12 as before.

## For the owner's ruling

None of these is decided here, and none has a PARITY entry. The first group is
reproduced, the second is not reproducible, and the third is where Oxhaven differs.

Reproduced as Java does it (`docs/PARTITIONED.md`, "The proxy", the last list):

1. `PartitionedTableProxy.sort` reads a string as the sequence of its characters
   (`py/server/deephaven/table.py`, `PartitionedTableProxy.sort`, no `to_sequence`).
2. `select()`, `select(None)` and `update([])` fail with `IndexError`.
3. `weighted_avg_by(wcol)` without group columns is `avg_by(wcol)`.
4. The failure messages of `abs_sum_by`, `weighted_sum_by`, `weighted_avg_by`, `group_by`,
   `update_by`, `aj` and `raj` name another operation.
5. A filter that reads a column as an array fails through a proxy for want of a query
   scope (`PartitionedTableProxyImpl#where`).
6. A filter that reads key columns and a row variable is applied to the underlying table
   (`#isValidAgainstKeyColumns`).
7. `sanity_check_joins` with one match column fails with `NullPointerException` on a null
   join key (`#validateConstituentJoinKeys`, the map of owners).
8. `sanity_check_joins` of a join without exact match columns fails whenever two
   constituents have rows.

Unsafe or not deterministic in Java, not reproduced:

9. Java was seen to hang for good in `PartitionedTableProxyImpl#aggBy` (Python `agg_by`
   with `agg.formula`) of a refreshing partitioned table when an update cycle fell due
   during the call. Oxhaven makes the result on the calling thread under the lock.
10. From reading `#validateConstituentJoinKeys`, not observed: a join key that moves in
    one cycle to a constituent that appears in that cycle may fail the check or not,
    depending on the order in which the constituents report. Oxhaven reads the keys at
    the end of the cycle and does not fail it.
11. Which constituent's failure a failed operation reports: Java makes the constituents
    on several threads; Oxhaven reports the first in row order.

Differences that remain:

12. A proxy result that failed in a cycle afterwards: as PARITY Q11 for a transform.
13. `partition_by` of the same table and columns answers one partitioned table in Java
    (memoized), so proxies of two such calls are equal there and not here.
14. `PartitionedTableImpl#filter` sets "constituent changes permitted" when the filtered
    table refreshes; `PartitionedTable::with_table` keeps the flag it had. Older than
    this task, read and not probed: a filter string of a partitioned table that does
    not refresh cannot make it so.
