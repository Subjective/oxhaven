## Scope

- `PartitionedTable.from_partitioned_table`, with every argument and with none
  (`PartitionedTableFactory#of`), and `from_constituent_tables`
  (`PartitionedTableFactory#ofTables`), with Java's checks and texts.
- `partitioned_transform` of a partitioned table whose keys are not unique: the `join` of
  the two underlying tables.
- A copied cell of a column of tables (`select`, `snapshot`, a static `update`) keeps its
  table, as Java's does.

Then, as far as context allows (otherwise task 7.6.4 stays as sized in
`tasks/7.6-partitioned-tables.md`): `get_constituent` with a key value Java converts;
match filters and `where_in` on a column of tables; a column of tables in a formula.

## Notes

- Outside the owned paths: `crates/oxhaven-column` (`tables.rs`, and `FlatSource` and
  `WritableSource` keep the tables of the handles they store), `ops/partitioned/cells.rs`
  (the registry moved to the column crate), `console/python/partitioned.rs`
  (`constituent_for` without keys).
- Java checks the constituents of only the first 2048 rows it is given
  (`PartitionedTableImpl#validateConstituents` reads one chunk), when a partitioned table
  is made and of the rows added and of those modified in a cycle. Reproduced, for the
  owner's ruling: a null or incompatible constituent further down passes.
- The description of a table in Java's texts is `QueryTable` here always; Java writes
  other descriptions for some tables (`FilteredTable(null)` for a `where`).
- A copy of a cell keeps its table as long as the copying source stores the handle; a
  `WritableSource` gives tables up when it compacts its storage, so a table a refreshing
  copy no longer holds can live a little longer than in Java, never shorter.
