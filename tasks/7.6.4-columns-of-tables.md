# 7.6.4 Partitioned tables: columns of tables in filters and formulas, keys Java converts

- **Status:** in review
- **Track:** C
- **Needs:** 7.6.3
- **Owns:** `PartitionedTable.get_constituent` in `deephaven/table.py`; match filters and
  `where_in` of a column of tables (`crates/oxhaven-engine/src/ops/filter/`,
  `ops/distinct/where_in.rs`); the aggregations that copy cells of a column of tables
  (`ops/agg/`); a column of tables in a formula, as far as the formula crate needs it for
  that; their tests

## Scope

In this order, each probed on Java 42.9 first:

1. `get_constituent` with a key value that is not of the key column's type.
2. Match filters on a column of tables: `C == null`, `C != null` and what else Java's
   convertor takes for that type.
3. `where_in` and `where_not_in` on a column of tables.
4. Aggregations that copy cells of a column of tables (`first_by`, `last_by` and the
   like), keeping the tables alive through the sources of `crates/oxhaven-column`.
5. A column of tables in a formula, as far as Java supports it and it is cheap and
   clearly defined; the rest refused by name.

## Gate

- `OXHAVEN_TEST_SEEDS=full cargo test -p oxhaven-engine partitioned`
- `cargo test -p oxhaven-server partitioned`, with and without `--features python`
- The replay gate, as before.

## Probes

Each case run on Java 42.9 (`oracle/bin/start-java.sh`) and on this server with the same
script through `run_script`, the results compared line by line. "Same" is the same value,
or the same failure with the same text after the Java exception's class.

Aggregations of a column of tables: `first_by`, `last_by`, `agg.first`, `agg.last`,
`agg.sorted_first` copy the cell, also read after the partitioned table is gone; `group_by`
makes a vector of tables; `count_by` works; `min_by`, `max_by`, `sum_by`, `agg.unique`,
`agg.distinct`, `agg.count_distinct` fail on both (Java "Failed to add data", here "not
ported"); `head_by` and `tail_by` fail on both with Java's text. Same here.

Formulas: `isNull(C)`, `!isNull(C)`, `C == null`, `C != null`, `C == C`, `C != C`,
`C == 1`, `` C == `a` ``, `C == K`, `C == true`, `C == 1.5`, `C != 1`, `isNull(C) ? `none` :
`some``, `update("D = C")`, `select("D = C")` and a filter of it, `update("D = isNull(C) ?
null : C")`: same. `update_view` and `view` of `isNull(C) ? null : C` on every source: "Cannot
use view or updateView to produce results of type class ...QueryTable", same. `C.size()`,
`C == null ? 0 : C.size()`, `C.toString()`, `(Object) C`, `C + "x"`: Java computes (or
fails on the null cell) and here they are refused. `view("C")`, `view("D = C")` and
`update_view("D = C")` of a natural join, an `update` or a ticking join: Java refuses, here
they work.

## Notes

- Outside the owned paths: `ops/select/mod.rs` (the refusal of `view`), `crates/oxhaven-expr`
  (`is_object` and `class_of`: a cell of tables is an object), and the text of a failed
  literal conversion of a match filter, now Java's "Failed to convert literal value" with
  the Java class of a column of tables or of a time class (a console test checked the old
  text).
- No scenario: the probes above are kept as the engine tests `partitioned::column_tests`
  and the Python test `get_constituent_converts_key_values_as_java_does`; a recorded
  scenario would change `oracle/`.
- For the owner: Java's `get_constituent` truncates a float key toward zero and wraps an
  integer key to the column's width (`1.9` finds key 1, `4294967297` finds key 1 of an
  `int` column, `257` finds 1 of a `byte` column). Reproduced, not decided.
