## Scope

`include_constituents`: the rows of the source under the finest groups of a rollup.

- The level: the source partitioned by all the group-by columns; without group-by columns
  the source under the grand total. Static and ticking.
- The snapshot: the columns of the source after those of the aggregated nodes, each null
  for the rows of the other kind; the fields of the schema as Java describes them.
- Sorts of the rows of the source: the Python recorder for `NodeType.CONSTITUENT`, and
  the translation of the sorts of `Apply`. Filters, which the rows of the source follow.
- The IDE's Rollup Rows panel with its default, constituents included.

What a client sees is in `docs/HIERARCHICAL.md`, "Constituents".

## Handover: 7.8.2, format views and update views

Not started. What the next task finds:

- **Java, read but not probed in this task.**
  `RollupNodeOperationsRecorder#updateView` refuses a column that exists (`Column <name>
  already exists`), keeps the first of two views of one name, and a recorder's result
  definition is the node definition with the views applied to an empty table.
  `BaseNodeOperationsRecorder#formatColumns`, `#formatRowWhere` and `#formatColumnWhere`
  go through the table's own format methods on a recording adapter and keep the
  resulting formatting columns (`ColumnFormatting#isFormattingColumn`); anything else is
  `Invalid formatting columns found in ...`. A node's table is its base table with the
  update views, then the formats (`RollupTableImpl#applyNodeFormatsAndFilters`), then the
  sorts. `RollupTableImpl#withNodeOperations` rebuilds the available columns when a
  recorder has formats or update views, so the snapshot schema grows by the new columns,
  per node type. `RollupTable#withUpdateView` is the aggregated recorder's `updateView`.
- **The service.** `HierarchicalTableServiceGrpcImpl#apply` reads update views, then
  format views, validates their expressions against the *source's* definition
  (`#translateAndValidateUpdateViews`), and applies them per node type before the filters
  and the sorts; for a rollup without constituents it drops the constituent ones without
  a word. For a tree it reads neither (`docs/HIERARCHICAL.md`, "Where Java does
  otherwise"): probe again, the ruling is still open.
- **Translation.** `#translateAggregatedNodeOperationsForConstituentNodes` also carries
  formats and update views to the constituent nodes when every column they read is a
  column of the source of a compatible type; only the service's sorts call it today.
- **Here.** `RollupTable` keeps two lists of sorts (`sorts`, `constituent_sorts`) and
  `Hierarchy::order` applies them at a snapshot; update views and formats need the
  same per node type, evaluated in `Hierarchy::fill` for the rows of the viewport, and
  `Hierarchy::columns` already allows a column per node type. A sort by a column an
  update view adds then needs the view evaluated for the whole node. The schema writer
  (`crate::schema::arrow_schema`) already links `<name>__TABLE_STYLE_FORMAT`,
  `__TABLE_NUMBER_FORMAT` and `__TABLE_DATE_FORMAT` columns to their column. The
  `deephaven` package here has no `Table.format_columns`, `format_row_where` or
  `format_column_where`, and no script scenario formats a table: formats of plain tables
  are not ported, so the formats of a node have nothing to stand on yet. Whether
  `oxhaven-expr` compiles what a format needs (colour constants and the functions of
  `io.deephaven.gui.color.Color`) was not looked at; report what is missing rather than
  extending the expression crate. Update views need formulas only and can come first.
- **Gate as tasks/7.8-rollup.md has it:** scenarios `rollup_formatted*` and
  `rollup_update_view*`, and the snapshot schema of each compared with Java's field by
  field in a handler test.
