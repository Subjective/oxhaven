## Scope

In order, each probed on the Java reference before it is written:

1. The tree recorder's formats and filters: `format_column`, `format_row_where`,
   `format_column_where` and `where` of the Python `TreeNodeOperationsRecorder`
   (`TreeNodeOperationsRecorder#formatColumns`, `#formatRowWhere`, `#formatColumnWhere`,
   `#where`), applied with `TreeTable.with_node_operations`; the formatting columns in the
   snapshot schema; a node's rows that a node filter drops, and the expandability of a row
   whose children it drops. `Apply` keeps ignoring a tree's views, as Java's does.
2. Colours as formula values, refused in 4.21: a colour as the value of a column
   (`AK = RED`, `RED.toHex()`, `new Color(..)`), `io.deephaven.engine.util.ColorUtil.RED`,
   `colorRGB(int, boolean)`, with the column type Java sends for a colour column, if the
   object column type of 5.10 can hold it without a contract change.
3. Formats and update views carried to a rollup's constituent nodes as
   `RollupTableImpl#translateAggregatedNodeOperationsForConstituentNodes` allows, only on
   the call paths where Java does it.

## Notes

- **Piece 1, built.** The tree recorder is the rollup's `NodeOperations` with filters
  (`where_filters`) and without update views; `TreeTable::with_node_operations` takes
  one, with Java's refusal of a recorder that changes the columns of nodes that have
  operations. A node's table is its rows with the formatting columns, then the rows that
  pass the filters (`node_ops::filtered_node`), evaluated at every snapshot; a row none of
  whose children pass is not expandable. Scenario `tree_formatted` (ticking, with the
  refusals) recorded from Java 42.9, clean. `docs/HIERARCHICAL.md`, "Trees", has the
  observations.
- **Found and reproduced:** with node filters and sorts, a key that expands a row the
  filter drops fails the view of a ticking tree in Java (`LinkedDirective#setRowKeyInParentSorted`
  asserts) and is passed over for a static one (`SortOperation#getReverseLookup` has no
  lookup for a static sort). The walk now fails only when the hierarchy's source is
  refreshing; no other case of a static node missing a row exists. Needs a ruling, as
  the failure is an assertion of Java's.
- **Piece 2, in part.** Java sends a colour column as Arrow `Utf8` with
  `deephaven:type` `io.deephaven.gui.color.Color`, cells `Color{r,g,b,a}`
  (`Color#toString`), not sortable. `ColumnType::Object(Some(class))` names a class by a
  `ColumnType`, and no `ColumnType` is `io.deephaven.gui.color.Color`, so a colour column
  needs a contract change (a variant for the class, or an object type that carries a
  Java class name and a text form of its cells); not done. Built without it:
  `io.deephaven.engine.util.ColorUtil.<colour>` and the three bits of `ColorUtilImpl`
  are `long` styles in Java (observed), with `PINK`, `ORANGE` and `GREEN` those of the
  `DB_` colours; `colorRGB(int, boolean)` as an argument of the style functions has the
  style of its red, green and blue (observed), with a literal flag only (a flag that may
  be null is refused). Scenario `table_format_colors`, clean. Still refused by name:
  `AK = RED`, `RED.toHex()` (which needs a null `Color` to fail, and a style cannot say
  null), `new Color(..)`, `colorRGB(int, boolean)` as a value.
- **Piece 3, skipped: Java never does it.** The only caller of
  `RollupTable#translateAggregatedNodeOperationsForConstituentNodes` is
  `HierarchicalTableServiceGrpcImpl#apply` (line 319), with a recorder of sorts alone
  made just before; its formats and update views are always empty there, and the Python
  package does not call it. Formats and update views are never carried to constituent
  nodes in Java 42.9, so nothing is carried here; the sorts already are (7.8.3).
- No contract changed. Changed under `oracle/` (additive): two scenarios, their
  recordings and their two `clean` lines in `oracle/replay-baseline.json`.
- Outside the listed paths: one condition in `ops/hierarchical/walk.rs` (above), and
  `static_field` of `crates/oxhaven-expr/src/types/mod.rs`, which asks `types/color.rs`
  for the fields of `ColorUtil`.
