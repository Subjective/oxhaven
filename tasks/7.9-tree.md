## Scope

Task 7.8 wrote the design and built what a tree shares with a rollup: key table directives
and their linking, the walk and its snapshot of a range of rows, the view, `View` and
`ExportSource`, the object type and its descriptor, the subscription, the harness's `views`
directive and the IDE route's helpers. None of it knows about rollups; it is written against
the trait `ops::hierarchical::Hierarchy`.

This task is the tree's `Hierarchy` and what makes one:

- `tree(source, identifier column, parent column)`: one node table per parent identifier,
  which is the source partitioned by the parent column (`partition_by`); the root's children
  are the rows whose parent is null. A node key is one value, the identifier; its depth is
  found by walking up.
- A row can be expanded if its identifier is a parent of some row, and `__EXPANDED__` is
  null for a row that is not. `Hierarchy::rows_expandable` answers for a whole level
  (`Expandable::All` or `None`); a tree needs the answer per row, which is a third case of
  `Expandable` and of the walk where it writes the column.
- `promote_orphans`: rows whose parent is not an identifier of any row become children of
  the root, and stop being so when the parent appears.
- Ticking: a row that changes its parent, a parent that appears or goes, an expanded node
  that goes away.
- `HierarchicalTableService/Tree`, the `treeTable.*` metadata of the snapshot schema
  (`HierarchicalTableSchemaUtil`), Python `Table.tree` and `TreeTable`.
- The key table of a tree's view has `__DEPTH__` and the identifier column; read
  `TreeTableImpl#makeNodeKeySource` and `#getDefaultExpansionNodeKeys` before assuming it is
  the rollup's.

Left to follow-up tasks, to be written into this file when the first slice is done:
filters, which keep the ancestors of the rows that pass (`TreeTableFilter`), and the node
operations of `Apply` (sorts, formats, update views), which are 7.8.1 and 7.8.2 with a
tree's one node type.
