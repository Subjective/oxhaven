# 8.1 End-to-end benchmark against Deephaven

- **Status:** in review
- **Needs:** none
- **Owns:** `bench/`, `docs/BENCHMARK.md`, the `bench/` line of the layout table in `AGENTS.md`

## Scope

A first end-to-end benchmark of Oxhaven against Deephaven 42.9: a runner under `bench/` that
runs each case on two servers through the oracle's Python client, checks that both give the
same result, and writes a JSON file and a Markdown table; a first set of static cases at two
sizes and one ticking case; one measured run; `docs/BENCHMARK.md` with the method, the results
and a reading of them. No engine, server or oracle changes, and no tuning.

## Gate

`cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`, `scripts/check-commit-subjects.sh origin/main..HEAD`, and a complete
run of `bench/bench.py run` against both servers.

## Notes

- Results, method and reading: `docs/BENCHMARK.md`; raw results of the two runs and the full
  table with min-max and load per case: `bench/results/2026-11-17*`.
- Every case gave the same result on both servers in both runs (row count, numeric column sums,
  a position-weighted sum, first and last three rows). No case was refused and none failed;
  no wrong answer or crash in Oxhaven to report.
- Both runs were taken while other agents were building and testing on the machine (load
  average 2.9 to 9.2 on 4 cores); the load could not be made low. The doc says so and records the
  load per case.
- Java was started with `oracle/bin/java_server.py` as the oracle does, but with `--heap 5g`
  instead of 2 GB for the 10M-row tables.
- `perf` is not installed, so the causes in "Reading the results" come from reading the code
  paths, not from a profile.
- Ticking: one case only (appends to an input table, `where` + `sum_by` downstream, timed to a
  barrier and a fetch of the result); `time_table` left out because the two servers cannot be
  made to tick in step.
