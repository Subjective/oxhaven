# 9.1 Fast natural and exact joins

- **Status:** in review
- **Needs:** 4.2 (natural join), 8.1 (benchmark)
- **Owns:** `crates/oxhaven-engine/src/ops/join/`, `crates/oxhaven-column/src/redirect.rs`,
  `crates/oxhaven-engine/examples/join-phases.rs`, the "After task 9.1" block and follow-up
  notes of `docs/BENCHMARK.md`, `bench/results/2026-11-17-task-9.1*`

## Scope

Make `natural_join` and `exact_join` fast without changing what they do. The first benchmark
(`docs/BENCHMARK.md`) had them 18x to 40x slower than Deephaven 42.9.

1. A row redirection that keeps dense row keys in a flat array, with previous mappings kept
   as Deephaven's redirections keep them, behind the type the engine already uses.
2. Join keys hashed a chunk at a time without a heap-allocated key per row, with typed paths
   for one primitive key and one string key and a general path for the rest; per-left-row
   state only for a join that has to follow a refreshing right table.
3. Same results, errors, ordering and incremental behaviour; tests for the new paths.
4. Before and after measurements with the benchmark's join cases, and phase timings.

Not in scope: sort, `select_distinct`, aggregations, formulas, and the as-of join.

## Notes

- Results and reading: `docs/BENCHMARK.md`, "After task 9.1". In short: `natural_join` and
  `exact_join` are 14x to 88x faster than before, at Java's earlier times with 1,000,000 right
  keys and below them with 10,000; `join_on_key` is unchanged and `aj` 7% to 20% faster.
- `ops/join/key_table.rs` (`KeyTable`) numbers the distinct keys of chunks of key columns. It
  is public and not specific to joins, so the aggregation key table, `select_distinct`, the
  cross join, the as-of join, `multi_join`, `range_join` and `where_in` can use it. Its key
  equality is that of `ops/join/keys.rs` (`Cell`), which a test checks on random tables.
- `WritableRowRedirection::new()` now starts as a flat array and changes form by itself, so
  sort, the as-of join and `multi_join` use the array without a change. A whole result should
  be made with `WritableRowRedirection::from_rows`, which costs one vector; sort still calls
  `put` once per row.
- New dependencies of `oxhaven-engine`: `hashbrown` 0.17 (the hash table, for its API that
  stores slot numbers and takes the hash from the caller) and `ahash` 0.8 (hashing with fixed
  seeds). Both are MIT or Apache-2.0 and were already in `Cargo.lock` through arrow, with
  the same versions; `Cargo.lock` gains only the two dependency lines of `oxhaven-engine`.
- One difference in memory, none in results: a join's key table keeps a key after its last
  row has left, as Java's hash tables do. The ordered map it replaces dropped such keys. A
  refreshing join whose keys never repeat grows by the size of each key.
- When one cycle makes a join refuse several keys, the failure still names the least key (the
  old code met the keys in key order): the refused keys are read back and compared.
- No `unported!` added; the one for a key column of an unsupported type is kept, with the
  same message. No contract change was needed.
- Java was not run again for the measurement; the document says which numbers are whose.
