## Scope

With `--threads 1` Oxhaven at 10M rows is slower than Deephaven in `where_range` (88 ms
against 31 to 37), `where_conj` (97 against 51), `update_cond` (118 against 70 to 84) and
`update_arith` (195 against 129 to 144): the cost per row on one thread is too high and
threads hide it. Bring these down, measuring each part before changing it. Results, row
order, error text and reported failures do not change.

## Notes

### What was slow (measured before the change)

`filter-update-cases -- 10000000 3 1,4`, one thread, load average 1.6 to 1.9
(`bench/results/2026-11-17-task-9.10-engine-before-10m.txt`); the example now also prints
the new pages of memory each case is given.

- `where_range` (74 ms) is a formula, `A >= 20000 && A < 60000`: 55 ms evaluating it and
  about 30 ms for the row set. A pass over the column that counts the rows in range takes
  6 to 7 ms. Each comparison made an array of its literal for every piece of 65,536 rows,
  widened the `int` column and the literal to `long` arrays, and judged each row through
  `Option`s into one bit at a time.
- The row set of the 4M kept rows (3M runs): the runs of a piece's mask were walked from
  run to run, a branch on each run's length that the processor guesses wrong when runs are
  1 to 2 rows long (12 ms of the 30 after the change below, 18 before), and the row set
  is then built from the runs, a range at a time (`RowSet::from_ranges`), though at this
  density a block of the row set is stored as a bitmap: the mask itself.
- `update_arith` (239 ms) and `update_cond` (115 ms): 48,830 and 19,532 new pages a run,
  the 200 MB and 80 MB of the results, at 1.8 to 2 microseconds a page on this machine (a
  virtual machine): about 93 ms and 37 ms that no evaluation can save. The rest was the
  same arrays of literals and widened copies, a division per row for `Id % 7`, and a
  conditional that read its condition a bit at a time.
- No fixed overhead per piece or per operation showed: the filters are given no new pages
  at all, and one thread runs the pieces on the calling thread.

### What changed

- `oxhaven_column::bits`: `pack` judges 64 values into bytes in a loop without a branch
  or a bounds check, which the compiler makes vector comparisons of, and packs the bytes
  into a word with eight multiplications; `for_each_run` gives the runs of set bits of a
  mask by taking the starts and the ends of the runs of each word as two bit sets and
  pairing them, a loop whose only branch is its end.
- `oxhaven-expr`, `eval/scalar.rs`: a comparison or an arithmetic operator with a literal
  on one side loops over the other side's values in their own type, with no array for the
  literal. Comparisons: the integer domain for `byte`, `short`, `char`, `int` and `long`
  operands (in the operand's type when the literal is one of its values, as `long`s
  otherwise), the floating point domain for `float`, `double` and the integer types that
  are exact in a `double`; nulls are put right afterwards with the validity bits. Left to
  the general kernel: a literal that is null, NaN or zero in the floating point domain
  (`Double.compare` tells the zeros apart), `long` against floating point, comparisons
  through `float` of anything but a `float`, strings, `Boolean`s, times. Arithmetic: every
  operator; a remainder with the literal on the left or an integer zero divisor is left
  to the general kernel, which finds the row that fails.
- A remainder by a literal: where the value and the divisor are both below 2^32 in size
  it is two multiplications (Lemire, Kaser and Kurz, 2019) with the sign of the dividend;
  other rows divide as before.
- A conditional whose branches are both computed reads the condition a word at a time,
  and the validity of its result is made with bit operations. When a branch fails, the
  rows that take it decide, as before.
- `ops/filter`: a piece's kept rows are read from its mask with `for_each_run`.

### Handover (stopped at the context budget)

Done and pushed: the three changes above. Not done, in the order of what they are worth:

1. **A row set from a bitmap (a contract gap).** `where_range` still spends about 21 of
   its 41 ms turning the mask of each piece into runs and the runs into a row set whose
   blocks are then bitmaps again. `oxhaven_contracts::rowset::RowSet` has no constructor
   from bits; one such as `RowSet::from_bitmap(first: RowKey, bits: &[u64], length: usize)`
   (the keys `first + i` for the set bits `i`), which copies the words of a block that is
   dense and makes runs of one that is not, would take this to a few milliseconds and
   `where_range` on one thread to under 20 ms. The contracts crate is protected, so this
   was not done.
2. **`where_conj`** (75 ms against Deephaven's 51) was not changed apart from the runs.
   Measured: `K10 = 3` over 10M rows 31 ms, `B > 50000.0` over the 1M kept rows 31 ms,
   `A < 50000` over 650,000 rows 18 ms. Two things to do: the typed kernels of the match
   and range filters still judge each row through an `Option<i64>` and, for a match, a
   list of keys (replacing `collect_bool` by `pack` alone gave nothing, so the test
   itself must be written in the column's type); and the second and third filters read
   their columns at scattered rows and build a row set from a scattered selection (30 ns
   a kept row), where judging the whole piece of a flat column (under 1 ns a row) and
   testing the mask at the selected rows would be cheaper down to a selection of a few
   percent. That is only sound for the kernels that cannot fail, and only when the rows
   between the selected ones exist in the table (a table whose row set is one range).
3. **The first write of a result.** What is left of `update_arith` and `update_cond` is
   mostly new pages (93 of 161 ms, 37 of 75 ms). Transparent huge pages are set to
   `madvise` on this machine, so a result buffer advised with `MADV_HUGEPAGE` would be
   given 2 MB pages; that needs `libc` and `unsafe`, or an allocator that keeps large
   buffers, and was not tried.
4. The conversion of an operand to the result type (`B * 1.5 - A` widens `A` to a
   `double` array per piece) and the copy of each piece into the result buffer are still
   separate passes.
5. The end-to-end benchmark (`bench/bench.py`) was not run, by the task's terms.

No `unported!` added or removed; no contract change; no new dependency; no `unsafe`.

### What changed

- **Contracts, one addition** (allowed for this task): `RowSet::from_bitmap(first, bits,
  length)`, with the private helper `container::seal_words`. No existing signature, type
  or behaviour changed. It cuts the words a block at a time and stores each block as
  `Piece::seal` stores a bitmap, so the layout is the one `from_ranges` gives.
- `kept_of_piece`: a piece of contiguous rows hands its mask to `from_bitmap`. A piece of
  scattered rows that lie close together (first to last at most 64 keys a row) puts each
  range's bits at its keys in a bitmap; rows further apart are joined range by range as
  before.
- `ops/filter/kernels.rs` (new): the typed kernels of match, range and between. A filter
  becomes the nulls, the stretch of values and the NaN it keeps (`Kept`), and one loop
  asks each value that. A match of more than eight values is judged cell by cell as before.
- `Resolved::filter_stored`: scattered rows of a column that is an array in memory, under
  a filter with a typed kernel, are judged with the rows between them and intersected with
  the selection, when first to last is at most 32 times the selected rows (measured: equal
  at about 64). The rows between need not be rows of the table: the array has them.
- **Contracts, a second addition** (allowed for this task): the provided method
  `ColumnSource::stored_values(&self) -> Option<ArrayRef>`, `None` by default.
  `FlatSource` overrides it with its array; `oxhaven-column/src/flat.rs` changes nothing
  else.

### Design: how a filter knows a column is an array in memory

The rows between selected ones may be read only from a source whose every row can be
read at no cost and without a failure: a view column computes a row when it is read and
may fail on a row an earlier filter dropped, as in Java. A first version kept a
process-wide record, by address, of the `FlatSource`s made with a `shared()` constructor.
That was replaced, because a record by address depends on every table being built
through the right constructor, takes a lock on every filter, and ties the answer to
memory addresses rather than to the source. The trait now says it:
`ColumnSource::stored_values` returns `Some(array)` only when the array holds the value
of row key `k` at position `k` for every key `0..len` (whether or not the table has the
row), in the column's Arrow type, never changes (so it is the previous values too, in
every phase of a cycle; `filter_stored` ignores `use_prev`), and cannot fail to read. A
key at or past `len` is not covered, and `filter_stored` falls back to reading then.

The default is `None`, and no wrapping source forwards it: `RedirectedSource`, the
storage wrappers `ReadsThrough` and `Shared`, `TableColumn`, the union and slot sources
and every formula source keep `None`, since their row `k` is not the inner array's
element `k`, or is computed. Every `FlatSource` now takes the fast path. Each user was
checked: `in_memory_table`, `select`/`update` results (`materialize.rs`), the static
`snapshot` (`snapshot/plain.rs`), the sorted merge (`merge/sorted.rs`), the empty table of
a partitioned merge, the constituent column of a partitioned table (a `Table` column,
behind `TableColumn`, which has no kernel anyway), the inputs of an array formula, CSV,
the console's tables from Python, the demo, meta and column-statistics tables. All are
static tables, or inputs read once, over an array that is never written: the promise
holds for every `FlatSource` by construction, since it has no way to change its array
and its `chunk` and `prev_chunk` read nothing else.
