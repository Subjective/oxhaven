# 9.11 Third end-to-end measurement: Deephaven on four processors, and both on one thread

- **Needs:** 9.8 (the second measurement); 9.9 and 9.10 (merged, so measured too)
- **Owns:** the "Third measurement" section of `docs/BENCHMARK.md` and one-sentence

- **Read:** `docs/BENCHMARK.md` (all of it); `tasks/9.8-benchmark-rerun.md`

## Scope

Both earlier measurements ran Deephaven with `-XX:ActiveProcessorCount=2` and Oxhaven with
4 threads, so they did not compare like with like. Measure every case again, at the sizes
and repetitions of the second measurement, in two fair configurations: (A) Deephaven on 4
processors against Oxhaven on 4 threads; (B) both on one (Deephaven with
`-XX:ActiveProcessorCount=1`, Oxhaven with `--threads 1`). Deephaven keeps its 5 GB heap
and the same warm-up. The servers run one at a time, never together, with no build running.
No engine code changes; a failed or timed-out case is recorded, not fixed.

## Gate

`cargo fmt --all --check`; `python3 -m py_compile bench/bench.py`;
`scripts/check-commit-subjects.sh origin/main..HEAD`; the eight `bench/bench.py run`
passes (two per server and configuration). Only `bench/bench.py`, docs, results and this
file changed, so no `cargo clippy` or `cargo test`.

## Notes

- **Result:** every case gave the same result on both servers in both runs of both
  configurations (the checks compared by `bench.py merge` exactly as `run` compares them;
  the ticking case also against the client's sums). No case was refused, failed or timed
  out.
- **Summary** (`docs/BENCHMARK.md`, "Third measurement"): of 74 pairs of case and size,
  Oxhaven is faster (ratio below 0.8 in both runs) in 44 in both configurations. A: 22
  level or between, 1 where the runs disagree, 7 slower by more than 20% in both runs
  (`agg_by_multi` and `last_by` at 10M, `group_by` at both sizes, `sum_by_high`,
  `avg_by_high` and `count_by_high` at 1M; 1.2x to 1.75x). B: 21 level or between, 1
  disagreeing, 8 slower (`agg_by_multi` and `group_by` at both sizes, `last_by` and
  `avg_by_med` at 10M, `sum_by_high` and `avg_by_high` at 1M; 1.2x to 1.7x).
- **Processor count of Deephaven:** `oracle/bin/java_server.py` hard-codes
  `-XX:ActiveProcessorCount=2` and `oracle/` is protected, so the count was overridden
  with `_JAVA_OPTIONS=-XX:ActiveProcessorCount=<n>`, which the JVM applies after its
  launch options. Confirmed by "Picked up _JAVA_OPTIONS", by the update graph's log
  ("starting with 4" / "1 notification processing threads"), and in B by
  `Runtime.availableProcessors()` = 1 read on the server (G1 kept: `deephaven_server`
  passes `-XX:+UseG1GC`).
- **One server at a time:** `bench.py run` was given one `--server` per pass; the new
  `bench.py merge` joins the Deephaven and the Oxhaven file of a run into the two-server
  format and computes `match`. Tested on the second measurement's run 1 split in two: the
  merged `match` of all 74 rows equals the original, and a changed row count gives `NO`.
- **Commands:** `cargo build --release --locked -p oxhaven-server` at `c7ff97bc` (3 min
  20 s, before measuring); Deephaven:
  `_JAVA_OPTIONS=-XX:ActiveProcessorCount=<4|1> oracle/bin/java_server.py --port 10868 --psk oxhaven --heap 5g`
  (venv of `oracle/requirements.txt`, Python 3.13); Oxhaven:
  `oxhaven-server --host 127.0.0.1 --port 10869 --psk oxhaven --threads <4|1>`;
  `bench/bench.py run --server <Name>=dh+psk://oxhaven@127.0.0.1:<port> --out <file>`
  with default sizes and repetitions, twice per server process; order Deephaven A,
  Oxhaven A, Deephaven B, Oxhaven B, 01:59:57 to 02:15:51.
- **Load:** no build running and no other agent building. One-minute load average 0.88
  to 1.80 at the start of each run, 1.01 to 1.80 at its end, 0.88 to 2.07 before each
  case.
- **Not run:** `cargo clippy`, `cargo test` (no Rust changed).
