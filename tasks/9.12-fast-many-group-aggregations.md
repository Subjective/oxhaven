### Where the time went

Under callgrind (`examples/aggregation-cases.rs`, collection limited to
`Aggregator::initial`) and with `getrusage`:

- With 10,000 or more groups nearly every group of a chunk of 4,096 rows has one row.
  Sorting the chunk's rows by slot, one `add_runs` call per group and operator and one
  mark per group and operator were most of `agg_by_multi`, `sum_by_med` and `avg_by_med`.
- `Min` and `Max` kept a `Scalar` per group and compared through it.
- `group_by` built a `RowSet` per group with `RowSet::from_keys` (1M of them at 10M rows
  by `K1M`), then read each back to make the result.
- `last_by` of six columns ran six `FirstLastCell`s that each kept the same row key per
  group.
- The first result wrote keys and results by slot into a place per key and noted every
  slot as added.
- Page faults on fresh memory were about half of `sum_by_high` at 1M rows; over a whole
  benchmark run the server spends 11 to 12.5 s of 72 to 84 s in the kernel.

### What changed (`ops/agg`)

- **Rows in row order with values** (`operator.rs`, `aggregator.rs`, `sum.rs`,
  `min_max.rs`, `group.rs`). `AggOperator::add_rows` now receives `Rows`: the chunk's
  slots, its distinct slots in order of first appearance, an index into those per row,
  the row keys and the operator's values. `Count`, `LongSum`, `LongAvg`, `FloatSum`,
  `FloatAvg`, `MinMax` and `Group` take rows so, for a static or add-only parent. Each
  keeps a partial per distinct slot of the chunk and adds it to the slot's state once,
  with one mark, so a state sees exactly the per-chunk sums it saw from `add_runs`: a
  `long` sum that reaches `NULL_LONG` and a floating point sum are unchanged bit for bit.
  `Aggregator::process` takes this path when every operator of the aggregation does and
  either no group rows are kept or the first result is being made.
- **Typed extremes** (`min_max.rs`): `long`-like and `double`-like columns keep
  `GrowingLongs` or `GrowingDoubles` in place of a `Scalar` per group. The first zero
  met stays (`-0.0` against `0.0`), and a NaN is handled as before.
- **Group rows as flat arrays** (`operator.rs`, `FlatGroups`): during the first result of
  a static parent the row keys are sorted by slot by counting into one array with one
  offset per slot; `GroupReader` reads a group's rows from it. Row sets per group are
  built only for a refreshing parent, which changes them later.
- **One first or last row per group for all columns** (`first_last.rs`, `mod.rs`): the
  cells of one `first_by`/`last_by` in `ByRowKey` mode share one `ShownRows`; the first
  cell leads (compares and writes), the others follow its marks.
- **The first result** (`aggregator.rs`, `slot_source.rs`): marks are recompute-only
  (nothing reads "added" there), key columns are collected and written once
  (`fill_from`), and for a static parent a result column keeps the one batch it was
  given (`State.dense`) with no place per key. `FloatCounts` allocates its NaN and
  infinity counts when the first one is met.

### Four threads against one (item 5)

Not reproduced. Same session, same binary, medians at 10M rows on 1 / 4 threads: before
`sort_int` 501 / 497 (run 1) and 527 / 524 (run 2), `sort_string` 1406 / 1494 and 1501 /
1524; after `sort_int` 525 / 544 and 529 / 521, `sum_by_high` 521 / 486 and 545 / 492.
None of these cases uses a second thread, and the server's processor time per run is the
same on 1 and 4. The third measurement's difference was between two runs of the machine.

What moves these cases is the allocator. With `mimalloc` as the server's global
allocator (an experiment, not in this change), system time per run fell from 11 to 12.5 s
to 2.5 to 2.7 s, `sort_int` at 10M rows to about 404 ms and `sort_string` to 1200 to
1254; the process kept more memory between cases. `GLIBC_TUNABLES` that keep memory
(`mmap_threshold` 32 MB, `trim_threshold` 4 GB, one arena) gave part of it. Left out: a
new dependency built from C and a memory policy for the whole server, which wants its own
task and measurement.

### Tests

New, in `ops/agg/tests/by_rows.rs` unless said:

- `sums_averages_and_counts_take_rows_as_they_take_groups`: each operator fed the same
  chunks through `add_rows` and `add_runs`, same states and marks; the values include
  nulls, `long`s whose sum overflows, both zeros, NaN and both infinities.
- `minimum_and_maximum_take_rows_as_they_take_groups`: the same for `MinMax` of `long`,
  `int` and `double`; the states that keep a multiset and the string states still take
  groups only.
- `typed_extremes_keep_the_first_zero_and_any_nan`.
- `rows_are_brought_together_by_group_in_order`: `FlatGroups` against a row set per group.
- `static_aggregations_by_rows_are_a_look_at_every_row`: an `agg_by` of sum, average,
  minimum, maximum, first, last and count, and a `group_by`, against a look at every row,
  with 1, 10, 4095, 4096 and 4097 groups and one group per row over 3 * 4096 + 77 rows
  (group counts on both sides of the chunk size). The new path has no threshold of its
  own: it is taken by what the operators and the parent are, not by a count.
- `slot_source::tests::a_column_written_once_from_the_first_key_reads_as_one_written_by_keys`.
- `first_last::tests::cells_that_share_their_rows_are_cells_on_their_own`.

Seen to fail, each with the source changed and then restored: a sum by rows that notes
nothing (the sums test and the static test); `<=` for `<` in the typed minimum
(`typed_extremes`); the counting cursor of `FlatGroups` not advanced
(`rows_are_brought_together`, the static test); a dense column that reads its first value
everywhere (the `slot_source` test); follower cells that mark nothing (`cells_that_share`);
every row of a chunk counted for the chunk's first group (the static test); an extreme by
rows that notes nothing (`minimum_and_maximum`, the static test); the collected key
columns never written (the static test).

### What is left

- `avg_by_high` at 1M rows on 4 threads is still 1.25x Deephaven's time (level, 1.09 to
  1.11, on 1 thread), and `count_by_high` at 1M was 1.26x in one run of four. With one row
  per group, numbering 1M new keys (the key table growing and rehashing) and fresh memory
  are what remains; the allocator experiment brought `sum_by_high` at 1M rows from 126 to
  134 ms down to 106 to 129.
- A refreshing parent's `group_by` still builds a row set per group in its first result.
- Rows added in a later cycle to an aggregation with many groups
  (`append_only_cycles` in `aggregation-cases`: 11.6 s for 19 cycles of 500,000 rows) take
  the same path as before when group rows are kept, and were not the subject.
- No contract change was needed.
