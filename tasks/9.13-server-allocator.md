# 9.13 Choose the server's memory allocator by measurement

- **Status:** in review
- **Needs:** 9.12 (found the cost of fresh memory and tried `mimalloc` and glibc tunables)
- **Owns:** the `mimalloc` feature and dependency of `crates/oxhaven-server` (`Cargo.toml`,

- **Read:** `tasks/9.12-fast-many-group-aggregations.md`; `docs/BENCHMARK.md` ("After task
  9.12"); `tasks/9.11-benchmark-four-processors.md` (sizes and repetitions)

## Scope

1. Measure one server build in three configurations, the whole case list on `--threads 1`
   and `--threads 4`, two runs each: (a) the system allocator; (b) the system allocator
   told to keep memory; (c) `mimalloc`. Per-case times, the server's user and system
   processor time, peak resident memory (`VmHWM`) and resident memory after 30 idle
   seconds; and three passes against one process per configuration, resident memory after
   each.
2. Decide by the numbers: `mimalloc` as the binary's default allocator behind a default
   cargo feature if it gains 10% or more on the sorts and high-cardinality aggregations
   without peak memory more than about 25% above the system allocator's and without growth
   across passes; the tuned system allocator if it gets most of the gain; otherwise no
   change. Only MIT or Apache-2.0 licences.
3. Document it (`docs/BENCHMARK.md`, the README), raw results under `bench/results/`.

No change to engine code, `crates/oxhaven-contracts`, `PARITY.md` or `oracle/`.

## Notes

- **Chosen: `mimalloc`**, feature `mimalloc` of `oxhaven-server`, on by default; only the
  binary (`#[global_allocator]` in `src/main.rs`). `--no-default-features` gives the
  system allocator. Numbers and reading: `docs/BENCHMARK.md`, "After task 9.13".
- **Gain:** mimalloc over system, mean of two runs, 1 / 4 threads: `sort_int` 10M 0.70 /
  0.72, `sort_two` 10M 0.78 / 0.84, `sort_string` 10M 0.84 / 0.85, `sum_by_high` 1M 0.73 /
  0.71, `avg_by_high` 1M 0.78 / 0.85, `count_by_high` 1M 0.81 / 0.89, `group_by` 10M 0.71 /
  0.67, the joins at 10M 0.62 to 0.85. System time per run 11 to 13 s with glibc, 2.5 to
  3 s with mimalloc.
- **Memory:** peak (`VmHWM`) with mimalloc 0% to 3% below glibc's; resident memory after
  each of three passes 1182 to 1347 MB (no growth), and 76 to 89 MB after 30 idle seconds
  against 1265 to 1337 MB with glibc. Tuned glibc (`GLIBC_TUNABLES`, the environment
  variable; no `mallopt` was written since it was not chosen) peaks 7% to 9% lower but
  holds 2010 to 2138 MB when idle, growing pass by pass, and is as fast as mimalloc only
  from its second run.
- **Slower with mimalloc:** `sum_by_med`, `avg_by_med` and `agg_by_multi` at 10M rows may
  be up to about 10% slower in the median (wide spread on both; minimums equal within 8%,
  measured again alone in `bench/results/2026-11-18-task-9.13-recheck.txt`).
  `count_by_med` and `last_by` at 10M read slower in the first measurement and were level
  when measured again.
- **Licences** (`cargo tree -p mimalloc -e normal,build`, `cargo metadata`): `mimalloc`
  0.1.52 MIT; `libmimalloc-sys` 0.1.49 MIT (bundled C source of mimalloc, MIT, Microsoft
  Corporation and Daan Leijen); build dependencies `cc` 1.11.2, `find-msvc-tools` 0.1.15,
  `jobserver` 0.1.35, `libc` 0.2.191, `shlex` 2.0.1, all MIT OR Apache-2.0 and already in
  the tree. Only `mimalloc` and `libmimalloc-sys` are new in `Cargo.lock`.
- **C libraries:** the crate does not replace `malloc`, so CPython and librdkafka keep
  glibc's allocator and free only what it gave them. The `kafka-broker` CI job runs the
  tests of `oxhaven-kafka` only, whose test binaries keep the system allocator: not
  affected. `GetHeapInfo`'s `free_memory` now counts only glibc's side
  (`docs/CONSOLE.md`).
- **Commands:** release builds as in `docs/BENCHMARK.md`, "After task 9.13"; each server
  `oxhaven-server --host 127.0.0.1 --port 10969 --psk oxhaven --threads <1|4>`;
  `bench/bench.py run --server oxhaven-<name>=dh+psk://oxhaven@127.0.0.1:10969 --out <file>`
  three times per process; `/proc/<pid>/stat` and `/proc/<pid>/status` read after each run
  and after 30 idle seconds.
