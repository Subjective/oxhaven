## Scope

Make `select_distinct`, `last_by` and aggregations with many groups fast without changing any
result, group order, error or incremental behaviour: a group key table without a heap
allocation per row, aggregation result columns indexed by slot, `select_distinct` on the same
key table, `first`/`last` of static and add-only parents by row key. `group_by` only if it can
stay identical. Not joins (9.1), sort, formulas.

## Notes

### Where the time went (measured before the change)

`examples/aggregation-cases.rs` runs the benchmark's aggregation cases inside the engine (no
server) on a static table built as the benchmark builds its source. Phases were timed with
temporary timers in `Aggregator::process`/`initial` and `select_distinct`'s first pass (not
committed), release build, 1M rows, one repetition, machine shared with other builds:

| case | phases |
| --- | --- |
| `select_distinct_one` | encode keys to `Vec<Vec<u8>>` 47 ms, `BTreeMap` entry per row 266 ms |
| `select_distinct_two` | encode 123 ms, `BTreeMap` 135 ms |
| `sum_by_high` | keys (row format + SipHash `HashMap<Box<[u8]>>`) 504 ms, operators 41 ms, writing results (`WritableSource`, a `BTreeMap` per column) 253 ms |
| `count_by_high` | keys 515 ms, operators 15 ms, writing results 111 ms |
| `last_by` | keys 43 ms, operators 117 ms (a `Scalar` per run, an `Arc<str>` per string) |
| `group_by` | operators and group row sets 203 ms |
| `sum_by_low` | keys 34 ms, sorting a chunk by slot 11 ms, operators 7 ms |

So the reading of `docs/BENCHMARK.md` held for `select_distinct` and the high-cardinality
cases. For `group_by` the larger cost was not the Arrow lists but inserting each run of each
chunk into the group's `RowSet`.

### What changed

- `ops/group_keys.rs`: `GroupKeys`, an open-addressed (linear probing, at most half full)
  table of slot numbers. Layouts: one column of at most 64 bits (the bucket holds the key's
  canonical bits; NaN and `-0.0` canonical as before), one string column (bytes in one
  buffer), anything else (Arrow row format, as before, bytes in one buffer). The null key of
  the typed layouts is a slot outside the table. Hasher: `ahash` 0.8.12 (MIT OR Apache-2.0,
  already in the lock file through `arrow-array`) with fixed seeds; hash values never reach a
  result. Task 9.1 may unify its join key hasher with this module.
- `ops/agg/keys.rs` keeps the `KeyTable` API (also used by `head_by`) over `GroupKeys`.
- `ops/agg/slot_source.rs`: `SlotSource`, the result column of aggregations and
  `select_distinct`: a vector of places indexed by slot, values kept as the Arrow arrays
  written, previous values recorded per cycle as `WritableSource` does (a slot that did not
  exist before the cycle needs no record). A column of tables stays a `WritableSource`,
  which keeps the tables alive.
- `select_distinct` uses `GroupKeys` per chunk of 4,096 rows and a vector of touched groups.
  Its type check (`distinct/keys.rs`) refuses the same Arrow types with the same message as
  the old encoder.
- `first`/`last` of a static or add-only parent use `FirstLastCell` (a row key per group, the
  cells read once per cycle) for every column type, as Java's
  `BaseAddOnlyFirstOrLastChunkedOperator` shows the input column through a redirection.
  `FirstLastCell` keeps its cells in a `SlotSource`.
- The aggregator sorts a chunk's (slot, position) pairs packed in a `u64`, skips the search
  for modified slots when every slot is written (the first pass), and in the first pass of an
  operator that needs group rows collects (slot, row key) pairs and builds each group's row set
  once.
- `group_by` still gathers its vectors into Arrow lists at creation; that is unchanged.

### Tests added

`group_keys_tests.rs` (every one-column layout and type, pairs of columns, NaN/`-0.0`/null,
forced hash collisions, growth over many calls, `find` of absent keys, checked against a
model), `slot_source_tests.rs` (previous values within and across cycles, compaction,
refusals), `agg/tests/many_groups.rs` (keys by int, string and both; groups emptied and
refilled; key modifications; the table growing across 12 cycles; checked with
`ConsistencyChecker` against the static path; a group returning to its row key after the table
grew). Each was seen to fail with a deliberate defect (no byte comparison on equal hashes, no
NaN canonicalization, no previous values).
