# 9.3 Fast sort, and fast reads through a row redirection

- **Status:** in review
- **Needs:** 3.3 (sort), 8.1 (benchmark), 9.1 (flat row redirections)
- **Owns:** `crates/oxhaven-engine/src/ops/sort/`, `crates/oxhaven-column/src/redirect.rs`,
  `crates/oxhaven-column/src/flat.rs` (`chunk_by_keys`), `crates/oxhaven-engine/examples/sort-phases.rs`,
  the "After task 9.3" block of `docs/BENCHMARK.md`, `bench/results/2026-11-17-task-9.3*`

## Scope

Make `sort` fast without changing what it does. The first benchmark (`docs/BENCHMARK.md`) had
`sort` of an int column 4x to 10x slower than Deephaven 42.9, two columns 2.3x to 4.2x and a
string column 1.5x to 2.8x.

1. Static sort with no heap allocation per row: typed paths for one fixed-width column and
   one string column, and a general path for the rest.
2. Incremental sort: the same results, without a heap-allocated key per row.
3. `RedirectedSource` reads a chunk through the redirection without collecting row keys one
   by one or a lock or lookup per row; previous values stay right within a cycle.
4. Same order (ties, nulls, NaN, `-0.0`, descending, absolute), errors and incremental
   updates; tests for each typed path and for redirected reads of current and previous values.
5. Before and after measurements with the benchmark's sort cases.

Not in scope: aggregations, `select_distinct`, `ops/join/key_table.rs`, the cross join.

## Notes

- Results and reading: `docs/BENCHMARK.md`, "After task 9.3". In short, against `main`
  before the change, in two interleaved runs: `sort_int` 16x to 19x faster, `sort_two` 3.2x
  to 5.7x, `sort_string` 2.6x to 3.6x, all below Java's earlier times at 1M and 10M rows;
  `natural_join_small`, `aj` and `head_half` unchanged within the noise.
- Phase timings (`examples/sort-phases.rs`) confirmed the reading of the first benchmark only
  in part: the box per row was 5% of a 10M-row int sort and the comparison sort over the
  boxes 77%; sorting positions over one buffer of the row format was slower still. So every
  path sorts small values that carry their key (a 64-bit integer, or the first 15 bytes and
  length), and the single fixed-width column uses a stable radix sort.
- Order is unchanged: every existing test and the recorded-corpus test pass unchanged. New
  tests compare the fixed-width form with the row format for every fixed-width type,
  ascending, descending and absolute, with nulls, NaN, `-0.0` and the minimum values; the
  string forms with Java's UTF-16 order (U+E000 against U+10000, long strings, a sliced
  chunk); keys appended in sorted order as the incremental sort keeps them; the radix sort
  against a stable sort; random incremental updates through single-column sorts; and
  redirected reads of current and previous values through both forms of the redirection.
  The fixed-width, string, radix and redirected-read tests were each seen to fail with the
  behaviour they check broken (`-0.0` not made `0.0`, the UTF-16 byte change removed, a radix
  pass skipped, previous mappings not laid over); the random single-column test was not
  checked that way.
- `RowRedirection` gained `redirect_rows` (a provided method), which `WritableRowRedirection`
  overrides with a slice copy per range; `RedirectedSource` reads through it. The other
  redirections (cross join, flatten, select) keep the provided method, as before.
- Not done: the incremental sort is still linear per cycle, because the result is positional
  and every shifted position is written to the redirection, which records each write in an
  ordered map of previous mappings. What it would take is in `docs/BENCHMARK.md`.
- No `unported!` added or removed; no contract change.
