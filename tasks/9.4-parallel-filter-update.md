## Scope

Make static `where` and the formulas of `update`/`select`/`view` scale at 10M rows without
changing a result, a row order or a reported failure: remove per-row overhead first, then use
several threads. Not `ops/sort`, `oxhaven-column/src/redirect.rs`, `ops/agg`, `ops/join`.

## Notes

### What was slow (measured before the change)

`examples/filter-update-cases.rs`, release, one thread, load average 3.0 on 4 cores
(`bench/results/2026-11-17-task-9.4-engine-before-*.txt`). A pass over the `int` column's memory
costs 0.4 ns per row at 1M rows and 0.9 at 10M. Against that:

| part | 1M rows | 10M rows |
| --- | ---: | ---: |
| evaluate `A >= 20000 && A < 60000` | 12.5 ns/row | 32.1 |
| evaluate `A * 2 + 1` | 13.0 | 25.1 |
| evaluate `B * 1.5 - A` | 18.0 | 42.4 |
| evaluate `A > 50000 ? B : -B` | 17.6 | 46.1 |
| row set of the kept 40% of rows, one key at a time | 7.9 | 10.8 |
| whole `where_range` | 30.9 | 42.0 |

So the benchmark document's guess (threads) was not the main cause: one thread was 15 to 50
times slower than a memory scan. The causes, from the code: every arithmetic operator, cast and
negation built its result from an iterator of `Option`s; an operand that already had the result
type was copied; a comparison decided every row through `Option`s and a dynamic operator; a
conditional filtered both branches and interleaved them row by row; and at 10M rows every
intermediate was an array of 40 to 80 MB, so the cost per row doubled or tripled. A match or
range filter widened each cell to an `Option<i64>` in a vector and made its row set one key at a
time.

### What changed

- `oxhaven-column/src/parallel.rs`: the thread count (`OXHAVEN_THREADS`, default the available
  cores; `set_threads`, `with_threads`) and `map_pieces`, which runs numbered pieces on scoped
  threads and returns the results in piece order. No new dependency: `std::thread::scope`.
- `oxhaven-expr`: typed loops for arithmetic, casts, negation and null-free comparisons; no copy
  of an operand that has the result type; a formula made only of operators (columns, literals,
  `i`/`ii`/`k`, arithmetic, comparisons, `&&`, `||`, `?:`, casts, string `+`, `isNull`) is
  evaluated in pieces of 2^16 rows, on several threads, after its columns are read on the calling
  thread. A piece reads no table and takes no lock, so this is also used inside update-graph
  cycles. If any piece fails, all rows are evaluated again in one pass, so the failure reported
  is the one reported before. `&&`, `||` and `?:` compute both sides for every row of such a
  formula and fall back to the selective path when a side fails or is null. Every function call
  (random numbers, the clock, external and Python functions, vectors, `Column_`) keeps the old
  one-pass, one-thread path.
- `ops/filter`: match, range and two-ended range filters of primitive and `Instant` columns have
  typed kernels; every single-column filter (those and pattern filters) is judged in pieces of
  2^16 rows on several threads from a chunk read once on the calling thread; kept rows of a
  contiguous selection are added to the row set as ranges.
- Java's rule, for the record: `DhFormulaColumn#isStateless` is true by default
  (`QueryTable.statelessSelectByDefault`), and only a formula that uses Python is not run in
  parallel (`DhFormulaColumn#isParallelizable`, `ConditionFilter#permitParallelization`); `i`,
  `ii` and `k` are allowed. Oxhaven is stricter (no function calls at all in parallel).
