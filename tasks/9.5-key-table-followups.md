## Scope

The performance follow-ups that 9.1 and 9.2 left open, each measured before it is changed:

1. One typed key table for joins, aggregations, `select_distinct` and everything else
   that hashes key columns, instead of `ops/join/key_table.rs` and `ops/group_keys.rs`.
2. The keyed cross join on that table instead of a key per row in an ordered map.
3. `last_by`, `first_by` and the like without a call through a trait object per run of rows.
4. `group_by` without building every group's vector when the result is made.
5. The end-to-end benchmark of the cases above, main against the branch, and an
   "After task 9.5" block in `docs/BENCHMARK.md`.

Results, row order, error text and incremental behaviour do not change.

What the measurement decided:

- Neither old table was faster throughout. For small tables the group table's loop was
  faster (no copy of the keys to an `i64` array first, the key in the bucket); for large
  tables of byte keys hashbrown found keys faster and the group table inserted them faster.
  The unified table keeps the group table's layout and adds what the numbers asked for.
- Finding a key in a table larger than the caches is where the unified table gains most
  (1.3x to 2x): keys are hashed a block of 256 rows at a time and the bucket of the row 8
  rows ahead is read early, so the cache misses of several rows overlap. The read-ahead is
  off below 2^17 buckets (2 MB): with it on for a table of 10,000 keys, `select_distinct`
  of one int column measured 5.6 to 5.9 ms against 4.4 before, and 3.9 with it off.
- Rows of several columns are encoded 4,096 rows at a time also when a join passes a whole
  table, so the encoded rows are hashed while they are in the cache (int and string in one
  chunk: 15 ms against 21 and 40).
- Inserting a million new keys did not get faster (60 to 80 ms either way). The cause was
  not found; growth alone does not explain it, since rehashing moves keys in two
  sequential streams. It is the largest part of `natural_join_large` and the
  high-cardinality aggregations that is left.
- Two cells are not better and inside the noise: a string key found in one chunk of 1M rows
  (10.8 against 9.4 for the join table), and two int columns inserted in one chunk (24.6 in
  this run against 16.1; the same case measured 16.7 and 19.2 in two earlier runs of the
  same code).

### What changed

- `ops/key_table.rs`: `KeyTable`, the one table. `KeyTable::new()` takes its kind of key
  from the first columns inserted and checks column types as the joins did (the same
  `unported!` text, timestamps without their time zone annotation, a converter per
  combination of column types, so that the columns of two tables go into one table);
  `KeyTable::for_types` is made for declared types as the aggregations' table was (the same
  errors). `insert`/`find` answer `Vec<u32>` with `NO_SLOT` as the joins use them;
  `find_or_create`/`find_all` append `usize` or `u32` slots and report the rows that made a
  slot, as the aggregations and `select_distinct` use them. Slot numbers are the same as
  before in every case: the order keys are first inserted.
- `ops/join/key_table.rs` and `ops/group_keys.rs` are gone. `natural_join`, `exact_join`,
  the aggregations (`ops/agg/keys.rs`, and through it `head_by`/`tail_by`) and
  `select_distinct` use `ops::key_table`.
- `hashbrown` is no longer a direct dependency of the engine (it had no other user). No
  dependency was added.

### Item 2: the keyed cross join

Measured first with a new example, `examples/crossjoin-cases.rs` (1M left rows, the
benchmark's `join_on_key` shape and five others; numbers in `docs/BENCHMARK.md`, "After
task 9.5"). Timed in parts with temporary timers in `Keyed::build` (not committed), the join
on an int key with 10,000 right keys took about 545 ms: about 250 ms making a `Vec<Cell>`
key per left row and numbering it in the `BTreeMap<Key, slot>` with a `BTreeMap` of members,
about 130 ms for the right rows, and 100 to 280 ms putting each left row's slot in the
layout's `VersionedMap` (a `BTreeMap`). Reading the added column of 1M rows took 180 ms,
two `BTreeMap` lookups a row. With 1M right keys the join took 3.4 s.

What changed (`ops/crossjoin/keyed.rs`, `layout.rs`):

- Keys are numbered by `ops::key_table::KeyTable` (`KeyTable::new()`, as the natural join
  uses it) a chunk at a time, through `KeyColumns::chunks`; `KeyColumns::read` is no longer
  used here. Slots are made in the same order as before: left rows, then right rows
  (inserted when `all_right`, found otherwise); in `apply_right` removed rows by previous
  keys, shifted rows, added rows, then for modified rows `find(before)` and
  `insert`/`find(after)`; in `apply_left` modified rows `find(before)` then `insert(after)`,
  then added rows. A left row changed key when its two slots differ, which is when its two
  keys differ.
- The slot of each left row is a `WritableRowRedirection` (`oxhaven-column`, public API
  only), made at once with `from_rows` and then tracking previous values with the result's
  clock. It is a flat array while the left row keys are dense. Its previous values follow
  the same rules as the old `VersionedMap` (first write in a cycle wins, only while the
  clock is updating). One difference in a case no test reaches: a join built while the graph
  is updating no longer records its initial slots as changes of that cycle.
- The right rows of each slot are `RightGroups`: for a static right table one array of row
  keys grouped by slot (`Fixed`, never changed), for a refreshing one a `RowSet` per slot in
  a `VersionedVec` (a `Vec` by slot with the previous value of each slot changed this
  cycle), which replaces the `VersionedMap` keyed by slot.
- The left rows of each slot (`Slots::left`) are kept only when the right table is
  refreshing: only a change of a slot's right rows asks for them.
- Every per-row lookup of a left row's slot in `on_update` and `apply_left` reads the slots
  of all the rows in one `redirect` call.

Result: 562 to 17 ms for the `join_on_key` shape, 3368 to 168 ms with 1M right keys, the
column read 187 to 27 ms. Tests: all 33 cross join tests (unit, Java updates, corpus,
random with the consistency checker) pass unchanged, with `OXHAVEN_TEST_SEEDS=full`; new
`layout::tests::fixed_right_groups_read_positions_in_the_slot`. Seen to fail: a defect in
`RightGroups::Fixed` reads (one position past a group) failed the new test; taking every
modified left row as keeping its key failed 7 existing tests (corpus, Java updates, random).

### Item 3: first and last without a call per group

Measured with `valgrind --tool=callgrind` on `aggregation-cases 1000000 1 last_by` (the
example takes an optional case-name prefix now): of the aggregation's 740M instructions per
call, `Aggregator::apply` was 560M, of which 230M was `FirstLastCell::add` (12M calls over
the two calls of the case) and most of the rest the `Run` built and the effect noted per
group. With 10,000 keys and chunks of 4,096 rows nearly every group of a chunk has one row,
so a call per group is a call per row.

What changed: `AggOperator::add_runs` and `remove_runs` take every group of a chunk
(`values::Runs`) and append an effect per group; the default calls `add`/`remove` per
group, so every other operator is unchanged. `FirstLast` and `FirstLastCell` override both;
`FirstLast` now reads a value only for a row it takes. `apply`'s instructions fell 28%
(1128M to 814M over the two calls). In interleaved runs `last_by` went from a median of
45 to 50 ms to 36 to 40 ms (load 1.7 to 5.4; see `docs/BENCHMARK.md`). Test:
`first_last::tests::a_chunk_of_groups_at_once_is_a_group_at_a_time`, both operators, every
mode, first and last, added and removed, against a call per group. Seen to fail: swapping
the first and last row of `Runs::ends` failed it and 19 existing aggregation tests.

### Item 4: `group_by`

The `group_by` case of `aggregation-cases` built its 1M-row source table inside the timing,
which was most of its 137 ms; the table is now built first (`group_by` is about 60 to 75
ms), and a `group_by_read` case also reads every vector. Under callgrind, per call: about
260M instructions in the work every aggregation does, 195M making each group's `RowSet`
(`collect_group_rows`), 125M in `Group::recompute` reading the values back through those row
sets, and 52M in `Group::results` copying them again with `take`.

What changed: `Group::results` uses a slice of the elements `recompute` read when the slots
asked for are the groups read, in that order (how the framework asks), and copies only
otherwise; `Group::results` went to 2M instructions per call and `group_by_read` from about
80 to about 60 ms. Lazy vectors (Java's `AggregateColumnSource`) were not built: group
contents are now 18% of the operation, and a lazy column would move their cost to whoever
reads them, which in the benchmark is every vector; it would also need previous values from
previous row sets. Test: `group::tests::vectors_asked_for_in_any_order_hold_their_group_s_values`
(in order, from a later group, out of order, repeated, groups without rows and never read).
Seen to fail: slicing from 0 instead of the first group read failed it; no existing test
failed with that defect.
