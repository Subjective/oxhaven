## Scope

Two bottlenecks the tasks before named, each measured before it was changed.

A. A small update to a large sorted refreshing table costs about the update, not the
   table. Ten cycles that each append 1,000 rows to a sorted table of 10M rows took 17 s.
B. The row set of the rows a filter keeps is built without a pass over every kept range on
   one thread, and the later filters of a conjunction read their column on several threads.

Results, row order, error text and reported failures do not change. The row keys of an
incremental sort result do (`PARITY.md` A4: row keys are never compared).

## Notes

### A. Incremental sort

- Measured first (`sort-phases -- 10000000 --incremental-only`): a cycle took 1.5 to 1.9 s.
  Ten million redirection writes alone take 1.03 s inside a cycle, where each records a
  previous mapping in an ordered map, and 0.16 s outside one. So the reading of task 9.3
  holds for about 60% of the cycle; the rest was the other passes over every row (the
  survivors, the merged keys, the shift data).
- Now (`ops/sort/gapped.rs`): the result's key space `0..len` is cut into leaves of 128
  keys, and a new result puts 96 rows at the start of each. An insertion goes to a free key
  after the row it follows when there is one. Otherwise the rows of the smallest window of
  leaves around it that has room (a leaf may be full, a larger window keeps an eighth free)
  are laid out again evenly, and the rows that moved are reported as shifts. When the whole
  key space is too full it grows to three quarters full, which moves every row once. Rows
  added after the last row extend the key space and move nothing. This is a packed-memory
  array; Java instead starts dense at `2^30 - n/2` and leaves a gap of 64 keys after every
  64 rows it has to move. The keys stay dense enough for the redirection's flat array.
- No reverse lookup is kept. A row that leaves (removed, or modified with a new sort key
  and a new place) is found by binary search with its previous sort key, read from the
  parent's previous values, and its parent key; ties are in parent-key order, so the pair
  is unique. The sort keys are kept in one buffer that is compacted when more than half of
  it belongs to rows that left.
- Java's rule for a modified row whose sort key changed (modified in place, or removed and
  added) is kept; the fixture recorded from Java (`sort_modified_rows.json`) passes
  unchanged.
- Tests changed, both because they asserted the row keys and shifts of the positional
  layout: `a_modified_sort_value_that_moves_is_a_remove_and_an_add` (the row is now added
  at key 4, after the last row, with no shift; it was key 3 with a shift of the three
  others) and `removed_rows_leave_and_later_rows_close_the_gap`, renamed
  `removed_rows_leave_their_keys_free_and_no_row_moves` (no shift now). The rows and their
  order asserted by both are the same. New: `insertions_beyond_a_leaf_spread_over_more_leaves`,
  seen to fail when a window is laid out unevenly (the checker reports a shifted key that
  collides with an unmoved one).
- Result at 10M rows: ten cycles 16.8 s before, 0.32 s after (int key), 17.6 s and 0.30 s
  (string key), same rows in the same order. See `docs/BENCHMARK.md`.

### B. Row set of a filter's kept rows

- Measured first, 10M rows, 40% kept in 3M ranges: the ranges 42 ms, one sequential
  builder over them 84 ms in all on one thread (the join was serial), of 117 ms for
  `where_range` on four threads. In `where_conj` the second and third filters spent half
  their time in a serial gather of their column (20 ns per row, cache misses) and half in
  the row set.
- Now each piece of 2^16 rows makes its own row set on the thread that judged it, and
  `oxhaven_rowset::concat_ordered` joins them: an insert past the end of a row set
  rebuilds at most its last block. `FlatSource::chunk` gathers scattered rows in pieces on
  several threads and concatenates them.
- Tests: `concat_ordered` against `from_keys` over cuts inside blocks and at their edges;
  `kept_of_piece` against a key-by-key pick for five shapes of selection; the scattered
  gather on 1, 2 and 4 threads with nulls, strings and a key past the end. Each was seen to
  fail with the code broken (a part left out, a key off by one, two pieces swapped).

### Not done

- A parent shift still costs a pass over every row of the sort (each row's parent key is
  rewritten), as before.
- A sort result whose rows mostly left keeps its key space: when fewer than a quarter of
  the keys hold a row the redirection moves to its ordered map, which is correct and
  slower. Laying the rows out again when the table has shrunk would avoid it.
- Growing the key space moves every row in one cycle (about one old cycle's cost); a
  redirection replaced in bulk, with the old array kept once as the previous mappings,
  would make that cheap.
- Reading a column of an incremental sort back (9.8 s at 10M rows) is unchanged: the time
  is in the input table's column, read a cell at a time (`WritableSource`).
- The end-to-end benchmark (`bench/bench.py`) was not run.
- No `unported!` added or removed; no contract change.
