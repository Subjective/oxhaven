## Notes

### 1. Reads of a refreshing table's column

- Measured first (`sort-phases -- 10000000 --reads-only`,
  `bench/results/2026-11-17-task-9.7-reads-before.txt`): the columns of an input table are
  `WritableSource`s. A read of all 10M rows of one at scattered keys took 9.4 s (int,
  double and string alike) against 0.18 to 0.48 s for a static table's `FlatSource`, and
  a read in row order 0.29 to 0.41 s against nothing (a slice). The cause: the place of
  each row key's value was kept in an ordered map (`BTreeMap<RowKey, (batch, index)>`), so
  a read by key was one map lookup per row (0.9 microseconds each at this size), and the
  values were then gathered with `interleave`, with a hash-map lookup per row to number
  the arrays in use. No lock was taken per key; the previous values were not the cost.
- Now (`tracked.rs`): the places are in a flat array indexed by row key while the keys
  are dense (at most four cells per value, the rule the row redirection already had) and
  in the ordered map otherwise; the form follows the keys as they come and go. Previous
  values are recorded as before, in a small ordered map of the keys changed in the cycle,
  laid over the array by a previous-value read.
- Reads (`writable.rs`): rows that were written in row order are found as runs of places
  and returned as a slice of the written array, or a concatenation of a few slices; other
  reads gather, in pieces of 2^16 rows on the threads `oxhaven_column::parallel` allows,
  with `take` when a piece reads one array. `FlatSource::chunk_by_keys` gathers in the
  same pieces (it was one `take` on one thread), which is the read-back of a static sort.
- Who gets it: every table whose columns are `WritableSource`s, with no change to them:
  input tables (append-only, keyed, blink), ring tables, the materialized columns of
  `update`/`select` on a refreshing table (so a table derived from `time_table`), snapshot
  results, and the tables Kafka feeds (`oxhaven-kafka` writes through the engine's
  stream tables). `time_table`'s own column is computed from the row key and was never
  slow.
- Tests (`writable.rs`): `a_source_agrees_with_a_map_through_random_changes` (300 cycles
  of fills, removes and shifts near and far against a model, current and previous reads
  by row set and by key, in both forms), `many_rows_are_read_the_same_on_any_number_of_threads`
  (five pieces, three arrays, changed in a cycle, ints and strings, 1, 2 and 4 threads),
  `rows_written_in_row_order_are_read_without_a_gather`; the read by keys was added to
  the flat source's test. Each was seen to fail with the code broken: no previous values
  laid over the array, a previous record ignored by a read of one key, runs that ignore
  the array or count a slot short, two pieces swapped, keys beyond the array, the key that
  makes the keys sparse lost, the count of values not kept.
