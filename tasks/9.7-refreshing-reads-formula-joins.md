## Scope

Four leftovers of tasks 9.3, 9.4 and 9.6, each measured before it was changed:

1. Reading a column of a refreshing table at scattered rows (a sort result read back):
   10 s at 10M rows against 0.3 s for a static table.
2. The pieces of a formula result are joined by a copy into a new array.
3. String concatenation in a formula formats one `String` per row.
4. The thread count can be set only with `OXHAVEN_THREADS`: a server option.

Results, row order, error text and reported failures do not change.

## Notes

### 1. Reads of a refreshing table's column

- Measured first (`sort-phases -- 10000000 --reads-only`,
  `bench/results/2026-11-17-task-9.7-reads-before.txt`): the columns of an input table are
  `WritableSource`s. A read of all 10M rows of one at scattered keys took 9.4 s (int,
  double and string alike) against 0.18 to 0.48 s for a static table's `FlatSource`, and
  a read in row order 0.29 to 0.41 s against nothing (a slice). The cause: the place of
  each row key's value was kept in an ordered map (`BTreeMap<RowKey, (batch, index)>`), so
  a read by key was one map lookup per row (0.9 microseconds each at this size), and the
  values were then gathered with `interleave`, with a hash-map lookup per row to number
  the arrays in use. No lock was taken per key; the previous values were not the cost.
- Now (`tracked.rs`): the places are in a flat array indexed by row key while the keys
  are dense (at most four cells per value, the rule the row redirection already had) and
  in the ordered map otherwise; the form follows the keys as they come and go. Previous
  values are recorded as before, in a small ordered map of the keys changed in the cycle,
  laid over the array by a previous-value read.
- Reads (`writable.rs`): rows that were written in row order are found as runs of places
  and returned as a slice of the written array, or a concatenation of a few slices; other
  reads gather, in pieces of 2^16 rows on the threads `oxhaven_column::parallel` allows,
  with `take` when a piece reads one array. `FlatSource::chunk_by_keys` gathers in the
  same pieces (it was one `take` on one thread), which is the read-back of a static sort.
- Who gets it: every table whose columns are `WritableSource`s, with no change to them:
  input tables (append-only, keyed, blink), ring tables, the materialized columns of
  `update`/`select` on a refreshing table (so a table derived from `time_table`), snapshot
  results, and the tables Kafka feeds (`oxhaven-kafka` writes through the engine's
  stream tables). `time_table`'s own column is computed from the row key and was never
  slow.
- Tests (`writable.rs`): `a_source_agrees_with_a_map_through_random_changes` (300 cycles
  of fills, removes and shifts near and far against a model, current and previous reads
  by row set and by key, in both forms), `many_rows_are_read_the_same_on_any_number_of_threads`
  (five pieces, three arrays, changed in a cycle, ints and strings, 1, 2 and 4 threads),
  `rows_written_in_row_order_are_read_without_a_gather`; the read by keys was added to
  the flat source's test. Each was seen to fail with the code broken: no previous values
  laid over the array, a previous record ignored by a read of one key, runs that ignore
  the array or count a slot short, two pieces swapped, keys beyond the array, the key that
  makes the keys sparse lost, the count of values not kept.
- Result at 10M rows: a scattered read of every row 9.4 s before, 0.11 to 0.18 s after;
  a read in row order 0.29 to 0.41 s before, 15 to 58 ms after; a column of a sort of the
  refreshing table 9.1 s before, 0.24 s after. See `docs/BENCHMARK.md`.

### 2. The pieces of a formula result

- Measured first (`filter-update-cases -- 10000000 3 1,4`, the parts at the end): joining
  153 pieces of doubles with `concat` takes 40 to 49 ms of the 105 ms of `B * 1.5 - A` on
  one thread. But a copy of the same pieces into a buffer made beforehand takes as long,
  and `B * 1.5` computed straight into one buffer takes 33 to 39 ms: the cost is the
  first write of 80 MB of new memory, not the copy. So the item is a real cost on several
  threads (the join ran on one, after the pieces) and a small one on one thread.
- Now: `oxhaven_column::parallel::fill_pieces` cuts a buffer with `chunks_mut` and hands
  each piece its own part (a queue behind a mutex, taken once per piece; no `unsafe`).
  `Pieces::in_one_buffer` in `eval/mod.rs` uses it for results of the fixed-width types
  (the integers, `char`, the floating point types, `Instant`): a piece is evaluated as
  before and copies its values into its part on the thread that computed it; the
  validity bits of the pieces are joined afterwards, when any piece has a null. Other
  result types (`boolean`, strings, lists) are joined by `concat` as before.
- The kernels still make an array per piece, which the piece then copies: writing a
  kernel's result straight into the part would save that copy (within the cache, about
  0.3 ns a row) and needs every kernel to take its output as a slice.
- Tests: `each_piece_fills_its_own_part_on_any_number_of_threads` (`parallel.rs`);
  `pieces_with_and_without_nulls_share_one_buffer` (`tests/formulas/pieces.rs`), and the
  tests of task 9.4 there, which compare 30 formulas with one pass on 1, 2 and 4 threads.
  Seen to fail with: a piece without nulls marked all null, the nulls dropped, a piece
  reading another's rows, the time zone of an `Instant` result lost.
- Result at 10M rows, 1 / 4 threads: `update_arith` 255 / 173 ms before, 229 / 132 after;
  `update_cond` 120 / 95 before, 97 / 54 after, under a higher load after.

### 3. String concatenation

- Measured first: `S + "_x"` evaluated in 1534 ms at 10M rows on one thread; with Arrow
  alone, a `String` per row 422 ms and offsets and bytes written directly 162 ms. The
  evaluator made three `String`s per row (each side by `java_strings`, then `format!`).
- Now `text::concat` writes the result's bytes and offsets directly: `String`, `int` and
  `long` operands from their arrays (a null `String` as `null`, a null number as the
  value Java reserves), the other types from the texts `java_strings` makes, as before.
  The array is built with the checked constructor, so the bytes are validated once.
- Test: `concatenation_prints_each_row_as_java_prints_its_two_sides` (every pair of six
  operand types, sliced arrays, against `java_strings` and against literal Java texts).
  Seen to fail with the digits not reversed, a null string printed empty, a null int
  printed from its buffer, a minus sign lost.
- Result at 10M rows, 1 / 4 threads: `update_string` 1274 / 496 ms before, 236 / 112
  after; `build` 2096 / 1087 before, 1000 / 545 after.

### 4. The thread count as a server option

- `oxhaven-server --threads <count>` (in the usage text, where the options are
  documented): a positive number, given to `oxhaven_column::parallel::set_threads` before
  the server listens; without it the default stands (`OXHAVEN_THREADS`, else the cores).
  The server logs the count it uses.
- Tests in `main.rs` (its first): the option parses, refuses 0, a negative number and
  text with the message of the other numeric options, and reaches `parallel::threads`.
  Seen to fail with the option parsed and dropped, and parsed and not applied. Tried on a
  server on port 10888: `Table operations use up to 2 threads`.
