# 9.8 Second end-to-end measurement against Deephaven

- **Status:** in review
- **Needs:** 9.1 to 9.7 (merged; `main` at `8a21018b`, which contains `55bb54de`), 8.1 (the benchmark)
- **Owns:** `bench/bench.py`, the "Second measurement (after tasks 9.1 to 9.7)" section and
  the two new rows of the case table of `docs/BENCHMARK.md`, `bench/results/2026-11-17-task-9.8*`
- **Read:** `docs/BENCHMARK.md` (all of it); `tasks/8.1-benchmark.md`

## Scope

Run the whole benchmark again, Deephaven and Oxhaven, now that the performance tasks 9.1
to 9.7 are merged: a release build of the server from `main`, every case at 1M and 10M
rows, two passes with default threads and one with `--threads 1`, at a low load. Add the
cases the performance tasks optimised but measured only inside the engine, where the client
API can express them identically for both servers. No engine code changes; a crash, wrong
result or hang is recorded here, not fixed.

## Gate

`cargo fmt --all --check`; `python3 -m py_compile bench/bench.py`;
`scripts/check-commit-subjects.sh origin/main..HEAD`; the three passes of `bench/bench.py run`.

## Notes

- **Result:** every case gave the same result on both servers in all three runs (row
  count, numeric sums, position-weighted sum, first and last three rows; the ticking case
  against the sums the client computes). No case was refused, failed, crashed or hung.
  Nothing to reproduce.
- **Tables and reading:** `docs/BENCHMARK.md`, "Second measurement". Of the 74 pairs of
  case and size, Oxhaven is faster in 34 (ratio below 0.8 in both runs), level or between
  level and slower in 31, and slower by more than 20% in both runs in 9: `aj` (1M and
  10M), `last_by` (1M and 10M), `ungroup` (10M), `where_range` (10M), `count_by_low`,
  `avg_by_low` and `sum_by_med` (10M).
- **Cases added to `bench.py`:** `sort_refreshing_append` (1,000 rows appended per
  repetition to an append-only input table of n rows with `sort("A")` downstream, timed to
  the barrier; the input table is filled on the server with `InputTable.add` of a view of
  the source) and `doget_sorted_refreshing` (DoGet of the first 1M rows of that sorted
  refreshing table). `Ctx` gained a `state` map for state a case keeps between its
  repetitions, and `Case` a `checker` for a check other than `checksum`: the appended
  sort is checked on a `snapshot()`, because the check's `ii` formula is for static
  tables, and the sorted read with a position-weighted sum computed by the client.
- **Already there:** the keyed cross join (`join_on_key`) and `group_by` were cases of the
  first measurement. Nothing in the list could not be expressed.
- **Commands:** `cargo build --release --locked -p oxhaven-server` (3 min 27 s, 4 jobs);
  Deephaven: `oracle/bin/java_server.py --port 10868 --psk oxhaven --heap 5g` with a venv
  of `oracle/requirements.txt` (Python 3.13); Oxhaven:
  `oxhaven-server --host 127.0.0.1 --port 10869 --psk oxhaven` (run 3 with `--threads 1`);
  `bench/bench.py run --server java=dh+psk://oxhaven@127.0.0.1:10868 --server oxhaven=dh+psk://oxhaven@127.0.0.1:10869 --out <file>`
  with the default sizes and repetitions, three times one after the other.
- **Load:** no other agent was building. One-minute load average 0.87 when run 1 started,
  1.21 at its end, 1.29 at the end of run 2, 1.19 at the start and 1.03 at the end of run 3;
  0.9 to 2.0 before each case, the benchmark itself. A whole run took about 4 minutes.
- **Not run:** `cargo clippy` and `cargo test` (no Rust changed).
